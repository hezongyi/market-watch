# Volume 数据链路修复方案

日期：2026-10-02，修订稿 R2。问题基线：`v1.3.0` / `b9d69dd`；实施基线：用户指定已发布源码 `v1.3.2` / `9596b25eda507ef708a327feb5271f238cdfdc0b`，schema 为 `o16_managed_revisions`。本文只修订方案，Volume 尚未实施或更新 Ubuntu Docker 实例。

本稿落实[独立评审](volume-repair-spec-review.md)的三个 P1 契约及两个 P2 修订。该评审针对原稿，其行号和“尚未定稿”结论保留为历史记录，不表示本稿已经再次通过独立审核。

## 目标与已确认断点

平台、自建两个系列的主行情都能向原生图表提供来源明确的 Volume，覆盖历史读取、实时更新、切换周期、保存重开和 CSV。不能只让指标入口出现；必须能绘制真实数据。

本机 API 实测：BTCUSDT、OANDA:AUD_CAD 的 M5 各返回 50 根 K 线，带 volume 的数量均为 0。复现材料暂存 `/tmp/mw-volume-api-repro.py`、`/tmp/mw-volume-api-repro.json`。

确认的源码断点：

- `backend/alerts/provider_chart.py:native_page` 丢弃 OANDA candle.volume 与 Binance kline[5]。
- `backend/alerts/providers.py` 的自建 M1 适配器同样丢弃这两个字段。
- `domain.Candle`、`storage.Bar`、行情写入与聚合均未包含 volume。
- `advanced-host/bridge.js:barsOf` 的主行情映射只有 OHLC，即使 API 增加 volume，前端仍会丢弃。
- 平台 `ProviderBar.payload` 是 JSON，缓存本身可以容纳新增字段；现存价格缓存不能证明成交量已准备好。

`advanced-charts-user-guide.md` 当前把成交量相关能力列为未支持，需要随修复更新。

## 1. 数据口径与契约

| 来源 | 输入字段 | Volume 含义 | 图表说明 |
| --- | --- | --- | --- |
| Binance Spot | kline[5] | 基础资产成交数量，BTCUSDT 单位为 BTC | 成交量，Binance Spot / BTC |
| OANDA | candle.volume | 该周期内创建的价格数量，通常称 tick volume | 报价量，OANDA；不是全市场成交量 |

不把 Binance 的报价资产成交额 kline[7] 或交易笔数 kline[8] 混入默认 Volume。若以后提供这些字段，应使用独立名称。

确定的数据契约：

- `volume`：可空非负 Decimal；API 按当前价格习惯用十进制字符串输出。真实零值保留为 0，未知为 null，禁止把缺失填成 0 或 1。
- 系列元数据包含 `volume_kind`（base / tick / unavailable）及 `volume_unit`（如 BTC / quotes），并随工作区初始元数据和后续 resolve 返回。
- `volume_complete` 独立于价格 `complete`：只有桶已收盘、价格完整且所有实际应有成员都取得有效量时才为 true。形成中且观测范围无缺量的桶可以返回截至当前的累计量，但此标志为 false；有成员缺量时返回 `volume=null`。合法休市不产生虚构成员。旧 payload 缺少该字段时按 false 处理。
- 形成中的 bar 可以显示截至当前的累计量，并保持未收盘状态；已收盘 bar 的 Volume 缺失不得显示成完整统计。
- 无可用来源的历史返回 unavailable/缺失状态，说明位于品种信息或任务详情，遵守绘图区不叠加进度文案的既有要求。

当前活动来源 OANDA/Binance 按上表接入。其他来源必须独立确认语义和可取得性，不能拿当前来源的数据填入不同来源的自建历史。

PostgreSQL 使用 `Numeric(38, 18)` 保存量，允许非负、最多20位整数和18位小数；越界或非有限输入作为明确数据错误处理，不静默舍入。聚合使用足够精度的 Decimal 上下文，结果同样检查范围。API/CSV 保留十进制值；原生图表转 JavaScript Number 只用于绘制，不宣称 Decimal 无损。OANDA 输入要求整数报价数。

真实持久化精度以 PostgreSQL 验收为准。SQLite 用于逻辑回归，SQLAlchemy Numeric 在 SQLite 中不能保证无损小数往返，本轮不承诺 SQLite 精确量存储，也不以其测试代替 PostgreSQL 精度测试。

## 2. 平台原生周期

1. 在 `native_page` 中提取两个来源的 Volume，校验非负、有限；保留小数精度。
2. 将 Volume 原样放入平台缓存 payload，读取、SSE bar 事件及 CSV 使用同一契约。
3. 在平台缓存 identity 中引入独立 payload 版本，升级为支持 Volume 的新版本；不修改真实品种、价格/日历口径，不伪称分桶规则发生变化。
4. 新版本只复用经证明包含 Volume 的数据。默认按原生实际请求窗口重新取数，再执行现有有限预热；旧缓存保留至正常清理或回退，不清空整个数据库。
5. 升级时 API 与相关 worker 使用相同 payload 版本；旧实例停止后再启动新实例，避免旧解析器写入新版本的数据集。
6. 修订比较包括 Volume：OHLC 不变但 Volume 修订也要推进修订号；最新桶通过 SSE 更新，历史修订遵循现有公开 reset 流程。
7. 所有缓存入口共用 payload 版本，包括历史读取、有限预热、订阅、修订检查和内存缓存。该版本区分完整契约与旧价格数据，不表示每根量都可取得；量缺失的响应必须保留明确状态。

平台 JSON payload 无需为 volume 单独新增数据库列。版本切换会产生新的冷请求，缓存性能须在重建后验收，不能把旧价格缓存命中当成新缓存完整命中。

## 3. 自建 M1、派生周期与发布快照

1. 扩展 `Candle`，在现有位置参数之后增加可空 volume，保留旧调用兼容；为 `candles` 增加可空 `Numeric(38, 18)` 量字段、独立量完整标志、量观测时间及量修订计数。旧行量为 null、量完整为 false、量修订为0，不默认设量为0。既有价格 `received_at`/revision 不承担仅量变化的标记，量修订只在值/量完整性真实变化时递增。
2. 更新 Binance/OANDA M1 适配器、raw rows 转 Candle、`Bar.candle()`、`candle_dict()`、旧 JSON 恢复、单条及批量 upsert，以及所有重新构造 Candle 的包装点，防止任一层再次丢字段。调用未提供量与提供量必须在归并输入阶段区分，不能只依靠 Candle 的默认 None 判断。
3. 单条/批量写入共用下述合并规则，并返回价格变化、仅量变化和无变化三类实际变更集合。归并之后用 PostgreSQL `IS DISTINCT FROM` 等 NULL 安全比较执行写入，不使用普通 `!=` 判断 null→有效值，也不使用无条件 COALESCE 保留旧量。
4. 自建高周期使用 M1 量求和；M30 经 M15、W1/MN 经 D1 的读取路径也必须带量。不得改成从平台高周期复制数据，NY17/UTC0、DST、批准起点和原有完整性规则保持各自口径。
5. 已收盘桶中任一应有成员的 Volume 缺失，桶量设为未知，不把已知部分之和当成总量。合法休市不会生成虚构成员；真实无成交的已确认 bar 可以为零。
6. 仅量更新触发受影响桶的量聚合及发布任务，更新 `chart_published_bars` 的 payload 和图表行修订；价格 revision 不变。复用 o16 的已发布桶修订与历史重载机制，包括 M15→M30、D1→W1/MN；消费者看到已发布结果，失败不替换原快照。
7. 补采只覆盖已批准自建范围，不前移起点、不创建平台到自建复制入口、不改变持续维护开关。

`o16_managed_revisions` 已提交并归属 v1.3.1。Volume 新迁移接在 o16 之后，暂用后继 `p17_volume` 名称，落地前核对单一 Alembic head；不修改历史迁移或占用其他任务的编号。

### 3.1 输入合并：保留已知量，防止旧量配新价

写入前校验来源、品种、时间桶、价格/日历口径，并携带实际观测顺序。迟到旧观测、未收盘观测不得覆盖更新的确认数据；自建使用独立量观测时间，平台沿用已有 observed_at/complete 防护。

| 输入场景 | 合并与修订规则 |
| --- | --- |
| 同 OHLC，字段未提供或来源明确返回未知/null | 保留已有确认量；没有旧量则保持未知。不能将缺字段解释为清除命令。 |
| 同 OHLC，取得有效数值（包括0） | 比较值和量完整性，真实变化才写入并触发量任务；值相同、状态相同不递增修订、不重复安排任务。 |
| 来源明确更正有效量 | 新有效观测覆盖旧量，记录量修订；历史图表按修订重载，不重算价格预警。 |
| 明确撤销量 | 普通缺字段/null不构成撤销。只有受控、可审计的修订操作可以将确认量改为未知；首版不增加普通用户清除入口。 |
| 正常实时/价格维护中 OHLC 真正更正，且新观测带有效量 | 价格与量采用同一新观测，执行既有价格修订语义及受影响桶重算。 |
| 正常价格维护中 OHLC 真正更正，但新观测缺量 | 接受有效价格修订时使旧量失效为未知，安排重新取得量；不能把未经确认的旧量配给新价格。 |
| 专用旧历史补量发现 OHLC/complete/时间或来源口径差异 | 默认保留已有价格和量，记录冲突，不自动执行价格修订、不写本次量；单独显式执行价格修复后再重试量任务。 |

### 3.2 修订分流与消费者隔离

- **价格变化**：OHLC、桶时间、价格完整性或真实价格来源发生变化，进入既有价格维护/失效/修订流程；量不得掩盖这些变化。
- **仅量变化**：保持 M1/派生 OHLC、价格 complete、价格 coverage、价格 received_at/revision、预警 state/cutoff/暂停状态及已有演练快照不变。量写入与量聚合任务入队同事务提交；不得调用当前 `ingest(defer_aggregation=True)` 中无条件将高周期 `complete=False` 的路径，也不得运行预警热身/历史重放来响应量更新。
- **无变化**：不制造行情修订、量修订审计、聚合或发布任务。任务游标/租约和观测新鲜度可以推进，但不能伪装成数据修订。

派生桶的量重新从成员值求和，不在旧总量上累加。首版扩展现有 `ChartAggregationJob` 的工作类型为 price/volume；volume 类型只改量及量完整状态，保留价格字段。任务相同范围去重；若同桶已存在 price 工作，price 工作吸收量重算责任；量执行器锁内发现成员价格不完整或新价格任务时不得发布旧价格配新量，交给价格任务完成或保持量未知。

价格读取在量任务运行、取消、失败期间保持可用；已发布量保持最后确认的快照，任务详情显示 pending/partial，完成一个桶的校验后以短事务替换量快照。已有演练快照不改写，新建演练的价格完整性不能受补量影响。图表可复用已发布行 revision，不要求增加价格预警共用的 revision。

包含 K 线 payload 的读取/导出缓存必须感知独立量修订或已发布 revision，不能继续只以价格 received_at/revision 判断是否刷新。现有 Python 指标输入行缓存也需更新其中的量字段；只依赖价格的指标计算结果可继续复用。图表历史变化标识包含量更新，预警仍只按价格版本推进，不能为了清除图表缓存伪造价格修订。

## 4. 旧历史补量

已有 OHLC 无法推导 Volume，需要从同一来源重新读取对应 M1。

首版新增独立持久 `VolumeBackfillJob`，由现有 chart-history-worker 执行有界量补采，复用行情资源 lane、退避和背压，不新增 worker 进程或通用调度系统。独立任务避免把已完成的价格计划重新设为 pending。顺序为当前可见/最近窗口优先，再分批向已批准历史起点补齐；新实时数据从升级时开始正常带量。

- 平台：通过新的 payload 版本按需取得原生周期数据，无需一次性重下载全品种历史。
- 自建：只对已有 M1 桶核对来源、时间、OHLC 与价格完整性；匹配时只补量。价格差异保留原值并记录冲突，按3.1节显式价格修复后重试；补量不插入缺失价格行，也不改写 MarketCoverage。
- Volume 补齐后重新聚合受影响桶，短事务更新发布快照；重试、失败不损坏已发布价格，也不把未完成量伪装成零。
- 已完整的 OHLC 覆盖不能让任务跳过 Volume 缺失桶，需独立检查缺量；重复执行不重复累加、不重复制造修订。
- 使用现有历史额度和退避，优先让位实时维护、近期修复与前台请求；不增加数据库连接池预算。

上游历史不可取得时保留未知并报告范围；不能承诺所有旧历史都能补齐，也不承诺初次全历史完成时间。

### 4.1 任务范围、授权与控制

- 每项任务持久保存 instrument/source/basis/calendar、批准的半开范围、固定截止点、游标、状态、generation/lease_token/lease_until、重试次数/时间、错误和未解决范围。任务完成后不追逐不断变化的 now；实时采集负责新数据。
- 已批准历史范围取计划 target_start 与任务创建时已收盘且已有M1的固定截止点交集；相同来源/品种的重叠活动任务合并或复用，不重复请求同一缺量片段。未解决片段逐页持久化为独立片段记录，按 instrument/来源/范围索引并分页查询，不把全历史的所有缺量时间戳塞进一个无界 JSON 字段。
- 本机升级步骤明确启动既有批准范围内的补量：仅对未取消、实时维护仍启用的计划创建任务。价格计划已 complete 不阻止补量，但也不重启价格计划；已取消计划或 `realtime_enabled=false` 不自动补历史，需要用户在历史任务页显式启动量补采，仍不改变实时维护开关。
- 无 ChartHistoryPlan 的旧自建历史不自动生成维护计划；可由管理员显式建立一次性任务，只覆盖所选来源已有 M1 的固定范围，不超出已有数据范围。未维护品种、平台浏览和页面翻页均不创建自建补量授权。
- 历史任务页展示量任务，提供独立的查询、取消、恢复和重试操作；认证/CSRF、品种权限与现有任务一致。取消整个品种历史任务时也取消其量任务；恢复价格计划不自动恢复已取消量任务，量任务需要明确恢复。关闭页面不取消已启动任务。
- 取消与写入使用相同 instrument/job 锁次序，并递增 generation、撤销租约。网络在事务外；取得响应后的提交事务再次检查状态、generation、lease、游标及授权范围。在取消/过期/新执行者取得租约后，旧响应不得写量或新增聚合/发布任务。已经原子提交的量和任务保留，由新状态管理后续工作。
- 量任务恢复只复查尚未解决范围，不能扩大授权；来源/价格口径变化使旧任务失效，须重新确认任务。升级自动启动清单与手工操作均留审计。

### 4.2 完成条件、游标与失败

- 每页最多覆盖600个自然分钟，符合现有历史单位上限；按真实来源M1和已存行核对，只有实际存在的已收盘 M1 才要求有量。页面数量或价格 coverage 不代表量完成。
- 向历史起点倒序推进调度游标，每片段把已补齐桶、合法无bar、仍缺量、暂时失败、不可达和价格冲突分别落盘。允许扫描下一片段，但未解决范围必须持久保存，不能靠越过游标遗忘失败；旧价格覆盖不能跳过缺量桶。
- 状态采用 pending/running/complete/partial/failed/cancelled。可重试错误有界退避；扫描完成且所有所需量、派生量及相应发布已完成才为 complete。确认不可达/量缺失/价格冲突仍存在时为 partial 并列出范围；不能以 HTTP 200、价格存在或游标到起点宣告 complete。失败页保留原游标及错误，重启可续做。
- OANDA 合法无观测/休市且没有对应已存 M1 的片段无需制造量或K线；已有 M1 但来源不再返回该桶，记录缺量/不可达。对应历史从未取得量时继续为 null；已确认旧量按3.1节保留，不把新的空响应当成撤销。
- 仅量变化要通过独立量修订链到达发布快照；任务等待聚合/发布完成后才将该片段标记已发布完成。失败不破坏此前完整价格或量快照。

### 4.3 资源与调度

每次 worker 轮转最多处理一页；前台平台需求、自建实时/近期修复优先，量补采走历史额度。HTTP 前和下一页调度前检查现有全局/逐品种聚合积压上限，量任务也计入上限；网络不占数据库连接或 instrument 锁。短事务只提交已校验页，历史量聚合与价格聚合公平轮转并对前台焦点提升优先级，沿用来源退避和现有数据库/HTTP并发预算。

## 5. 原生图表与导出

修改 `barsOf` 的普通主行情路径：已知量转为原生 Bar.volume 的数值，未知量不填造假的数值。同一映射同时服务 getBars 与订阅回调，历史和实时必须一起修复。

保留 Python 合成指标当前用 volume=0/1 判断指标值是否有效的内部协议；这些不是市场 Volume，不能全局替换为成交量，否则会影响已有 Python 指标。

通过原生公开接口配置 Volume 类型/精度，并在品种说明中标注口径。`create_volume_indicator_by_default` 当前关闭只是默认不自动添加，不能靠修改此开关代替供数修复。用户添加 Volume 后应正常绘制，保存重开应保留指标与样式。

CSV 现有 volume 列接入真实数据，并输出或明确关联口径/单位。报价面板若有 24h volume，应单独定义统计窗口，不能拿最新一根 K 线量冒充。

首轮验收目标是原生 Volume 指标。成交量蜡烛、VWAP、成交量分布须按原生公开能力分别测试后才能宣布支持；OANDA 的报价量不能被宣传为真实成交量加权统计。

## 6. 测试与验收门槛

| 层级 | 必须验证 |
| --- | --- |
| 提供商解析 | OANDA 报价数量、Binance 基础资产数量精确保留；零、未知、小数、形成中数据 |
| 平台缓存 | 冷读/持久缓存读/SSE 都带量；旧价格 payload 不当成新版本完整命中 |
| 自建存储 | PG精确数值/范围、null→有量、有量后旧格式重放、零值、价格修订且缺量、同页幂等、迟到观测；单条/批量合并一致 |
| 聚合 | 九周期求和、缺量不能报总量、DST/休市/截断起点、未收盘桶 |
| 补量任务 | 已完成价格计划仍补缺量；暂停/取消/无计划授权；空响应/不可达/价格冲突为partial；取消在途响应不能提交；崩溃/租约接管/重试不漏片段 |
| 发布与恢复 | 量单独修订、快照带量、历史重载保持视区；price/volume任务竞争；无变化无修订；聚合/发布失败及重启续做不重复累加 |
| 原生浏览器 | 两来源×平台/自建×九周期：真实接口供数，添加 Volume 可见柱形；零与缺失状态正确 |
| 回归 | 补量过程中与结束后OHLC/complete/价格revision/coverage/预警状态逐项不变；并发新建演练及已有快照不被量任务污染；Python内部0/1、工作区/画线隔离、CSV及手机只读 |
| 性能 | 沿用大多数冷首屏<3秒、完整新缓存请求到显示<1秒；八图负载下维护不被补量饿死 |

不能仅以 API 有 volume 字段或浏览器没有报错作为成功。需保留真实来源正量样本，对齐某个已收盘桶的上游量、API 值、聚合/发布值，并在浏览器确认 Volume 数值及柱形可见；真实零值没有柱高是正确行为。缺字段显示为空且不误报零须使用实际安装的原生包验证，不由类型声明推断。动态未收盘桶采用同一时刻采样，避免跨时刻误比较。

验收必须包含当前评审的反例：在已有完整 M5 上执行相同OHLC的补量两次，第一次量出现且价格/预警不变，第二次不产生新数据修订；并发创建演练不得得到量任务制造的“不完整K线”。PG覆盖 NULL 安全 upsert 和小数精度；SQLite只证明逻辑，不承担精度结论。
