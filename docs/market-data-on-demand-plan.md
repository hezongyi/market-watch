# 行情服务与按需历史补数方案

日期：2026-09-29。状态：方案已形成，部分基础能力已有开发实现，尚未完整验收、未切换生产。实际进度见[实施记录](market-data-implementation-progress.md)，后续顺序见[本次实施安排](market-data-execution-order.md)。
关联：[原生图表接入方案](advanced-charts-native-integration-plan.md)。本方案优先于其中涉及行情供给的早期简化描述。

## 1. 目标与边界

- 正常看图体验优先：打开可用品种即按需加载，往前拖动或跳转日期自动补历史；无需手动导入。
- 优先本地缓存，超过等待阈值明确提示正在拉取/排队/计算，保留已有图表和操作能力。
- 不以一次下载十年M1为目标，不预下载整个OANDA目录。
- 数据来源：OANDA账户实际可用品种目录；Binance现有BTCUSDT继续沿用。目录可搜索不代表所有资产的日历和所有周期已经就绪。
- 继续系统自行分桶：原M1为基础，NY17/UTC0及既有价格口径不变，W1/MN从D1生成。未经确认不混入供应商高周期K线。
- 交易、策略/回测新功能不在本次范围；原有策略、演练、通知继续运行。

## 2. 当前事实与待定位问题

以下为设计时的代码基线，其中部分问题已修复；当前状态以实施记录为准：

1. advanced-host/bridge.js品种搜索和解析为固定三品种；历史链路只查询/charts/data。
2. 后端providers.fetch_oanda只接受EUR_USD/XAU_USD；每次覆盖4000个自然分钟、串行请求，结果收集在内存后返回。
3. 本地无历史时桥接可能返回noData=true；本地缓存终点不等于供应商历史终点。
4. market.upsert存在逐根查询/flush；批量补数前必须改进，不直接对数百万条执行此路径。
5. 已有ImportJob（游标、租约、重试、优先级）、coverage区间判断、OANDA请求覆盖审计、行情入库和分桶，不另造一套同职能基础系统。
6. chart_api数据/指标路径有扫描全历史及计算全前缀行为。数据量扩大后需针对普通K线查询与递归指标分别优化，不能只优化下载。

首先复现并记录：本地有数据却不翻页、本地无数据未补取、时间标签/cursor错误三类问题，分别验收。以上事实不是所有加载失败的完整诊断。

## 3. 结构与复用

原生图表 → 官方JS Datafeed适配器 → 受控消息桥 → 统一行情服务 → PostgreSQL缓存/覆盖索引/任务 → 已有OANDA或Binance客户端。

- 使用官方getBars/resolveSymbol/searchSymbols/subscribeBars以及Quotes协议。图表引擎的缓存和渲染不重写。
- 继续JS Datafeed而非再建设平行UDF API：更适合现有鉴权、隔离、Python指标与异步任务。
- 扩展已有客户端、ImportJob、聚合和事务模块。持久化任务使用现有PostgreSQL租约机制；首版不增加Redis/Celery/InfluxDB依赖。
- 图表通过新的历史服务接口获取补数状态，原策略服务不依赖图表页面是否打开。
- 图表补数虽复用原始数据，但独立资源预算与执行worker，防止挤占实时监控及其修复任务。

## 4. 品种目录及启用生命周期

### 目录

从OANDA账户品种接口同步实际可用目录；服务器保留source、provider_symbol、显示名、资产类型、价格精度、目录更新时间/版本。账户凭据仅在服务器。

沿用已有三品种内部ID，新增通过(source,provider_symbol)唯一映射，防止多个来源同名冲突。不简单去下划线后当成全球唯一ID。

每日后台更新目录（可配置），搜索查本地索引，不每次键盘输入请求OANDA。账户不可用/目录更新失败显示缓存及状态，不直接删除已有历史。

### 使用状态

- discovered：可搜索，没有自动下载任务。
- chart_active：当前图表有订阅租约，按需补历史并维护近期数据。
- pinned：加入自选；使用合并报价订阅，可在预算内维护近期K线，不无限下载历史。
- strategy_required：已有有效预警/演练需求，遵从原监控保障规则，不因关闭图表停更。
- inactive：图表关闭并超过宽限期、无自选/监控需求，停止图表主动轮询；已有历史保留。

建议活动租约每30秒续期、关闭后2分钟宽限（可配置），不是必须保持浏览器长连接。未打开的已保存工作区不自动为所有品种永久启动采集。

### 日历能力

账户目录通常不足以提供完整历史节假日/特殊休市。按资产类别建立已验证日历映射，不把所有OANDA品种套用外汇或黄金规则。新增品种自动完成元数据注册，但只有已验证的session配置才开放相应聚合周期。配置未就绪的品种保留搜索结果并明确原因；不伪造周期或沿用错误日历。首批验证外汇、现有黄金；其他资产按日历能力逐类扩展。

## 5. 历史请求契约与Datafeed状态

建议接口（新接口，路径可在实现时统一命名）：

- GET /api/market-data/catalog?query=...：品种搜索。
- GET /api/market-data/symbols/{id}：元数据、支持周期、日历能力。
- POST /api/market-data/history：instrument、resolution、from/to、count_back；时间单位在协议明确（后台UTC毫秒，库from/to秒、bar.time毫秒），to排他。
- GET /api/market-data/tasks/{id}：任务状态/进度；后续可复用事件通知，首版可退避轮询。
- 报价、最新K线订阅由现有受控桥代理对应服务；不将第三方密钥交给浏览器。

history返回：bars、status、request_id/task_id、coverage、revision、has_more_local、remote_boundary（known/unknown）、next_cursor、retry_after及有限错误信息。

状态必须区分：ready / partial / pending / exhausted / unsupported / error。partial只表示可显示部分，不表示停止补数；图表已返回部分数据后，补齐通知走缓存失效+重新请求，不能二次调用同一个getBars历史回调。

### 请求流程

1. 规范化品种/价格口径/周期/时间边界，按countBack优先规划所需交易K线；不能用300分钟直接代替300根非连续交易K线。
2. 有足够覆盖时，读目标周期缓存并返回，不扫描整个M1历史。
3. 不足时合并/加入补数任务；已有数据可先显示，缺失不填零、不造K线。
4. 短等待内完成则一次返回；超时转任务状态、提示并继续后台处理。JS getBars回调的生命周期必须由适配器明确管理：待处理不反复返回空数组noData=false，更不能用noData=true终止历史。
5. 长任务在约定等待预算结束后，通过onError/状态提示结束该次请求，任务继续；完成后对相关symbol/resolution请求重载，避免轮询死循环。
6. 切品种/周期或销毁页面后，取消其等待者和预取优先级；共享任务有其他需求则继续。旧请求结果不能写入新图表。
7. 历史修订通过reset-cache回调及所需的图表resetData路径处理；实时回调只更新末根或新增，不用于把旧K线塞进最新流。

noData=true只在确认请求方向上没有更早可供数据时使用。供应商某次空响应、休市、超时、权限错误或本地无缓存都不能据此确认十年历史终点。不能确认时保留unknown，有限范围探测并向用户解释；不无限向过去扫描。

## 6. 覆盖索引与持久化

复用现有candles及ImportJob，必要新增：

- market_instrument_catalog：供应商品种/元数据/映射，避免直接把全部目录变成enabled监控品种。
- market_data_coverage：以instrument/source/basis/source_resolution、半开区间标识已成功查询的范围；记录provider空返回/实际bar数量/抓取时间/版本；可合并区间但保留必要来源证据。
- 活动租约与需求记录：按品种和使用者记录期限，去重维护需求。
- 任务需求关联：图表请求关联共享ImportJob；不是每张图一个独立下载任务。

OANDA现有provider_query_coverage审计是迁移依据，先构建专用查询索引，保留审计，不立即删除/改变旧策略使用逻辑。区分“成功查过”“返回了数据”“符合交易日历的完整桶”三种含义。

覆盖提交与原始K线写入同事务；失败回滚，不能记录“已覆盖”而数据没有落库。对临近当前时间的未收盘段不永久标记完成。更正的历史记录revision并只使受影响的聚合/指标缓存失效。

已有历史默认保留；首版不自动删数据。记录容量和增长趋势，超过配置预算暂停低优先级预取并提示，不自动清理策略所需数据。

## 7. 调度、批量写入与聚合

- 改造客户端为逐页产出，任务每页入库并推进cursor，支持中断续传；不一次积累多年结果。
- PostgreSQL批量upsert，借助已有唯一键防重复；仅实际变化更新revision，并保留修订审计。避免每根SELECT+flush。
- 锁与租约以小区间任务为单位。重叠需求归并、相邻区间适度合并；任务崩溃后租约到期重领，完成页不会重复产生副作用。
- 实时采集/有效预警修复优先；其次当前图表视区，再是有等待者的历史请求，最后预取/收藏预热。采用独立预算/公平调度，防止任一类永久饥饿。
- 尊重429 Retry-After；网络/5xx有限指数退避，401/403归为配置错误，不无限重试。不能把代理故障标为无历史。
- 每页完成后只重算受影响桶及必要的相邻边界；D1变化再更新对应W1/MN。使用已存M1聚合，数据不完整时明确完整性标记。
- 普通图表读取目标周期的索引区间；复杂聚合先计算并缓存。避免每次拖动扫描全表。
- Python递归指标须维持原口径：短期用异步结果缓存与同请求合并控制成本，长期按算法支持情况保存检查点/状态。不能通过任意截断历史前缀提速而改变EMA/MACD等结果。

## 8. 初始性能参数（待基准测试校准，不是性能承诺）

| 项目 | 起始配置建议 |
|---|---|
| 首屏 | 以库countBack为准，结合可见宽度和指标预热；默认目标约300根，不固定给每个周期下载同样天数 |
| 慢请求提示 | 约1秒仍未完成即显示“正在拉取历史数据”；使用原生可用状态/通知接口，不重做工具栏 |
| 单次等待预算 | 约15秒，超过则进入可重试任务状态；不以15秒作为下载终止条件 |
| 后台请求并发 | 初始每供应商2个历史请求，再实测调整；保留实时请求预算，不把库API限流上限当实际吞吐 |
| 单页数据 | 首先沿用已验证4000分钟窗口；实测比较合法窗口/数量策略，不直接扩大供应商限制 |
| 数据库写入 | 每页分批写入，批大小根据事务时间/内存实测 |
| 预取 | 完成当前视区后预取约一个视区；快速拖动/远距跳转取消陈旧预取优先级 |
| 任务轮询 | 初始1–2秒，等待较久逐步退避；事件通道可复用，但任务完成仍以数据库状态为准 |
| 缓存命中验收目标 | 在开发机实测常用请求P95约500ms内作为调优目标；记录实际环境、样本和冷热条件 |

加载提示区分“排队”“拉取”“写入/计算”“失败可重试”“数据源无更早历史”。未知总量不显示虚构百分比；可显示已获得根数/日期范围。加载中保持已呈现K线及操作，不把整页变成阻塞弹窗。

## 9. 评测与验收

### 基准测试

一个既有品种先测一天/一周/一个月M1，再按结果选更大范围。分别记录请求数、代理/直连耗时、字节量、解析、写库、聚合、目标周期查询、Python计算、浏览器首屏和拖动等待。相同数据重复请求用于验证缓存；不为做基准直接请求十年历史。

### 功能测试

- 本地命中翻页、缓存边界补数、跨周末/节假日、跳转旧日期、历史起点未知/已知。
- from/to与countBack、NY夏令时、短日、周/月边界、Bid/Last，返回排序唯一。
- OANDA目录新增、搜索后打开、未知日历品种说明、目录不可用缓存回退。
- 429/断网/代理失败/任务超时、任务崩溃续跑、关闭图表、快速切换、8图重叠请求去重。
- 原始写入与覆盖索引一致；重复页不重复数据；修订只影响相关周期与指标。
- 新补历史不触发在创建预警之前的历史信号；既有armed_at/处理水位语义保持。
- 活动品种退出、收藏报价、监控品种不断更；手机浏览也可触发必要补数，但不保存工作区修改。
- 原工作台、策略、演练与通知回归；性能指标包含前台补数时的原实时任务延迟。

### 交付门槛

在现有三品种上完成“打开→拖动到本地边界→看到拉取提示→自动补齐→再次访问命中缓存”的闭环，优先于批量扩展品种或铺开全部图表菜单。
