# 行情入口整合与性能优化实施方案

日期：2026-11-13。状态：方案已形成，尚未开始实施。

## 1. 基线与已确认决定

- 代码分析基线：正式 `v2.0.9`，提交 `eaacf47ef86b082f7a80b81841366dc1aa8908e4`。
- 当前文档工作树：`market-watch-market-review-20261113`，分支 `docs/market-data-review-20261113`。实际实施前重新核对 main、已合并版本及相关代码差异，不把本方案基线当成届时运行版本。
- 平台行情改名为 **原生行情**。
- **自建行情**保留名称；“行情库”等候选不采用。
- 不再将组合行情作为并列主入口；改为自建行情的可选 **实时接续** 扩展。
- 四项性能优化纳入本方案：列表摘要与增量分页、原生历史按月合并与未变化块继承、接续多周期共享准备、原生行情展示快照清理与锁优化。
- 当前授权仅为记录和形成方案。业务实现、实例部署、PR、合并和正式 tag 均未因本方案而执行。

代码证据与取舍见 [分析记录](../research/market-data-code-review-20261113.md)。

## 2. 目标与本次范围

用户面对“原生行情 / 自建行情”两类业务入口；任务与记录、来源状态、交易日历继续作为辅助分区。自建行情一条数据集只展示一条主列表记录，实时接续的来源、配置、运行状态和修订归入其详情。

性能改进通过减少重复请求、重复解码、重复准备和不必要的锁等待实现。保持当前可见状态刷新节奏、接收报价、确认输入、多周期维护和告警语义；新浪、腾讯已有原生周期继续直接获取。

本次不包含：新增接续供应商或品种、股票/期货接续、逐配置独立实时调度、公式合成行情、底层组合表合并、旧身份批量迁移、历史块读取缓存、到期调度重写、报价事务改造、新监控服务。既有筛选项遗漏作为附带问题留档，不在本次扩建通用能力系统。

## 3. 产品行为合同

### 3.1 入口与详情

- 原生行情替换面向用户的“平台行情”文案；保留内部 `platform` / `provider` 名称、API 与 ticker。
- 自建列表显示来源、日界或原生周期口径、历史可用范围、维护状态、实时接续状态。
- 详情保留现有覆盖、周期和历史查看能力；加入“实时接续”，将映射、接续健康、历史基线和修订迁入该区域。“引用”继续承担依赖与回收保护。
- 原“组合行情”独立列表不再出现在主导航。旧组合详情地址继续解析原对象，可由兼容页面进入所属自建行情；不得将其无条件重定向到当前默认接续修订。
- 旧 `tab=composite` 列表地址转入自建列表的接续视图；保留能够映射的搜索条件和返回位置。旧映射地址归属自建分区。新路由查询字段同步更新白名单、导航和位置保存逻辑。

### 3.2 实时接续开关

开关表达用户意图，运行状态另行展示：准备中、运行中、闭市、异常、已关闭。复用既有实时开关，不另建调度体系。

1. 新自建行情默认不启用接续；升级保留已保存的开关和既有兼容初始化逻辑。
2. 不支持接续的数据集显示原因，不显示可直接开启的有效操作。判断同时核对当前映射能力、历史产物与账户，不能仅依赖来源名称。
3. 首次开启引导选择并核对实时来源；配置成功后，通过显式写请求创建或复用接续对象并开启。GET、展开详情和浏览列表均不启动采集。
4. 准备失败显示可重试原因；原历史始终可读。若尚未完成有效配置，不保存为已开启；配置已完成但后台准备失败时可以保留开启意图并显示异常，重试沿用同一配置。
5. 暂停历史维护与关闭接续为两个独立开关。
6. 关闭移除该数据集的新采集需求，保留映射、修订和已确认尾部。共享来源仍可因其他需求继续采集。相关实时告警依既有生命周期暂停判定，必要的已提交输入结算保留。
7. 重开须恢复有效价格基准；不补报关闭期间的实时穿越，也不无条件恢复所有暂停规则。

### 3.3 默认接续配置与图表

- 只有一条可用配置时复用它；存在多条时要求显式选择，不取数据库第一条。所选默认配置可用现有 Preference 机制保存，按数据集限定并在读取时校验归属、映射和账户；选择默认配置不改变任何旧引用。
- 默认配置只影响今后的普通“打开图表”。现有开关仍覆盖该数据集相关接续修订，不在本次实现逐配置启停。
- 开启且默认配置有效时，普通打开进入接续视图；未开启时打开可用历史。开启但准备未完成时展示准备状态及“查看固定历史”操作，不静默改用另一来源。
- “发布版本”始终能够打开固定历史。固定历史图不因接续开启而自动切换。
- 关闭后，已打开或保存的接续图保留原身份和已确认尾部，并停止新增观察；不切成最新历史，也不继续展示新的临时报价。
- 来源信息分别显示历史来源和接续来源；黄金等跨产品差异继续展示。
- 每日历史发布不原位修改接续基线；保留现有自动基线准备、校验与切换流程，通过新修订表达切换。

### 3.4 兼容与回收

保留 `RealtimeMapping`、`MarketComposite`、`CompositeRevision`，以及固定基线、拼接点、确认输入和审计。旧 `MWH:` / `MWC:`、保存的工作区、告警版本、API/MCP 继续解析原身份；不为统一标签重算 SHA 或更换版本。原有历史回收依赖检查继续有效。

## 4. 工作包与执行顺序

按以下顺序逐项提交和验证。性能工作包先固定输入测量，再修改；不把界面改名算作 CPU 优化。

### P0：实施前盘点与可比基线

- 核对届时代码、开发实例镜像和持久状态；列出数据集、映射、接续修订及旧引用的脱敏计数。
- 在独立 Ubuntu Docker 任务环境建立固定输入基线：列表 1/5/10 页、跨月历史与修订、三条接续身份的确认分钟及九周期、多图快照并发。
- 复用现有测试和一次性测量工具，记录 SQL 数、请求数、解压次数、CPU 秒、峰值内存、就绪延迟；不引入常驻采样服务。

### P1：原生行情改名与自建实时接续整合

主要文件：

- `web/src/market-data/Window.tsx`、`Center.tsx`、`location.ts`、`navigation.ts`、`returnContext.ts`、`router.tsx`：导航、旧路由和返回状态。
- `ManagedMarket.tsx`、`DatasetDetail.tsx`、`DatasetReferences.tsx`、`MappingForm.tsx`、`Composites.tsx`、`CompositeRevisions.tsx`、`DatasetViews.tsx`、`OpenChart.tsx`、`types.ts`：详情入口、接续配置、摘要和打开图表。
- `backend/alerts/market_data.py`、`data_center.py`、`composite_center.py`、`composite_matching.py`、`realtime_switch.py`：按需补充可用性原因、默认配置和数据集范围状态。复用现有规则，避免复制两套能力白名单。
- 检索共享图表宿主、品种搜索和来源展示中的旧标签，按展示语境替换；不全局替换历史文档、协议值或数据库字段。

新增接续详情组件应复用现有映射、修订和状态组件；原组合组件中仍被旧路由使用的部分保留为兼容实现。

本工作包完成条件：两类主入口、独立接续开关、旧对象可读、旧图表与告警身份不变、浏览无采集副作用。

### P2：列表摘要、批量刷新和增量分页

主要文件：`backend/alerts/data_center.py`、`composite_center.py`、`market_data.py`；`web/src/market-data/MarketList.tsx`、`ManagedMarket.tsx`、`PlatformMarket.tsx`、`types.ts`、`api.ts`。

- 统一后的自建列表批量获取一页数据集及接续摘要，不再每行调用完整详情。
- 列表只返回行展示及打开图表所需的周期、版本和接续信息；完整映射与修订按需读取。
- 新增摘要或批量状态接口采用兼容增量方式；既有完整接口保留，避免其他调用方依赖被削减的响应。
- 加载下一页仅取新页；既有行按 ID 批量刷新，保持可见刷新节奏。页面隐藏时暂停管理列表刷新，恢复后立即校验。
- 状态筛选成员变化时重新校验分页成员；不能只更新旧行。搜索切换取消过时请求。
- 返回原生行情目录先恢复缓存行与滚动位置，再校验目录变化。

完成条件：无刷新、重试和数据变化时，顺序加载 10 页为 10 次分页请求；后台可按同批 ID 有界刷新，不能出现每行追加详情查询。筛选、周期版本、返回位置与详情一致。

### P3：自建原生历史按月合并与继承

主要文件：`backend/alerts/native_history_archive.py`、`source_history_store.py`；按需调整 `history_mode_artifacts.py`、`history_versions.py` 中的发布校验调用。

- 在不改持久格式的前提下，让来源页解压解析一次，按月顺序合并；父块建立月份索引或顺序遍历。
- 先核实上游页顺序。无法保证全局顺序时采用有界分段暂存，保持乱序与重复观测处理规则。
- 未变化周期直接继承已校验块引用；变化月份才重新合并。仍验证身份、价格规则、清单完整性和回收保护。
- 不缩小供应商历史复查窗口；不顺带实现跨版本周期产物复用或改变 `overlap_bars` 语义。

完成条件：相同输入的 OHLC、覆盖事实及发布清单一致；历史纠正、旧月份保留、失败周期继承和重试正确；解压次数不再随月份数重复放大，内存保持有界。

### P4：实时接续多周期共享准备

主要文件：`backend/alerts/composite_aggregates.py`、`composite_realtime.py`、`composite_aggregate_worker.py`；按需调整 `composite_inputs.py` 的有界读取。

- 对同一接续修订和明确输入版本，在一次有界工作批次内共享冻结的元数据与确认分钟读取。
- 各周期仍按既有任务领取、租约和水位提交；优先共享重复读取，不先合并为九周期大事务。
- 补齐路径按有界变动范围批量读，保留不超过目标输入版本的最新分钟修订选择。
- 批次内缓存不跨输入版本、修订或账户复用；并发新输入留给下一批，不推进未完成水位。
- 保持失败周期独立重试、提交后唤醒、旧修订隔离、临时观察不落入确认产物。

完成条件：三条身份 × 九周期在相同输入下，OHLC、确认版本、覆盖事实与告警结果一致；SQL 与 CPU 秒下降，确认到可判定时间无可重复的退化。某个周期失败不阻断其余周期。

### P5：原生行情展示快照清理与锁优化

主要文件：`backend/alerts/provider_display_snapshots.py`，并检查 `display_observations.py`、`provider_cache.py` 的事务和容量边界。

- 过期筛选、排序和有界删除移入 SQL，避免加载全部 JSON 快照到 Python。
- 有效且无需续期的命中路径先做轻量判断；普通写入保持幂等。
- 首版保留现有容量串行化，先消除锁内整集合解码成本。确认快照和临时分钟容量互不依赖并通过 PG 并发验证后，才为快照使用独立事务锁。
- 保持现有 TTL 与硬容量上限；不额外缩短 TTL，达到容量上限时仍按既有规则淘汰；不只依赖定时清理控制容量。
- 价格和指标继续共享同一快照，过期、历史修订、身份或日历变化仍按原规则拒绝。

完成条件：PG 并发发布不超限、无死锁、旧价格/指标一致；清理不再取回全量快照内容，多图请求 SQL/锁等待或 P95 有可解释改善。

### 性能对比口径

- 固定输入进行基线/候选交替回放，先验证结果相同，再比较请求、SQL、解压次数、CPU 秒和延迟。
- 真实实例另分无人浏览但三条接续运行、活跃告警、单图、多图、历史维护窗口；不在采样时并行构建或测试。
- 同窗记录各服务 CPU 秒、报价数、确认输入数与周期产物数，同时报告单核百分比和四核归一化百分比。
- 本次没有新的 CPU 实测；历史 CPU 不作为当前基线。不承诺未经验证的降幅，也不将此前讨论的单核 3% 设成未验证的交付保证。

## 6. 提交、回退和停止条件

- 建议一个实施分支、按 P1–P5 分开提交，最终汇总一个 PR；每步留下定向验证和性能证据，便于评审和定位回退。P0 作为基线证据记录。
- 沿用旧接口、格式和对象；第一阶段无需删表或批量数据迁移。默认配置若使用新增 Preference 键，旧版本应能忽略它，不改变原开关。
- 业务回归时停止当前工作包，按提交回退；对输入结果不一致、旧身份失效、告警补发/漏判、容量超限和失败周期互相阻断，不能用性能收益豁免。
- 若测量表明某项无稳定收益，记录事实并缩减该项，不能继续叠加复杂缓存。不会为了达到预估百分比擅自降频或削弱数据语义。
- 若实施发现必须迁移持久格式、重写旧身份、扩大接续品种或引入逐配置调度，先更新范围并报告该具体冲突；不顺手扩大本次方案。
- 本方案没有授权更新现有共享开发实例、合并 PR、正式打 tag 或生产发布；这些操作按之后的实际指令执行。CI 以实施时用户要求为准，不在本轮查询或等待。

## 7. 是否还需澄清
