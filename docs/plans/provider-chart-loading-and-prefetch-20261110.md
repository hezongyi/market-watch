## 1. 目标、范围与完成条件

目标是缩短平台行情未缓存品种的首次单图打开时间，并提高单次采集和后台空闲时段的利用价值。必须同时做到：

1. OANDA 正常网络下争取约 3 秒出图；Yahoo、AKShare、FXCM 争取约 10 秒。不得用重复打开同品种的缓存成绩替代。
2. 六个来源分别设置首屏采集目标、后台储备目标；设置可在界面保存，重启后保留。
3. 当前品种的工作区配置、元数据和图表资源尽早并行；可选自选表、搜索预热不阻塞首屏。
4. 保持唯一取数核心、缓存身份、覆盖判定和维护入口。各来源只承担自己的协议适配与能力约束。
5. 短请求及时交付，较慢来源和多页读取继续使用已有历史任务，避免为预取储备阻塞出图。
6. 数据身份、OHLC、取消世代、历史修订、真实指标输入、多图公平性、任务回收与实时报价保持正确。
7. 完成代码、针对性回归、隔离 Ubuntu Docker 验收、开发实例验证和可审查证据。按仓库规则准备 Draft PR；未经本次明确授权，不合并 main、不创建正式 tag、不发布生产。

本方案只覆盖平台行情。自建、组合的数据形成、不可变发布版本和告警判定语义不变；它们与公共图表启动、调度相关的兼容性需要回归。

“3 秒/10 秒”是性能验收目标，不是上游每次请求的超时设置。失败必须保留，不得提前返回空 K 线、陈旧行情或错误的 noData 来满足目标。

## 3. 配置设计与建议默认值

### 3.1 每源独立两项

每个顶层来源分别保存：

- `initial_bars`：首屏机会采集的总根数目标，包含必需根数，不是额外增加量，不是视口显示根数，也不是必须完成的分页数。
- `reserve_bars`：后台在当前需求锚点前希望保有的连续可用历史总根数，包含已采集数据，不是在 initial_bars 之外再加一次。

来源键沿用 `oanda/binance/dukascopy/yahoo/akshare/fxcm`。AKShare 下新浪、腾讯共享该来源设置；价格序列、复权和实际来源身份仍严格隔离。本轮不增加账户、品种、周期三级配置。

建议默认值：

| 来源 | initial_bars | reserve_bars | 原因 |
|---|---:|---:|---|
| OANDA | 2000 | 4000 | 已有 200/2000 的真实成本对比；当前单页可容纳 |
| Binance | 1000 | 4000 | 当前单页 1000，后台分页补齐 |
| Dukascopy | 2000 | 4000 | 当前页容量可容纳；必须保留超时样本并验证成本 |
| Yahoo | 2000 | 4000 | 按原生周期与保留窗口取数；不可为附带量强制增加来源请求 |
| AKShare | 1000 | 4000 | 优先复用一次快照，按当前页能力交付；不足再后台推进 |
| FXCM | 300 | 2000 | 先适配当前每页 300 的事实；扩大页容量需真实 SDK 验证 |

以上是初始默认值，不是各源不可更改的上限。用户可把各行独立改为其他值；如果适配器单页较小，首屏不为凑够目标阻塞，余量由后台补齐。

验证输入为严格整数。范围为 `0..min(20000, 当前历史容量)`；后台储备开启时要求 `reserve_bars >= initial_bars`，`reserve_bars = 0` 则允许独立关闭后台储备。任一项为 0 表示关闭对应可选能力，不影响真实首屏、历史翻页或指标必要输入。降低已有历史容量时，有效目标按容量收敛，保留原配置值和已有数据，不删除行情；界面展示实际生效值。

真实需求若大于配置目标，始终满足真实需求。来源真实上市边界、保留窗口或可用窗口不足时，后台以已有合法证据结束，不能伪造补齐或无限翻页。

### 3.2 唯一设置与持久入口

扩展现有“历史数据容量”对话框为“历史数据与预取”，保留原容量输入，增加六行预取配置。汉堡菜单和数据中心相关跳转指向同一组件，不再增加第二个维护入口。

采用现有 `Preference` 表的独立键 `advanced:provider-prefetch:v1` 保存完整六源配置；不新增表。建议结构：

```json
{
  "version": 1,
  "sources": {
    "oanda": {"initial_bars": 2000, "reserve_bars": 4000},
    "binance": {"initial_bars": 1000, "reserve_bars": 4000},
    "dukascopy": {"initial_bars": 2000, "reserve_bars": 4000},
    "yahoo": {"initial_bars": 2000, "reserve_bars": 4000},
    "akshare": {"initial_bars": 1000, "reserve_bars": 4000},
    "fxcm": {"initial_bars": 300, "reserve_bars": 2000}
  }
}
```

`provider_history_policy` 作为唯一配置读取、校验、默认值和有效值计算入口。缺键使用默认值；旧全局参数只保留必要的兼容回退，不能再与新配置同时指挥采集和预取目标。

新增已鉴权 `GET/POST /api/charts/provider-prefetch`，复用既有登录与 CSRF。POST 原子保存完整表；非法来源、布尔、字符串、小数或越界值返回 422。GET 返回保存值、有效值、默认值和当前适配器页容量。不要把来源凭据、账户范围写入此接口。

保存影响后续读取和预取轮次，不重启服务、不清缓存、不重算已有指标。已经在途的页面按原受控预算完成；后续目标按最新设置合并，降低目标时不让旧任务继续扩展。

## 4. 首屏加载依赖调整

### 4.1 启动只等待必要输入

当前链路近似为工作区激活 → 图表资源 → 旧订阅回收/偏好迁移 → 配置和自选表预热 → widget 构造 → 商品解析 → getBars。

改为：

1. 进入图表路由即并行准备工作区、当前商品元数据、必要偏好/协议配置和图表资源。
2. 当前元数据拿到后可复用到 resolveSymbol，避免仅“最近一个工作区列表”入口能获得启动元数据。各入口共享解析合同、有效期与取消世代。
3. 图表库与 runtime 有真实依赖时保留执行顺序，但资源准备与工作区 I/O 重叠。仅登录或设置页仍不加载图表库。
4. 旧订阅先本地失效以隔离旧回写；远端清理有界完成，不因远端回收拖住新图表。不得破坏生命周期上限。
5. 偏好迁移必须幂等。已迁移用户不应每次先单独 POST 再读取配置；可将迁移检查放入一次权威启动读取中。首迁移仍正确恢复设置。
6. 自选表元数据、搜索目录预热和未打开的管理对话框移出首屏等待。侧栏可增量就绪；已有保存布局和必要指标定义仍准确恢复。

不靠无限缓存 Yahoo 元数据加速；不能给一个品种复用另一个账户、来源或复权身份。`advanced-charts/catalog` 是指标定义目录，不是商品全量目录。

### 4.2 首屏采集和交付

以必需需求 `D`、指标必要前缀 `H` 和来源首屏目标 `P` 为输入：

- 真实必需量为 `D + H`，始终优先。
- 可选采集量希望达到 `max(D + H, P)`；单次请求还受来源页容量、合法窗口与现有容量约束。
- `screen_bars` 只描述视口和调度上下文，不再把来源机会采集量截成一屏。
- 可选量不能触发另一轮来源 HTTP、另一段强制分页或延长首屏的重试。需要额外请求才取得的储备交给后台。
- 图表可接收真实请求边界前的合法附带 bars，视口不强制扩展到全部采集根数。单次交付受现有容量和响应字节保护。
- 指标计算保持原 D/H 输入与修订合同。可选 raw bars 可以入共享缓存，不得改变固定指标窗口、递归前缀或修订判定。

缓存中已有必需数据时立即交付，不等待后台目标完成。大批量增加的解析、落库、传输和原生接收成本必须纳入实测；不是只比较供应商 HTTP。

## 5. 短请求及时交付，长请求沿用现有任务

继续使用 `/charts/history-loads`、现有任务行、数据集租约和 `provider_cache`，不增加第二条供应商取数/缓存核心。

### 5.1 缩短固定调度等待

采用窄范围的 PostgreSQL 事务后通知：

- 新有效任务提交后通知现有 native-history worker，避免空闲时必须等下一次 1 秒检查。
- ready/failed/cancelled 等状态提交后通知有等待者的 API。
- 通知只携带部署作用域和任务标识，作为唤醒提示；权威结果必须重新读取任务和一致数据快照。
- 数据 worker 与 API 每进程至多一个监听连接；不得每个页面新增数据库连接，不从短事务连接池长期占用业务连接。
- API 用异步事件等待，不占用数据事务或等待期间的数据库连接。worker 正常忙时仍按现有受控领取，不开启无界线程或按任务起进程。
- 通知丢失或重连依靠有界超时、已有周期扫描和结果重读恢复，通知不能变成唯一正确性依据。

该辅助模块限定为历史任务唤醒；不建设通用消息队列、全系统调度框架或新的浏览器 SSE 服务。

### 5.2 有界等待合同

在现有 history-capabilities 中声明可选等待能力。新前端提交 `/history-loads?wait_ms=3000`：缓存命中立即返回；缓存未命中仍创建原任务，在最多 3000 毫秒内等到真实结果则同次返回，未完成返回原 load 句柄。

后续 `/history-loads/{id}/result?wait_ms=1500` 可在任务有效时等待完成提示，完成即权威重读返回，不再同时叠加前端 1500 毫秒 sleep。未声明能力的旧前端/后端继续原协议。

开始等待前和交付前均验证 owner、状态与世代。断开连接取消等待，不错误取消其他消费者共享的采集；失效消费者按原 TTL 和取消合同回收。失败及时交付，不一直等满预算。

保留普通在途、原生生命周期、owner 任务数和来源额度各自上限。它们约束不同资源，不可通过简单提高并发掩盖等待。

## 6. 后台预取与来源适配

### 6.1 共用预取目标

复用 `ProviderInterest`、现有 `provider_service` 轮次与共享缓存：

1. 当前品种、当前周期优先补到 `reserve_bars`，已经拥有的连续数据计入目标。
2. 取消旧的“所有周期都固定跑 1000/4000 两轮”默认扩散；其他周期只在真实使用后形成各自兴趣和有限目标。
3. 首屏与主动翻页优先于后台，后台逐页让出执行机会，不能跨页长期占有来源和数据集租约。
4. 复用现有 600 秒兴趣有效期、兴趣数量、缓存天数和总量预算。当前与近期实际访问是默认候选，不自动维护整个目录，也不为提高利用率重复下载完成区间。
5. 首版不自动为全部自选表×全部周期建预取目标；自选用户实际打开后沿用同一机制。这是实现范围决定，不是缺失功能。
6. 设置增加、减少、关闭与兴趣续期均使用已有 generation/CAS 规则，旧 worker 回写不能覆盖新目标；同一数据集的用户需求共享缓存和采集。
7. 历史库存按缺口补齐；最新尾部沿用实时采集所有权和新鲜度政策。预取不得启动第二个最新行情采集者。

实施调整：腾讯有日期范围的接口不提供可信的永久最左边界。若一次成功分页之后，同一需求锚点的覆盖区间和可用根数均无推进，则只停止本轮可选储备，记录 `stop_reason=no_progress` 与 `satisfied=false`。不添加来源边界、窗口或 `noData` 证据，不阻止真实历史查询。新目标及配置增加仍可重新尝试。验收须把储备达标、合法窗口结束和无进展停止分别报告，不能把后者计为达标。

### 6.2 按来源处理

- **OANDA**：验证 2000 根完整路径成本；保留账户、报价口径、日界线和最新数据所有权。兼容 stream 与 rest_batch 两种配置，不能因设置预取而绕过 rest_batch 的账户采集所有权。
- **Binance**：首屏最多利用当前单页；更大储备分页准备，遵守既有限流/冷却。
- **Dukascopy**：保留有限快照、来源时区和历史边界；超时保留为失败，不用成功样本掩盖。
- **Yahoo**：分析 SDK 锁、认证、限速、日期窗口、超时后再次取数及落库。缓存身份、保留窗口、复权修订规则不变；不能仅增加 metadata TTL 或删验证来满足目标。
- **AKShare**：替换显式跳过全部预取的分支，接入同一有限当前周期目标。新浪一次快照只采集和解析必要次数，保留可复用合法历史；平台 count 截取不能导致后续重复启动 SDK 下载同一快照。保持新浪/腾讯、复权和量口径隔离。核查子进程启动和导入成本，必要时复用有界 SDK worker，不能引入无限常驻子进程。
