## 目标与展示取舍

进入条目后能直接知道：是什么数据、目前能用哪些周期、历史更新到哪里、后续怎样更新、实时是否开启且正常。默认层给业务结论；需要核查时再展开具体依据，不要求用户对照多个时间、版本号或状态码自行推理。

- 保留身份区、“历史数据”“实时行情”两大区与既有操作，不新增统计卡、大状态卡、顶部总结横条或第三套导航。
- 身份区保留代码、简明中文名和历史供应商。历史模式、价格口径、日线划分使用一行紧凑说明，可自然换行；例如 `分钟线聚合 · 买价 · 纽约17点日界`。字段语义/辅助技术名称仍清晰，不能只拼三个无人理解的缩写。
- 同一事实只表达一次；“已有历史”“可用周期”等上下紧邻且重复的文案合并。没有数据时明确“尚无历史”，不堆多个 `—`，也不把未配置/读取失败显示成正常状态。
- 首层必须能发现实际问题；异常不藏进折叠详情或日志。技术原因、长代码、版本身份和诊断字段按需展开，不在主层堆满。

## 首层信息与文字规则

### 历史数据

1. **历史口径说明**：模式使用易懂名称，必要时点开补一句解释：
   - `分钟线聚合`：M1 基础派生，采集分钟线并聚合其他周期。
   - `日线聚合`：D1 基础派生，采集日线并生成周/月线。
   - `各周期直接采集`：原生多周期，各周期直接使用供应商数据。
   - 价格口径用“买价/卖价/中间价/成交价”等可靠映射；股票/相关品种另说明“原始价格/前复权/后复权/来源价格”，不能混为同一概念或将未复权猜成成交价。优先复用可靠展示字段，无法确认不编造。
   - 日线划分使用“纽约17点日界/UTC零点日界/按来源交易日”；不是维护任务执行时区。纽约规则按实际时区含夏令时解释，不固定换算成北京时间。
2. **周期可用情况**：正常时一行“可用周期”；有配置但尚不可用的周期，直接在该处注明“生成中/尚无数据/更新失败”等有依据的事实。不能只列成功周期，把未完成部分悄悄隐藏。
3. **历史数据至**：替代当前含糊的单一“可用范围”。各周期范围一致时可显示共同截止时间；不一致则直接写“各周期范围不同 · 查看明细”，不要取最新截止冒充全部周期均已更新。共同截止也不承诺区间内逐根齐全；完整起止日期留给周期明细。日期必须含日期与时间依据，不能仅用“几分钟前”代替覆盖事实。
4. **自动更新**：一句说明“每日 HH:mm（维护时区）”或“一次性”；有独立周期计划时写“按周期更新”，展开看规则。下次计划作为同一行的次要信息，按后端实际 `next_at` 展示；暂停/归档/未配置时显示对应状态，旧计划不能看起来仍在执行。活跃任务期间避免把到期时间写成保证启动时间。
5. **最近更新结果**：优先表达当前需要知道的状态，如“正在更新”“部分更新失败，已有历史可用”“更新失败，已有历史保留”；空闲正常时显示最近成功时间即可。不重复显示多个“可用/已完成”徽标。任务提交只表示已排队，不冒充完成。

不要仅凭数据时间距现在多久判“陈旧/异常”：闭市、节假日和来源可提供范围会影响新鲜度。已有明确 freshness、任务结果、计划或会话证据时才作相应判断；证据不足就显示真实时间或“状态待核实”，不另建复杂预测规则。旧数据可用与本次更新失败可同时表达，不能二选一覆盖。

### 实时行情

1. **先显示可直接理解的状态**：`读取中`、`未开启`、`已开启 · 准备中`、`已开启 · 运行中`、`已开启 · 闭市`、`已开启 · 连接异常`、`暂不支持`等，来自实际响应。休市不当断流，enabled 不等同于 receiving。
2. **实际实时来源**：能确认时显示供应商及目标品种。若历史和实时供应商不同，必须一眼可见，不能让用户默认二者相同；不硬编码供应商作为未知值回退。
3. **接续进度**：将“基线至”改为易懂的“历史接到”与“实时已确认至”，紧凑成相邻信息。明确后者是已确认 K 线进度，不是最新报价时间，不冒充实时流最后收到消息时间。
4. **不可操作原因/异常**：按钮附近一句给原因与下一步，如“先准备历史”“需核对实时来源”“来源认证失败”；有对应入口就复用它。接口只返回笼统原因时不要凭前端猜更具体原因。无法开启与当前关闭区别展示；来源异常时仍保留原可关闭能力。
5. **基线自动轮换**：正常自动轮换不加常驻成功条；准备/暂缓/异常且影响当前使用时，就地显示一句真实说明。最近成功轮换时间与版本在展开详情中查看，不以历史维护成功时间替代轮换时间。

初次读取没有 live 数据时不能显示“未开启”；请求失败、离线旧快照和已核实关闭必须区别。保留上次值可以帮助阅读，但要沿用轻量缓存说明，不能将旧状态当刚核实。轮询不反复清空已知内容或重排页面。

## 默认收起的详情

使用现有 Collapsible/DataMore，保持一个清晰的“数据明细”入口；不再叠加多层抽屉或替代既有维护设置表单。

- **周期明细**：合并维护已配置周期与实际周期产物，按项目周期顺序列出。每项先给 `H4 · 可用 / 生成中 / 更新失败`，再给实际范围；沿用旧发布时明确“沿用上次数据”。`freshness`、产物状态与 available_version 的业务含义分别核查，不能把有数据当本次更新成功。若该模式允许按周期增补/删除，保留未配置但仍有保存数据的真实事实，不自行删除产物。
- **维护明细**：目标历史起点、已配置周期、各周期计划/下次到期、必要复查窗口。首层正常摘要不再重复一遍；复杂规则只在这里查看，编辑仍走现有“维护设置”。
- **数据标识与精度**：价格小数位、供应商原始代码（仅与显示代码不同或核查需要时）、当前可用固定版本短标识。多个周期可对应不同可用版本，不伪造统一版本；完整标识在既有版本页查看，不常驻长 UUID/哈希。
- **接续明细**：当前实时使用的历史版本、最近基线轮换时间及已有必要差异说明。没有接续时不显示空技术字段。固定历史最新版本与实时当前基线是不同事实，不能拿其中之一替代另一项。
- 详细任务、完整版本列表、区间补数复查、来源映射核对沿用原入口，不复制网页端全部诊断、柱数/完整率/覆盖分区/请求记录等到手机首层。

## 源码依据与实施路径

1. 主入口 `web/src/mobile/DataManagedPage.tsx` 的 `ManagedDetails`：当前缺模式/口径/日界，范围使用 dataset 级 version.start/end，只列 usable_timeframes；实时未返回时三元表达式会写“未开启”。先处理这些准确性问题，再调整展示密度。只影响手机自建详情，不顺手重排列表或自选曲线。
2. 复用 `web/src/market-data/types.ts` 的模式名称及 Dataset/Period/Plan 字段，必要时提炼手机专用的简短展示函数；中文展示不能反向影响持久 mode/basis/adjustment。`DataMaintenanceSheet.tsx`、`DataContinuationSheet.tsx` 作为既有编辑/核对入口，不复制业务命令。
3. 数据依据是 `backend/alerts/data_center.py::dataset_detail` 的 `periods`/可用版本、`history_maintenance.py::plan_report` 的计划和任务事实，以及 continuation 的实际来源、revision/preparation/rollover。顶层 version 范围不是每个周期实际范围，API 的时间区间端点也不能直接当最后一根 K 线时间；实施时核对端点语义，展示“覆盖至”或实际末柱时刻，不擅自减一分钟处理所有周期。
4. `web/src/market-data/DatasetContinuation.tsx` 的手机共用类型目前只覆盖响应子集；核实实际 API 后兼容补齐必要读取类型。多数数据已返回，不增加逐周期、逐行或每个展开字段独立轮询。若确有必要且现有响应没有字段，明确缺口后只作兼容扩展，不杜撰。
5. 日期复用/扩展 `dataOperations.ts` 的格式化能力，注意当前 `dataTime` 默认浏览器时区且无时区标记。详情统一说明时间基准，维护规则仍标自身时区；不要为本页直接改变所有页面的时间语义。样式限定自建详情，沿用 `data-controls.css` 和共享事实布局。
6. 风险初判 P0（只读展示与局部状态修正）；涉及兼容 API 扩展则按 F0 验证。不改采集、聚合、预取、轮换、实时订阅、固定版本开图或告警语义；不为了展示写入/创建采集需求。
