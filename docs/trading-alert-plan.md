# 个人行情预警网站：第一版设计草案

日期：2026-09-28。状态：需求已确认；组件、行情与 Android 交付方式是待验证的技术建议，尚未实现。

## 范围

- 单人账户，用户已有服务器、域名，主要在中国大陆使用。
- EURUSD、XAUUSD、BTCUSD 或 BTCUSDT（比特币可以使用交易所现货）。优先免费行情；报价源和具体市场须明确显示。
- 手动开启一次性监控；满足条件后停止该监控，创建独立的待确认通知。
- 网页提示和声音；Android OPPO Find X8 手机锁屏、关闭网页时通知，支持指定铃声、重复提醒、确认停止、重复次数及夜间静音。
- Python 策略，网页修改常用参数；历史信号标记、指定日期回放及在回放中手动开启预警。
- 不包含自动下单、多用户平台和收益率回测。

## 已确认的信号语义

### 回落后买入、反弹后卖出

默认 H4，连续根数 N 默认建议 2，可改为 3 或更多。仅处理已完成 K 线。

- 买入准备：连续至少 N 根阴线（close < open），且这些 K 线的 low 逐根严格下降。
- 卖出准备：连续至少 N 根阳线（close > open），且这些 K 线的 high 逐根严格上升。
- N 根之间比较 N-1 次高低点；不额外要求第一根与序列外的上一根比较。这是实现默认解释。
- 准备条件满足后进入等待状态。买入触发为本根 close > 紧邻前一根 high；卖出触发为本根 close < 紧邻前一根 low。
- 等待期间允许小阳线、小阴线或十字星，不要求突破紧接准备序列，也不固定用准备序列末根作突破参照。
- 等号不构成突破；未进入等待时，十字星或高低点关系不满足会中断准备序列。
- 默认等待直到触发或用户取消；可后续增加过期时间或失效规则，第一版不擅自增加。
- 开启前已完成 K 线可以建立准备状态，历史触发不能补发。开启前历史需要按时间顺序处理，已被历史突破消耗的准备状态不沿用；之后的新准备序列仍有效。该消费规则需在界面说明，避免将很早以前的回落误当作当前机会。
- 开启时未收盘的 K 线，若在开启后收盘，可以触发。
- 可单独选择买入、卖出或双向；双向共用一次性监控时，最先发生的信号结束整条监控。若要两个方向独立通知，应建两条监控。

### 前日高低点突破

- 默认用 M5 收盘确认，周期可在每条预警中独立设置。默认双向监控。
- 每根当前确认 K 线选择其所属交易时段的前一个有效交易日，得到固定比较阈值 H、L。
- 上破：previous.close <= H 且 current.close > H。
- 下破：previous.close >= L 且 current.close < L。
- 跨日时，以上两个收盘价都与当前 K 线选出的同一组 H、L 比较，避免混用两天阈值。
- 开启时已在区间外，下一根仍在区间外不触发；必须出现新的向外穿越。
- 跨日自动更新前日区间。FX/黄金跳过没有有效交易的周末；异常数据缺口不能被当作休市跳过。
- 归属按 K 线区间起点确定，例如 [16:55,17:00) 归于结束的旧交易日，而不是新交易日。

## 行情、时间和数据质量

- 所有时间内部存 UTC；交易日规则采用 IANA 时区 America/New_York，FX/黄金日边界是纽约当地 17:00，自动处理夏令时。比特币为 UTC 00:00。
- FX/黄金 H4 以其交易日开始时间为锚，比特币以 UTC 00:00 为锚。交易日边界、DST、周末、假日短时交易用显式日历策略处理并显示实际起止时间；不得用固定 UTC-5 代替纽约时间。
- 优先选有历史与实时接口的同一个源，用已完成 M1 OHLC 作为基础数据，自行合成 M5/H4/D1。M1 无法重建分钟内部的逐笔路径；第一版收盘策略和逐根回放不依赖该路径。
- 对网站当前价格展示另用最新报价。快照或抽样流不一定包含全部高低点，不能未经核验就将它当作准确 OHLC 来源。
- 若基础 M1 的边界、完整性或报价口径不符合要求，再考虑逐笔数据。不能简单拼接不同报价源历史与实时数据。
- OHLC 聚合：首个 open、最大 high、最小 low、末个 close；使用 [start,end) 区间，仅在基础数据已完成并满足完整性条件后发布高周期收盘。
- 明确源、市场、bid/ask/mid/last 价格口径及交易日配置。FX/黄金初步建议同源 mid，最终依可用接口确认；交易所现货使用该交易所成交价。
- 数据缺失时标记不完整、暂停相关判断、补齐后按时间恢复；不得插值制造高低点。正常闭市与断线分别识别。
- 记录事件发生时间、收到时间、收盘确认时间、信号时间和实际通知时间。补数导致的迟到信号单独标记；监控暂停必须在网页有可见状态。
- 定时任务重启后按持久化检查点重放；同一基础 K 线和信号使用唯一键去重。数据修正保存版本和审计，不静默改写已发通知。

## 技术组成建议

| 部分 | 初步建议 | 采用理由／边界 |
|---|---|---|
| 网站 | React + TypeScript | 常规表单、图表、实时状态 |
| K 线图 | TradingView Lightweight Charts | 成熟金融图表；不包含行情、策略或 TradingView 全站功能，遵守许可证及署名要求 |
| API 与策略 | FastAPI + Python | 用户熟悉 Python，便于直接维护 |
| 存储 | PostgreSQL | 保存基础行情、监控状态、策略版本、信号、发送任务和确认记录 |
| 运行进程 | Web API、行情/策略 worker、通知 worker | 网站关闭后持续运行；初期共用一个仓库和服务器 |
| 指标 | 有需求时接 TA-Lib Python | 第一版两条规则直接依赖 OHLC，暂不需要指标依赖 |
| 部署 | Docker Compose + 已有反向代理/HTTPS | 适合单机维护 |
| 手机 | 优先验证 ntfy Android 循环响铃与确认按钮；按需接 Tasker/MacroDroid，仍不满足再做最小 Kotlin 客户端 | Python 保留用于服务端和策略，移动端遵守 Android 平台生命周期 |

组件事实与数据源可用性见 companion 文件 trading-alert-sources.md。这里的建议不表示已经做过端到端验证。

策略接口只接收截止当时的数据与持久化状态，返回新状态和可解释信号；规则参数、规则版本、日历版本、价格口径随每条预警和信号保存。实时和回放使用同一实现。Python 编辑由受信任的部署者完成，第一版不提供任意代码上传执行。

## 通知可靠性

- 信号入库、一次性监控完成、创建通知 outbox 在同一数据库事务内完成。
- 通知至少一次投递，通过 signal_id/notification_id 去重。投递回执与用户确认是两个不同状态。
- 状态区分待投递、设备已接收、提醒中、已确认、重复次数耗尽、因静音暂缓。耗尽不能伪装成已确认。
- 可设响铃 15 秒、停止后等待 30 秒再响；这与每隔 30 秒开始一次不同，界面需明确。
- 可设置无限重复或最大次数；网页和手机均可确认，服务端保存并同步结果。
- 夜间静音必须说明是否恢复后补响，建议保留通知并于静音结束继续提醒。时间按用户配置时区。
- 手机已收到事件后，重复节奏宜由设备本地控制，避免每次响铃都依赖网络；设备未收到事件时仍依赖实际可用的推送通道。
- ntfy Android 当前源码包含最高优先级通知的循环播放能力，停止方式与通知移除相关；优先验证该现成功能及 HTTP 确认按钮。指定 15 秒/30 秒节奏、取消与服务端确认一致性、OPPO 锁屏可靠性仍需实测，不能由支持推送直接推出。
- Android 自定义声音、通知权限、前台服务启动、勿扰模式、厂商省电策略分别验证。不能承诺 PWA 或常驻连接在所有手机状态下必达。
- 设置独立“测试提醒”功能，显示设备在线/上次连接与最近一次送达；用户可据此演练。

## 页面

1. 行情与监控：三个品种、报价源与延迟、K 线、前日区间、已有监控、创建/取消预警。
2. 预警配置：策略、方向、周期、连续根数、已完成历史用于准备状态的说明、通知方案与有效状态。
3. 信号中心：时间、触发条件与具体价格、关联 K 线、行情版本、设备送达/确认状态。
4. 历史演练：日期范围、隐藏未来、移动到历史时刻、手动开启、逐根/加速播放、暂停、信号标记。演练默认只做模拟通知，避免触发手机真实告警。
5. 设备与提醒：配对、测试、铃声、时长、重复间隔/次数、静音、确认。

## 开发顺序与验收

先完成两项可行性验证，再定最终接入组件：

1. 行情：服务器实际连通，拿到三个品种所需的历史 M1 和实时基础数据；确认权限、费用、限速、价格口径与补数能力。核对自聚合 K 线及前日高低点。
2. 手机：OPPO Find X8 实机验证前台、锁屏、关闭网页、应用后台、长时间待机、Wi-Fi/移动网络切换后的首次送达及重复响铃；确认后不再重响。强制停止和离线情况如实显示限制。

之后依次交付：数据/时间核心 → 两条策略与持久化一次性监控 → 网页和通知 → 历史图表与交互回放。

必要验收覆盖：N=2/3、阴阳线/十字星、严格突破、等待多根、开启边界、双向镜像、跨交易日、夏令时、周末、重启补数与去重；同一数据和配置下实时模拟与回放输出一致；回放不访问未来 K 线或未完成的当日高低点。
