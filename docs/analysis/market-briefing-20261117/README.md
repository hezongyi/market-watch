最新范围校正：先搭建简报基础框架，首期以涨跌概览跑通全流程。新机会栏目随后逐步增加；四周突破只是设想，不属于首期，也不需要现在确定定义。未来可以复用指标结果实现该栏目。

## 1. 从用户决策出发

告警解决“我已经在盯这个条件，变化时请及时叫我”。简报解决“在我没有持续盯盘时，帮我定期检查关注范围，告诉我发生了什么、现在值得看哪里”。两者互补：简报发现值得关注的品种，用户查看图表后，可以为后续变化建立告警。

真正有价值的输出，是用有限阅读时间决定接下来查看哪些图表。单纯把所有涨跌幅抄一遍，主要节省打开 App 的操作；找出新变化并说明依据，才能节省筛选时间。

简报价值取决于：覆盖到关注品种、筛出有意义的变化、计算口径可信、阅读足够省时。容忍数据延迟，可以换取更广覆盖和更低维护成本；但不能容忍把旧数据说成最新情况。

建议将其定位为“定期市场扫描与汇总”。已有告警的期间回顾可以作为附加栏目，但不是简报的数据入口，也不能限制其覆盖范围。

## 2. 三类内容应分开

| 内容 | 回答的问题 | 推荐呈现 |
| --- | --- | --- |
| 市场概览 | 最近一个已完成交易周期，谁涨谁跌？ | 按资产类别分组；涨跌幅排行和全量列表 |
| 新出现的事件 | 自上期以来，哪些已完成 K 线产生过指定信号？ | 方向、事件时间、周期、实际值与阈值 |
| 当前状态 | 截至最新可用的已完成 K 线，哪些条件仍成立？ | 简明状态；必要时注明持续了多久 |

例如，日线曾在两次简报之间向上穿越均线，随后又跌回去。只检查最后一根会漏掉事件；只列出“价格仍在均线上方”又会每天重复。扫描应覆盖报告窗口内所有新增的确认柱，再把“期间发生”与“目前成立”分开说明。

首期只实现概览，以上事件与状态区分用于约束未来栏目的输出。以后接入指标时，持续成立的条件不应每天反复叫作“首次突破”。指标条件也只能称为信号或观察候选，不能由技术条件直接推导出入场建议。

## 3. 推荐首期

- 品种范围：绑定用户指定的自选分组，动态跟随成员变化。分组可包含原生行情，无需逐个创建告警、打开图表或开启实时维护。支持同时选择几个分组属于后续界面范围，尚未专门确认。
- 交付：北京时间（Asia/Shanghai）每天 08:00 一份，通知给摘要，App 保存全文。时间与渠道已确认。
- 内容：最近已完成交易日的收盘涨跌幅；预留添加内容栏目的简单代码接口，首期不实现突破或指标信号。
- 阅读顺序：分类涨跌概览 → 覆盖与数据异常。首屏限制篇幅，完整列表可展开；以后新增机会栏目时再调整排序。
- 正常出报即发送摘要，不能要求存在指标信号才能发报。
- 详细行能打开相同来源、口径和周期的图表。精确事件定位不作为首期框架的前置条件。

首期验证“分组变化能跟随、行情口径可信、准时生成、推送能进入正文”。涨跌概览是第一个真实栏目，既提供日常用途，也验证后续栏目共享的完整链路。

下一步再接入一两种用户实际使用的指标模板，例如指定参数的均线穿越或 RSI 越过阈值。算法、参数、历史起点、初始化和确认规则应与图表一致；不另写一套近似指标，也不默认所有图表指标都适合扫描。

### 框架与栏目的最小边界

公共框架负责：计划与定时、读取动态分组、行情读取与缓存、组织栏目、保存每期报告、App 正文与摘要投递。具体涨跌计算、指标筛选和栏目内容由各自的栏目函数负责。

推荐采用少量普通函数和一个简单栏目注册表。框架提供统一的本期上下文，包含固定成员、报告窗口及截止时间，并提供行情读取入口。每个栏目声明所需周期和参数，返回结构化结果：标题、条目、行情截至时间、覆盖数量和不可用原因。框架统一保存、排版和推送，不解析每种指标的内部含义。

接入新内容的步骤收敛为：确定指标／算法和参数 → 增加栏目函数 → 注册到简报 → 验证输出。新增栏目不应要求重写定时器、分组同步、报告保存或推送；一个栏目失败也不应让已有涨跌概览无法出报。

首期不建设动态插件加载、任意脚本执行、规则编辑器或完整指标扫描平台。未来指标栏目需要持续状态或期间事件时，再按真实需要增加进度记录和事件去重，不为尚未确定的信号预建一整套引擎。

指标算出数值后，通常还需要很薄的一层判断，确定“满足什么条件”“展示当前状态还是期间新事件”“怎样生成解释文字”。四周突破以后可以通过已有／新增指标提供高低区间或信号，再由栏目判断并输出；目前无需实现该指标或确定突破细节。

## 4. 发送频率、计算周期、数据更新是三个不同参数

| 简报形式 | 推荐关注内容 | 数据要求 |
| --- | --- | --- |
| 每日晨报（首期） | 最近交易日涨跌 | 确认 D1；后续栏目按需增加周期 |
| 每周简报（后续） | 上周整体变化、周线信号、趋势状态 | 确认 W1 和足够历史 |
| 每四小时简报（后续） | 期间新信号，优先呈现变化 | 按能力使用确认 H1/H4；也可汇报新到的 D1，但不得假装有四小时行情 |

“每四小时发送”不意味着必须计算 H4。“四周突破”不意味着只能每四周检查。日线四周突破也可以每日检查、每周汇总；周线规则可以每四小时检查更新，但没有新完成的周线，就不会产生新的周线信号。

Yahoo 当前原生周期没有 H4。不能因为其他来源支持，就给 Yahoo 承诺原生 H4；需要 H4 时，应使用已验证的聚合能力或明确限制模板。

配置建议收敛为：名称、品种分组、发送频率／时间／时区、内容模板、模板计算周期。首期不暴露 cron、任意表达式或复杂工作流。选定一种首发节奏，内部保留复用计算和汇总的边界即可。

## 5. 必须明确的行情口径

### 涨跌幅

默认使用同一来源、同一价格口径的最近两根确认日线：`(本交易日收盘 / 前交易日收盘 - 1) × 100%`。前收为零或数据不适合该百分比公式时，不输出误导性百分比。

“昨日”建议在界面写成“最近交易日”，并显示日期。周一早晨可能对应周五；多个市场的最新交易日可能不同，不能强制套用发送地的昨天。

股票要固定并标明复权口径；连续期货要说明换月拼接的影响。Yahoo 黄金期货、Dukascopy 黄金 CFD 即使都与黄金有关，也不能混成同一条价格序列。

普通收盘涨跌幅不是汇率换算后的美元收益率。跨外汇、黄金、股票的涨跌排名，首先按类别呈现；不把原始涨幅大小等同于机会质量。首期无需再引入复杂的统一机会评分。

### 未来指标栏目

四周突破的计算定义、周期、指标参数和事件判定，等实际接入该栏目时再确认。通用框架只要求明确来源、参数、计算周期和结果截至时间，不提前绑定具体突破策略。

## 6. 延迟可接受，误导不可接受

每期固定计划时间与纳入截止时间。每个品种还要记录真实行情截至时间／交易日，不能拿抓取时间代替行情时间。

| 情况 | 对用户的表达 |
| --- | --- |
| 市场正常休市 | 沿用最近完成的交易周期，显示日期；不当作断更 |
| 应有的新柱尚未发布 | 尚未更新；旧结果只作参考，不当本期新结果 |
| 历史不足或该周期不支持 | 明确未计算；不能算作未命中 |
| 源失败或超时 | 该品种暂不可用；其余正常出报 |
| 部分成功 | 显示“成功 N／总 M”，并区分无新周期、缺历史和请求失败 |
| 全部无法评估 | 显示简报未完成，不能输出“市场没有机会” |

发送前留有限的补取窗口，不能为了一个品种无限等待。首期只需要最近可用的确认日线和真实交易日，不需要建立指标事件扫描游标。

未来增加事件栏目时，延迟收录必须按原事件时间标明。届时按品种、规则及数据序列保留扫描进度，失败的品种不能被推进成功游标。首次开启默认建立基线，不推送整段历史的旧信号。这些是后续事件栏目的约束，不列为首期实现工作。

出报时固定品种成员、来源、参数、覆盖状态和结果。以后打开这一期应看到当时发布的内容，不能由最新行情悄悄改写。参数或分组改变用于下一期；没有必要首期就做完整版本管理平台。

## 7. 简洁实现的边界

建议流程为：到时 → 固定本期范围 → 有限补取确认行情 → 复用计算 → 保存报告 → 推送摘要。

后台独立于手机运行，关掉 App 后仍能出报。每期用计划和计划时间形成唯一标识，避免重复生成；投递失败进行有限重试，正常投递后不因没有点开而重复催促。服务端接收成功不等于手机已收到，不承诺网络推送严格恰好一次。

现有行情缓存、历史读取和 ntfy 通道值得复用；简报调度、栏目入口、报告历史和安静投递语义需要补充。指标算法与期间扫描在实际增加指标栏目时接入。先在现有后台中加入小型定时职责，无需为个人使用新增消息中间件、通用调度平台或独立微服务。

任务只在出报前按需刷新，并使用现有来源限流、缓存与请求资源约束。多个品种共享同一数据集／规则时避免重复读取；不把所有原生品种永久升级成实时订阅，不自动开启全市场历史维护。若用户选择全市场扫描，应先评估目录完整性、接口批量能力和规模，再确定交付承诺。

现有告警通知有确认和重复提醒行为，不能直接给简报套用。建议增加简报专用类型或明确的非重复投递分支；复用通道不代表继承响铃、确认、未读告警数和重复催促。

页面建议为“更多 → 简报”，包含计划、历史与预览；点击通知直接打开本期正文。报告中点品种进入图表。入口位置目前是建议，未做 UI 设计或实现。

首期以确定性规则和固定模板生成中文，不要求接入大模型或外部新闻。自然语言润色可以后加，事实与数值必须由结构化结果提供；润色失败也应照常出报。

### 动态分组的具体含义

每期开始时读取分组当前成员，并固定为该期名单。出报过程中增删的成员，下期生效；已发布报告保留原名单。相同来源、品种、口径与周期的重复成员只计算一次；不同来源不能按显示名称直接合并。

首期新加入品种，直接在下一期展示最近交易日涨跌；移出品种不再进入后续报告。未来增加信号栏目时，新加入或重新加入的品种再按栏目建立观察基线，避免追推入组前的旧信号。基线细节在接入该栏目时确定。

删除绑定分组时提示计划需要重新选择；不能悄悄扩大到全部自选。分组为空则明确本期无扫描品种，避免输出“没有机会”。

## 8. 当前代码依据与待核实边界

以下是对基线代码的静态核查，没有访问生产行情、发送测试通知或验证具体品种的运行可用性：

- `backend/alerts/provider_capabilities.py`：六类来源及其周期能力；Yahoo 没有原生 H4；来源间价格规则与日历版本不同。
- `backend/alerts/provider_yahoo.py`：原生历史、交易所时区、部分交易所延迟标签、确认状态、限流与有限请求预算。
- `backend/alerts/provider_akshare.py`：按需快照与品种／来源族周期能力；不能把支持集合等同于每个品种都有可用历史。
- `backend/alerts/provider_indicator_inputs.py`、`fixed_indicators.py`：冻结输入、固定历史、指标计算与修订处理。可复用算法，不代表现成接口直接适用于简报扫描。
- `backend/alerts/chart_alert_application.py:capabilities`：原生／旧来源的告警可用性受既有退役与实时链路边界限制。简报不应为了使用原生历史而重新开放旧告警执行路径。
- `backend/alerts/notify.py`：已有 ntfy、Outbox、投递记录、确认和重复提醒；当前领取类型需增加适配，简报专用语义不是开关即得。
- `backend/alerts/storage.py`：已有通知、Outbox 与事件模型；未发现专门的简报计划和报告模型。
- `backend/alerts/publication_schedule.py`：负责图表数据发布，不是用户简报日历调度，不能误认为已有日报调度器。

实施阶段需以选定范围验证：来源实际启用状态、样本 D1 与日历确认、有限扫描耗时、手机全文入口和投递行为。W1 和指标图表一致性在相应栏目接入时验证。当前分析只增加文档，不部署、不发送消息。
