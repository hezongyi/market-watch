## B 实际拓扑：共享数据库，按工作类型拆进程

```flow LR
图表 iframe -> React 外壳: postMessage
React 外壳 -> FastAPI: HTTP 与 SSE 通道
受控 Agent -> FastAPI: 可选 MCP
FastAPI -> [(PostgreSQL)]: 业务状态与结果
FastAPI -> API 后台线程: 启动供源维护与告警监控
API 后台线程 -> [(PostgreSQL)]
采集进程 -> 行情来源: 有界获取
采集进程 -> [(PostgreSQL)]: 提交价格与证据
计算进程 -> [(PostgreSQL)]: 任务、指标与发布结果
通知进程 -> [(PostgreSQL)]: Outbox 与事件投影
通知进程 -> ntfy 与手机: 外部投递
```

数据库也承担任务队列、租约、订阅结果和审计记录。
发布唤醒使用 PostgreSQL LISTEN/NOTIFY。
持久任务状态是事实来源，唤醒消息只是提示。

生产模板定义13个常驻服务，另有迁移和维护备份。
外部 PostgreSQL 不计入上述数量。
这描述仓库模板，不代表本次核实了线上容器。

证据：`compose.production.yaml:20`、`storage.py:1080`、`publication_wakeup.py:13`。

## C 领域模型：价格身份、版本和质量证据

| 系列 | 核心含义 | 主要模块 |
|---|---|---|
| 平台 provider | 供应商、账户、原生参数和周期明确 | provider_chart、provider_cache |
| 固定历史 history | 已发布历史版本与固定产物 | history_versions、history_artifacts |
| 组合 composite | 固定基线、拼接点、映射和实时尾部 | composite_revisions、composite_series |
| 自建 managed 查询 | 既有自建数据及图表发布读取 | managed_dataset、chart_api |

显示代码不能单独充当缓存键。
数据身份包含来源、通道、账户指纹、价格口径和日历版本。
来源身份还包含影响返回价格的供应商参数。

| 历史维护模式 | 基础数据 | 周期处理 |
|---|---|---|
| base_m1 | 来源 M1 | 按本地规则聚合 |
| base_d1 | 来源 D1 | 按来源交易日期生成周、月产物 |
| native_periods | 来源各原生周期 | 独立归档、独立检查点 |

时间结束、供源确认和覆盖完整是不同事实。
FXCM 原生快照明确保留“供源确认未提供”的状态。
空成功响应也不自动证明休市或历史到头。

证据：`market_contracts.py:21`、`source_registry.py:16`、`provider_fxcm.py:59`。

## D 四条关键链路

| 链路 | 实际路径 | 重要边界 |
|---|---|---|
| 初始历史 | 图表 → 消息桥 → React → query_chart → 系列读取 | API 可能触发必要的供源获取 |
| 持续行情 | 注册 → 共享任务 → worker → 持久结果 → SSE | SSE 不按连接重复执行昂贵计算 |
| 历史与指标 | 来源证据 → 固定版本 → 周期产物 → 绑定快照的指标 | 固定历史与实时尾部分开 |
| 告警与通知 | 判定 → 同事务 Signal / Notification / Outbox → 投递 | 网页事件投影不重新触发告警 |

共享行情使用 generation、epoch、sequence 和租约隔离旧结果。
任务共享不意味着连接没有成本。
行情 SSE 仍按连接续租并每0.5秒检查结果。

图表告警循环当前位于 API 进程的后台线程中。
关闭网页不会停止它，重启 API 则会暂停该循环。
旧监控仍有其他判定入口。

证据：`chart_api.py:865`、`market_stream_api.py:157`、`chart_alert_service.py:302`、`provider_service.py:689`。

## E 现有设计中值得保留的部分

| 设计 | 实际收益 |
|---|---|
| 不可变身份和历史版本 | 防止账户、来源或规则变化被当作同一条价格系列 |
| 历史与实时尾部分离 | 组合接续不必改写固定历史 |
| 需求、租约与共享结果 | 多图复用计算，并隔离过期消费者 |
| 判定与 Outbox 同事务 | 降低信号已产生而投递任务丢失的风险 |
| 可重放的消息投影 | 重建消息中心无需重发通知 |
| 历史、实时和计算分进程 | 限制网络等待影响其他工作类型 |
| 独立图表 origin | 外壳集中处理业务请求与会话 |

前端包含 React 外壳、Advanced Charts 宿主和兼容图表运行面。
宿主与外壳双方检查消息窗口、origin 和 channel。
两套静态资源仍需要配套发布和验证契约。

证据：`AdvancedWorkspace.tsx:473`、`bridge.js:3128`、`notify.py:129`、`notification_center_worker.py:13`。

## F 主要架构压力：按维护影响排序

| 优先级 | 已观察事实 | 建议 |
|---|---|---|
| 高 | 外壳2149行、bridge 3482行，消息覆盖多个业务域 | 按消息域提取 handler，统一消息类型和过期规则 |
| 高 | API 启动供源维护与告警循环 | 显式列出后台角色；有连续运行需求时再独立部署 |
| 高 | 共享计算 worker 从 chart_api 导入查询模型与执行逻辑 | 提取业务查询服务，HTTP / MCP / worker 保持薄适配 |
| 中 | storage 集中102张表，被127个模块直接引用 | 随功能迭代分组模型，保留统一事务入口 |
| 中 | 数据库同时承载查询、写入、队列和结果投递 | 先测连接等待、排队时间与阶段耗时 |
| 中 | readyz 只代表基础数据库可用 | 另行呈现来源、价格新鲜度、告警与任务健康 |
| 中 | 图表补丁绑定固定第三方 bundle | 保留内容校验，单独验证升级契约 |
| 低 | README 与不同 Compose 拓扑存在漂移 | 增加当前架构入口，标明历史资料 |

这些是架构压力判断，不是已复现故障。
数据库租约和事务防重已有实现。
不能仅凭后台线程数量推断重复投递。

## G 演进顺序：先减少调用方需要知道的细节

| 顺序 | 具体工作 | 保留的边界 |
|---|---|---|
| 1 | 整理进程职责与数据流索引 | 不改用户行为与部署实例 |
| 2 | 提取共享查询服务和行情、告警消息 handler | 复用现有计算与恢复逻辑 |
| 3 | 显式化 API 后台角色与业务健康摘要 | 根据实测决定进程拆分 |
| 后续 | 按来源、历史、组合、告警、通知分组 ORM 模型 | 不为移动文件同时改变数据库 |

回归应覆盖切换取消、断线重连、历史不可变和告警防重。
不应只用文件变短来衡量改进。
当前不建议引入 Kubernetes、Kafka 或独立服务数据库。
