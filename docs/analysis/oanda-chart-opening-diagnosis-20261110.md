# OANDA 冷品种开图诊断与方案调整建议

日期：2026-11-10。状态：分析完成，修订实施建议待评估；本轮没有修改或重新部署业务代码。

## 结论

需要调整实施优先级。当前主要问题是：当前商品首次取数仍排在原生图表初始化之后；同一历史任务重复构建最终响应；整轮截止时间会使接近预算的来源成功请求在落库前失效。来源网络也有真实长尾，不能保证每次 3 秒。

保留每源配置、2000 根机会采集、4000 根后台有限储备、统一缓存/任务核心。下一步先验证首批采集和图表初始化能否重叠，再减少后端重复处理；六源扩展验收暂缓。本文修订建议不代表性能已经达标。

## 3. 原因与证据

### A. 首次取数启动太晚：已确认，是整页首要问题

普通成功样本 CADJPY 的真实时间线：

| 阶段 | 时间 |
|---|---:|
| 导航 → widget 构造 | 1.29 s |
| widget 构造 → 首次 resolveSymbol | 1.25 s |
| resolveSymbol → 解析回调 | 0.42 s |
| 解析回调 → 首次 getBars | 0.13 s |
| getBars → 非空数据回调 | 2.66 s |
| 非空数据回调 → 可见 | 0.34 s |
| 合计 | 6.08 s |

原 5 样本首次 getBars 在导航后 3.09–3.85 s；本轮补测为 3.47–3.79 s。此时 OANDA 取数尚未开始。已有资源和配置并行仍没有跨过“等原生图表提出需求才开始采集”的边界。

同页切换只需约 0.14–0.27 s 就进入 getBars，支持启动固定成本的判断。CPU 样本中原生图表 bundle、runtime 和业务 runtime 有明显执行成本；资源压缩已经生效，例如业务原生 bundle 解压约 1.04 MB、传输约 0.31 MB，压缩无法消除脚本执行和图表初始化。

### B. 接近 8 秒截止后重取：已确认，需要修正预算分段

GBPCHF：第一次 worker 轮次耗时 8.15 s，来源 HTTP 6.92 s，提交页数为 0；下一轮再次 HTTP 0.80 s，落库 0.50 s，最后整页 15.08 s。

`native_history_loads.once` 将 `request_seconds` 同时用于整轮 read_context 截止；`provider_cache.check_cancelled`、`database_budget` 在来源返回后继续检查该截止。成功收到并解析的页面可能没有剩余落库预算，导致下一轮重新采集。这解释了该样本的放大机制；未来需补“来源成功返回但剩余落库预算不足”的确定性回归，进一步锁定实际抛出位置。

本轮另用真实 CADSGD 页面做受控故障复现：适配器真实返回 2000 根后，诊断探针立即令本地截止过期；`fetch_page:569 → check_cancelled:98` 抛 TimeoutError，实际落库为 0 根。没有伪造价格；该实验只证明截止检查机制，不将人为过期计为真实网络慢样本。命令为 `docker exec -i mw-dev-data-worker-1 python - < /home/quant/.local/share/market-watch-dev/evidence/provider-prefetch-20261110/oanda-diagnosis/reproduce-deadline.py`；结果 `received_bars=[2000], committed_bars=0, reproduced=true`。脚本已消费此新品种的空数据集身份，重复运行需另选未使用品种。

调整建议：来源 I/O、受租约约束的落库收尾、整体消费者生命周期分别设有界预算。收到有效页面后，消费者仍有效且持有正确 generation/lease 时，允许有限收尾；不放宽取消、身份、租约、修订和数据库 statement_timeout，也不延长重试循环来掩盖性能。

### C. 大批量收益存在，完整路径成本也存在：已确认

同一私有诊断进程直接调用真实适配器，不写 K 线缓存，EURHKD 按 200、2000、2000、200 顺序请求，依次 1.63、2.78、0.97、0.45 s。首次包含约 1.11 s TLS 成本；2000 的一次慢请求主要是响应等待。四次均真实来源请求，不是行情缓存命中。

可见 2000 不会按根数放大十倍，但也不能承诺与 200 相同。冷缓存 2000 根的统一核心剖析另测得：总 2.79 s，来源 HTTP 1.49 s，提交 0.49 s；40 次 SELECT（含 statement_timeout 设置类语句），另有 INSERT/UPDATE。该调用在独立诊断进程运行、无 client 兴趣，且带 cProfile，不能当作开发实例开图成绩。

当前真实 worker 常见 2000 根提交为 0.36–0.55 s，慢样本达到 1.36–1.55 s。CHFJPY 的来源 HTTP 仅 0.63 s，worker 填充却耗时 4.81 s，其中提交 1.36 s；剩余本地开销尚未细分到明确函数或锁，不能全部归因于数据库或后台预取。

保留大批量方向。先优化重复处理与串行等待，再决定首批返回全部合法附带 bars 还是只返回足够可见/指标必需的部分；采集根数、持久根数、首次绘图交付根数应分别核算。固定缩回 200 还可能因真实 from/countBack 范围不足引发额外分页。

### D. worker 和 API 重复构建响应：代码已确认，净收益待测

冷请求先做缓存探测；worker `once` 调用完整 `cache.data`，包括最终 bars 读取、展示快照捕获/发布、兴趣激活以及有指标时计算；返回值被丢弃。API 在 ready 后 `result → read_cached → cache.data` 再构建一次权威响应，`read_cached` 还序列化一次用于字节检查，HTTP 层再序列化传输。

保留 API 最终权威快照是正确性要求。可拆出同一核心的“保证必需覆盖”步骤，让 worker 只采集、提交、验证覆盖；最终快照、计算和响应只在交付处执行。不能简单缓存 worker JSON 跨修订返回，也不能移除必要的前后世代校验。

### E. 固定队列等待已非本批主要瓶颈；资源争用仍待定位

上述冷样本首次创建到领取约 24–217 ms；没有证据表明原先 1 s 空闲扫描仍支配这批时延。多数快样本由提交长轮询直接返回，通知与有限等待已有收益，继续仅缩轮询间隔收益有限。

`warm_step` 已按 interactive_busy 让位，价格页面仍受统一租约保护。后台工作可以在前台填充结束、浏览器绘制之前启动，存在争用可能；当前日志不足以证明它就是 1.5 s 提交慢尾的原因。

native_history 只有一个全局执行轮次，其他来源慢请求可能阻塞 OANDA，属于结构风险；当前 OANDA 样本领取很快，不能用该风险解释本批 6–7 秒。仅在并发实测复现后再决定是否按源采用固定数量的执行槽。

此外，浏览器临时将 resolveSymbol 中两个界面刷新延后做了四次已缓存页面对照。解析回调时间有所缩短，但 getBars 启动时间未稳定改善。此对照只用于隔离前端开销，不作为冷品种验收，也不足以承诺整页收益。

## 4. 建议的修订执行顺序

1. **先验证当前商品首批采集提前。** 仅在用户明确打开平台图表、已确认来源身份和当前周期后，通过现有任务/缓存核心准备一页；与原生图表初始化并行。单图、无指标先做小原型，比较三个新品种。初始目标为 0 时保持关闭，不因打开目录、解析自选表或其他周期自动拉行情。
2. **明确准备任务的接管和取消。** 原生真实 from/countBack/指标前缀到达后，以权威快照判断能否满足；不足继续同一核心补齐，不能假定 2000 必然够。换商品/周期、离页、旧响应迟到必须取消旧消费者；不新增价格缓存，不复制取数入口，不绕开账号和实时尾部所有权。
3. **拆分填充与最终响应。** 提取覆盖准备的深层方法，由现有 worker 调用；最终 API 仍在一致快照中读取/计算/交付。先量出重复组装、快照发布、配置读取、响应编码各自成本，再作相应修改。
4. **修正截止后的有限收尾。** 先写实际任务入口回归，模拟一次成功的来源响应耗尽 I/O 预算；正确持有租约时只提交一次，取消或 generation 过期时不能提交。HTTP 超时、有限落库预算与整任务过期分别验收。
5. **定位本地慢尾。** 增加必要分段：source decode、覆盖检查、批量 SQL、事务提交、展示凭据、兴趣激活、结果重读、编码。只记录计时/数量，不输出账号、代理、价格或私有工作区标识。再做后台预取开启/关闭的交错新品种对照，恢复原设置。
6. **最后恢复六源验收。** OANDA 先证明完整链路有稳定改善，再扩展 Yahoo/AKShare/FXCM。保留此前所有慢样本和失败；不要把不同版本结果混成同一最终成绩。

## 5. 验证、完成与停止边界

当前 3 秒目标继续保留。将“整页冷开图”和“已打开页面冷切换”分别验收；普通网络样本争取整页约 3 秒，但已实测来源请求自身超过 6 秒，不能承诺每次 3 秒。

每步只调整一个因素并选新冷品种，不用重复同品种冒充冷成绩。首次价格可见、必要指标完成、后台储备完成分别记录；后台有限目标和设置语义保持。

实施前先更新主方案中的依赖顺序和文件变更：启动准备涉及 `ChartApplicationPage.tsx`、`nativeHistoryLoads.ts`、现有 history-load API/worker；覆盖准备与收尾涉及 `provider_cache.py`、`native_history_loads.py`、`provider_history_policy.py`；原生接管涉及 `advanced-host/chart-runtime.js`。原型若无法减少真实关键路径，应记录结果并重新评估，不能直接扩成新框架。

需要保持此前真实 PG、租约/CAS、来源身份、取消、指标前缀和修订回归。发生数据错源、租约失效后回写、取消失效、连接或任务无界增长时停止扩大试验并保留证据。

本轮没有合并、打 tag、生产操作、清理价格缓存，也没有将目标标记完成。已部署版本继续保持，下一次代码实施应以修订后方案和小原型证据推进。
