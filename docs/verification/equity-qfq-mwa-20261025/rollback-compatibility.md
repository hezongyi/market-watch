# 旧二进制与回退边界

本版读取旧 M1 的升级兼容，和旧二进制能否维护新模式，是不同方向的合同。

在应用库实际恢复副本 `application_restore` 上，分别运行未修改的原计划基线 `7fc4fbb84e613e12e4540d7582ea78d137bfcdbd` 及当前 Python 读取代码。两者读取同一个已发布旧 M1 版本，身份 key、版本 checksum、256 条原始记录及 100 根 M1 图表数据的逐值摘要一致。连接外层拒绝 SELECT/SHOW/SET 以外的 SQL，读取后回滚事务；旧读取代码必要的 FOR SHARE 锁仅作用于恢复副本。没有 bootstrap、worker、迁移或数据写入。见 [legacy-reader-compat.json](legacy-reader-compat.json)。该证据限于所选旧 M1 固定版本，不代表所有旧消费者已逐一运行。

同一次比较确认旧 `DatasetIdentity` 拒绝新模式身份，而当前解析器接受。因此不支持把新 D1/native_periods 数据集交给该旧二进制创建、采集、调度或恢复。qfq-v2 的原始数据、同源依据与产物规则同样不属于复权实现前二进制的写入合同；不得用旧 artifact worker 继续处理这些新任务。

本轮没有进行旧二进制在含新模式库上的全面可写回退验证，也不宣称成功。实际回退材料为私有目录的精确旧镜像/配置及完整已验证备份。回退必须保留原库和新数据；不能 DROP 新周期表、删除字段、清库或恢复旧备份覆盖当前数据来制造兼容。需要切换旧服务时先停止会维护新模式/qfq-v2 的写入者，再根据该次明确授权处理；当前没有执行切换。

长期实例继续运行本轮 r12/r10/r1 候选。已有工作区/偏好审计差异保留，未通过恢复备份或改写基线消除差异。
