## 代码与真实页面证据对应

- `advanced-host/bridge.js`的rememberIndicatorBinding明确保留provider在第一次Python结果中确定的calculationStart，普通价格分页不更新它，避免把视口页首误当计算起点。
- startIndicatorCoordinator.binding随后把该起点作为calculation_origin放入每次指标请求，后端provider_indicator_inputs.freeze按`ProviderBar.start >= origin`选择输入；即使缓存/窗口中已有更早bar，这些bar也不会参与计算。
- 页面重建清空绑定，第一次指标请求不带旧起点，后端采用当时可用完整前缀，因而出现新的起点和数值。
- `verify-provider-origin-replay.cjs`重放实际桥接函数及上一轮真实XAU记录，可稳定触发“保存/恢复改变起点”的诊断断言。运行结果是**预期失败**，作为未修复证据；不是加入CI的通过测试，也没有拿回放替代本次同快照真实HTTP对照。

## 修复边界与建议

需要修的是“依赖发生历史扩展后，已存在的指标如何重新初始化”，不是加快窗口获取bar，也不是把EMA500换成窗口近似算法。

建议在服务端明确返回绑定于已接受snapshot/history epoch的规范计算起点或起点代次。确认更早历史已接受后，使旧指标起点/输入/结果失效，以新generation按合法完整起点或同规格checkpoint重算、提交覆盖，并让布局恢复采用同一策略。未达到初始化条件时应显示“历史不足/正在准备”，而不是无解释的ready全空。

不能简单让每个价格页的页首覆盖起点：分页和缩放会改变视口边界，递归结果将随视口漂移。也不能只保存旧起点来让刷新继续全空，掩盖已经可用的历史。修复验证应覆盖首次218根→较早历史已到达→无需刷新自动更新，以及随后刷新、A→B→A参数、多输出、旧世代迟到和快照更正边界；相同输入仍须保持与现有Python算法一致。

本轮完成核实，没有实现上述方案；需要先补实际调用链回归再改产品。旧性能矩阵、CI失败和单末点oracle范围均未改判。
