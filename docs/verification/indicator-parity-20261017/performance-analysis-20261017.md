## 3. 已证实的重要卡点：GC 暂停能落在多个阶段

独立进程使用同镜像、同冻结输入和原 `data_sync`/FastAPI 编码路径，记录 GC 回调，再短暂关闭自动 GC 对照：

- GC 开启的 30 次回放：总耗时 p50 90.0、p95 304.8 ms；全代 GC 单次 57.9–154.8 ms，多次 collected=0。
- GC 关闭的 30 次回放：总耗时 p50 88.1、p95 130.9 ms。中位数近似，尾部显著缩短；这不是浏览器 SLO 成绩。
- 未启用 cProfile 的独立样本中，精确计算段约 24–29 ms；结果命中约 0.9 ms。cProfile 会显著放大耗时，其调用排序只用于找热点。

真实 API 临时挂载诊断入口，记录完整 GC 事件、SQL 次数和函数边界，与浏览器按 period/HTTP 时间对应：

| 同一个操作 | 浏览器总耗时 | GC 事件 | 对应解释 |
| --- | ---: | ---: | --- |
| period 276 | 408.0 ms | 115.2 ms | GC 落在 167.6 ms 计算段内 |
| period 286 | 400.3 ms | 152.0 ms | GC 落在 191.0 ms 计算段内 |
| period 298 | 599.6 ms | 244.8 ms | GC 落在 artifact 读取/解码阶段；该次 artifact block SQL 执行约 0.5 ms，不能把 253 ms 读取函数耗时归给 SQL |
| worker 已停，period 345 | 525.2 ms | 196.1 ms | GC 与 HTTP 的计算函数开始前等待重叠，不是本次 TA-Lib 内核慢 |

因此 `fixed_read_freeze`、`calculation_ms`、HTTP 额外时间都可能吸收同一种进程暂停。看到哪段慢就分别重写那段，会误判。一个线程触发的 GC 也会影响同进程其他线程，不能只看本请求线程的 GC 列表。

**已确认的是 GC 是重要尾部来源；“哪个缓存/对象图贡献了多少扫描成本”还没有完成逐项消融。** 当前代码确实为每个新规格构建/保留全前缀的大量嵌套 dict/list，而缓存最多保留 16 项；这使压缩结果对象成为优先验证方向，但还不是已验证的修复。

tracing 自身会分配对象，可能移动 GC 触发位置；顺序组还存在冷暖及主机负载差异。因此不把 tracing 组之间的差值等同于可交付收益。临时关闭 GC 只用于诊断，已撤回，不能作为长期内存方案。

证据：[回放结果](performance-analysis/analysis-gc-replay-result.json)、[真实 API 事件](performance-analysis/analysis-api-probes.jsonl)、[150 个请求的对齐结果](performance-analysis/analysis-aligned-api.json)。

## 4. 其余开销与已经削弱的假设

### 请求中的重复工作仍然有成本

真实添加一个新 study，在共享输入命中后通常仍有 **34 条 SQL**，首次输入 miss 为 52 条。包括 metadata、固定 run、容量/需求、artifact 生命周期及已有输出检查；同事务内版本、dataset、instrument 有重复读取。独立回放复用同一 consumer，常见 31 条，不能直接当作真实新 study 的查询数。

GC 关闭组中，读取/冻结 p50 74.4、p95 158.2 ms；一次需求 renew 最慢约 71.9 ms。说明没有 GC 也还有事务/调度等待，不是只改 TA-Lib 就能全部解决。采样中 advisory lock 多数约 1 ms，个别较慢；尚无证据表明它是所有尖峰的共同根因。

响应约 264 KB。独立回放 `jsonable_encoder` 约 20–23 ms、JSON render 约 3–4 ms；真实 tracing 中编码中位数约 27–30 ms、p95 约 46–50 ms。它是可以审查的重复遍历成本，但单独省掉这一步仍不足以保证 300 ms。

本轮未插 tracing 的 dependencies 组，浏览器请求前中位数约 24 ms，请求结束至 native 两帧提交约 48 ms。它们是用户总等待的一部分，不能删去或改用服务器计时来通过。

### 算法内核不是唯一决定因素

当前 full-origin 精确 oracle 在回放中计算约几十毫秒；批量计算仍为所有 5,760 行创建依赖和呈现对象。继续微调数值内核，收益可能小于减少对象和重复 I/O。

### 没有证明“只要加资源/停后台就行”

241–270 组以 10 ms 间隔采集任务容器 cgroup CPU：整个约 45 s 采样中，API throttled=0 ms；PG 约 200 ms。最慢 478.1 ms 样本的 API/PG 均无配额节流，459.7 ms 样本 PG 节流约 20 ms。不能用旧累计节流数解释全部慢请求。

这不排除 Ubuntu 宿主机调度和其他任务竞争，也没有做加配额的正式因果实验；所以既不承诺“加资源解决”，也不宣称“加资源完全无用”。稳定态暂停专属 worker 后仍出现 525.2 ms p95，说明前后台重复计算竞争不是必须存在的根因。后台持久化与前台快速计算确有重复，但应按实际容量需要处理，不为它贸然重建调度架构。

## 5. 方案按收益依据与维护成本排序

| 方案 | 证据与可能收益 | 成本/风险 | 建议 |
| --- | --- | --- | --- |
| 保留依赖窗口优化 | 已有候选测试与本轮端到端结果；降低常见计算成本 | 低；继续遵守已有 seam/checkpoint 格式 | 保留，但不称 SLO 完成 |
| 减少全前缀结果的嵌套对象，只在展示时物化所需行 | 针对已观测到的分配/GC 暂停；可考虑列式数组或紧凑不可变结果，继续复用同一 oracle | 中；必须保持输入证据、coverage、依赖元数据、cache key/预算与逐点一致性 | **优先的下一轮性能修复**；先测对象数量、GC 和内存，再测真实 p95 |
| 合并同请求内重复 metadata/context 读取，审查重复 JSON 转换 | 真实请求 34 次 SQL、约几十毫秒编码；已有可量化边界 | 低至中；不能省略需求登记、取消 fence、容量检查或版本核验；直接 JSON 响应须验证全部输出类型 | 与上一项分开做小对照，避免多变量一起变 |
| 有限依赖指标只算可见区间所需前缀 | 对 LWMA/SMA/BBANDS/STOCH 可减少分配和扫描；例如 409 可见行、period 300 理论上约需 708 行，而非 5,760 行 | 中；gap、接缝、依赖起点、warmup 和浮点误差必须对照 oracle 验证；不能直接套用于递归指标 | 第二顺位；有限依赖并不自动保证切窗后的浮点结果合格 |
| 命中同规格合法 checkpoint 后只回放后缀 | 长历史递归指标的正确减量路径 | 中；全新参数没有 checkpoint，不能借其他参数状态 | 保持长期路径，不把任意新规格当缓存命中 |
| 继续把所有算法搬到浏览器 Worker | 有机会减少服务往返，但输入和合法初始化仍不可省 | 高；双份算法、插件/日历/修订/多输出/seed/数值一致性维护 | 当前证据不支持优先做全量移植 |
| 长期关闭 GC、停 worker、增配后只展示最好成绩 | 诊断性关闭 GC 仍未达 300；停 worker 没消除尾部 | 隐藏内存/持久完成/资源问题，不能形成合格验收 | 不作为交付方案 |

不报未经验证的“再花几小时一定完成”。下一轮要回答可证伪的问题：**对象压缩后，GC 暂停和分配是否确实下降，且在同预算浏览器中稳定改善 p95？** 如果没有，停止围绕该实现继续堆优化。

## 6. 是否需要死磕 300 ms

**不需要把所有场景的 300 ms 都作为无限投入的硬阻断。** 这是初始体验目标；当前没有数据证明 300 与 370/450 ms 的分界足以抵偿双份算法和更复杂缓存/状态体系的维护成本。但当前也没有证据证明 300 做不到，更不能把一次 371 ms 当成稳定上限。

建议分两步收口：

1. 性能上只再做一轮有界的对象/GC 与请求重复开销改进，保留一项变更一个对照；观察固定组重复结果，而非循环碰运气。保持 oracle 容差、正确 revision、原生过渡展示、完整可见 coverage、容量及内存预算。
2. 如果剩余常见新参数请求稳定落在约 300–500 ms，而继续达到 300 需要显著扩大架构与维护面，建议更新方案：热结果/可复用常规路径继续以 300 ms 为优化目标；输入已加载但全新规格的精确计算可考虑 500 ms 预算；真正冷输入、长起点和复杂插件各立预算、报告总等待及进度。这里的 500 ms 是**待决定的建议**，没有修改现行 A1，也不是其他场景已通过的结论。

立即反馈、保留有效旧参数曲线和可重试状态仍需验收，但不能冒充当前参数数值。若仍有经常超过秒级的等待、任务长期 pending、失败、错值或修订混用，这些应继续作为阻断项处理，不能一并改成“性能债”。

全 A1–A16、四类数据、复杂新参数、EMA500、真正冷布局、超过 6,000 行起点及压力下资源公平性仍未收口。放宽一个数值目标不等于可以跳过这些正确性与可用性检查。
