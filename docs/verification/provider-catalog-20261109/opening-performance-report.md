## D 后续优化优先级

| 顺序 | 对象 | 判断依据与建议 |
|---|---|---|
| 1 | 空关键词首页 | 全部类型 p95 349ms，先分析去重排序与混合分支取数 |
| 2 | 管理列表 | p95 416ms，保留总数需求下核对计数与排序成本 |
| 3 | 弹窗打开过程 | 分解初始化、请求调度与渲染，控制接近 1 秒的波动 |
| 4 | 列表响应字段 | 50 条约 71～78KB，可分析哪些字段延后加载 |
| 暂缓 | 代码与中文搜索 | 本轮相关接口 p95 48～121ms，优先级较低 |

响应体大小按解压后的内容计算，不是实际网络流量。
接口和浏览器分开测量，不能直接相减来归因。
缓存首次打开、自建选择首屏、深页性能仍缺数据。
接口入口收敛是维护问题，不能据此承诺提速幅度。

## E 测量条件和旧数据如何解释

- 使用当前分页优化候选，提交为 62f9df75。
- Ubuntu 本机隔离 Docker，真实目录约 2.2 万条。
- 本轮不增加合成目录，不修改应用代码。
- HTTP 每项预热一次，再顺序测量 20 次。
- HTTP 与浏览器分开执行，不同时跑两组压力。
- HTTP 开始时主机 load 为 6.27、6.75、7.00。
- 浏览器为 1440×1000，每次打开新应用页面。
- 同一浏览器上下文复用登录与静态资源缓存。
- 这不是整个网站的无缓存冷启动测试。
- 本轮浏览器无 pageerror。

此前 569ms 对应 4.7 万条目录的平台列表。
其中 2.5 万条是合成负载，接口每页返回 25 条。
它不能和本轮 50 条、约 2.2 万真实目录直接比较。
此前 1.902 秒也是另一轮页面单次测量。

初步补测的 1.42～2.54 秒包含自动化点击等待。
最终采用 B 表中按真实输入事件计时的结果。

原始证据：opening-performance-http.json、opening-performance-browser.json。
