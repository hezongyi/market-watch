需要先做整体调度设计，再分层改造图表加载链路。现有证据支持统一需求分类、资源预算和生命周期规则；尚不足以支持重写全系统的执行机制。

本文件是方案评估。产品实现尚未修改，收益与回归仍需候选版本验证。

## A 为什么值得重新设计

问题已经跨越前端、后台任务和数据库事务。继续在各调用点增加特例，会让优先级、取消和容量规则更难保持一致。

| 已确认的问题 | 实际影响 | 单独调整队列顺序是否足够 |
| --- | --- | --- |
| 价格、报价、指标释放和部分预取争用四个普通槽位 | 活动 H1 曾纯排队 238–499 ms；第五图 H4 曾排队 5703 ms | 不足；已派发的长任务仍占槽 |
| 固定行情预取缺少平台预取的调度身份 | 同类后台工作受到不同限制 | 需要统一请求用途 |
| 默认预热在价格事务中等待全局锁 | 单次组合 H1 中，预热锁 SQL 等待约 1235 ms | 不足；需要缩短持锁事务 |
| 成功价格结果仍等待句柄清理 | 一次平台 H1 回切中，清理请求耗时 1442 ms | 不足；需要调整完成与回收的关系 |
| 平台 worker 按页数、停滞次数和创建时间排序 | 未用已有 focused 信息区分当前首屏 | 需要公平且有边界的前台优先规则 |

这些是原实现中的观测，不是候选版本的回归数据。上述耗时来自不同层级，不能直接相加。

## B 重设计应覆盖什么

建议先将范围限定为图表加载链路，同时明确它对实时行情、报价和预警的资源约束。

| 层次 | 调整职责 | 继续复用的机制 |
| --- | --- | --- |
| 前端调度模块 | 统一活动首屏、其他可见图、主动翻页、前台指标和可选预取的用途；限制后台占满容量 | 现有 bridge 通信和原生缓存 |
| 后台任务调度模块 | 按当前有效需求认领工作；页与批次之间让出执行机会；等待越久获得更多机会 | 现有持久任务、worker、租约和断点 |
| 资源准入模块 | 分别约束数据库、供源和计算资源；可选工作不能延长价格事务的持锁时间 | 现有供源配额与冷却机制 |
| 生命周期管理模块 | 区分结果可交付、任务仍有效和句柄已回收；清理有容量、期限和失败处理 | 现有取消围栏、世代和过期机制 |

跨层统一的是含义与约束，各层按实际资源执行。将所有请求塞进同一个全局优先队列，仍无法解除事务持锁，也无法准确表达不同资源的占用。

现有实现已经具备可复用基础：供源按用途分配额度；指标任务具备前台需求、预热并发限制和维护轮次；原生历史具备每页执行与消费者租约。重设计应先补齐衔接，避免平行建立第二套机制。

## C 应先确定的四条规则

1. **请求用途贯穿链路。** 平台、自建和组合读取使用一致的调度分类。用途不改变数据集、修订、strict／observed 政策或缓存身份；旧消费者不能获得当前前台优先级。
2. **优先级与预算共同生效。** 前台保留准入余量，后台有最低服务机会。只改变排队顺序，不能抢占已经执行中的慢请求；安全让出机会应发生在页或批次边界。
3. **等待与执行分别记账。** 逻辑任务、在途 HTTP、数据库连接和供源额度分别设限。以后若让等待任务释放 bridge 槽位，须同时限制未完成任务，防止后端拥塞。
4. **取消消费者与保留共享结果分开处理。** 失效消费者退出，仍可复用的历史缓存保留。合并工作仅限数据身份、修订和输入政策兼容的需求；后台只要仍有有效消费者，就不能因另一个图格退出而被误取消。

建议将这些规则集中在小接口后面，由现有读取路径作为适配实现。调用点声明用途、消费者有效性和数据身份，调度模块统一承担准入、公平性与生命周期管理。

## D 会不会导致其他性能下降

有局部退化风险。目标是减少价格关键路径中的等待，并对其他工作的退让设置边界。

| 改动 | 可能变慢或增加的成本 | 需要的约束 |
| --- | --- | --- |
| 延后可选预热 | 某些首次指标请求可能等更久 | 真实前台指标需求继续优先；默认 strict 预热不能直接复用为 observed 图表缓存，实际影响需测 |
| 当前首屏优先 | 其他图格、历史预取和回切所需缓存可能晚些完成 | 保证可见图与后台服务机会；同时验收全部图格和向左拖历史 |
| 成功返回不等待清理 | 清理与后续加载重叠，短期任务数和 API 请求压力可能增加 | 有界回收、超时与错误处理；检查任务数和租约最终回落 |
| 将等待从执行占用中分离 | 放行过快可能把积压推到后端 | 同时限制未完成任务和实际执行并发，保留背压 |

当前 ready 句柄也计入 owner 活动任务数，实例上限为 8。API 数据库池只有 2 个连接；清理移出关键路径并不消除它的成本。因此不能直接放开任务数或扩大前端并发。

## E 建议怎样推进

**先画清规则，再逐项替换实现。** 第一批仍保持普通并发 4 和现有供源预算，避免同时改变过多容量参数。

1. 明确需求分类、各层资源预算和取消／回收合同。补齐排队、锁等待、worker 认领、结果交付与清理的分段观测。
2. 先处理两个有直接证据的等待：成功结果不等清理；可选预热不阻塞价格，随后移出价格事务。
3. 将前端分散的调度判断集中到模块中。补齐固定行情预取身份，加入有界的前台优先与后台公平性。
4. 根据实际认领和供源数据调整原生历史 worker。保留已有配额、租约和指标维护保障；每项变更分别对照验收。

验收同时记录活动图、全部图格、首次指标值、缓存回切和历史翻页。报价／预警延迟、错误率、队列积压、任务回收、锁等待及主机资源也要对照，不能只展示活动图变快。

使用相同版本基线、图格、视口、指标和缓存类别做交错对照。稳定环境下每个主要场景至少收集 30 次，报告样本量、p50、p95 和最大值。共用主机存在其他任务竞争，原有单次观测不能用于承诺具体提速或零退化。

完成上述改造后，继续观察跨 worker 的资源争用。若实时、图表、指标和批任务仍反复互相阻塞，再评估更广范围的统一准入。当前没有必要先迁移任务框架或重写供源、发布、预警等全部执行链路。
