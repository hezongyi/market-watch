# 自选切换延迟：深入分析与修复方案

2026-10-22。对象为现有 `mw-acceptance`。这是诊断与设计交付，尚未实现或部署性能修复。

## 结论

延迟来自**价格读取被后台工作、事务锁和收尾请求串联阻塞**，五图把这些等待放大。已有证据足以支持三项独立修复：

1. 平台价格结果先交付，再回收历史任务句柄。当前成功读取也要等待 `/cancel` 完成。
2. 将默认指标预热的阻塞等待移出价格事务，缩短组合展示快照的锁占用。
3. 为当前活动图首屏保留调度能力，并显式标记所有行情类型的预取。

平台历史任务本身仍需进一步区分覆盖、新鲜度、worker 认领和供源等待。不能承诺上述三项实施后，所有冷读取都在固定秒数内完成。

## 本轮补齐了哪些证据

交接报告已证明“慢”，但还缺少具体阻塞者和后端分段。本轮补充：

- 249 条 bridge 请求的入队、派发、完成记录，调度顺序与并发上限未改。
- 319 组数据库只读采样，约每 500 ms 一次。保存等待类型、锁、阻塞 PID、任务状态；未导出 SQL 参数、会话凭据或原始 SQL。

- 独立进程执行真实固定读取调用链，记录函数与 SQL 耗时。六次读取均回滚外层事务，未提交预热、快照或需求修改。
- 直接执行真实 `nativeHistoryLoads.ts` 模块的可控探针，验证价格结果已存在时，清理请求仍会阻止函数完成。

## 发现一：价格请求与释放、报价、旧缓存读取争用四个槽位

证据入口：`advanced-host/bridge.js:751`、`:810`、`:399`。

当前普通请求上限为 4。已有独立管理容量只识别 `data-center-api` 与 `preferences`。指标需求的释放／续租、报价、图表 RPC、价格和预取都可能使用普通槽位。

最终回切平台时，H1 入队时四个槽位由 **3 个 `indicator-demand-release` + 1 个 `quotes`** 占满。该次 H1 纯排队 238 ms；自建、组合静稳切换的 H1 分别排队 455、499 ms。平台非活动 H4 还因前四个完整历史操作占用槽位，排队 5.703 秒。

这修正了“前端总会排队四五秒”的过度概括：静稳点击中活动图多为数百毫秒，但第五个图仍可能等待数秒。加载中回切的原脚本另测到 H1 `getBars` 后约 8.83 秒才发出 POST；那轮缺少队列插桩，不能把整段精确分摊到每个旧请求。

### 固定行情预取还缺少调度身份

`bridge.js:930` 的 reserve transport 分两条路：

- 平台行情带 `native_reserve`，调度器可识别其 reserve 身份与并发限制。
- 自建／组合行情直接调用普通 `query()`，没有同等的本地预取标记。

因此固定行情预取可被当成普通价格请求，绕过当前基于 `native_reserve` 的优先级与在途计数。这是代码确认的结构问题；不能把每条固定历史补页都直接认作无用预取。

**修复方向：**在 bridge 内增加请求用途，区分活动首屏、其他可见图首屏、用户翻页、生命周期操作、指标和 reserve。固定行情也要传递 reserve 用途。用途是本地调度元数据，不应把平台专用 `native_reserve` 参数硬塞给固定行情 API。

保留普通总并发 4，先为当前首屏保留至少一个可用位置，限制后台读取占满全部容量。优先级无法抢占已经派发的慢请求，因此只给队列排序还不够。旧请求若仍能填充原生缓存，应降级或限制后续预取，不应一律取消；失效消费者则正常结束回调与租约。管理与生命周期操作也要有界，防止反向饿死。

## 发现二：默认预热已被证实进入价格锁等待

证据入口：`series_access.py:184`、`indicator_demands.py:30`、`:212`、`fixed_indicators.py:79`、`display_snapshots.py:34`。

无指标的固定价格请求，只要带 client 且返回 bars，仍同步执行 `warm_defaults()`。它登记 SMA／EMA 20，调用全局 `pg_advisory_xact_lock(8675313)`。组合价格在同一事务前部还会锁 LiveState、准备状态，并可能获取展示快照全局锁 `8675310`；这些锁要等价格事务结束才释放。

独立进程使用真实 `series_access.chart_data()` 路径的分段结果：

| 场景 | 总耗时 | 默认预热 | 预热锁 SQL | 快照锁 SQL |
| --- | ---: | ---: | ---: | ---: |
| 组合 H1，样本 1 | 2410 ms | 1405 ms | 1235 ms | 624 ms |
| 组合 H4，样本 1 | 1374 ms | 1013 ms | 893 ms | 约 1 ms |
| 组合 H1，样本 2 | 102 ms | 52 ms | 约 1 ms | 小于 1 ms |
| 组合 H4，样本 2 | 133 ms | 74 ms | 约 1 ms | 小于 1 ms |

表中的预热锁包含在默认预热耗时内，不能重复相加。H1 样本 1 中，两把锁的 SQL 合计约占总耗时 77%；默认预热占约 58%。H4 样本 1 的默认预热占约 74%。这些是单次调用的占比，不代表整个浏览器切换的总体占比。

同一真实调用路径也能在约 0.1 秒完成，说明不能将该读取描述为固定需要 1–2 秒的纯计算。样本间有主机调度、数据库缓存和进程初始化差异，不将“样本 1→2”表述为修复效果。

数据库采样另出现 6 组同一连接**持有 `8675310`，同时等待 `8675313`**的现场；其他连接又等待其快照锁。它证实可选预热会延长组合快照锁的占用，扩大到其他读取与写入。500 ms 采样不能精确计算锁等待总时长，也不能凭 PID 直接归属到某个 HTTP 请求；前述独立进程剖析补齐了具体函数归因。

还有一个效用问题：默认预热调用 `fixed_indicators.request()` 的默认 strict 政策，而自建／组合图表实际指标显式使用 observed 政策。两者 algorithm／run 身份隔离，strict 预热不能直接充当 observed 指标的计算缓存。业务 strict 需求仍应由其真实消费者维护，不能合并两种口径来省计算。

**修复方向：**

1. 最小候选先让可选默认预热非阻塞准入；锁繁忙时跳过本次可选预热，保留真实前台指标需求。围栏要覆盖 `request()` 和 `renew()` 全链，不能只把其中一个 guard 改成 try-lock。
2. 随后将默认预热从价格事务移走，以独立短事务接入现有需求／worker；不新建第二套任务服务。按真实指标、政策与有效消费者预热，保留容量和取消围栏。
3. 缩短展示快照全局锁保护的容量检查／插入段。若拆分价格读取事务，必须先冻结一致的 input revision 与观察内容，再从不可变快照读取；不能直接提前解锁后混入新的实时数据。

不要用 `async` 包装同步数据库函数后继续占用原 Session，也不要取消全局容量保护或放宽 strict 数据完整性来换速度。

## 发现三：结果已到达，仍等待成功后的 cancel 才显示

证据入口：`web/src/advanced/nativeHistoryLoads.ts:117`。

`loadNativeHistory()` 在成功取得 result 后返回，但 `finally` 仍 `await /cancel`。JavaScript 要先完成 finally 才结束函数，因此清理延迟进入 `getBars` 的关键路径，并继续占用 bridge 槽位。

最终平台回切 H1 的关联时序：

| 点击后的时刻 | 事件 |
| --- | --- |
| +0.584 s | 提交历史需求 |
| +1.475 s | submit 响应，返回 waiting 与 load.id |
| +3.097 s | 数据库首次采样到 ready、pages=1；真实 ready 在相邻采样之间 |
| +3.627 s | 开始读取 result |
| +5.063 s | Playwright 已读取完 result JSON |
| +6.494 s | 清理 POST 完成 |
| +6.499 s | 活动图价格就绪 |

同一 H1 的清理 POST 用时 1.442 秒；桥接完成比 result JSON 晚约 1.412 秒。M5 清理约 1.617 秒。网络响应监听有毫秒级观测误差，但不影响“价格结果等清理”的结论。

真实 TypeScript 模块探针也通过：让 result 立即可用、让 cancel 保持 pending，函数依然不完成；解除 cancel 后才返回价格。命令为 `node docs/verification/watchlist-switch-latency-20261022/deep/probe-cleanup.cjs`。

**修复方向：**成功结果立即返回；句柄回收使用独立、有截止时间且可跟踪的清理生命周期。真实取消、失败、布局销毁仍要回收；不要丢弃错误处理。保留现有幂等 API，优先避免引入旧客户端不认识的任务状态。必须验证五图快速连切时，清理未完成的 ready 句柄不会撞到当前每 owner 8 个活动任务的限额。

任务状态采样中的 `ready→cancelled` 是客户端成功后回收句柄，不表示该次图表加载失败。

## 发现四：平台任务、轮询与第五个图继续放大延迟

两次平台五图的 10 个首屏 submit 全返回 waiting，最终均 pages=1。已有真实任务 ID 关联，不再根据结果返回顺序猜周期。

`native_history_loads.once()` 逐次认领任务，排序使用 pages＋stalls 与创建时间，未使用请求中已有的 focused 信息；主循环还在图表任务前调用一次组合价格确认。后者有供源 I/O，但本轮没有证明它阻塞了某个具体慢样本。

前端一个 bridge 槽位覆盖的是完整 `loadNativeHistory()`，包括 submit、等待、轮询、result 和最后清理。第五图 H4 因此先排队数秒，再开始自己的任务。最终平台回切 H4 在点击 +6.072 秒才提交，五图到 +12.638 秒就绪。

已有 cache hit 是**最终读取**的状态，不证明首次提交满足覆盖和新鲜度。实际配置为 REST batch、15 秒 freshness。当前证据仍不能将所有 waiting 分成“历史缺口”和“等待共享实时来源”。

API 实际数据库池为 size=2、overflow=0；前端普通槽位为 4，API 还处理流和其他请求。池等待值得分段测量，但本轮未在 API 进程中直接测 checkout，不能把 HTTP 与 SQL 的差值全称为连接池等待。

**第二批优化：**先补 cache miss reason、worker 认领、dataset lease、供源配额／I/O、共享 latest、ready 和前端应用时间。再按证据给当前首屏有限优先级，并保持其他图和长历史的公平性。复用已有通知能力唤醒 ready，或减少 ready 后的往返；保留轮询退路。不能简单提高轮询频率或把 freshness 从 15 秒放宽来伪造快路径。

## 推荐实施顺序与风险

每项单独实现、验证，保留对照。先修有直接证据的等待，再决定是否扩容。

| 顺序 | 候选 | 主要文件 | 风险与最小验证 |
| --- | --- | --- | --- |
| 1 | 成功价格交付不等待清理 | `nativeHistoryLoads.ts` | F0。真实模块可控清理探针；失败／取消；五图快速连切及 owner 容量回收 |
| 2 | 可选预热非阻塞准入，再移出价格事务 | `series_access.py`、`indicator_demands.py`、`fixed_indicators.py` | F1。真实 PG 并发、取消围栏、容量边界、strict／observed 隔离、实际恢复与回滚兼容性按受影响范围选择 |
| 3 | 首屏调度保障、固定 reserve 身份 | `bridge.js`、reserve 调用点 | F0。真实调度器重放；4 槽位竞争；后台不能饿死；旧原生缓存回切；Ubuntu R1 |
| 4 | 平台 miss／worker／ready 优化 | `native_history_loads.py`、`provider_cache.py`、`nativeHistoryLoads.ts` | 后台调度变更按 F1。供源限流、共享消费者、修订一致性和缺口分页 |

第一批不需要 schema 迁移。若后续设计引入新状态或持久合同，重新核验旧客户端与 worker 兼容性。这里没有创建 Issue／PR，没有从方案推断实例更新、合并或生产发布授权。

### 应保留的回归合同

- 同一价格页、revision、展示快照与指标输入保持一致；旧结果不覆盖当前图。
- 真正缺口、超时和供应商失败不能转成 `noData:true`。
- 不清空可复用原生缓存，不隐藏仍未完成的图或指标，不减少用户需要的根数。
- 管理、需求释放和报价保持有界可用；旧消费者不会因延后清理复活。
- 所有优化都在原五图、原指标与正常后台需求下验证，不能靠关 reserve、关指标或改真实数据制造加速。

### 建议性能门槛

以下是待实施后检验的建议，不是当前已达到或已获用户确认的 SLA：

| 项目 | 建议门槛 |
| --- | --- |
| 当前活动首屏的纯前端排队 | 稳定环境下样本 p95 ≤100 ms |
| result 可用后的应用等待 | 不再取决于 cancel 的网络耗时；模块探针直接断言 |
| 无指标价格对默认预热锁的等待 | 0，繁忙时跳过可选预热 |

| 真正需要供源的新读取 | 单列供源、任务与应用时间，不强行承诺 3 秒完成 |

性能验证固定版本、图格、视口、根数、指标与缓存类别。先等待初始队列静稳，另测加载中连续切换；预热后每个主要场景至少收集 30 次，报告样本量、p50、p95、最大值与主机负载。不得自动停止其他任务以获取空闲主机，应由用户安排性能窗口。
