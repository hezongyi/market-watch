## 已知卡点的解释边界

平台首例 H1 bridge 派发等待为 0 ms，但派发后约 8.56 秒才完成；HTTP 观测中先经历 filling，最终 result 内部读取约 224 ms。因此下一步应细分原生历史任务的认领、填充、ready、轮询与结果应用。现有数据不足以将剩余时间全部归于供源、某条 SQL 或 worker 单一函数。

最终连切失败是当前最重要的正确性卡点，不应仅按“仍慢”处理。尚未区分准入／取消状态、当前消费者回调与后台任务等待，也未证明是否本次改动引入。不能直接解释成主机负载，也不能据此断言需要全局重构。共享主机 load 曾升至约 8.7，但没有隔离负载因果实验。

前两次补验收各有一项保护器判定问题，分别是匿名 401／被拦截通知查询 404，以及缓存翻页没有新 datafeed 回调。均已修正并保留分轮记录；最终 90 秒超时发生在修正后的检查中，无 pageerror 或意外 HTTP 失败。没有把脚本问题与实际未就绪混为一个故障。

## 建议与决策含义

建议继续推进**局部**工作：先最小化连切 90 秒未就绪，并锁定能检出该故障的回归；然后对平台任务链路逐段计时，只调整已证明的等待位置。修复后分别验活动价格、五图价格、原指标、翻页、连切、报价与回收。由稳定窗口的重复样本确定 p50／p95 和可接受目标。

这不等于批准或立即实施全系统调度重写。只有后续证据持续显示实时、图表、指标与后台任务跨链路互相阻塞，再评估更广的统一准入／执行设计。

若选择本阶段收口，准确含义是“保留当前修复和候选，把连切未通过与平台延迟列为明确尾项”，不能标成“性能问题已解决／完整验收通过”。若选择继续，建议范围先固定为上述局部闭环；当前无新代码、换版或回滚动作正在进行。
