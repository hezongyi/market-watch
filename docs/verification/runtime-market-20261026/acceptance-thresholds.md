# 阶段 0：业务验收阈值（草案，尚未确认）

基线 `v1.29.1 / 78697159`。当前状态：源码盘点与五场正式 fixture 采样均完成。现有证据及边界见 `baseline.md`；下表是业务门槛建议，不是用户已接受的标准。用户确认前不开始依赖这些数字的调度迁移。沉默和超时都不算确认。

## 范围与计时

代表性任务：一个自建品种，七条规则（两个确认柱、两个盘中触价、两个独立 ATR、一个 EMA 盘中条件），九个组合周期，一个打开的供应商图表低频需求；正常、历史/指标积压、候选历史/周期/组合指标重建、一个来源超时。旧部署独立 owner 进程运行于同一受控 cgroup，迁移后保持相同总资源、任务起点、输入频率和样本。不是生产库盘点，不是完整 HTTP/浏览器/R2 联合验收；A08 后续覆盖真实五/六服务及前台查询。

输入为明确标注的 fixture：报价每 2 秒；业务时钟按墙钟速度推进，M1 只在分钟边界确认，不能把一分钟每两秒推进造成的假 quote gap/追赶当作正常源延迟。外部真实供应商、手机到达时间不由该探针认证。所有阶段延迟用同机 monotonic，业务时间只用于合同与 ID 匹配，禁止将两种时间直接相减。

- source：供应商 source_time → 系统收到输入。确认柱另报告 bar end → 实际来源确认，不能把分钟等待算成判定耗时。
- ingestion：已收到输入 → 接收事务提交。
- publication：接收提交 → 相应修订/周期结果提交可见。探针观察点有上界采样误差，明确单列，不伪装精确 SQL commit 时间。
- evaluation：该输入可供判断 → 实际 judgment/signal 事务提交；总延迟从接收提交一直到事件提交，不能只报 evaluate 函数服务时间。
- projection：同一 signal 提交 → 同一 source_id 的网页 NoticeEvent 投影提交。
- delivery：同一 Outbox 已可投递 → ntfy stub/服务器接受；网络结果未知按原重试语义另计，accepted 不是手机到达。

原始输入、输入/规则配对、未处理/未发布分母、预期但缺失事件必须保留。p95/p99 的数值样本不含失败样本，因此同时报告完成率；不以极少事件的 p99 声称持续容量。正确性回归与时延认证分开。

## 业务建议

| 项目 | 正常、忙碌与健康来源的建议门槛 | 慢源 / 故障范围 |
|---|---|---|
| 可判断输入 → 判定 | p95 约 1 秒，p99 ≤2 秒 | 一个源超时不放宽其他健康源/规则门槛；故障源无有效输入明确暂停 |
| 接收提交 → 自建 M1 发布 | p95 ≤2 秒，p99 ≤5 秒 | 不把供应商尚未确认的输入算作系统已接收；确认等待单列 |
| 接收提交 → signal 提交（端到端内部） | p95 ≤3 秒，p99 ≤6 秒；正常/历史积压/候选重建同门槛 | 没有交叉时以 judgment/检查点延迟测活性，不能伪造信号；有确定性交叉必须核对事件分母 |
| 事件 → 网页投影 | p95 ≤2 秒，p99 ≤5 秒 | 慢投递不能阻塞投影/健康巡检 |
| 可投递 → ntfy 服务端接受 | 正常 stub 网络 p95 ≤3 秒，p99 ≤10 秒 | 外部超时/鉴权失败明示 unknown/blocked；重试到期另计，不保证外部网络/手机到达 |
| 实时组重启恢复 | 已就绪基线、窗口内输入、正常来源下 ≤60 秒恢复采集、聚合及判定 | 候选未准备好/供应商未恢复时显示 waiting/stale，不计假成功；离线超过30天按缺口合同暂停 |
| 运行故障提示 | 持续关键故障发生后 ≤60 秒在网页可见并排队到 ntfy；健康网络、非安静时段 ≤60 秒服务端接受 | API/浏览器离线仍适用；通知组/PG/宿主/网络/ntfy 同时不可用是内部自报警盲区 |
| 周日候选准备与激活 | 周日01:00 UTC 开始；代表性已准备历史候选 ≤2小时，并在市场日历恢复前至少2小时完成 | 准备不齐或历史覆盖不足则保持旧修订/安全暂停、单条失败汇总，不清理，不放宽实时判定延迟 |

告警约 1 秒的可见→判断目标沿用 `docs/verification/issue-13/acceptance-thresholds.md` 中已确认、适用的业务口径；没有据此批准任意更大 p95。该历史文件的 managed 发布15/30秒、ASGI服务耗时、固定10身份吞吐和原机器配额只在同一工作范围可比时直接适用，不将它们等同于本任务 composite 新流水线的端到端门槛，也不擅自改写原门槛。

告警/投影/投递不能重复制造逻辑事件。正常稀疏行情与已证实休市不按来源故障处理。恢复不补发切换价差、停机期间错过或旧历史条件。

## 从业务目标派生的运行策略建议

这些策略随一次业务确认固定，线程/连接池等技术参数不交用户逐项审批。

| 策略 | 建议值 / 约束 |
|---|---|
| 关键循环健康写入 / 巡检 | 实际有效检查后限频5秒，巡检5秒；异常立即尽力落盘，不由总心跳代写 |
| 关键循环失联 / 短暂错误 | 最后有效检查15秒后 stale；持续15秒才首报，正常空闲仍推进检查；慢IO循环另配合理 deadline 和进度，不统一误判 |
| 启动宽限 | 60秒，使用显式 expected-role 配置；反复启动达到5分钟内3次时汇总提示，不当作精确 Docker restart count |
| 故障持续 / 恢复 | 同事故最多15分钟重复一次，实际恢复一次恢复提示；跨通知组重启持久去重，确认不等于恢复 |
| 计划维护 | 明确范围及到期时间，默认最长2小时；失联不自动标为维护 |
| 安静时段 | 沿用现有设置，系统故障也不隐式绕过；上述手机提醒目标仅在非安静时段适用。要求绕过需显式改变业务选项 |
| 来源新鲜度 / 未来备用源 | 正常可交易时，连续15秒无合格输入标 stale；只在故障持续15秒且兼容候选已就绪时切换，候选输入至少稳定60秒 |
| 备用源切换 / 回切 | 候选已就绪后60秒内一致激活；10分钟冷却，优先源稳定5分钟才重新评估；没有真实已验收备用源时只测 fixture，不部署生产自动切源循环 |

## 资源与待补证据

阶段0测量预算：PG 0.75 CPU/768MiB，probe owner 进程合计1.5 CPU/1536MiB；PG14.24/JIT off，独立 schema 起点；每进程 pool2、overflow0、pool timeout15秒（旧版原值），max_connections40。记录各进程 CPU/RSS/线程、SQL读写、PG后端/IO和 cgroup throttle/OOM；pool acquire 包含首次建连成本，不将其全部称为连接争抢等待。

迁移目标池和并发容量按实际同时在途事务测量后决定，不原样复制所有旧池、不强制各组都只有2连接。不承诺未经测量的资源节省比例。

正式基线及事件分母见 `baseline.md` 与 `results/baseline-summary.json`。样本分母完整地保留在报告中；不能将若干未处理的输入/规则配对藏在百分位之外。尚缺：阶段 2 新运行组实际恢复计时、带目标优先级调度器的 A08 对照，以及用户明确确认记录。短 fixture 不是长期 p99 或生产容量认证；当前建议不能记作已验收。
