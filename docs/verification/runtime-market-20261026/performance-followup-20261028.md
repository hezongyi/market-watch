# 实时判定性能优化：独立后续事项

日期：2026-10-28。用户已决定维持五个应用服务，ChartAlert 内嵌 market-runtime；本项不阻塞当前正确性和运行组迁移收口。

## 已知事实

- ATR 行情可见→判断目标仍约1秒。旧内嵌合成忙载 p95 为1.197秒；独立告警六 owner Compose 忙载 p95 为1.163秒（40个样本）。两轮源码、拓扑和条件不同，不能据此证明拆出告警有优势。
- 六 owner 场景601笔输入、20个确认M1，17个预期 Signal/Notification/Outbox 均存在；接收提交→M1发布观测 p95 为0.621秒，输入提交→ATR判定 p95 为1.530秒。投递关闭，没有 ntfy accepted 时延。
- 原始材料：`results/runtime_compose_busycompose28e*`、`results/stage2-final-embedded-load-summary.json`。既有结果不覆盖、不改写为通过。
- 宿主机存在其他任务竞争；默认停止宽限使六 owner 退出137，缺最终SQL/CPU总结。功能PG后来提升至1536MiB，不能用于冒充原768MiB性能对照。

## 下一位开发者的执行边界

1. 以五服务迁移完成后的同一 commit、固定数据库起点和输入录制建立新对照，记录应用及PG独立cgroup预算、宿主竞争、源码指纹和完整样本分母。
2. 将单个输入/规则的时间关联到：供源接收→确认提交/实时发布→组合聚合→指标依赖可用→告警读取/判断→Signal/Outbox提交→到期投递→stub accepted。区分等待源分钟关闭、排队、SQL和实际计算，不能将不同样本的p95相减来归因。
3. 按观测到的最大开销选择一个局部改动；保留版本、输入修订、新鲜度、租约和重复抑制。不要为了降低读数取消正确性检查或改变阈值。
4. 固定条件复测 normal/busy/candidate/slow-source，记录漏报、重复、未处理输入/规则配对和延迟。需要新增常驻服务或改变业务阈值时先报告，不能从本事项推断授权。

验收以新增可比较证据为准；真实供源、手机送达及生产发布仍有各自授权与签收边界。
