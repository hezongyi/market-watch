## 2. 已确定的架构决策

1. 一个后端包、一套 ChartAlert 判定实现、一个 PostgreSQL，保留单一 Advanced Charts 业务前端。
2. 默认部署为 `web`、`api`、`market-runtime`、`data-worker`、`notification-worker` 五个常驻应用服务。
3. 默认三个后台组通过同一入口的三个固定 profile 启动；保留第 2 节所述独立告警的单一条件化预案，不做任意角色组合、通用插件平台或新任务中间件。
4. 告警独立于 API，默认与自建行情实时采集、接续和增量聚合同处 market-runtime；采集、聚合、判定各有独立循环和有界执行资源，不在采集回调中串行执行全部工作。
5. market-runtime 故障或重启会同时暂停其中的采集、实时计算和判定；继续使用既有租约、检查点和恢复语义，不承诺零中断。
6. 历史下载、固定版本及其周期产物准备、大范围指标初始化/批量重算，以及供应商图表打开期间的低频更新任务归 data-worker；自建行情的高实时性输入、组合实时发布及判定所需轻量指标推进归 market-runtime。供应商展示不创建后台常驻全品种采集，按打开图表的短期订阅需求低频取数，关闭时取消、失联时租约到期；不将所有包含“计算”的工作一概放到 data-worker。
7. 通知投影与投递同处 notification-worker，但各用独立循环；通知组可在 API、计算组停止时处理已有 Outbox。
8. 五服务是应用部署口径。外部 PG、一次性迁移、按需备份及必要的有界供源辅助进程另计。不得用三个容器隐藏十个常驻旧 worker 来凑数。
9. 本项目同时做行情代码职责收敛和运行组迁移，按阶段交付；不全面并表或重写行情算法。
10. ntfy 是主要手机推送渠道，本轮完成行情告警、运行故障提醒和测试消息的共享持久投递路径及验收，不另留一个“之后再接通知”的任务。网页通知继续可用；不新增手机 App 或重建 ntfy 服务。
11. 供应商行情仍可看图和通过 MCP 查询，OHLCV 沿用 PostgreSQL 有界缓存；供应商直连及独立 managed 系列不再作为新 ChartAlert 的来源。日常自建行情以现有 composite 连续序列呈现，底层 history/managed 仍可承担历史资产与维护职责。
12. 共享聚合首先要求规则与结果一致、现有实现复用及唯一发布者；本轮不强制将批量与增量改写为一个新累积器。搬入同一进程不等于减少 SQL，内存直送与回读优化以测量为依据。
13. 自建行情的实时部分至少保留滚动 30 天，满窗数据仅在对应切换整体成功后回收，不新增长期归档；当前实时源 OANDA 与 Dukascopy 历史分开。每周日 01:00 UTC 自动开始基线准备，通过校验后图表/活跃告警共同更新并重建判定基线，不因来源替换触发告警；真实缺口显示并暂停受影响告警。自动基线与清理属于核心迁移之后的独立轨道，按第 7 节分步验收。
14. 实时来源是可配置角色，当前默认 OANDA；每个有效运行版本只选一个实时来源，切换先准备、后激活。没有指定并验证的真实备用供应商前，只完成通用映射边界及双来源 fixture，不部署无真实候选的生产故障切换循环；真实备用源接入后按第 3.6 节自动切换，无需逐次许可。

五服务是默认部署手段，已确认的延迟与可靠性门槛优先。用户已认可单一条件化预案：先做有界调度与必要资源调整；若对比测量证明 market-runtime 内采集、实时聚合与判定的线程/CPU/生命周期争用仍使判定超标，则拆出独立告警服务，保持原门槛并验证改善。此条件下六服务属于本方案已授权技术范围，执行 Agent 报告证据和部署变化后可继续实现/Ubuntu 验证，无需重复询问同一架构原则；生产与合并授权不变。

必须分解来源更新、输入发布、判定、Outbox 等待及外部投递延迟。供应商迟到、PG 拥塞或派生输入滞后不因拆出判定自动解决；不能未经定位就增加服务，也不能只报告拆分后的进程内耗时来掩盖输入到事件总延迟。若六服务仍不达标或需要进一步改变业务语义/增加其他常驻组，按范围检查点报告，不放宽门槛。

## 3. 行情合同与存储边界

### 3.1 保留不同身份，共享基础能力

| 行情类型 | 合同 | 不能被本次改造改变的语义 |
|---|---|---|
| provider 供应商行情 | 读取供应商对应周期原生 OHLCV，按需缓存 | 不能替换成本地聚合后仍称原生；保留原生时间标签与来源能力 |
| managed / history 历史资产与维护 | 持续维护的本地行情及固定历史发布版本，作为自建连续序列的基础 | 不改写既有 ID、ticker、历史块与发布 manifest；不丢失被引用版本 |
| composite 自建连续行情 | 每个运行修订固定历史版本在 T 之前；实时流按自建品种配置选择启用或关闭；启用时使用指定确认实时来源在 T 之后，临时尾部显式标识 | 同一修订可追溯；按第 3.5/3.6 节自动准备/激活新修订，先接续 M1 再按既定日界聚合，不平移价格；运行绑定切换有审计记录；关闭实时流不影响历史维护与查看 |

“组合”在本项目主要指历史与实时接续，不将其扩展成多品种加权合成产品。内部四种读取身份 provider / managed / history / composite 继续可区分；用户无需在日常选图中理解四种技术类型，具体呈现与告警边界见第 3.3 节。

基础输入按既有维护模式处理：base_m1 保留原始 M1；base_d1 保留 D1、只派生既有允许周期；native_periods 分别保存所选原生周期，不跨周期推断。FXCM 已有历史能力不升级为实时来源；各来源能力限制、价格调整、量口径与实际历史窗口保持。

来源身份至少保留实际来源族、环境或账户范围、确切品种、价格口径、周期、复权与影响结果的参数；派生身份还需区分日界、日历和规则版本。只有语义及修订一致的数据可以共享；不能仅按品种名或时间戳去重。凭据不进入公开身份。

### 3.2 PostgreSQL 继续保存什么

| 类别 | 本项目默认处理 |
|---|---|
| 基础 K 线、来源修订与已有历史归档 | Dukascopy 历史按已有维护范围保存；选中实时源分钟/修订至少保留 30 天，成功切换后才可按第 3.5 节回收，来源分别管理、不互相改写 |
| 历史块、内容引用、固定版本和组合定义/修订/T | 保留可恢复内容及引用；组合复用历史，不复制整段历史 |
| 确认尾部、覆盖证据、确认水位、观察时间与修订 | 选中实时源至少保留 30 天，仅在切换成功后按第 3.5 节回收合格数据；必要事件证据单独保留，窗口外不承诺完整重放；正常稀疏行情不机械判为故障 |
| 高周期、已发布快照、组合聚合产物 | 保留现有必要持久化；明确它们是派生或发布结果及输入版本 |
| 指标状态与检查点 | 保留必要恢复与预热数据；不要求每次重启全量计算 |
| 供应商 OHLCV 缓存、SSE/共享图表快照和临时状态 | 沿用 PostgreSQL 有界缓存及清理，标明活跃消费者、任务与未完成退役的兼容引用；不把展示缓存升级为自建历史 |
| 维护计划、任务、租约、告警状态、判定依据与 Outbox | 持久保存，使用既有事务和幂等机制 |

`candles` 与 `chart_published_bars` 的暂存/发布区别继续存在，不能因 payload 相似直接并表。基础输入、发布版本与派生缓存各自明确写入者和失效条件。

不建设永久全量 tick 仓库。保持现有跨进程共享报价与临时柱状态，保留实际告警观察的必要依据；事后 OHLC 不能证明所有盘中触价顺序。可重建产物只有在基础数据、规则及受保护输入引用均可恢复时才允许回收机制清理；本项目按第 3.5 节在成功切换后回收所选实时源满 30 天且窗口外的数据，Dukascopy 历史不受实时保留策略影响；过期后的恢复/重算边界须明确。

### 3.3 两类日常入口与唯一告警数据合同

| 用户概念 | 看图与查询 | 新建/编辑为可执行告警 |
|---|---|---|
| 供应商行情 | 保留供应商原生行情查看、参数配置、分页、指标和必要订阅；按需读缓存、补取与有限预热 | 不支持；网页、HTTP、MCP 和后端执行边界一致拒绝，不只隐藏按钮 |
| 自建行情 | 以现有 composite 连续序列作为日常对象，显示历史来源、实时来源及就绪状态 | 仅支持这类序列；绑定明确组合修订、固定历史版本、实时映射、日界与确认语义 |

独立 managed 图表和固定历史版本以“历史数据集 / 历史版本”呈现，降为数据管理/档案中的检查入口，不再与上述两类并列为第三种日常模式；保留必要历史读取、MCP 数据查询及已保存图表的兼容打开能力，不重写已有 ticker 或偷偷把其解析为另一系列。旧输入若已按第 3.5 节过期，明确返回可用范围/过期状态，不假装还能完整读取或静默替换成另一来源。日常筛选与默认创建流程统一，数据来源详情和固定版本仍可检查。“自建”是业务展示概念，不新增一套替代 composite 的物理表或重复领域模型；不能据此让所有 managed/history 数据自动获得告警资格。纯历史、无有效实时映射或尚未就绪的序列可查阅，但不能伪装为已就绪告警。

创建、恢复运行、复制、编辑和 MCP schema/能力发现均收口为 composite 告警；旧 provider/managed 配置和事件保留可读取格式，后端不能把旧活跃记录继续送入已退役的执行分支。阶段 0 按第 10 节盘点现存非 composite 规则及影响，生成退役/显式重建清单；不按同名品种自动迁移，供应商原生周期与本地聚合结果不保证同义。兼容读取、停用、导出与历史证据保留；真实实例的规则停用随正式切换授权核对，不以方案文档授权生产改写。实时响应型告警必须引用实时流已启用且有健康来源的自建品种；实时流关闭或输入过期时，明确显示不具备实时判定条件并暂停受影响规则，不能把无输入解释为条件未触发。告警来源限制与保留告警的触价/确认、ATR、次数及通知语义分别验证。

供应商缓存沿用 `provider_datasets` / `provider_bars` 等现有 PostgreSQL 实现。页面请求或有效订阅驱动更新，预热仅围绕当前视窗及指标必要前缀并受现有容量/来源预算约束；没有告警驱动的永久 provider 采集需求。重新登录不代表整段历史重拉：复用已覆盖历史，按来源规则刷新过期尾部或核验历史。服务重启可复用 PG 缓存；不改为仅内存缓存、不新增 Redis，不去掉现有分页、修订或快照合同。退役完成前保留旧引用保护，完成后删除只服务于旧供应商行情告警的需求扫描与 ATR 分支；供应商行情订阅、协调租约和必要历史任务仍保留。

### 3.4 实时聚合职责与最小迁移方式

data-worker 准备并发布固定历史及周期/指标基础产物；market-runtime 读取所需基线、接缝周期输入与检查点，持续接入实时分钟，增量接续、聚合、推进必要指标并判定。每个进程导入共享代码并持有自己的状态，不新增内部 HTTP、跨进程内存总线或通用计算框架。历史获取沿用既有维护计划及支持的周期，不把“每天维护”改成每天全量重拉。

先将现有组合聚合调度整体归到 market-runtime，保留 PG 输入事件、任务租约、输入版本、检查点和有界批次。一个组合修订/周期的可发布结果只有一个调度归属；data-worker 不并行领取该组合聚合任务。组合首次准备、离线积压和修订重建仍按既有任务分段处理，market-runtime 为实时推进和判定留出容量，不在采集回调中同步做大范围重算；需历史/指标基础产物时仍等待 data-worker 的就绪结果。不得在本轮自行增加两组同时处理同一组合队列的动态分流协议。

当前批量 `composite_series.aggregate()`、增量 `composite_realtime.Bucket` 及历史产物逻辑已有不同实现；复用现有代码和对照测试，明确日界、价格/量口径、来源、接缝、确认/质量政策及版本。优先消除直接重复且容易漂移的规则，不强制全量改写为一个累积器，不为“共用算法”改变现有缺数或休市政策。原生周期、D1 基础和 M1 派生仍遵循各自合同；同一适用输入/规则经全量、分块、增量及恢复计算的结果须一致，覆盖乱序、重复、修订、DST 与周/月跨接缝。

搬进同进程不自动减少 SQL。先测 PG 查询/写入、连接池等待与告警总延迟；若回读构成瓶颈，再用已提交输入及有界进程内缓存减少读取，保留持久检查点与恢复。内存仅作加速，不把未提交输入发布为确认结果，也不跨线程共用 ORM Session。最新临时柱与已确认输入分开，图表更新不意味着历史已确认。不能把多年 M1 全量加载或“一天只读一次 PG”当成目标。

每个已发布运行修订的历史版本、来源和接缝仍不可偷偷改写；当前图表/活跃告警按第 3.5 节每周共同跟进已就绪新修订，备用实时源按第 3.6 节健康策略自动切换。过去事件保留原输入身份和必要证据，不把另一来源价格改写成原 OANDA 观测；供应商浏览缓存 TTL 与自建实时至少 30 天的保留窗口分别管理。

### 3.5 实时保留窗口与周日自动基线更新

用户已明确选择：Dukascopy 固定历史继续按原维护范围保存；当前 OANDA 及未来被选中的备用实时源至少保留最近 30 天，满窗且无有效引用的数据仅在关联切换整体成功后回收，不长期归档为自建历史。来源身份、口径和数据维护分开，不能把实时源价格写入 Dukascopy 历史版本；自建图表仅按明确接缝接续它们。30 天窗口针对所选实时源，不是删除 Dukascopy 历史。

| 数据类别 | 生命周期与清理合同 |
|---|---|
| Dukascopy 历史数据集 / 固定版本 | 沿用既有维护和引用策略；本次不对其设置实时窗口 TTL |
| 当前选中实时源的确认 M1、源修订、组合实时引用 | 至少保留最近滚动 30 天；超过窗口后仅在关联切换整体成功后才具备回收资格，不压缩归档成该来源长期历史，不并入 Dukascopy |
| 当前选中实时源的临时报价、未确认柱、展示快照 | 按实际有效期/确认状态清理，受实时窗口约束；不删除仍在使用的当前状态，不让旧快照长期固定行情明细 |
| 过期输入事件、旧聚合/指标产物与缓存 | 随保留边界整理，解除过期任务/版本引用并回收；不能仅删 M1 而把同一段 OANDA 原始明细藏在事件 payload 或另一缓存里长期保存 |
| 告警事件、判定证据与通知状态 | 保存必要事件时间、来源/版本身份、实际观察值、指标值与判定结果及未完成投递状态；不因此长期保存整段 OANDA 原始行情，不承诺窗口外任意历史输入的完整重放 |

**保留窗口口径。** 30 天是最小保留窗口，不是到期即删的定时 TTL。按 UTC 当前时间向前滚动 30×24 小时，以 K 线所属时间比较，不按 30 个交易日或最后一条行情倒推；未满 30 天的数据绝不可删除。满 30 天仅表示可进入回收候选集，必须等关联的基线/来源切换整体成功后才可执行有界清理。切换失败、只完成部分激活、任务重启或单纯时间到期，都不能触发本批次实时源清理；失败后保留数据供当前版本继续运行或恢复，待后续一次切换成功后再回收已满窗口且无有效引用的数据。成功切换后的清理可分批重试并记录滞后；清理中断不回滚已完成的有效切换。读取、准备和自动切换候选只承认窗口内数据，不能清理后又从供应商重拉过期数据；停机后不从旧接缝无限补取。指标依赖或任务积压不能让未满 30 天的数据丢失，也不能把窗口外数据重新视为可用输入。

**现有实现的冲突。** 当前 composite 从固定 `seam` 之后一直读取所选实时源；告警固定 `history_version_id`、组合修订和接缝，`composite_inputs.rows()`、确认水位和指标恢复会读取对应源分钟/修订。若接缝长期不动而删掉窗口外实时数据，历史末尾与当前尾部之间会出现缺口，旧基线指标也可能无法重建。因此需要周日切换新运行修订并明确窗口外不完整重放，不能同时要求长期固定旧版本、严格 30 天删除和无限期完整重放。

**已确认的每周基线更新。** 每周日 01:00 UTC 自动开始一次工作：使用已准备且验证通过的最新 Dukascopy 版本，为自建行情准备新组合修订/接缝及所需周期、指标产物。通过完整性和就绪检查后，无需用户逐次批准，自动将图表和活跃告警统一切到同一运行修订。01:00 是开始时间，不是假定耗时为零的强制切换时刻；按市场日历和阶段 0 测量设完成时限，应在实时市场恢复前准备就绪。规则条件、几何、次数和通知选择不偷偷改写；切换重建判定基线，不把来源价差、历史版本差异或停机期间错过的条件补发为新告警。既有规则版本/事件保留身份与必要自足证据，不再要求永久保留其完整实时行情。若 Dukascopy 最新可用历史未覆盖实时保留窗口，显示缺口、暂停受影响告警并通过 ntfy 提示，不伪造连续、不扩大 30 天窗口。

用户已明确选择每周固定窗口自动切换及至少 30 天实时保留，不需要逐次许可。图表/告警引用稳定的自建行情身份；每周切换记录新运行修订和规则运行绑定，复用既有版本/激活机制，历史规则配置和过去事件身份不原地改写。来源替换的指标/周期结果允许变化，需重新准备并建立基线；条件、绘图端点、价格/次数、冷却和通知选择保持，几何条件若无法重定位则明确暂停，不能擅自移动用户画线。候选准备和计算在切换事务外，最终有效指针/绑定一致提交；判定轮次读取同一运行修订，旧任务/旧输入不能在切换后提交为新版本事件。一次切换只有在候选输入、周期/指标、图表与活跃告警绑定完成一致激活，且旧任务已被 fencing 后才算成功。切换失败或部分激活失败时保留旧修订/安全暂停状态、不运行实时源清理，并通过本次切换运行的一条汇总 ntfy 报告失败阶段、原因和当前状态；该次运行的重试与多条规则错误合并去重，不逐规则或逐重试推送。成功切换后才启动对应清理批次。若旧修订所需数据仍在至少 30 天窗口内且新鲜则继续工作，否则显示缺口、暂停受影响告警并报警；切换失败不豁免 30 天最小保留，也不触发删除。

**清理执行。** data-worker 复用统一监督器执行有界清理，但清理任务必须由持久化的成功切换事件解锁：每周基线切换或备用源故障切换未整体成功时，本次不做任何实时源数据回收；成功后按 UTC 30 天下界和有效引用检查分批回收。不能由每小时定时器单独触发删除。data-worker 重启后仅可恢复/续跑已有成功切换批次，不能把普通定时 tick 或失败批次推断为清理授权；批次以切换运行 ID 幂等处理。market-runtime 继续唯一负责实时写入和组合发布；共享来源按账户/环境身份核对，不删除其他实时源数据。`market_composite_minutes`、`market_composite_minute_inputs`、`market_source_minutes` 引用 `market_source_minute_revisions`，聚合顺序消费 `market_composite_input_events`，必须在清理事务中协调来源锁/租约、活跃运行版本下界、检查点与 FK 删除顺序。已不再有效的运行修订不持续领取新实时数据或聚合任务。最小兼容的保留边界/任务恢复扩展可纳入 F1，不新增归档表或归档服务。过期输入不能再被当作可用；需要它的任务明确失效/重建/暂停，不以“未处理”为由删除未满 30 天数据。

切换后旧运行修订冻结其输入水位并结束持续采集/计算需求，仅保留必要短期读取与事件证据；每周新版本不能让所有历史修订永远继续接收实时分钟。重点修改 `composite_inputs.apply_minutes()` 当前遍历所有修订的写入分发，以及组合聚合 claim 对所有缺任务修订自动登记的行为：只装配当前有效或正在准备且未过期的运行修订，过期修订不再扩写/重新入队。共享行情来源仍可供其他有效消费者使用；停止旧修订不是误停账户级采集。输入事件 payload、源页面缓存及聚合旧版本一并纳入同一清理清单，不以复制到另一张表规避 30 天策略。

**验证。** 阶段 0 盘点超过 30 天输入依赖、指标/周期及 Dukascopy 最新覆盖；轨道 C 实现周日 shadow/自动基线更新、成功切换后清理和对应恢复。A04a 覆盖 shadow 差异与不改有效绑定；A04b 覆盖自动激活、版本/接缝切换、失败通知和 fencing。A13a 覆盖 30 天下界和引用保护，A13b 覆盖切换成功解锁、失败安全及 dry-run 报告，A13c 覆盖备份恢复硬门槛、首次真实清理与中断续跑。必须证明未满 30 天数据不删、切换失败/部分激活失败时不清理、切换成功后才回收已满窗口且无有效引用的数据；并覆盖周末/长假、历史更新失败、离线超过 30 天、共享引用、清理进程重启/续跑与旧数据不回填。A05/A08 验证告警持续性和延迟门槛。来源更换后重新计算，不要求新旧价格相等；窗口外完整重放不作为通过条件。每个失败切换运行仅产生一个按运行 ID 去重的 Outbox 汇总消息，重试复用同一逻辑消息、逐规则错误合并；维护最近成功/滞后及长期失败复用现有健康状态与通知。


### 3.6 可切换实时来源，保持单一有效输入

当前使用 Dukascopy 历史与 OANDA 实时，未来可配置备用实时源。逻辑自建行情身份及用户图表/规则不因换源重建一套；来源映射、账户/环境、确切品种、bid/ask/mid 等价格口径、精度、日界、确认与新鲜度能力进入具体运行修订。每个自建品种有独立的实时流启用状态：关闭时保留每日历史维护和图表查询，不登记实时采集需求、不参与自动切源、不占用实时尾部保留/清理任务，也不能承载实时响应型告警；重新启用时先验证候选源和接缝准备就绪，再恢复实时告警资格。迁移时已有有效实时映射和活跃实时消费者的品种保持启用，纯历史品种保持关闭，不能因新增开关意外停掉既有行情。开关配置复用现有自建定义/修订存储；仅在阶段 0 证明无兼容位置时才做最小 additive schema 变更。存在原生行情查询能力不等于具备可用实时尾部能力，不将 FXCM 等仅历史适配器标成就绪备用源。

本轮建立最小来源能力边界和自动切换流程：复用现有映射、修订与准备/激活机制，去掉领域层仅允许 OANDA 的硬编码前提，OANDA 专有鉴权/账户 owner/fencing 留在其适配器。以两个明确标为 fixture 的不同来源验证独立身份、故障检测和切换；尚未指定第二供应商，不虚构真实接入成功，也不建设万能供源插件框架。具体源加入可自动切换列表前须实现并通过其适配器、确认契约和同一套验证，不需要每次事件单独许可。

1. 已接入实时源按用户设置的优先级维护；只有账户/环境、品种、价格口径、精度、确认方式和实时新鲜度能力已匹配且候选输入就绪的源可以进入候选。故障判据采用阶段 0 实测后写入的健康/延迟阈值，过滤短暂抖动；不对不兼容源做猜测性替换。
2. 每周日 01:00 UTC 自动开始 Dukascopy 基线候选准备。历史版本、接缝、实时尾部、周期/指标和规则绑定全部验证后自动激活；此时间是开工时间，允许准备耗时。优先在按市场日历确认的周末低活跃窗口完成，不能仅凭固定星期假设市场已关闭。
3. 实时源达到已确认故障条件时，自动选择优先级最高且就绪的备用源；先准备至少 30 天保留范围内可用的候选窗口与指标，再统一激活新映射、图表和规则运行绑定。切换期间原源仍健康则维持原源；原源已不可用且无候选就绪时，显示 stale/gap、暂停受影响告警并通知，不读半准备结果。该切换未整体成功时不触发任何实时数据清理。
4. 候选来源的确认输入、周期/指标和规则绑定准备完成后，按第 3.5 节统一激活并建立新判定基线；判定不能读取旧源价格配新源指标。源间价差不平移、不作为真实价格穿越发送告警。激活失败原子回滚到旧修订；若旧源不健康则进入暂停/等待状态。每个切换运行最多创建一条按运行 ID 去重的 Outbox 汇总消息，包含失败阶段、原因、受影响来源/规则数量及当前运行状态；重试更新/复用同一逻辑消息并合并逐规则错误，不逐项新建通知。整体激活成功后才解锁清理，按至少 30 天最小窗口处理过期且无有效引用的数据。
5. 切换有效性按映射/运行修订和既有任务 owner 校验，旧响应不能提交到新修订或推动当前告警。旧源若仍有其他有效自建消费者则按来源身份继续服务；无消费者后停止其采集需求并按 30 天策略回收，不留下永久订阅。
6. 自动切源后按明确冷却/稳定窗口再评估恢复优先源，避免来回振荡；恢复源也必须先补齐窗口内可用数据、验证并重建基线。回切不伪触发告警。自动故障判据、冷却和切换耗时进入阶段 0 阈值建议及用户既定的一次业务阈值检查点，数值固定后按策略运行，不逐次许可。

周日调度自动执行版本切换；备用源自动切换由已确认健康策略触发，不等待用户许可。二者都不承诺零价差、零准备时间或始终无中断。备用源复用至少 30 天保留窗口，不另开长期实时历史。每周历史更新与故障切换并发时，以已核对的当前修订为条件激活；过时候选丢弃/重试，不覆盖较新的运行版本。每个切换事件成功后才执行对应回收；失败时保留数据、暂停不安全的受影响告警，并以单条汇总 ntfy 通知该次失败。

## 4. 默认运行组与调度所有权

以下按前置任务清理后的实际代码重新核对。每项持久任务和持续循环必须有唯一调度归属；API 可以执行有界交互查询，但不得启动持续采集/判定调度。不同角色可依现有锁/租约共享存储，不用新增分布式 owner 系统。

| 当前职责/入口 | 目标归属 | 迁移要求 |
|---|---|---|
| api lifespan 中 provider_service 的供应商订阅轮询、预热与清理 | data-worker | 仅维护打开图表的有效低频订阅；预热限于该视窗及必要指标前缀或明确的活动需求；关闭即取消、断连由订阅租约到期；无活动需求时不遍历/采集全供应商品种，也不进入 market-runtime |
| 保留的统一告警调度及自建告警输入需求 | market-runtime | 自建告警输入需求独立于网页；移除已退役的 provider 告警/ATR 扫描；API 不再调用完整 start |
| pricing-worker / oanda_worker | market-runtime 的 pricing 逻辑角色 | 账户实时采集、账户租约、epoch/fencing、断线及确认恢复不变 |
| 自建行情当前选中实时源及合格备用源的输入/恢复 | market-runtime | 高实时性输入由唯一活动来源负责；OANDA 保留既有 owner/fencing，供应商图表低频订阅不在此角色 |
| chart-history-worker、native-history-worker | data-worker 的有界 I/O 循环 | 后台分页可恢复；前台等待需求优先于多年历史回填 |
| history_versions 的计划、准备、归档与导入 | data-worker | 拆开网络和计算调度；沿用任务 checkpoint/lease |
| chart-aggregation、managed publication、固定历史周期产物 | data-worker 的历史准备通道 | 保留现有发布合同、任务检查点及有界批次；不领取组合实时聚合队列 |
| composite aggregate / 实时接续与聚合发布 | market-runtime 的独立计算循环 | 整体迁入现有组合聚合调度，含有界首次准备/追赶/修订任务；实时推进有保留容量，不在采集回调中串行重算 |

| 周日历史更新与当前运行修订切换 | data-worker 准备历史/指标基础，market-runtime 准备候选实时输入并自动统一激活/重建判定基线 | 每周日 01:00 UTC 自动开工；候选通过门槛自动切，不经逐次许可；同一图表/告警运行绑定不混版 |
| 备用实时源自动切换 | 健康巡检/来源策略选候选；market-runtime 准备/激活 | 只从兼容且就绪列表自动选择；阈值/优先级明确，不默认额外常驻进程；抖动不来回切 |
| 活跃自建告警所需轻量指标推进与判定 | market-runtime | 复用既有算法和持久状态；依赖历史初始化时明确等待就绪，不承诺所有计算独立于 data-worker |
| notification_center_worker | notification-worker 的投影循环 | 可重建投影；不承担新告警判定或网络投递 |

| api 的 provider_transport / 请求客户端 | api 本地资源生命周期 | 可保留有界查询所需客户端维护；不能用此恢复持续告警循环 |

旧 composite_watches 退役不代表组合行情聚合退役。历史/采集共享能力不能按文件名含 legacy、Watch 或 composite 全删。

`provider_service.start()` 是高风险拆分点：按逐源 live、需求维护、判定、逐源预热、清理、目录初始化分别登记到 `ownership.md`，标明保留、迁移或退役。供应商图表低频订阅、补取与预热归 data-worker，仅由活动图表需求驱动，关闭即取消、断连靠租约到期；不得启动全供应商常驻采集。旧 provider 告警持久采集与独立 ATR 扫描删除；自建告警输入维护及统一判定归 market-runtime 且不得漏迁。每项写明原启动路径、目标角色、调度入口、客户端/执行器/停止事件的创建与关闭者、依赖资源和对应验证。目录初始化按实际前置实现明确唯一执行或既有安全幂等规则，不能遗漏，也不新增常驻目录服务。market/data 两组都不得调用完整 start；现有 `_EXECUTOR` 防重仅在单进程内有效，不提供跨组互斥。启动装配测试须证明保留职责恰好启动一次、退役分支不启动、API 不启动持续调度，停止资源由对应所有者关闭；独立告警预案启用时，同步验证 market 不再启动判定。

OANDA 所有权限定为现行账户实时报价、确认与 REST batch live 契约。合法历史请求继续走现有身份与资源预算；不可把“独占实时”扩大成禁止所有历史读取，也不可允许通用实时角色重复发 OANDA live 请求。

OANDA 当前已含确认、续租等内部线程，迁移重点是保留其状态机并适配外层生命周期。账户租约、epoch/fencing、确认与断线恢复、鉴权退避和当前采集模式保持；仅做接入组停止信号、主线程信号处理、适配器初始化/关闭及必要监督上报。保留 `live_pricing.py` 中仍被使用的行情所有权与写入保护能力，不能随旧告警入口按文件名删除。停止、失去租约或旧连接未及时结束时，迟到响应仍须被原有事务 fencing 拒绝；不能先释放资源再容许旧线程继续提交。

## 6. 生命周期、资源预算与故障处理

### 6.1 有界并发和资源

- 运行组拥有停止事件、客户端、连接池和少量固定执行通道。长循环保留专属执行容量，不将全部常驻循环排进可能饱和的共享小线程池。
- 多来源网络等待分别推进，保留原有逐源并发、冷却、限流和重试。线程迁移时显式传递或恢复 lane/deadline 及相关预算/取消上下文，不让历史任务误用实时预算。在线程任务入口设定、结束时恢复；有意继承上下文的提交逐次复制，不能并发复用同一个 Context，也不能把启动线程的请求 deadline 固定给常驻循环。测试跨线程传递、异常退出后的恢复及线程复用无串扰，不能只检查 ContextVar 声明。
- provider/OANDA 已有内部线程；合并时核对原进程隔离的模块全局状态、停止事件、缓存、客户端和执行器是否会被不同逻辑角色误共享或互相关闭。数据库 engine/pool 可按组共享，Session/事务及 ORM 可变工作状态不跨线程共享；客户端按库的线程安全契约及既有 lane 隔离规则使用，不盲目共用或逐线程复制全部池。
- 判定不等待某一供源请求完成才轮到自己。market-runtime 的组合实时增量、必要指标推进与判定有保留容量；data-worker 的历史网络和 CPU 批任务受预算约束，不能挤占宿主机与 PG 的实时余量。
- `history_versions.worker_tick` 现有异常隔离不等于时间隔离，应拆开网络阶段。market-stream 也可能触发受控供源读取，不能按“纯 CPU”无限提交。
- 沿用聚合切片，验证单轮上界；既有预算不能抢占在途 SQL，数据库查询与网络都需有效超时和短事务。
- 按并发事务需求设置每组 pool size、overflow 和连接等待超时，核对 API、三个组、LISTEN/维护连接的总预算。不原样复制十个池，也不强制所有组都只有 2 个连接。
- 记录线程数、进程树、RSS、连接数、CPU 和日志上界。CPU/内存限制需留出实时组及 PG 的余量，不能靠线程宣称完全隔离 CPU/GIL。
- 日志使用运行组、逻辑角色、任务标识与安全错误类型；不记录凭据、账户私有响应或含密码连接串。Compose 默认日志轮转可沿用 10 MiB × 3。

具体线程、连接池和切片默认值由阶段 0 基线与测量确定，写入配置文档。实现者可自行决定数值，不把常规调优问题逐项交给用户。

### 6.2 退出与循环故障

- 主线程统一处理 SIGTERM/SIGINT；循环用 stop.wait 代替不可中止长 sleep。
- 收到退出后停止领取新任务，完成或安全放弃有界在途工作，再按现有租约释放/自然到期和 fencing 规则关闭资源。
- 停止超时不能强行把未完成任务标成功；旧响应不得覆盖新 owner 的提交。
- 可恢复单轮错误按角色退避，单来源故障不停止全部循环。关键循环意外退出须让组健康降级，并由主线程清理后非零退出，利用现有 restart 策略恢复。
- 心跳由实际循环完成推进；不能由一个仍存活的总心跳掩盖子循环失效。数据库不可达时保留旧时间和安全错误，不伪造成功。
- 不依赖 Docker unhealthy 自动重启；明确关键循环退出触发进程退出。普通供源故障只显示对应状态，不造成持续重启风暴。

### 6.3 可观察状态

复用现有心跳存储与 `/api/health`：展示组/角色的 expected、running、idle、waiting_input、degraded、stale/disabled 语义或项目等价状态；给出最近循环完成、输入确认水位、检查点、积压及最近错误。

状态页区分“无活跃任务”“已证实休市”“来源延迟/缺数”“判定循环失效”“通知积压”。图表可读、来源已确认和告警可判断不是同一状态。`/readyz` 继续表达 API 基础就绪，不冒充行情新鲜度。

后台健康探测直接读取角色状态或执行本地命令，不调用 API。即使 API 完全停止，也能通过 Compose、日志和任务测试确认后台运行。

阶段 0 先确认心跳存储粒度。现有 `Preference(key, JSON value)` 并未把表结构限制为固定 worker，限制主要是 `worker_health.py` 的角色白名单与查询；优先为关键逻辑循环分配稳定独立 key，扩展已有代码而非直接新增表。记录部署/角色、运行实例或启动标识、最近有效检查/成功时间、当前错误，以及业务水位；不要让多个循环对同一大 JSON 做读改写而互相覆盖。核对旧实例迟到写入不能冒充新实例健康，按既有所有权及明确写入规则验证，不能只添加 boot_id 字段便宣称有 fencing。写入限频/过期阈值须满足已确认异常提示时间，不直接沿用现有所有角色五分钟阈值。

优先复用存储不等于禁止 schema 调整：若实际证明兼容表示或并发写入约束有缺口，可采用最小 additive 变更并验证旧记录，记录原因；与第 6.5 节系统消息的持久格式扩展分别判断。

### 6.4 先建立最小循环监督原语

此项为用户已认可的实施细化。先实现小型共用原语并配好测试，再迁移各 worker，避免重复实现停止、退避、心跳和失败传播。不建设通用任务调度框架。

`runtime_roles.py` 或等价模块保留稳定逻辑角色名和构建函数，角色明确依赖、资源生命周期与状态上报。告警角色仅装配判定，不顺带启动采集；默认 market profile 组合相关角色。独立告警预案需验证资源初始化、唯一调度以及原 market 组不再启动判定。目标是拆分不重写业务逻辑，不仅凭角色注册表就承诺“未来只改配置”；不预先建设任意角色排列组合框架。

- 所有顶层运行循环接受统一监督。简单单步任务使用公共 `step()` 循环；已有复杂循环保留 `run(stop, …)`，监督器负责启动、退出、失败传播及资源收尾。
- 进程主线程接收 SIGTERM/SIGINT 并设置共享 stop；停止能够打断公共等待/退避。关键循环非预期返回或未处理异常必须通知主线程，停止其他循环并非零退出；后台线程抛异常本身不代表进程已退出。
- 循环完成、空闲检查及失败使用明确的结果/回调更新角色状态；复杂 run 内部已处理的错误也需上报，不能因异常未外抛而被当作成功。正常无任务仍有循环活性，业务水位与循环活性分别记录。
- 监督器心跳复用既有存储和限频机制。只有实际工作循环完成或有效空闲检查才能更新相应状态；不能由独立定时心跳掩盖卡死，也不能在恢复重试开始时清除尚未恢复的故障。
- 错误恢复保持来源/任务语义。单轮可恢复错误局部退避，致命配置/契约错误或关键循环异常终止触发组级失败。已有业务退避不在监督器再叠一套重试，避免双重等待或重试放大。
- 保留告警单调时钟节奏及错过轮次合并、OANDA 账户租约/认证/连接状态机、聚合 budget/wakeup，以及 Outbox 到期重试；不强制它们改用统一固定 sleep 或统一指数退避。
- 阻塞网络与 SQL 依靠有界超时和既有 fencing 处理，不尝试强杀 Python 线程。监督器不能在未验证线程退出与在途工作状态前宣称组已完成安全收尾。

先以一个简单有界循环和一个复杂保留 `run(stop)` 的循环验证 Interface，必要时调整原语，再扩大迁移。覆盖 stop 打断退避、正常空闲活性、失败不刷新成功时间、内部错误上报、非预期返回、关键线程失败导致真实进程非零退出，以及资源关闭。调度节奏优先使用可控时钟测试，进程退出语义使用子进程行为验证。

### 6.5 ntfy 主推送链路与运行故障提醒

用户已认可运行故障主动推送，并要求本轮把主要 ntfy 推送链路接好以便测试。复用既有 ntfy 服务、配置、Outbox 投递、重试和确认能力，按阶段 3 实现与验收；不增加常驻应用服务。

**共用投递，明确消息类型。** 行情信号、运行故障/恢复、主动测试属于不同事件类型，共用通知组的持久投递路径。基线 Outbox 关联 Notification，后者必须关联 SignalRow，投递代码还会读取价格和阈值；因此不能宣称已经支持任意系统消息。以 v1.29.1 的实际模型和投递代码为准选择最小兼容扩展，保留旧信号关联和历史记录，允许系统/测试消息引用真实事件或有界内容。若确需 additive schema，明确列出迁移、约束、旧记录兼容和回退条件；不得伪造价格信号来绕过 schema，也不另建一套消息队列。

**主要渠道配置与创建行为。** 复用 ntfy URL/topic/token 和现有全局投递设置，不新增多供应商渠道框架。界面明确“已配置、投递已启用、请求已排队、服务端已接受、失败/结果未知、用户已确认”；不得将 topic 存在视为已连通。新建告警在 ntfy 已配置且投递开启时可默认勾选手机推送，并在保存内容中明确该选择，用户可取消；已有告警的 notify_ntfy 不自动改写，HTTP/MCP 的显式字段和兼容默认保留。指定手机推送但未配置时，创建/编辑流程明确显示不可投递原因，不静默变成只在网页显示。

**检测者独立于被监控者。** notification-worker 内增加独立、有界健康巡检循环，不依赖 API、网页或投影完成。巡检预期运行的角色是否缺失/心跳过期、关键循环失败、短时间反复业务启动，以及影响活跃告警的持续输入异常。关键进程退出前尽力记录错误，不能依赖它必然成功；首次启动从未写心跳的角色也要在部署启动宽限后检测。预期角色和启动宽限来自明确部署配置，不能从“已经存在心跳”反推应监控哪些角色。

**恢复与去重。** 用部署/角色/故障类别作为稳定去重依据，记录持久事故状态、发生/恢复时间及最近推送；首次通知、持续故障限频、实际恢复后一次恢复通知。通知组重启不重置去重状态。切换失败以切换运行 ID 作为事故归并键，切换流程产生的逐规则错误、激活子步骤错误及健康巡检发现的同源症状都并入该切换摘要，不再分别创建 ntfy；只有与切换无关的独立故障才建立独立事故。用户确认只是已知悉，不能将事故标为已恢复；原始故障的重复提醒在恢复后停止或更新，避免积压旧消息与恢复消息矛盾。告警持续时间、启动宽限、重复通知间隔与异常提示目标相匹配，在阶段 0 摘要一并说明，不新增多轮审批。

**抑制噪声与故障扩散。** 正常休市、无活跃规则、短暂可恢复错误不等同监控失效。计划停机使用明确且有期限的维护标识，仅暂停相应角色的预期检查；失联不能自行判定为计划停机。数据库不可达会导致多角色同时过期，应合并为受影响链路摘要而非每条规则刷屏；不能在通知投递失败时再递归生成同类推送。

**启动与重试证据。** 复用监督器记录业务启动标识与启动时间，巡检判断短窗内反复启动，不向应用暴露 Docker socket 或把它称为精确 Docker restart count。启动早期未写记录的失败由角色缺失/过期发现。普通来源失败局部退避，组级致命错误退出后的反复重启不能只留状态页无人提醒。

**投递语义与时效。** 网络请求在事务外，保留 Outbox 租约、尝试记录、超时结果未知、401/403 阻断与退避。行情事件继续遵守既有迟到事件及确认/重复规则；系统故障不直接套用价格告警的持续响铃，故障、恢复、测试均使用各自有限提醒策略。提供故障事件定位链接和必要影响摘要，手机确认或点击链接所需的 API 地址必须对该手机可达；API 暂停不影响已排队消息投递，但确认/详情访问可能等待 API 恢复。

**安静时段和外部边界。** 复用现有安静时段，界面明确它会延迟手机提醒，不隐式绕过。阶段 0 的手机提醒目标说明安静时段是否适用；若要求关键故障绕过，须作为显式业务选项确认。ntfy 服务端接受不等于手机已收到；notification-worker 整组、数据库、宿主机、网络或 ntfy 故障可能使内部自报警失效，记录为覆盖盲区。已有外部存活监控可复用，否则本轮只留最小接入说明，不新增外部监控平台或第六个常驻应用服务。

**主动测试也走真实业务路径。** 基线 `/api/notification-tests` 由 API 直接 HTTP 推送，绕过通知组；本轮改为提交持久测试事件并由 notification-worker 投递，复用限频与确认审计。普通按钮仅在全局投递启用时排队；关闭自动投递时明确提示，不能按钮显示通过却掩盖实际投递关闭。若需保留旧“关闭自动投递仍可主动测试”的功能，必须显式标为单次测试授权，并仍经通知组处理测试任务，不放行普通待发队列。提供独立自动化测试证明测试消息不产生 ChartAlert 或价格信号、不改变规则计数。

**本轮分两层验收。** 第一层以任务 stub 验证真实规则触发到 Outbox、投递、超时重试、重启恢复、幂等/确认、故障去重与恢复；不向真实订阅者自动批量发送。第二层用专用测试 topic 和用户指定测试手机做少量真实端到端验收，核对锁屏收取、事件信息、通知点击和确认及 API 恢复后的行为。真实 topic/订阅目标、手机平台与可达地址在验收前核实，复用已有明确授权，不因编写方案自动发送实际消息；信息未齐时继续完成 stub 验收及其他工作，记录手机验收待完成，不声称已经通过。

手机端只要求已安装 ntfy 客户端和必要通知权限/订阅配置。自托管 ntfy、域名/TLS/公网访问改造、专用 App、强制响铃或锁屏绕过不纳入本轮；真实手机验证发现这些外部条件阻塞时，报告具体差距并单列任务。

## 7. 分阶段实施与交付

同一项目按以下依赖顺序分段完成，每个阶段单独形成可审查、可验证的提交/PR，并通过该阶段门槛后再推进依赖它的后台迁移；不把入口收敛、实时流开关、worker 迁移和部署切换合成一次大改。出现回归时按最近已验收阶段定位和回退，不长期双跑新旧调度。最终完成要覆盖全部阶段。

### 阶段 0：确认前置、职责清单与可比基线

1. 读取 AGENTS.md、v1.29.1 前置完成审计和本方案，记录真实实施 SHA、schema head、已支持功能及现有已知失败；复核合并后的 chart-origin 退役、同源信任边界、旧告警活动路径与共享查询抽取，不把前置工作列入本项目重复实现范围。
2. 逐项登记现存后台职责、输入/输出、任务/租约/客户端、启动者、确认状态、恢复路径，保存到 `docs/verification/runtime-market-20261026/ownership.md`；区分保留、迁移及退役分支，明确组合聚合任务唯一发布者。盘点日常系列入口、已保存图表和非 composite 告警，生成第 10 节退役影响清单，不为此访问生产。对现有实时断线恢复/源端补洞、浏览器订阅取消与过期租约、供应商缓存清理、SSE 游标续接/重连和重载恢复逐项记录代码入口及测试证据，区分“检测缺口并要求重载”与“后台已补齐源数据”；迁移优先复用现有机制，只对验证出的行为缺口补实现。盘点自建品种实时映射与活跃消费者，定义每品种实时开关的兼容初始值。同步固定第 6.3 节子循环心跳 key/字段、写入者、实例更替与限频规则，并确认现有表能否满足，必要的兼容扩展在迁移前明确。
3. 在任务隔离环境记录正常使用及“历史下载、聚合、指标重算有积压，同时自建 composite 告警持续接收新输入”的并发基线，不能分别跑历史和实时后合称并发负载。另覆盖候选历史/周期/指标重建与实时输入及告警判定同时进行的场景，记录候选工作对判定延迟的影响，并验证低优先级/有界预算可抑制影响。使用代表个人实际规模的任务与数据，并覆盖一个打开供应商图表产生的低频前台 bar 需求；记录供源模式、品种/周期/规则数量、积压规模、输入节奏、样本数/测量窗口、机器与容器资源限制、PG 和池配置，迁移后 A08 以可比数据/负载/资源预算复测；重置任务起点或补充受控输入，使前后结果可比，外部源变化单独标注。记录来源更新、派生发布、判定及整体输入到事件延迟、候选重建耗时与争用、供应商前台 bar 等待、投影/投递等待、PG 读写及连接池等待、积压增长趋势、CPU/RSS/线程数；补记 OANDA 实时明细增长、清理引用、超过 30 天的输入依赖和 Dukascopy 最新覆盖范围，为第 3.5 节落实配套策略。用代表性实测确定参数，不另建长期压测平台。基线不佳不能替代业务门槛，仍按第 2 节及阈值检查点处理。
4. 创建 `acceptance-thresholds.md`，记录测试范围、时间定义、实测基线、正常/忙碌/慢源的建议门槛、恢复时间预算及测量方法。已有明确且适用的用户确认 SLO 直接沿用，其余业务目标不能由执行 Agent 自行批准。
5. 设置一次业务阈值人工检查点：给用户简短摘要，确认告警延迟、实时组重启恢复时间及监控异常提示时间。告警延迟分解为来源更新、系统内部判定及通知投递；不得把外部手机到达时间作为系统完全可控承诺。由 Agent 给出建议值及依据，用户只确认业务可接受程度，不审批线程/连接池参数或整份技术文档。
6. 记录用户确认及适用范围后固定验收标准，再进入依赖这些门槛的阶段 2/3 调度迁移。等待期间可以继续阶段 1 的查询边界复核、必要 HTTP 依赖解耦、职责盘点及其他不依赖未确认数值的工作；不得用默认选项、沉默或等待超时代替确认。
7. 阈值确认后不得因实现失败单方面放宽；无法达到时先调优，再报告事实。未经测量不承诺资源节省比例。
8. 输出 `docs/verification/runtime-market-20261026/implementation-reuse-inventory.md`，以本轮代码核对为起点、按实际实施 SHA 更新：逐项记录目标行为、现有模块/入口/测试、当前运行 owner、可直接复用的合同、尚缺行为及计划改动。至少核对 `chart_query.py` / `series_access.py` 共享查询、`composite_inputs.py` / `composite_aggregates.py` / `composite_series.py` 组合输入与聚合、`oanda_worker.py` owner/fencing、`market_stream.py` 订阅 lease 与 SSE 重放、provider 缓存/适配器、ChartAlert 判定、Outbox 投递、`worker_health.py` / `Pulse`、修订准备/激活及历史清理。复用成熟逻辑优先于复制或重写；每项拟新增代码须说明现有能力为何不能满足目标。
   明确记录以下核对结论并由测试/调用链验证：`chart_query.py` 已是 HTTP/MCP/worker 共用查询实现，不假定另有 `market_query.py`；组合实时输入和持久聚合算法已存在，主要变化是唯一领取者迁入 market-runtime；OANDA owner/fencing、浏览器订阅 lease、SSE 重放/重连和固定修订准备/激活已有实现，按代码事实迁移及补缺；ChartAlert 仍允许并执行 provider/managed，旧 Watch API 返回 410 不等同全部旧告警已退役；`CompositeWatchBinding` / `CompositeWatchJudgment` 的活跃调用与存量引用须分别查证，不能只因未发现活跃调用就直接删表或解除引用保护；当前 Outbox/Notification 与 SignalRow 绑定，API 测试通知直发，系统故障持久投递需要真实的兼容扩展；既有历史清理不等于所选实时源切换成功后的 30 天清理；修订激活原语不等于已有周日自动更新或备用源自动切换编排。

产物：复用清单、基线、建议阈值与用户确认记录、职责清单，以及包含这些范围的本地 Issue/PR 草案材料。确认可先针对业务摘要完成，随后由 Agent 将数值、计时边界及确认依据写回文档。

### 阶段 1：行情入口、告警边界与共享职责收敛

1. 复核 `chart_query.py` 已实现的共享查询边界及 worker/MCP 直接依赖；只修复基线中仍存在的 HTTP 模块反向依赖或遗漏调用，不重复搬迁已提取实现。
2. 固定 provider/managed/history/composite 的身份、确认/发布时间与版本输出，HTTP/MCP/worker 相同输入得到同口径结果。

### 轨道 C：自动基线与保留清理

轨道 C 在阶段 0—5 的核心运行组迁移及延迟验收通过后实施，保持独立 PR 和门槛，不与 data-worker/通知迁移混成一次发布。它按“候选准备与差异报告 → 一致激活并 fencing 旧任务 → 成功事件解锁清理”推进，复用第 3.5 节定义的业务合同。需要相关章节与验收矩阵引用本轨道，不得把自动激活或实时数据删除描述为阶段 3 的迁移工作。

1. 先交付周日候选准备与 shadow 报告：生成候选修订和周期/指标产物，比较 bar 差异、末端指标状态、缺口及将暂停的规则，不改变有效图表/告警绑定。通过 A04a shadow 证据和延迟/恢复门槛后，才启用自动激活；无需每周人工许可，不要求无依据地等待多个周日周期。
2. 自动激活必须一次性绑定图表与活跃告警、建立新判定基线并 fencing 旧任务。缺失数据、候选未就绪或部分激活时保留旧版本/安全暂停状态、通知并禁止清理。
3. 30 天清理首次默认 dry-run，只报告候选范围、行数/字节估算、引用保护和跳过原因。dry-run 与引用审计通过后，首次真实清理前必须完成一份适用回退候选的备份恢复演练，并证明回退版本能处理保留边界或能通过恢复重建/暂停。该门槛未满足时不得执行删除；满足后可按已授权策略自动运行后续有界批次，无需逐批许可。每个批次仍须由持久化的成功切换事件解锁。A13c 留存首次真实删除的逐项证据；dry-run 不得隐式升级为删除。
4. 自动实时源故障切换的真实 provider 尚未指定。当前只实现映射/能力合同和双来源 fixture；待某备用来源被实际接入并完成账户、品种、价格口径、确认与新鲜度验收后，再单独交付真实健康判据、冷却、切换及回切。届时按用户已确认的自动策略运行，不逐次请求许可。

轨道 C 门槛：周日 shadow 与自动基线、失败安全行为、清理 dry-run、适用备份恢复及首次清理验收全部通过。真实备用源未接入不阻塞核心项目完成，但不得标记真实自动故障切换已交付。

### 轨道 D：手机端签收

服务端持久通知链路、故障矩阵和 ntfy stub 属于阶段 3B 核心验收。专用 topic/设备上的手机收取、点击和确认作为 A17b 独立签收；外部设备或网络条件不阻塞核心运行组交付。未完成时如实标记待签收，不把服务端接受写成手机已送达。

### 8.5 ntfy 真实手机验收记录

## 10. 数据、切换与回退

- 行情主模型不做全面 schema 改造。第 3.5 节 30 天窗口/过期任务边界与第 6.5 节系统/测试消息允许必要兼容 additive 扩展，以 v1.29.1 schema 和实际运行查询为基线选最小实现，补迁移与历史记录兼容测试，不因这些已纳入范围的扩展重复索要技术确认。其他状态存储缺口先证明必要性；破坏性迁移、物理并表、删除仍需保留的历史资产或新数据库引擎超出本方案。
- 非 composite ChartAlert 退役影响清单记录规则身份/状态、来源、指标依赖、历史事件及未完成通知，说明停用、兼容读取和需要显式重建的对象；不按同名品种自动换源，不删除事件/判定依据/Outbox，也不把无实时映射的历史资产伪装成可用替代规则。只读任务实例与已授权材料即可形成实施清单，真实生产现状在正式切换授权后核对，不为编写方案访问或改写生产。
- 规则停用与代码退役配套：隔离验收验证旧活跃记录也不会执行；真实切换在已授权操作范围内保存原状态、停用非 composite 规则并核对影响，再启用新运行组。供应商行情告警专用缓存保护只能在对应引用确已解除后收口；历史证据所需保护继续保留。回退须核对旧版本是否会重启已决定退役的规则，不因恢复旧镜像而自动恢复其运行状态；回退演练覆盖这一风险。
- 后台退出并保留数据不等于删除资源；任务 PG、历史块、Outbox 和审计都应保留。新旧版本共享任务库的切换必须停止旧写入者并验证无在途旧响应可提交。
- 用户已认可轻量启动防错：在宿主切换入口按显式 project/label/已核实部署清单检查旧 worker 和启动持续调度的旧 API。发现存活冲突则拒绝继续，列出冲突安全名称；归属不明先报告，不扫描后随意停止其他项目。旧部署也可能不在当前新 project 中，应从核实后的迁移清单指定，而非只看新 project 服务。
- 现有部分心跳有五分钟过期窗口且不覆盖全部 worker，不能等同运行锁。心跳只作辅助诊断，不能因正常停机后残留记录强制等五分钟，也不能因心跳过期放行已知存活容器。新旧版本可能写同名心跳，不把它当 owner 身份。
- preflight 是切换防错，不能消除检查后旧版本再次启动的竞争窗口；停止旧部署时同时收口旧启动入口/重启配置，核实不会自动拉回。实际采集与任务仍由各自既有 owner、lease 和 fencing 保护；不宣称这些机制自动覆盖全部无租约循环。保持明确互斥切换，不为一次迁移新建通用分布式锁系统。
- preflight 在明确授权的实际操作主机运行，不为应用挂载 Docker socket；本轮只在 Ubuntu 任务实例演练，不因此取得生产访问、停机或配置修改授权。
- 切换顺序：保存脱敏配置与候选/回退镜像清单，停止明确旧调度，检查 owner/fencing 和在途任务，启动新组，检查关键输入/判定/通知，再启 API/web。回退先停新组，核对原配置支持现有 schema，再启旧组；不长期双跑。
- 30 天删除会改变旧二进制从固定接缝读取全部 OANDA 的前提。首次实际回收前，核实回退候选支持保留边界及重建/暂停，或已有经过验证的备份恢复方案；不能宣称旧版一定兼容已删除输入。生产例行维护在正式授权的保留策略/发布范围内运行，不要求每个批次重新审批；本轮文档与 Ubuntu 演练仍不授权生产删除。
- 生产模板变更只是候选交付，不意味着授权生产执行。正式 tag、Unraid、发布备份、停止生产写入者、切换、回滚与永久资源删除必须按仓库规则取得本次授权。
- 任务验收不自动执行 volume 清理或全局 prune；后续退役沿用明确 task/project 的清单、归档与实际恢复验证。

## 11. 完成标准、边界与交付物

### 完成标准

1. 核心运行组交付需阶段 0—5（含阶段 1A）全部完成，A01—A16 与 A17a 有可核对证据，关键 PostgreSQL/跨进程项不以 skip 代替。轨道 C 按独立门槛签收；轨道 D 的 A17b 手机验收单独记录，不阻塞核心运行组交付，也不得伪报为已完成。

3. 用户侧为供应商/自建两类日常行情；内部 provider/managed/history/composite 身份与真实价格口径保留，调用者不依赖 HTTP 实现。可执行告警仅绑定就绪 composite；旧 provider/managed 规则可检查且不再执行。同一版本内判定语义保持。周日自动基线与 30 天清理按轨道 C 单独签收；真实备用源尚未指定时，仅验收来源能力边界和 fixture，不宣称生产自动故障切换已交付。
4. 历史积压与故障恢复满足用户已确认的业务阈值及对应技术门槛，资源收益按实测报告，不虚构百分比。
5. 统一入口、默认配置、角色状态、启停和切换/回退文档完整；失效配置与当前旧运行入口已收口。
6. 提供实际运行主机、地址、启动/停止命令、候选 SHA、镜像标识、CI、自审与适用 review；未生产发布明确标注。
