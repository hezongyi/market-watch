# 本次行情与原生图表实施安排

日期：2026-09-29。依据：行情按需加载方案、原生图表接入方案，以及截至 ac96624 的开发记录。本文件安排后续工作，不代表已完成验收。

## 一、方案结论

采用“原生图表 Datafeed + 自有行情服务 + PostgreSQL 缓存 + 按需补数”。

图表负责提出品种、周期、时间范围和根数需求；服务端负责供应商请求、覆盖判断、任务去重、持久化、日历及分桶。Datafeed 是协议适配层，不会自动替项目下载并维护 OANDA 历史。

本地足够则直接返回；不足则后台补齐，完成后自动刷新相关图表。长请求显示实际状态，保留已显示的K线。无缓存、休市、网络错误都不能误判为“没有更多历史”。不以一次获取十年 M1 为目标。

OANDA 使用账户实际可用品种目录；可搜索与可正确聚合分开判定。优先开放已验证日历的外汇和黄金，其他类别明确说明尚缺哪些配置。BTCUSDT 沿用现有来源。M1 自行聚合，W1/MN 从本系统 D1 聚合，保持已有价格口径和 session。

## 二、已有基础与剩余风险

已有开发记录包括：批量写入、覆盖表、图表专用任务执行器、账户目录、动态解析，以及新品种首次补数成功。原生工作区和模板适配也已部分接线。无需重做这些基础，但不能将单次成功视为整体完成。

小范围实测：OANDA 一天 1433 根 M1 获取约 0.712 秒，一周 7159 根约 1.604 秒；开发库一天数据入库聚合对照由 3.389 秒降至 0.730 秒。这些是特定区间的测量，不可直接外推十年、多图或首次 D1/MN 加载速度。

主要剩余风险：历史拖动闭环、长等待和失败恢复、多图任务公平性、跨日历边界、指标计算成本、原生工作区首次绑定与保存冲突。授权包的数据导出组件缺失另行处理。

## 三、建议实施顺序

| 顺序 | 实施内容 | 进入下一阶段的条件 |
|---|---|---|
| 1. 行情基础收口 | 核对已有覆盖索引、批量写入和任务实现；完善幂等、重叠去重、断点续传、失败重试；限制图表任务资源 | 单品种重复/重叠补数结果一致，失败可恢复，已有预警采集不被饿死 |
| 2. 三品种看图闭环 | EURUSD、XAUUSD、BTCUSDT 首屏、连续向左拖动、跳转旧日期；处理 countBack、缓存刷新、慢请求提示、重试及取消等待 | 三品种均能“打开→到缓存边界→提示补数→自动出现历史→再次访问命中缓存”；快速切换不串数据 |
| 3. 周期正确性与速度 | 核验全部已约定周期，尤其 NY17、夏令时、W1/MN；增量聚合、有限预取；记录首次高周期加载成本 | M1 至 MN 数值/时间标签正确；休市不造K线；慢请求有可理解状态；缓存命中性能有实测证据 |
| 4. 品种自主维护 | 完成 OANDA 目录更新、搜索注册、日历能力提示、活动租约、自选 Quotes 及停用机制 | 新增已支持品种无需改代码即可开图；目录失败可用缓存；关闭图表后不永久采集；原监控仍持续 |
| 5. 原生工作区与设置 | 收口保存/加载/复制/删除、首次身份绑定、版本冲突、共享模板与独立绘图；通过后移除外层验证工具栏 | 刷新、切换、多窗口不静默覆盖；画线共享符合约定；手机浏览不保存桌面修改 |
| 6. 原生图表完整能力 | 按能力清单接入分析工具、对象树、数据窗口、比较、最多8图及同步、内置/Python指标、截图 | 每项标注已验收/待接入/库限制；Python 数值对照通过；8图重叠请求去重且交互可用 |
| 7. 综合验收与发布准备 | 原预警/演练/ntfy回归、真实操作验收、数据迁移与备份回退文档、版本记录 | 开发机验收通过后再安排生产切换；保留旧图表入口，远端 push 仍由用户执行 |

原生保存已有改动先保留，后续以阶段1–3为主线。避免同时扩大界面范围而掩盖行情问题。缺失导出组件不阻塞行情、保存和其他绘图能力，但必须列为未完成项。

## 四、体验与性能验收办法

- 缓存命中、首次补数分别测量，不用平均值掩盖冷启动；记录请求数、下载、写库、聚合、指标和浏览器耗时。
- 初始以约1秒出现慢请求提示、约15秒单次等待预算为设计目标；现有实现若不同，统一配置后验证。后台任务可继续，不因等待预算结束丢弃已完成页。
- 缓存常用请求 P95 约500毫秒为调优目标，不是尚未测量的承诺；首次高周期需要较多 M1，应显示已处理范围，不显示虚构百分比。
- 8图同品种/相邻区间、快速拖动、切周期、断网/代理错误、429、周末空区间均需专项验证。
- 历史补数不能触发创建预警之前的信号；同时测量补数期间原实时任务延迟。
- 原生内置指标依照库算法运行；Python 指标独立验证预热与递归状态，不能为提速任意截短历史而改变计算口径。
