# 自建历史行情按设定精度处理方案

日期：2026-10-10。

状态：实现、回归测试和 Ubuntu 隔离验收已完成；未执行生产重试、生产部署或 unraid 临时实例。

基线：`origin/main`，提交 `8c65edfdee15f0281750e888711cf8ecd20de1a0`；生产运行代码为 v1.18.0。

## 1. 确定规则

**按每个数据集设置的精度处理价格：超出时四舍五入，未超出时保持原值；沿用现有存储，不新增 M1 副本。**

- 精度来自该数据集对应的 `Instrument.precision`，不设置全局固定值。不同品种，以及同一品种在不同来源或数据集中的精度可以不同。
- EURUSD、GBPUSD 本次失败任务的设定均为 5；其他数据集使用各自设定的 0–10 位精度。
- 对 M1 的 open/high/low/close 分别判断有效小数位，只有超出设定精度才使用 `Decimal + ROUND_HALF_UP`。
- 未超精度字段保持原数值及原字符串，不补零、不截断、不调用舍入；末尾零不视为有效超精度。
- 入库、聚合、固定图表、回测和派生使用同一个处理函数和对应版本规则。

示例：

| 数据集设定精度 | 输入 | 输出 | 是否舍入 |
| --- | --- | --- | --- |
| 2 | `123.456` | `123.46` | 是 |
| 3 | `123.456` | `123.456` | 否 |
| 5 | `1.093887` | `1.09389` | 是 |
| 5 | `1.093880` | `1.093880` | 否，末尾零不改变数值 |
| 5 | `1.0938849` | `1.09388` | 是 |

显示层可以按设定精度格式化数字，不能把显示补零当作数据舍入。

## 2. 问题与恢复目标

生产 Dukascopy 的两项历史更新任务因价格含真实 6 位小数而停止，注册精度均为 5。

| 品种 | 原任务 ID | 已查询至（UTC） | 已保存 M1 观测数 |
| --- | --- | --- | ---: |
| GBPUSD | `e3cbf344-d1c4-4200-bffe-5f11d8a8a569` | 2024-10-04 11:48 | 1,400,295 |
| EURUSD | `aa4588c3-8952-4983-b1a6-a0c63d4616c3` | 2024-10-09 23:03 | 1,404,010 |

已确认两份失败页各含 5,000 根 M1，分别有 21、57 根包含超过 5 位的价格。已有前缀已通过严格 5 位校验，无需重处理或重新复制。EURUSD 既有发布版本仍可使用。

修复后在两个原任务上继续：记录新规则，保留任务身份、原 cursor、已保存块和既有错误读取记录，使用现有“重试失败范围”从断点接续。只允许对未发布、无有效写入租约、符合精度错误条件的任务启用该处理规则。

## 3. 沿用现有存储

目前 `SourceBlob` 已保存来源页，`HistoryChunk` 通过引用使用它，`Bar` 与周期产物服务于日常查询和固定图表。本方案保持这些角色。

1. 来源获取仍按现有方式保存、校验和共享来源内容。
2. 导入在内存中按该任务精度处理，写入现有 `Bar`；`HistoryChunk` 继续引用已有来源内容，不另存舍入后的整页。
3. 固定历史消费者读取来源块时，先验证原内容哈希，再按版本精度在内存中处理；M1 与高周期产物都由这份业务价格生成。
4. 同一原始来源页可被不同精度的数据集共享，每个消费者读取自身规则；禁止将精度 5 的结果覆盖来源共享缓存，否则会影响精度 6 的数据集。

仅增加少量任务／发布清单规则信息，不新增 M1 数据表、第二份处理后块或独立原始归档。复用现有 manifest JSON 记录精度与处理规则版本，原则上不需要 schema 迁移。

继续采集、生成周期产物和写入数据库会产生现有流程的正常增长；“不新增存储”指不因舍入再增加一份价格数据，不承诺数据库总字节保持不变。此前每百万根约 15 MB 的新增副本估算属于已撤回的双层内容方案，不适用于当前方案。

## 4. 一致性与历史保护

- 新任务创建时冻结该数据集精度与规则版本，之后读取自身规则，不读取其他品种或当前全局配置。
- 旧已发布版本的价格、manifest、checksum 和固定引用保持不变；缺少新规则的旧版本沿用原规则。
- 当前两个失败任务可以在原任务上启用规则，因为其已保存前缀满足原精度，处理前后数值一致；启用必须记录任务级审计，不伪造过去发生过的舍入。
- 新规则必须在首次接受舍入数据前持久化，并随发布清单保留；创建、publish 和维护代码不能覆盖或丢失它。
- 工作表写入、`snapshot_rows`、历史周期产物、版本价格比较与派生使用统一的版本价格读取接口；不能只修改工作表校验，使固定回测继续读取超精度价格。
- 原始哈希仍代表实际保存的来源内容。业务价格可由来源内容与版本规则重建，不将原始哈希描述为舍入后序列的哈希。
- 父版本与周期产物继承必须检查规则兼容性。不同目标精度或不同规则时，从已有来源块重新在内存中处理；不能对已舍入结果连续舍入。

本次针对 Dukascopy 自建历史消费者。来源选择、BID、NY17、成交量、未知覆盖、平台原生行情及组合实时尾段仍遵守各自已有契约。

## 5. 必要校验

先校验来源身份、时间与原始 OHLC 合法性，再进行精度处理。舍入不修复非法来源数据。

- 有效精度判断不经过 float，也不依赖会隐式舍入数值的全局 Decimal 上下文。
- 不舍入成交量，不修改时间、完成状态、日界或覆盖证据。
- 处理后再次校验正价格、OHLC 关系及 `Numeric(24, 10)` 范围；舍入为零、进位超范围仍明确失败。
- 原始输入继续使用现有 Decimal 可解析性、有限数、正价格、OHLC 和存储数值范围校验；未来合法 6、7、8 位价格可以正常处理。本 PR 未新增字符串长度、有效数字数目或指数绝对值的独立上限，现有 MinuteRow 也没有这些限制。若要增加，需单独确认供应商契约与历史兼容范围；不能把这些边界视为本次已完成的校验。
- 401、429、超时、非法负数或非有限数等仍保留正确错误分类。

## 6. 实施范围

1. 增加一个通用“按指定精度处理 OHLC”的纯函数和一个统一的版本价格读取接口。
2. 接入历史导入、工作表写入、快照读取、周期产物、价格比较与派生；确保各调用者使用本数据集或本版本精度。
3. 在新任务 manifest 中记录规则；为现有精度失败任务的安全重试接入规则冻结与审计。沿用当前任务控制入口。
4. 创建页及版本详情增加一句处理说明：“超出设定精度的价格自动四舍五入”。精度错误提示说明实际处理条件。

## 7. 验收与交付

开发和验收只在 Ubuntu 独立 Docker project、网络、volume、数据库及端口运行，按 `mw-docker` 构建与退役要求执行。

必须验证：

- 不同数据集精度 2/3/5/6 分别生效；同一来源页被不同精度数据集并发读取不互相污染。
- 未超精度以及仅有末尾零的价格不变；超精度、半单位与进位按 HALF_UP 正确处理；6/7/8 位输入均正常。
- 真实失败页继续通过；两个任务沿用原任务身份和 cursor，从断点采集到原冻结 end，并发布所需周期。
- 图表、回测导出、历史段组合及高周期结果，与统一处理后的 M1 一致；原始块哈希不变。
- 舍入后不新增处理内容块；除现有采集与产物外，仅增加规则和必要审计信息。
- 旧发布版本、固定引用及已保存前缀不变；重试、暂停、取消、重启和父版本继承正确。
- 安全回退前暂停带新规则的任务；旧程序不得继续消费它。旧兼容发布版本仍可使用。

交付实际运行地址、启动／停止方式、验证结果与证据。生产恢复按后续授权及经验收的流程执行，生产供源默认启用配置继续保留。
