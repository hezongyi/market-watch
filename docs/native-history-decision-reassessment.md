# 大历史加载方案独立复评

2026-10-04。状态：供评审的建议，未实施、部署或合并。依据交接、`ea56630` 研究证据和当前工作区源码复核；没有重新运行浏览器或冷历史实验，也没有重新联网核验已归档官方资料。原有两个产品文件的修改及未跟踪测试原样保留。

## 推荐决定

**以有资源预算的原生连续加载作为主要路线，优先优化后端读取，并保留导航协调、失败恢复和语义十字线。暂不把自动混合切窗作为默认实现。**

用户提出的“按原生需求分页写 PG，第一次慢、以后复用”有合同与实测支持。旧方案把连续补齐走廊本身视为需要规避的异常，判断过于激进。真正需要解决的是应用容量拒绝后的失效状态、读取成本，以及最终视区与光标的时序。

但也不能无条件放开数量：库内保留大序列之后的旧侧追加会再次阻塞主线程，这不随 PG 命中而消失。有限窗口仍有用途，先保留为研究/回退候选；只有实际日常需求超出原生可接受预算，而且产品必须支持这种远跳时，才引入经过完整验收的历史浏览模式。不要在一次导航中因超时、回调失败或 hover 自动来回切换模式。

当前候选窗口版尚未完成修订、持续拖动等验收；这个建议不意味着可以直接上线候选，也不意味着现在回退全部修复。

## 问题应拆成五条因果链

| 问题 | 原因 | 独立解决方式 |
| --- | --- | --- |
| 超过 20,000 后卡住 | 宿主/模型/缓存层拒绝；原生错误与请求状态未完整结束 | 合理容量策略，加可恢复错误收尾 |
| 点击后静止的十字线错位 | 光标按旧视区映射，导航完成后没有重新投影 | 保存语义时间，在最终视区重放最新有效光标 |
| 历史图几秒后及 hover 时闪烁 | 流游标 gap 被等同于历史更正；视区事件被等同于用户向新侧拖动 | 核实已交付范围的实际修订；区分用户导航与程序视区变化 |
| 冷/热大请求都慢 | 上游分页、PG 写入、重复快照扫描及元数据解码、传输 | 分阶段优化和独立任务预算 |
| 数据交付/旧侧追加时停顿 | 原生大序列及指标处理，成本随已载入历史增长 | 限制浏览器常驻规模；极端场景另选浏览方式 |

所以，“修掉闪烁”不能证明有限窗口整体完成；“全部走 getBars”也不会自动修好错误恢复、同商品导航竞争或真正历史更正。

## 证据如何影响决策

原始依据见[性能报告](native-large-history-analysis.md)、[官方合同归档](native-large-history-official-research.md)、[实验数据](verification/native-large-history/evidence.json)和[热读取 profile](verification/native-large-history/hot-profile.txt)。本次核对了结构化案例、profile、读取 SQL、分页循环及导航代码。

| 观察 | 能推出的结论 | 不能推出的结论 |
| --- | --- | --- |
| 原始 v31.1 真正保留百万根 | 20,000 不是已知库总量极限 | 百万根适合正常交互 |
| 完全 PG 命中：约 6 万根端到端 6.42 秒、约 20 万根 21.00 秒 | PG 能省上游，但当前读取/交付仍贵 | 新页面“第二次打开”会瞬间完成 |
| 单图三指标 6 万根约 0.96 秒最长任务；20 万根约 2.92 秒 | 后端优化之后仍有浏览器处理成本 | 所有客户端都会出现相同绝对耗时 |
| 20 万根旧侧补几十根仍约 2.8～3.2 秒停顿 | 只愿意承受首次等待还不够 | 实时尾 bar 更新也同样慢；尾 bar 已有快速实测 |
| 四图各 20 万根三指标 JS 堆约 1.9 GiB | 多图应共享总资源预算 | 用户混合四图一定占 1.9 GiB；混合周期案例约 497 MiB |
| 原布局窗口候选静止/hover 不再重复重建 | 两个闪烁原因及候选处理有证据 | 窗口完整回归通过或性能优于原生某个倍数 |

三点加载提示对异步取数等待有帮助；同步长任务期间动画和取消按钮都可能无法响应。不能用“有 loader”替代交互验收。

真实 OANDA 端到端实验走研究 datafeed/HTTP，未走产品 `AdvancedWorkspace → postMessage → bridge` 的完整链路。产品还有数据复制、转换及 Python 指标交付成本，现有数字不能作为产品 SLA。JS 堆也不是进程总内存或峰值。

## 源码复核带来的额外约束

1. **当前切窗比“超过 20,000”更积极。**`prepareNavigation` 仅在没有历史窗口且距离不足约三屏时保留原生补齐；更远的未载入目标就可能重建窗口。因此实际重建频率不能只归因于 20,000 上限。主要路线改为原生时，应撤掉这条过早切窗策略，保留其他独立修复。
2. **全局容量参与普通读取成本。**`_native_read` 每轮以 `CAPACITY + 1` 调 `snapshot_transaction`。直接把 CAPACITY 放到百万，会让缓存足够多时的小请求也读取大量不需要的 bars。必须先把安全上限、真实必需量、查询扫描量、可选储备拆开。
3. **重复元数据有直接代码依据。**快照 SQL 把 dataset coverage/metadata 与每根 bar 连接输出；profile 中 JSON 解码累计约 3.4/4.4 秒。可以优化，但不能为了减少字段就拆成两个无一致性保护的 READ COMMITTED 查询。
4. **还有固定 80 轮分页限制。**以常见整页计算，OANDA 4,000 根约 32 万、Binance 1,000 根约 8 万便接近循环预算；最终成功还需读回确认，短页、重试及修订也会改变轮数。这不是可承诺的容量值，却证明删除 20,000 后还会碰到隐藏限制。
5. **有限窗口不自动证明长期内存有硬界。**初始化窗口根数有上限，旧侧仍能原生分页。长期只向旧侧浏览是否持续增长、何时回收，需要单独测量；不能用一次约 2,759 根的采样承诺始终固定内存。

## 三条路线的取舍

| 路线 | 日常混合四图 | 极远分钟历史 | 成本与适用条件 |
| --- | --- | --- | --- |
| 原生连续加载，带预算 | 已载入区间复用自然；新范围可能等待 | 走廊很大时需拒绝或改浏览方式 | 自定义状态较少，但必须治理读取、累计内存和失败 |
| 修正后的有限窗口 | 跨窗口需要重建；hover 不应触发重建 | 目标附近少量数据即可定位 | 首次远跳优势明确；窗口身份、双向拖动、修订、画线/指标恢复维护重 |
| 自动混合 | 可保留原生复用并对大请求切窗 | 理论上能兼顾 | 同时承担两套生命周期和切换状态；阈值附近抖动、并发修订与取消组合最复杂 |

**推荐第一条作为默认，第三条不作为第一阶段目标。**第二条保留在隔离候选中，后续若必须进入产品，先做明确的历史浏览模式：进入时固定模式，回到最新时退出，切换前准备好数据，失败保留原视图。它仍是两种机制的组合，但避免在每次 getBars 中临时猜测并切换。

这个推荐有明确代价：超出预算的极远导航，第一阶段可能只能保留旧图并提示缩小跨度/提高周期。若“任意远日期点击后所有分钟图都必须成功定位”是不可削减的需求，有限窗口就必须与原生优化一起完成验收，不能把这项能力承诺给纯原生路线。

## 建议的实现方案

### 1. 历史读取模块：分页和观察一致性留在后端

对调用方提供小 interface：提交真实需求、观察状态、取消自己持有的请求、读取最终一致结果。底层仍复用 PG 覆盖、供应商 adapter 和现有取数租约，不另造独立缓存系统。

- 用覆盖区间和实际 bar 查询确定 `max(countBack, [from,to) 实际数量)`，加入真实指标前缀；区分可选储备。日历估算只用于预估，不能替代覆盖证明。
- 快照元数据只返回一次。可选择单语句聚合或短 REPEATABLE READ 事务等方式，评估执行计划、内存和锁影响；bars、coverage、revision、修订判断必须来自同一观察。事务不跨越上游网络等待。
- 冷分页循环只读取下一页规划需要的信息和有界计数，避免每页解码全部增长历史。交付前再取一致快照并重新验证覆盖；不要简单把不同版本的分页数组拼接后附上最新 revision。
- 请求级读取量与全局硬上限解耦。使用显式页数、时间、并发及“游标确实前进”保护，替换隐藏的固定循环截断；保留终止保障。
- 大冷请求采用可观察、可取消的短请求任务协议，必要时轮询或事件报告“正在补数”。后台执行复用已有任务/租约设施；任务有过期回收和全局资源预算，不能仅把普通 HTTP 超时调到数分钟。
- PG 已完成页可在取消后复用；一个消费者取消只解除自己的兴趣，共享加载还有其他消费者时不能一并杀掉。没有消费者时停止后续分页，允许已发出 I/O 收尾。

原生 getBars 仍只收到本次最终 bars 或明确错误，回调异步交付。应用进度走独立通道，不把同一历史 callback 当分页流。既不静默截断 countBack，也不把超时、预算拒绝、暂时不可取伪装成 `noData`。

### 2. 导航模块：导航意图与取数、光标分开

以 `navigate(target)` / `dispose()` 为主要 interface，内部维护导航代次、数据源代次和独立光标版本。保留现有已验证的生命周期修复，按职责迁移，避免整个 `native-navigation.js` 一删了之。

新点击或回到最新使旧导航失效；hover 只更新光标语义，不触发重建或取消有效导航。同商品旧请求结果可成为 PG 缓存，但不能提交旧视区。所有成功、失败、取消分支必须结束自身原生等待状态，旧代次不能清掉新代次状态。

简单丢弃旧 HTTP 响应不够：原生 subscriber/deferred 也需结算。保留最小、可单独关闭的版本适配挂钩，继续 SHA/唯一锚点验证。公开接口优先；不承诺能够完全去除私有挂钩，因为原始库错误恢复及同商品导航竞争已有失败证据。

定位完成的标准是该代次数据处理及最终视区完成，然后按最新有效光标重放。单独 `dataReady()`、固定延迟或再次 hover 都不能证明成功。

### 3. 历史修订模块：reset 是待核实信号

对已交付数据保存观察范围和版本；流 gap、积压提示先做范围修订核实。最新尾部新增且未影响已载入历史时无需重建；真实范围内更正则失效并刷新受影响数据源，保存和恢复位置、指标与画线。

原生连续模式同样需要这项能力，而且受影响范围是整个已交付区间及指标依赖前缀，不能只看当前屏幕。并发 review 合并、源销毁取消，失败保留有效图并显示可重试状态；不能把“检查失败”当作“没有更正”。

公开 reset 探针丢失远历史位置并重新取走廊，所以刷新后定位恢复是验收项，不能把 `request_only_visible_range_on_reset` 写成已验证替代实现。

### 4. 预算模块：约束最终常驻量和并发量

后端限制供应商并发、页面、任务时长、响应 bytes 和指标计算规模；前端按独立数据源、实际常驻 bars、指标、正在交付的数据和新旧源切换重叠量做保守预算。

单次 countBack 上限不足：每次追加一千根也可能累计到百万。多图共享线程按实际独立源计数；无法确认共享时采用保守估计。浏览器内存估计和长任务反馈用于调优，不能作为跨浏览器精确容量保证，也不能等长任务发生后才保护本次导航。

6 万、20 万都是实验点，不指定为新产品阈值。先由代表性硬件、原布局及实际指标确定可接受的输入阻塞和总内存，再反推版本化预算。优先削减可选储备，必需数据仍超限则明确结束请求并保留旧图。

## 分阶段交付与停止条件

1. **可独立保留的修复。**语义十字线、错误恢复、导航代次、修订核实与 hover 隔离。当前窗口候选的真实修订和持续拖动未完成，不扩大其已通过范围。
2. **优化后端但暂不扩产品容量。**证明小请求在大缓存中不退化；冷加载避免逐页全量扫描；快照观察与并发修订保持一致；取消/超时后资源可回收。这一阶段对两种路线都有价值。
3. **在 Ubuntu 独立实例接入有预算的原生候选。**同时调整宿主校验、后端模型和内部策略，接入长任务协议；撤除默认过早切窗，保留独立修复与候选回退能力。
4. **用产品同条件比较决定有限窗口是否进入产品。**若优化后的原生在日常布局仍有不可接受的旧侧追加停顿，停止继续提高上限；对这类需求验证历史浏览模式。不要以“热请求变快了”绕过这个停止条件。

必要验收以用户真实 EURUSD 四周期布局、相同目标、指标、视区、CPU、缓存状态为控制条件，记录点击至可交互耗时、最长任务、实际常驻量与峰值内存。覆盖冷 PG、新页面热 PG、同 widget 已载入三种状态；再测 2/8 图、同商品同周期不同历史位置和实际 Python 指标组合。

正确性必须包含：静止点击与单纯 hover；加载中再点击/回最新；503、超时、取消后下一次操作；隔离 PG 中真实历史修订经 SSE 触发刷新；持续按住跨多个边界、release/惯性、日期跳转及布局恢复；交易日历和指标前缀；长时间旧侧追加后的累计资源。

本次无需重复分钟级冷实验即可做出路线建议。尚缺的完整产品 A/B、优化后 profile 与真实修订验收，决定发布资格和预算值，不能被现有研究替代。所有后续实例仍只在 Ubuntu 隔离部署；本文件没有改变现有验收实例或生产环境。
