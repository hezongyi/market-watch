## 目标与范围

- 平台行情、自建行情保持现有数据生产节奏及系列语义，不因为使用 SSE 提高上游采集频率。
- 组合行情随实时来源更新形成中的 bar；正确保留历史基线、接缝、日界、来源、临时/确认状态及量语义。
- 专业图表、自选表共享按需订阅出口。相同计算需求复用后端结果，不按页面、图表或连接重复聚合。
- 正常运行时前端不再每 15 秒查询最新 bar、报价及行情变化。首次加载、历史分页与恢复继续使用 HTTP。
- 协议允许未来外部客户端按权限订阅；本次不建设外部开放平台、凭据管理产品或新的消息中间件。
- 本次主要范围为专业图表及其自选表。数据中心简易图表迁移不作为本次交付要求，保持原行为。

“保持现有速度”指数据生产频率不变；已有数据经推送更早显示是预期效果。SSE 本身不决定价格更新频率，也不保证逐笔成交或无采样损失。

## 已核实的当前状态

- `advanced-host/bridge.js` 的平台 `subscribeBars` 已注册独立订阅；平台 SSE 每约 2 秒检查缓存修订，不直接采集上游。
- 自建/固定历史及组合图表仍通过约 15 秒 `tick()` 检查；该任务还处理报价、历史准备与修订、指标进度。
- 原生自选表通过 `getQuotes` 首读、`subscribeQuotes` 注册，实际持续报价由约 15 秒 HTTP 轮询获取。
- `/api/market-data/live/events` 每约 1 秒读取全量来源状态，发送具名 `snapshot`、`heartbeat`；尚非按组合、周期订阅的 bar 出口。
- 当前组合高周期临时柱读取可能重聚合 M1，并检查整个周期的分钟覆盖；已有周期产物不代表每次临时柱更新都便宜。
- 部分平台报价 HTTP 路径包含供应商读取；移除前端轮询前必须将仅自选表场景的采集需求交给后台。
- OANDA Practice 是账户环境，同时提供 REST 与价格流。本地平台路径使用 REST 原生 candles；组合实时来源使用价格流形成报价/临时 M1，并用 REST 确认柱。不得用实时流聚合替换平台原生系列。

## 决策

统一订阅协议和前端 SSE 连接，保留各类行情的数据生产实现。每个专业图表页面一个连接；不同页面或外部客户端各自连接。服务端按计算身份共享结果，按客户端权限和订阅分发。

SSE 是单向输出；订阅注册、修改、取消使用 HTTP。连接仅发送该客户端需要的数据，不广播全部品种，不为自选表计算全部周期。

不以“来源变化通知后由每个前端逐周期再拉三根柱”作为正常更新架构。也不把现有全部查询按秒搬进 SSE 循环。

## 订阅契约

| 需求 | 身份与参数 | 输出 |
| --- | --- | --- |
| 图表 K 线 | 系列类型、完整系列身份、版本绑定、周期 | bars、reset、status |
| 指标及比较系列 | 实际系列依赖、周期、计算规格与起点 | 对应 bar/指标结果及准备状态 |
| 自选表和报价区域 | 完整系列身份及其版本语义 | quotes、status |

- 显示代码不是身份；平台 EURUSD、不同账户/来源的 EURUSD、不同组合不能混用。
- 固定发布历史继续固定，不因后台生成新版本而自动切换。显式固定的组合修订不随活跃修订切换；跟随活跃修订的订阅发生切换时先重置、重建绑定，禁止拼接不同修订结果。
- 注册返回已解析身份和订阅世代；前端回调必须匹配当前世代。周期、工作区或绑定改变及取消订阅后，迟到结果不得进入旧回调。
- 同一计算身份、周期和相同指标规格共享计算；权限检查仍逐客户端执行。不同指标参数不能直接复用彼此输出。
- 共享计算键与客户端投递状态分开：已加载历史范围、游标、订阅世代和 reset 确认属于消费者状态，不应让不同历史窗口重复计算同一实时 bar。订阅须登记已加载范围及修订凭据；历史分页后更新范围，指标还须保留其递归依赖起点。复用现有 `history_check` 规则判断相关修订，不只检查最新柱或最新来源报价。
- 原生实际需求包含主图、比较系列和指标依赖；不只看主图名称。隐藏布局的订阅释放/暂停规则与原生缓存生命周期对齐，恢复时补齐。
- 自选表报价需求独立于图表：关闭图表后，仍在自选表中的品种继续按既有来源节奏更新。订阅不隐式创建新组合定义；沿用已有显式首次使用规则。
- 取消最后一个消费者后释放对应需求；断线使用有界租约宽限，避免短暂重连反复启动/停止采集。不存在有效使用者时不得永久保留计算任务。
- 上述释放仅针对本客户端的图表/报价需求。预警、策略、历史维护及其他页面具有独立需求；仅当所有相关需求都已结束时才停止共享采集，不能因最后一个图表关闭而停掉预警输入。
- 订阅注册/替换必须幂等，并按客户端世代排序；重连重复注册不增加引用，迟到取消不得删除新订阅。客户端标识不能代替认证身份，订阅和连接都须校验归属；会话结束时释放对应连接。设置有限的订阅数量、历史恢复范围和队列预算，复用现有权限及容量规则。

## 消息及原生接口

| 类型 | 内容与用途 |
| --- | --- |
| bars | 完整最新 OHLC、必要的指标结果、版本和时间信息；同时间更新、新时间追加 |
| quotes | 按该系列规则校验的报价、来源时间、价格口径及可用状态 |
| reset | 历史修订、绑定变化或无法连续补齐；触发原生历史恢复 |
| status | 准备、断线、过期、恢复及错误；状态变化不伪造价格变化 |
| heartbeat | 连接存活，与报价新鲜度区分 |

- `getBars` 继续处理首屏、历史分页和补读；`subscribeBars` 注册后由 SSE 驱动其回调。
- `getQuotes` 读取初始快照；`subscribeQuotes` 接收 SSE 报价；取消接口释放引用。
- 每个数据事件携带订阅世代、解析后的系列/版本身份及该共享结果内的单调序号。bar 时间不能作为唯一顺序判断：同时间的旧 OHLC 也必须被拒绝。行情输入修订、历史修订与传输序号分别表达，不以来源报价修订代替全部变化信号。
- 沿用后端周期时间标签和 `barsOf` 转换，特别是 D1/W1/MN 的日界标签；不使用客户端时间重新划柱。
- 来源 SSE 的 `quote_ready` 不足以证明组合报价可用；复用组合账户、owner/epoch、新鲜度及接缝校验。
- 当前临时柱无可靠量时保持不可用；不以 SSE 消息次数充当来源量。

## 后端计算与负荷控制

### 平台与自建

复用平台现有采集、缓存和修订逻辑。将只在报价请求中发生的必要采集接入后台需求调度，保持来源频率与限流规则；仅订阅报价不触发不必要的历史下载。

自建系列先核对 `managed` 与 `history` 两条已有路径，分别保持可更新数据与固定发布版本的语义。已固定且无变化的历史不重复推送；准备进度、已有范围修订等有变化时通知。

### 组合

- 首次使用某个周期时建立当前 bucket 的基础聚合；之后报价变化只更新临时输入，不每次重扫整周/整月。
- 已确认输入与可变临时部分分开维护。临时 M1 是可替换观察，不能仅不断累加高低价：来源确认、修订或恢复可能要求撤回旧极值并重建相关 bucket。
- 分钟切换时，已过时但尚未由 REST 确认的临时观察如何处理，必须与现有权威读取一致；不得为图表连续而自行累计成确认输入。无新报价时的临时观察过期/移除也属于重算触发条件。
- 确认输入修订、接缝或规则变化使相关缓存失效；分钟/周期切换建立新状态。日历覆盖证据、混合来源量、临时/确认语义与现有聚合结果一致。
- 聚合缓存区分组合修订、输入版本、周期、规则及必要来源世代；owner、新鲜度、账户和权限判断不因缓存而省略。
- 当前状态按稳定系列身份维护，输入修订作为状态有效性的凭据；不得每个报价修订都创建一份永久缓存。新确认分钟尽量增量并入；修订仅重建受影响部分，失效旧项有界回收。用于固定历史读取的版本化结果与当前可变状态分开。
- Python 指标继续复用固定输入及临时计算规则，共享相同规格结果；不能为每个订阅者重放完整历史。
- 计算共享必须覆盖不同 SSE 连接；多进程 API 下不能仅用每个请求各自的局部缓存声称已经共享。优先利用现有 worker 与持久状态设施，实施时确定唯一计算归属及故障接管方式。

### 发送与背压

按变化推送，连续同一 bar 更新允许短窗口合并，发送最后一份完整、权威计算结果。一般报价变化由后端形成 OHLC；确认修订允许合法缩小旧临时高低区间，因此发送层不得自行对多份结果取最高/最低值。具体合并窗口依据现有价格流落库节奏、回调延迟和负载实测确定，不预设每秒 4 次，也不把现有每秒一次的来源快照轮询加速后称为原生事件驱动。此机制不提高来源本身的更新频率，不承诺每笔报价送达。

队列有界，慢消费者合并同一当前 bar 的中间状态；不得静默丢失跨柱追加、reset 或绑定变更。无法保持连续性时明确要求补读。一个慢周期或慢连接不得阻塞其他订阅。

## 首读、恢复与历史窗口

- 首次历史响应携带版本/游标，注册订阅时承接该位置；握手期间缓存或重读尾部，避免历史读取与订阅生效之间的漏更。
- bar 回调只接受匹配当前绑定的非倒退结果；首屏尚未接受时协调暂存，不让实时响应抢先污染原生缓存。
- 断线重连以客户端游标和服务端修订核对；能补齐则按时间顺序补齐，不能保证连续性则 reset 后通过历史入口恢复。
- SSE 重连不等于可靠事件回放，不单靠 `Last-Event-ID` 假设数据完整。固定读取“最新三根”不能作为任意断线时长的恢复策略。
- 历史窗口订阅保留修订通知，但不得跨未加载缺口追加当前柱。
- 状态从健康变为过期/失效，即使没有新报价也须通知；heartbeat 不代表价格可用。
- 组合确认输入、历史修订、指标准备、账户/owner 变化及时间导致的过期均需独立触发检查；不能把来源 `LiveState.revision` 的变化当成唯一触发器。reset 期间协调补读与实时缓存，历史接受后再按新游标恢复交付。

## 15 秒任务的迁移

| 现有职责 | 最终归属 |
| --- | --- |
| 拉最新 bar、报价 | SSE 正常更新路径 |
| 历史修订检查、准备及指标进度 | 后端按有效订阅检测，变化时推送 |
| 行情需求续期 | 服务端订阅租约及有效连接保活 |
| 缺口恢复 | 重连/异常触发的快照与历史补读 |
| 自动保存等界面工作 | 独立计时或既有界面事件 |

后端可以按合适节奏检查持久状态，不要求所有 worker 改为事件系统。取消的是前端常态行情轮询，而不是供应商采集调度、连接保活或必要恢复请求。

迁移期间提供回退开关；一个订阅仅由一种正常更新链路交付，避免轮询与 SSE 双重回调。完成验收后默认关闭旧行情轮询；不把永久双链路作为最终方案。

## 实施步骤与主要文件

1. 核对运行后端差异，盘点需求、修订信号及自选表采集路径；在 Ubuntu 隔离环境建立延迟与成本基线。
2. 实现组合共享增量聚合，与现有 `chart_page`/`read_window` 做同输入差分验证；确认跨 API 进程的计算归属。
3. 实现统一订阅注册、租约、SSE 分发和恢复契约；适配既有平台、自建/固定历史及组合结果。补齐仅报价需求。
4. 父页面共享连接，桥接原生 bar/quotes 回调；分离并替换 15 秒任务中的行情职责。
5. 完成隔离验收、验证回退开关，形成交付记录。生产发布另按明确授权执行。

实施前置产物：第 1 步必须记录实际 worker/API 进程布局、共享结果的唯一计算归属、状态存储与接管方法、各类修订触发源及平台报价采集迁移点，再开展第 2～3 步。优先复用现有 worker、数据库租约和有界状态检查；只有实测显示这些设施无法满足目标时，才另行评估新增基础设施，不能在实施中默认扩成通用推送平台。

主要涉及：

- `backend/alerts/provider_service.py`、`chart_api.py`：复用平台需求与修订处理，接入统一出口。
- `backend/alerts/market_data.py`、`series_access.py`：报价需求、系列身份及快照/历史契约。
- `backend/alerts/composite_chart.py`、`composite_series.py`、`composite_quotes.py`、`fixed_indicators.py`：复用计算和校验，增加集中共享的实时计算模块。
- `web/src/advanced/AdvancedWorkspace.tsx`：连接与订阅 HTTP/RPC 管理。
- `web/src/advanced/providerSubscriptions.ts`：复用成熟的注册/取消顺序及重连经验，避免长期重复两套生命周期。
- `advanced-host/bridge.js`：原生订阅接入、响应世代检查、恢复与旧轮询拆分。

新模块命名和协议路径属于实施选择，不需要用户再次决定。

## 验收标准

### 正确性

- 平台采集频率、自建版本语义与已有行为一致；组合实时 OHLC 与相同输入下既有聚合一致。
- 单组合覆盖所有已支持周期 M1/M5/M15/M30/H1/H4/D1/W1/MN，包括分钟/日周月边界、NY17/DST、接缝、来源确认替换、修订与量不可用情形。
- 相同周期多图共享计算；不同来源、账户、组合修订、指标参数互不串流。
- 仅自选表、仅图表、两者并用、关闭图表但保留自选均能正确维持或释放需求。
- 切品种/周期/工作区、取消订阅、历史窗口、首屏与实时竞争、断线跨多个 bucket、服务重启后无漏柱、倒序或旧回调污染。
- 无新价格时也能报告过期、owner 失效和恢复；不把存储旧价冒充实时价。
- 同柱迟到消息、确认后高低值缩小、分钟跨界未确认、仅历史修订而无新报价、旧临时观察过期时，与权威读取结果一致。
- 关闭全部图表后活跃预警仍获取数据；重复注册、重连和迟到取消不泄漏需求或误删新订阅。
- 正常路径不再出现约 15 秒的最新 bar/报价/行情变化查询；界面保存与非本次数据中心轮询不纳入该判据。

### 性能

测量单周期、同周期多图、4～8 周期（含 W1/MN）、含/不含 Python 指标、多组合、多连接及多 API 进程。记录后台提交到原生回调延迟、聚合次数与耗时、SQL/扫描量、数据库写入、CPU/内存、发送量和队列长度。

- 相同组合/周期增加消费者，不按消费者数量重复聚合；增加传输量属预期。
- 无新数据不反复执行高成本聚合；W1/MN 报价变化不反复读取整个 M1 bucket。
- 在途工作和消息队列有界，慢消费者不拖住其他客户端；持续负载不出现不断增长的积压。
- 初始延迟验收目标：正常测试负载下，后端有效数据提交到原生回调 P95 ≤ 3 秒。该目标不包含来源尚未提供数据的时间，尚未实测，不能作为已实现保证。
- 具体 CPU/内存预算与并发容量依据 Ubuntu 基线和目标实例资源记录，不提前宣称“零新增负荷”或“8 周期一定可控”。

## 环境与交付约束

## 尚需实施核实的问题

- 生产后端与本地源码差异；`managed` 与固定 `history` 的实际使用范围。
- 现有 worker 中适合承接共享组合实时计算的归属与进程间通知机制。
- 组合高周期及指标的真实成本、多客户端与多进程下的容量。

以上不需要用户先做产品决策，但其中计算归属、变更触发源及运行版本差异必须在对应实现开始前明确。性能与容量通过隔离验收确定。外部开放认证、极低延迟逐笔推送、数据中心全面迁移均不作为本次默认需求。
