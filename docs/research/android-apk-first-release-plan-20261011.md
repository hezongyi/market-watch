# Market Watch Android 首期评估

> **归档说明（2026-10-11）：** 历史首期评估：本文保留早期五项功能及通知方案。通知准入门槛、先验证通知的顺序和 20–35 工作日总量均不适用于当前不含后台通知的界面方案；数据中心浏览范围与导航也是当时建议。当前范围与选型见 [讨论总览](android-apk-discussion-record-20261011.md)。

> 较早路线更新：用户当时明确选择不接 OPPO 通道，研究 App 原生后台直连服务器，记录见 [直连告警方案](android-direct-push-market-watch-plan-20261011.md) 和 [开源项目研究](android-direct-push-open-source-20261011.md)。下文厂商推送段保留作为早前候选调查，不能作为当前实施前提。

日期：2026-10-11。目标手机：用户确认的 OPPO Find X8 / ColorOS 16。首期功能：自选表、单图、指标、告警通知、数据中心。用户进一步明确，核心目标是及时收到告警，而不是要求 App 进程永不退出。

这是方案评估，未开始 App 实现或生产发布。官方资料及旧提醒原型的证据见 [通知与 WebView 研究](android-apk-notification-and-webview-evidence-20261011.md)。

## 建议与决策条件

适合做 Android APK，但应采用 **手机专用 React 页面 + Android 外壳 + 原生推送接收**，继续使用现有服务端和专业图表。已有图表和计算能力很有价值，重写行情、指标或 K 线绘制不是首期必要工作。

目前网页在触屏设备上是只读单图：`AdvancedWorkspace.tsx` 按 `(pointer:coarse)` 识别手机，传入 `readonly`；`bridge.js` 不安装指标选择器与数据中心，并关闭部分编辑工具。图表厂商也会在小屏隐藏右侧栏。把这张网页直接包进 APK，仍然缺少用户要求的入口。[S1][S2]

APK 能建立统一导航、登录和通知跳转，但 **APK 本身不证明提醒更可靠**。若仍依赖一个 App 的常驻连接，一旦连接所在进程被清理，问题可能重现。新客户端不能把 ntfy 当前的限制搬进去后宣称完成。[O1][S8]

对于 Find X8，优先核实 OPPO 正式系统推送的准入和效果，再决定是否进入完整 App 开发。OPPO 公开文档称其通知链路由 ColorOS 维护，应用进程不运行也可以收消息；新平台开启指南仍要求企业开发者和正式商店上架，未上架权限仅供测试。这里是研究得到的准入门槛，尚未在当前开放平台账户内实际申请核验，不能当成自用侧载已获得正式权限。[O2][O3]

本轮交叉读取的新文档进一步限制非 OPPO 软件商店官方渠道下载应用的公信服务；个人行情订阅需要按正式通讯服务/订阅类别申请模板及满足用户主动订阅要求。新版公信对其他 App 的单设备额度为 2 条/日，测试权限也有额度和使用范围，不能据此支持任意频率的重复行情告警。正式接入、类别审核、模板审核和安装渠道必须分别核实，不能用聚合 SDK 或常驻服务的存在推定这些要求已被解决。[O1][O5][O6][O7]

若无法取得合适的系统推送渠道，手机界面仍可开发，但它不足以单独解决用户当前的核心诉求。关键告警可考虑短信或电话作为独立备用通道；用户是否接受尚未确定，不默认纳入交付或发送任何通知。

已有 `mobile/` 是独立的小型提醒伴侣。可参考配对、确认补传、去重和响停状态机，但它没有四项浏览/分析功能，没有 OPPO 推送 SDK，也未通过 Find X8 锁屏验收。不能按现成五功能 App 估算。[S8]

## 首期建议范围

建议底部导航为「自选、图表、告警、数据中心」，指标按钮放在图表页。这样指标可以直接作用于当前单图，通知点击进入对应告警/图表，主要功能无需寻找桌面右侧栏。指标和数据详情用适合手机的页面或面板，避免挤压图表。早期界面规划参考的带标签主导航、返回状态保留和触控原则，已整理为仓库内的手机交互建议；无需本地技能文件即可查阅。[U1]

- 自选：查看实时行情、搜索加入、移除、分组、排序、点击开图；与桌面共用自选内容。
- 单图：切品种/周期、缩放、横屏；手机图表与桌面多图工作区分别保存，保留明确的导入途径。
- 指标：现有目录的添加、移除、参数修改及保存。新增计算公式或完整桌面样式模板管理另计。
- 告警：通知、列表、确认、历史和正确定位；若包含手机新建/编辑价格及指标告警，则复用已有表单和判定能力。精确重复响铃、画线告警编辑的全部桌面交互需要另行验收，不能由系统推送通知自动获得。
- 数据中心：首期假设查看/搜索平台、管理和组合行情，查看覆盖及任务/供源状态，打开图表、加入自选。若要求完整新建数据集、组合映射、采集、发布、版本与维护管理，工作量另增。

这是用于估算的建议范围，没有替用户删减首期要求；数据中心与告警编辑的具体管理深度需要在实施前明确。

## 推荐集成方式

1. 在现有主应用增加手机页面，由小型 Android 外壳加载受控 HTTPS 页面；沿用现有服务端、图表独立来源和受控数据请求。
2. 页面登录继续使用现有 `httpOnly` 会话与 CSRF。通知后台使用受限设备凭证；目前 device token 只用于提醒接口，不能直接当全部业务接口的登录 token。[S6]
3. 图表来源继续与可信主页面分离。原生桥只对可信主应用开放有限的通知/导航能力，避免向第三方图表 iframe 暴露凭证与任意原生操作。[O1][S2]
4. 告警判定始终在服务器运行；App 退出、锁屏或图表停止刷新都不停止判定。
5. 原生接收系统通知，点击携带稳定告警身份进入主应用；前台再获取可信详情。手机单图状态独立保存，自选可同步。

目前用户已验证同机 Chrome 可正常显示专业图表。WebView 仍需要单独验收其实际提供程序、两个 HTTPS 来源、登录与图表生命周期，不能把 Chrome 验证当成 APK 已验收。[O1]

## 以“收到并确认”组织提醒

建议处理链路：

```text
服务器持续判定 → 持久化告警 → 厂商系统推送 → 手机显示 → 用户确认
                              ↓ 未确认且仍有效
                       按策略重试 / 可选短信或电话
```

不同状态要分别记录：产生、推送服务受理、到达手机（渠道提供且可核实时）、展示/点击（有可靠证据时）、用户确认。**服务商 API 返回成功不等于手机展示，手机收到也不等于本人看到。** OPPO 官方回执文档明确说明接口成功只表示开始下发，`push_arrive` 只表示到达 OPPO PUSH 客户端，不含展示或点击。[O4]

现有数据库已经区分通知、投递尝试、设备到达与确认，这是可复用的基础。但目前 outbox 与 `notify.py` 只面向 ntfy，服务受理后设为 accepted，没有实现多渠道超时升级；`Outbox.notification_id` 唯一约束也不是每渠道/每设备的投递账本。需要在保留幂等确认的前提下扩展投递和升级状态。[S5][S6][S7]

未确认升级需要约定延迟、次数、有效期和恢复后的处理。重试应沿用同一事件身份，避免制造新告警；收到本人确认后停止未发送的重试。未确认不等于送达失败，但可以作为用户选择的提醒升级条件。厂商和 App 在同一断网/关权限场景下会共同失效，短信/电话可以降低单一渠道失效风险，也不是无条件的百分之百保证。

普通通知展示与持续大声响铃是不同能力。厂商通知能否响铃仍受该手机通知渠道、音量、勿扰和系统规则影响，不能承诺系统推送直接实现任意 15 秒响/30 秒停或强制绕过勿扰。

## “及时”的测量范围

实测时至少分别记录条件观测、服务器告警入库、推送受理、到达、展示和确认时间，衡量延迟分布与漏报，而不是只验证一条测试通知成功。

现有代码默认 `market_poll_seconds=15`，Yahoo 默认 `yahoo_poll_seconds=60`；API 已向用户解释部分告警按行情抽样观测，收盘模式还要等待周期收盘。它们是源码默认值，不是本次读取的生产实际配置。App 推送再快也不会消除行情源或判定模式的延迟。[S10]

建议先以已产生告警到手机可见的延迟为推送验收指标，再评价完整行情到提醒的延迟。厂商文档在良好网络、无拥堵下的通道时延描述不能当端到端 SLA。关机、断网、通知权限关闭或服务故障时需要显示真实状态并补收/升级，不能据此承诺无条件即时送达。[O1][O4]

## 难度与初步工作量

按一名熟悉现有项目、连续投入的工程师估算；是基于源码调查的排期量级，不是已验证工期，不含开放平台资质准备、审核等待或应用商店办理时间。

| 阶段 | 产物/决定 | 工作量量级 |
|---|---|---|
| 通知路线验证 | 核对正式权限，最小 APK 注册与系统通知、服务器受理/回执，Find X8 锁屏和清理后台后的实验。 | 2–4 工作日；资格不可用时应改变路线 |
| 手机五项功能界面与 Android 外壳 | 按上述数据中心浏览范围，完成自选、单图、指标、告警页及数据中心连接。 | 10–15 工作日 |
| 告警可靠性处理 | 推送接入完整化、token/撤销、多状态投递、幂等确认、有限重试/补收、跳转；若选备用通道，再单独核对供应商与费用。 | 6–10 工作日 |
| 真机与集成验收 | 锁屏、清理后台、网络切换、离线恢复、长时待机、升级、确认停止和重复事件。 | 2–5 工作日，含观察时间 |

总量约 **20–35 工作日，约 4–7 周**，前提是正式推送路线可接入。可安装并演示界面的 APK 会更早出现，但不能用该原型宣布告警可靠性目标已实现。

若把桌面数据中心全部管理功能搬到手机，再增加约 5–10 工作日作为初步缓冲，待具体交互确认后重估。若改为全面重写原生界面，首期重建与维护成本更高，图表仍需要 WebView 或另选图表技术，现阶段收益不足以支持这项重写。

## 后续实施与验收条件

先验证正式通知资格和手机链路，再开始完整界面；不应把只有测试额度的厂商账号当作正式生产能力。以用户所用 Find X8 / ColorOS 16 的真实结果为准，区分锁屏、从最近任务划掉、系统回收和用户在设置中强行停止；不从其他手机结果推定本机行为。

若开始开发，所有开发与服务端验证实例只在 Ubuntu 本机隔离运行。按仓库规则使用独立 worktree、Compose project/网络/volume/端口和 `mw-docker` 构建入口；不得在 unraid 建调试实例。APK 签名密钥、SDK 凭证、设备 token 与许可资源不提交仓库。本次未构建新 APK、未部署实例、未发送测试推送。
