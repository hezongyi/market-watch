# Market Watch APK：手机界面与集成方案续析

日期：2026-10-11。目标设备：OPPO Find X8 / ColorOS 16。本轮只分析产品与技术，不实现、构建、安装或发布 App。后台通知接收、保活、省电、无障碍服务、推送渠道及送达可靠性均不在本轮范围。

归档入口：[讨论总览与历史研究索引](android-apk-discussion-record-20261011.md)。交接上下文与早期调查已一并归档，不依赖临时文件或特定工作区。本文源码核对固定于 `afe7bcfb95fa69efa459003842720745c8926eff`；本次文档归档分支起点为 `368a87aa7ceec52c3ec2f2625a83984dd6fa0d46`。相对源码链接供定位，判断应按调查快照理解，不表示重新验收较新主线或生产。

## 判断与推荐

**推荐继续评估“手机专用 React 页面 + 小型原生 Android WebView 外壳”，复用现有服务端和 Advanced Charts。** 手机页面同时可以在 Chrome 使用。先做好移动交互，再把同一套页面集成进 APK，是本项目成本较低、后续较容易维护的路径。这是分析建议，尚不是用户已批准的选型。

用户后续补充：**仅供个人使用，维护简单优先，后续网页还会变化。** 这进一步支持在线加载方案：手机页面保留在现有 `web/` 工程，复用业务模块和适合共用的组件，Android 外壳尽量稳定。没有需要本地实现的功能时，不引入原生插件或页面与Android之间的桥。后台通知继续排除。

当前手机网页的缺口主要来自项目的触屏只读策略与桌面导航结构。APK 直接加载现有 `/advanced-charts` 仍会缺少指标、数据中心和独立自选入口。改善来自重新组织手机页面；APK 额外提供独立安装入口、系统返回与窗口生命周期集成、屏幕空间控制和 WebView 诊断。不能仅凭 APK 形式承诺更快的行情、更高的绘图性能或已经解决 360 黑屏。[S1][S2]

用户已确认同一手机 Chrome 能显示专业图表，360 极速浏览器黑屏。360 的具体原因尚未确诊；它与未来 APK 使用的系统 WebView 是不同的待验收对象。官方支持 WebView 集成，Chrome 的成功仍不能代替 Find X8 上的新 APK 验收。[P1][O1]

### 建议的模块与两处真实变化点

- 手机应用模块管理一级导航、返回栈、当前选择及加载状态。同一实现供手机 Chrome 与 APK 使用。
- 图表会话模块保留独立来源与既有 datafeed；界面通过小接口选择品种/周期、管理指标、保存/恢复手机状态，隐藏 widget 初始化与历史加载次序。现有消息通道继续按来源、窗口、会话、操作及负载校验。
- 数据中心模块的接口保留已有 `CenterContext` 的导航、`apply`、dirty 与 busy 行为。桌面窗口适配器和手机页面适配器提供不同展示/返回行为；业务页面无需再依赖桌面 iframe 会话。
- Android 能力适配器只提供必要的窗口/返回/生命周期能力，网页路径使用浏览器适配器。不设计任意 URL 认证请求、文件读取或通用原生执行桥。

移动路由可设为 `/m/watchlists`、`/m/chart`、`/m/data`、可选 `/m/alerts`；这是候选命名，当前尚不存在。页面展示模式与触屏输入属性应分开：单图、允许指标操作、自选写入、手机状态保存分别配置，桌面工作区写入由明确的状态作用域决定。`pointer:coarse` 继续用于手势/密度，不再兼任全部功能许可。

## 状态、返回和恢复

| 状态 | 建议归属与行为 |
|---|---|
| 自选组内容、品种顺序 | 继续共用 `mw.watchlists.v1`。每次写入基于已知 revision；非冲突操作可重新应用到最新版本，重命名/排序/删除冲突需提示。不能无限重试覆盖。 |
| 当前自选组、列表滚动与筛选 | 手机端独立。手机保存组内容时保留服务端原 `active`；桌面改了 active 也不切换手机当前组。当前组被删除则选择有效组。 |
| 单图品种、周期、指标/参数/样式、显示时区 | 保存到独立手机作用域；复用 native chart 保存/恢复能力，完整库文档不写回被手机打开的桌面工作区。桌面偏好可在首次初始化或明确“导入”时读取。 |
| native 图表文档大小和历史引用 | 现有偏好上限约 1 MB，native chart 内容上限约 4 MB；不能不经评估把完整库文档塞进普通 setting。推荐独立 mobile state 读写契约，复用现有版本控制、验证与引用保留规则。[S5] |
| 模板与收藏 | 读取可复用；手机图表参数变化不自动改共用模板。是否共享收藏写入作为独立选择，不通过全局取消只读顺带打开。 |
| 返回键与页面栈 | 先由键盘/系统弹层处理，再关闭网页指标/筛选/详情弹层，再回详情上级或来源列表；根页面遵循 Android 返回行为。自选开图后返回自选保留滚动；不要仅调用 WebView.goBack()。 |
| 横竖屏与图表页切换 | 旋转应调整布局并保留会话。短暂切换页可保留一个图表实例，避免反复重建；隐藏时暂停不需要的前台行情展示订阅，返回时先重新核对数据。内存回收后从已保存手机状态恢复。 |
| 断网、过期、失败 | 区分登录过期、加载错误、暂无数据及行情陈旧；保留上次真实数据和时间并给出重试。不能用空白黑底作为唯一反馈，也不把历史收盘价描述成实时价。 |

手机单图存储目前没有专用作用域；现有 `/native-charts` 与 `/workspaces` 列表会列出全部 AdvancedWorkspace。仅新建一个名为“手机”的桌面工作区不足以实现隔离。实现时要选择专用存储，或给既有存储增加显式 scope 并过滤默认桌面列表；必须同时处理历史版本引用，避免清理流程删掉手机仍在使用的数据。[S5]

品种身份必须保留现有编码：`MWP:` 平台行情、裸品种的 managed 行情、`MWH:` 固定历史版本、`MWC:` 组合。不得按显示名称重新匹配。组合“跟随当前修订”和“固定所选修订”也要区分；告警详情带来的行情身份不能被普通最近品种状态覆盖。[S11][S12]

| 手机专用网页，Chrome 使用 | 直接获得完整手机导航；现有 HTTPS 会话与图表来源可以沿用；页面更新方便。 | 依赖浏览器窗口及返回行为；360 特定故障仍另查。 | 作为同一套手机 UI 的浏览器入口，适合先验收交互。 |
| 小型原生 WebView 外壳，加载主应用 HTTPS `/m` | 沿用现有会话和两个来源；独立安装；系统返回、安全区、旋转、WebView恢复/版本诊断可按需求控制。 | 需要维护 Android 构建、签名、窗口/错误处理及少量桥；依赖网络和设备 WebView 提供程序。 | **当前优先候选。** |
| Capacitor 标准本地 Web 资产 | 适合更深本地能力和未来多平台；通用插件、原生工程和资源打包流程已有框架。 | 本地来源默认与主应用不同；相对 `/api` 需调整，登录/CORS/CSRF/前台流传输须重新设计；框架和插件也要升级维护。 | 在本地资源、离线或 iOS 成为明确需求时重评。 |
| Capacitor 以 `server.url` 加载远端页面 | 形式上可快速加载网址。 | 官方注明供 live reload 使用，非生产用途；`allowNavigation` 也不能当作独立的可信图表/原生桥权限设计。[O2] | 不用该配置作为首期生产架构依据。 |
| Android 原生/Flutter/React Native 重做业务界面 | 大量复杂手势或更深本地能力时可以获得平台控件优势。 | 本项目 Advanced Charts 仍需 WebView 或另选图表；新增一套列表/详情/参数/导航状态，并维护跨层通信。 | 首期缺少足以抵消重写成本的收益。 |

Capacitor 的标准方案并非不可用；它解决的问题与本项目当前最省改造的 HTTPS 集成方式不同。详细官方配置/源码证据见 [外壳事实核对](android-apk-shell-official-facts-20261011.md)。公开源码核对的是报告里固定的快照，最终所选 SDK 版本仍要检查。

### 登录与来源集成的验收重点

主 WebView 顶层加载可信主应用 HTTPS 页面；图表继续使用另一个主机名。现有发布记录为 `trade.kookvv.com:8443` 和 `charts.kookvv.com:8443`。只换端口不能隔离 Cookie；图表 API 请求继续由可信父页代理，图表来源 CSP `connect-src 'none'` 保留。当前 iframe sandbox 实际包含 `allow-scripts allow-same-origin allow-downloads allow-forms`；早期接入文档关于不允许表单的描述已落后于源码。[S1][S2][S3]

登录后，Cookie 应保留在 App 的 WebView 会话存储中；不能假设自动继承 Chrome 的登录状态。重新启动读取 `/api/session` 恢复 CSRF；401 重新登录并返回原页面，网络失败显示连接状态。源码默认会话时长 24 小时，实际部署值本轮未读取，不能承诺装成 APK 后永久保持登录。[S9]

静态图表不需要主应用认证 Cookie，不能为了 iframe 加载直接扩大高权限原生桥来源。若需原生消息桥，优先验证按来源授权且检查主 frame 的 WebMessage 能力；不支持时提供受限降级，不能默认用全 frame 暴露的通用桥。外部资料链接交系统浏览器，TLS 错误提供可恢复错误页，不能忽略证书错误。[O2]

这组问题可通过有明确范围的技术原型验证：登录→主来源手机页→独立图表 iframe→一次受认证行情请求→返回/旋转→关闭后再开→会话失效。技术原型应记录实际 WebView 提供程序及版本；这里只提出验证问题，没有构建原型。

### 安装与更新成本

首期可使用签名 APK 下载/侧载，保管固定 applicationId、签名密钥和递增 versionCode；正式密钥不进仓库。已有 `mobile/` 是提醒伴侣，仅可参考其 SDK/签名工作，不是现成完整客户端，也不能假设其裸 SDK 构建流程已具备 AndroidX WebView 消息桥。[S17]

远端页面与服务端更新会在后续加载体现；Android 外壳能力变更才需要 APK 升级。因此应保持页面/桥契约兼容、提供版本诊断和不支持时的可读反馈。标准 Capacitor 本地页面更新通常随 App 包发布，或另行引入资产更新机制及其维护成本。本轮不建议为了首期增加自动下载安装器。

### 按个人维护需求收敛技术选型

这些是常见技术路线，没有调查市场占有率或做流行度排名。

| 常见技术 | 网页持续变化时的维护特点 | 本项目适用度 |
|---|---|---|
| PWA（浏览器安装网页应用） | 主要维护现有网页；可获得桌面入口，无须维护自己分发的 APK。需要补安装元数据，并明确页面/行情的缓存策略。 | 如果不需要自己生成 APK，维护工作最少的候选。 |
| Kotlin + Android 系统 WebView，在线 HTTPS 页面 | 网页改动发布到服务器，下次加载即可使用。小外壳保留登录存储、窗口/返回与加载错误处理，偶尔跟进 Android/WebView 兼容。 | **明确要 APK 时的首选。** |
| TWA / Bubblewrap | 用浏览器全屏呈现已验证归属的网站；网页在线更新，自有 APK 只管理入口和少量原生配置。新增浏览器提供程序与域关联验证要求。 | 主要需要独立 APK 入口、愿意沿用浏览器能力时的备选；有自定义 WebView/桥需求时收益较少。 |
| Capacitor（可搭配 Ionic UI） | 标准方案把编译后的前端资源打进包，页面更新通常要随 APK 发布，或另行维护资产更新机制；当前同源认证还需适配。 | 明确需要本地 Web 资源、跨平台和多个原生插件时再选。 |
| React Native / Expo | 使用 JS/TS，业务纯逻辑可能共享，现有 React DOM 控件和图表宿主无法直接作为原生界面复用；相关功能仍需维护两套界面。 | 当前个人使用和维护取向下，首期成本较高。 |
| Flutter | 维护 Dart 界面及跨平台工程，图表仍需 WebView 或另选实现。 | 复杂跨平台产品可考虑；当前没有足够收益。 |
| Kotlin + Jetpack Compose 完整原生界面 | Android 控件/生命周期可深度控制，网页与 Android 页面分开维护，图表仍需 WebView 或重建。 | 首期无需投入完整原生业务界面。 |

建议的具体组合为：**现有 React + TypeScript + Vite 手机页面，Kotlin + AndroidX WebKit/Android 系统 WebView 的小型外壳，通过 HTTPS 加载同一站点的稳定手机入口。** 外壳只处理安装/启动、窗口、安全区、系统返回、外部链接及加载失败；自选、图表、指标、数据中心仍由网页维护。使用标准 Android 构建与签名流程；仅需要一个 WebView 时，不必为了容器再引入 Compose UI 或跨平台运行时。

维护边界：改列表、导航、指标参数、数据中心展示及多数业务流程，发布网页即可；网页与接口需同次发布时沿用现有服务端交付。已经打开的页面不会无条件热切换到新代码，应在下次加载或可控刷新使用新版。新增原生能力、改变页面/原生接口、包配置或系统兼容需要更新 APK。保持稳定手机入口及少量版本化原生操作，比让外壳抓取网页 DOM/按钮位置更容易随网页变化维护。

PWA/TWA 官方事实另见 [外壳事实核对](android-apk-shell-official-facts-20261011.md)。当前应用源码没有发现生产 PWA manifest 或 service worker 注册；测试脚本出现的 service worker 是浏览器测试设施，不能据此认定应用已经是可安装 PWA。AndroidX WebKit 的具体依赖版本、系统 WebView 提供程序及图表实机表现尚未选择/验收。

## 不含后台通知的阶段工作量

按一名熟悉项目的工程师连续投入、沿用当前图表与服务端、数据中心为上述浏览版估算。这是规划量级，尚未通过原型校准；包含独立手机状态及可交付验收，不沿用旧报告包含通知工作的总量。

| 阶段 | 交付内容 | 工作日 |
|---|---|---:|
| 关键集成验证 | Find X8 WebView、双来源加载、Cookie/CSRF、加载故障与返回/旋转的最小原型。 | 1–2 |
| 手机核心界面 | 导航/登录、共享自选及冲突处理、单图状态、指标选择与参数。 | 6–9 |
| 数据中心浏览 | 手机控制器、平台/自建/组合列表与详情、开图/入自选、任务/供源/日历。 | 3–5 |
| Android 外壳完整化 | 生命周期与恢复、安全区/键盘/系统返回、版本信息、签名/安装更新流程。 | 2–3 |
| 集成和真机验收 | Ubuntu 隔离环境、Chrome 手机页面和 Find X8 APK，对照保存/冲突/断网/升级。 | 2–3 |
| **基础合计** | **自选、单图、指标、数据中心浏览；不含可选前台告警。** | **14–22，约 3–5 周** |

可选增量：前台告警列表/详情/在线确认约 2–4 工作日；在此之上增加价格/Python 指标规则的新建、编辑、启停约 3–5 工作日。数据中心完整管理约另加 5–10 工作日，具体组合映射、版本与维护流程应逐项收敛；完整画线编辑需单独估算。这些是增量规划，不代表用户已选定。

2–3 天的小外壳或早期可安装演示仅能回答“能否装进手机、基础图表是否能显示”；包含状态同步、恢复、冲突与手机数据中心的可用首期产品需要后续阶段。

## 验收标准与剩余决定

必须验证的产品路径：登录→自选开图→切周期→加/改/移除指标→回自选；数据中心搜索→详情→开图/入自选→回到原筛选及滚动位置。若纳入告警，再覆盖列表→事件证据→在线确认→正确行情/周期。

状态路径：手机改自选后桌面重新读取一致；桌面同时修改时不无声覆盖；手机切品种/指标不改桌面多图；横竖屏、页切换、重启和 WebView 回收后的状态恢复；会话过期、前台 Wi-Fi/移动网切换、断网及图表加载失败均有真实反馈。固定历史和陈旧行情有明确时间/来源，不假造更新。

触控路径：竖屏及横屏、软键盘展开、系统字体放大、安全区、系统返回和图表缩放无主要操作冲突。浏览器模拟属于布局/自动化证据，Find X8 实机 APK 结果单独记录。

未来开发/验收仅在 Ubuntu 本机的独立 worktree、Compose project、网络、volume、数据库与端口运行；Market Watch 镜像经 `mw-docker` 构建。最终提供实际环境、可访问地址、启动/停止命令和验证结果。本轮只增加分析资料，没有部署实例、修改生产或产生新 APK。

影响范围的两个问题已向用户异步询问：数据中心是否包括新建/维护数据集与组合；前台告警是否只浏览/确认、还需编辑，或本轮不分析。未获回答时上述浏览版及可选增量仅用于比较，不作为范围批准。其他关键未知为 Find X8 WebView 行为、手机状态文档的实际大小/引用保存方式，以及最终分发与桥能力契约。
