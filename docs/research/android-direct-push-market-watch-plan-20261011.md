# Market Watch：Android 后台直连告警方案

> **归档说明（2026-10-11）：** 历史直连方案：记录用户当时排除 OPPO 推送、后来优先诊断现有 ntfy 的路线变化。本文接收端原型、后台设置及通知验收建议未在本次执行，不作为当前界面方案的实施前提。当前范围与选型见 [讨论总览](android-apk-discussion-record-20261011.md)。

> 当时的后续优先级：用户提出先解决现有 ntfy App 在后台停止接收的问题。优先诊断手机设置与 ntfy 服务恢复；自有接收端保留为后续选择，不因计划五项功能就默认重写通知。既有实测记录明确为从最近任务划掉后订阅服务通知消失、重开补收，尚不能证明这是不可修复的平台限制。

日期：2026-10-11。手机：OPPO Find X8 / ColorOS 16。用户明确选择不接 OPPO 厂商推送，要求分析 App 保持后台、直接接收服务器告警，并查找开源参考。本报告按这条路线评估，不将厂商推送资格作为继续分析的前提。没有实现、构建或部署 App，没有发送通知。

开源项目源码、版本、许可及上游限制见 [后台直连开源研究](android-direct-push-open-source-20261011.md)。早前 [首期评估](android-apk-first-release-plan-20261011.md) 的厂商推送主通道建议已被此次用户路线选择取代；已有五项功能的复用调查仍适用。

## 结论

### 先修现有 ntfy，再决定是否定制接收端

现有 ntfy 已经实现原生前台服务与服务器长连接。对于当前送达问题，先排查并修复它，比立刻开发新接收端更省工作，也更容易沿用已经通过的服务端→手机→确认链路。下面的自有 APK 集成方案是后续候选，不是解决通知的必经步骤。

当时核对的手机测试已摘录到 [历史验收摘要](android-apk-discussion-record-20261011.md#历史验收摘要)：正常前台和约 2 分钟锁屏接收通过；从最近任务划掉后常驻订阅通知消失、实时接收失败，重新打开会补收。部分重开对照中即时投递开关/常驻通知状态不确定，ColorOS 后台权限尚未记录为已调整并复测。因此已证明的是该测试条件下实时订阅停止，**尚未定位为手机清理、服务恢复受限、设置变化或 ntfy 缺陷中的哪一种**。原始记录在仓库外，本次仅归档摘要，不新增测试或发布私有运行信息。

合理顺序是核实当前版本与即时投递、允许后台活动/自启动、电池优化例外及最近任务保护；每次只改一个因素，比较正常退到桌面、最近任务划掉和锁屏。仍失败时，读取手机上 ntfy 进程/服务状态与日志，区分被清理、恢复启动被拒绝、连接未重建和通知未展示，再决定是否修复其开源客户端。不要仅靠继续发消息或切换传输协议推断原因。

设置页“强行停止”是另一种明确停止行为，不能从当前划掉测试推定已进入该状态，也不能承诺修改客户端后可以无条件绕过它。测试应以具体操作和日志定义反馈，而不是统称“杀后台”。

本轮没有新增手机实测或通知发送。原始记录中的短锁屏成功不替代长待机；此前用户取消的额外锁屏测试不重新标成未完成，若后续选择修复则对新改动单独安排针对性验证。

### 自有接收端仍是可行的后续选择

**这条路线可行，有成熟开源项目参考。** 最贴近的是 ntfy Android 和 Gotify Android。实际方案是用户开启的原生前台服务持有网络连接、显示常驻连接状态，通过 REST 完成补收与确认；图表页面不必在后台运行。[P1][P2]

需要把可靠性条件写清：前台服务提高进程重要性，用户关闭电池优化可减轻 Doze 的联网限制；仍须处理断网、网络切换、极端回收与恢复，不能承诺所有状态下即时收到。长连接协议不是保活能力。普通自用 APK 可以按这条路线开发和验收，不需要为它先申请 OPPO 推送权限，但需要用户允许通知和必要的后台运行设置。[A1][A2]

不能把项目的“常驻前台服务”解读为毫无后台限制。当前 ntfy 的失败经验说明本机条件需要实测；参考同类源码并不构成新 App 必然更稳定的证明。

## 项目选择

| 项目 | 可借鉴内容 | 对当前项目的适用判断 |
|---|---|---|
| [ntfy Android][P1]，Apache-2.0 | 原生订阅服务、HTTP/WSS 连接、通知、缓存补收、连接恢复与电池优化引导。 | 最接近现有 ntfy 发送后端；可先直接使用公开订阅协议或参考客户端实现。它是完整应用，不是可直接导入的精简后台 SDK。原样换壳仍受同类手机限制。 |
| [Gotify Android][P2]，MIT | 前台连接状态、OkHttp WebSocket、重连与消息补拉。 | 更容易阅读的另一份实际长连接客户端参考。安装使用它通常需要 gotify/server；其接口不直接兼容当前 Market Watch，没必要仅为借鉴后台逻辑迁移全部后端。 |
| [OkHttp][P3]，Apache-2.0 | Android HTTPS、WebSocket、SSE 网络实现。 | 推荐作为新 App 的网络依赖，连接我们自己的设备告警接口。它不提供完整保活、自动补收、可靠告警状态或用户确认机制。 |
| [UnifiedPush Android connector][P4] | 与消息分发器连接的标准接口。 | 不直接解决一个 APK 自己维持后台连接的问题。还需要实际 distributor 存活；由 ntfy 充当 distributor 时仍依赖它，所以本次不优先选。 |

ntfy 与 Gotify 的仓库在本轮读取时均未归档，2026 年有发布；GitHub API 显示 ntfy 最新 release `v1.25.2`（2026-07-21），Gotify `v2.10.1`（2026-07-06）。许可只用于判断源码复用方式，具体依赖和保留声明在实现阶段核对，不复制整项目后自动假定所有资源可任意分发。[P5][P6]

MQTT 也是可用协议；[HiveMQ MQTT Client][P7] 提供自动重连、持久会话与 QoS，但新增 broker、认证和设备订阅维护。QoS 是协议层投递语义，不保证 Android 进程联网，更不证明人已看到消息。现有项目只有单向告警和 HTTP 确认，首期采用 HTTPS SSE 更少引入基础设施；之后如多客户端/双向通信出现实际需求，再比较 MQTT。

## 推荐方案：原生前台服务 + 设备告警 SSE

```text
服务器持续计算告警并持久化
           ↓
设备专用 HTTPS SSE 长连接
           ↓
Android 原生前台服务 → 本地持久化/去重 → 通知/铃声
           ↑                                ↓
断线重连 + 快照补收                  received / 用户 ack
```

1. 用户在 App 内开启“告警监听”。原生服务显示低打扰的常驻连接通知；真正告警使用单独通知渠道。服务不依赖 React/WebView 定时器和页面存活。
2. 首次连接和重连时读取完整未确认快照，持久化事件身份与消费位置；运行中持续监听新增告警、确认与必要设置变化。
3. 断线、超时、服务器重启、Wi-Fi/移动网络切换时自动恢复；持久游标和快照兜住重连间隙。必须处理读取快照与开始订阅之间的竞态，可以先记录游标再取快照、重放后按 ID 去重。
4. 客户端先保存消息，再尝试显示/响铃与回传 received。用户 ack 是独立行为；离线确认持久保存并补传。重复投递不重新开启已确认事件或无限重置铃声。
5. 使用有上限、带随机抖动的重连退避，网络恢复时及时尝试；心跳频率结合反向代理、移动网络和耗电实测决定。不可照搬当前网页行情 SSE 的 0.5 秒心跳或旧客户端每 5 秒全量轮询来作为全天默认通信。
6. 系统允许的服务恢复、开机/解锁恢复需独立设计与验证。`START_STICKY` 是系统尝试重建服务的机制，不保证立刻重建；显式停止应停止，不能无限互相拉起。可在平台允许时恢复用户之前开启的监听状态。[A2]

第一版在 FastAPI 增加受限设备凭证的专用告警 SSE 更符合“直接接收自己的服务器”需求。接口名称只是方案建议，当前仓库尚未实现。服务端可以先以合理间隔读持久化告警/变更并推送，之后按规模决定是否加入内部通知机制，不需要先引入新消息服务器。

## 可以复用的本地资源与缺口

- 后台判定：现有 `chart_alert_worker.py`、`alert_monitor.py` 已独立于网页运行；`chart_alert_service.py` 持久化信号和通知。[R1]
- 凭证与确认：设备配对、撤销、`/api/device/sync`、`received`、`ack` 已有，适合作为直连的基础。设备凭证只授予告警能力，页面登录仍使用现有会话，不扩大为所有业务接口通用 token。[R2]
- Android 原型：已有 `specialUse` 前台服务、通知状态、`START_STICKY`、本地响停/确认补传，但只是提醒伴侣。需引入真正的长连接、连接恢复、现代 Android 设置与持久化，不继续依赖第二个 ntfy App 的广播。仍未经过本机锁屏验证。[R3]
- 现有 `/api/events` 是会话鉴权的 Audit 事件流，只发 kind/at、每 3 秒查一次，不能直接当受限设备告警流。行情 SSE 则归属于网页行情订阅，更不能在 App 后台把所有行情连接维持下去。[R2][R4]
- 当前图表告警通知资格和设备快照过滤都与 `notify_ntfy` 关联。新增 App 直连需要明确独立的通知选项及兼容迁移，不能在 UI 说停用 ntfy 后把要推送的 App 告警也过滤掉。[R1][R2]
- 当前 received 只记录客户端回传到达，不能证明系统已经展示或用户听到。新协议应分别保留持久接收、通知权限/尝试显示与本人确认状态。[R2][R5]

可选的另一条第一阶段路径是让新 App 直接订阅已有 ntfy 服务，再使用 Market Watch 快照/ack 作为权威记录。这样可保留当前服务器 ntfy 投递，但仍须实现客户端长连接和后台恢复；它只是复用更多，不比直连自动更可靠。

## Find X8 / ColorOS 16 的运行条件

需要核实并引导用户设置允许通知、锁屏提醒、后台活动/自启动，以及不优化电池。不同设置入口以该机实际 UI 为准，不根据旧 ColorOS 截图硬编码。

Android 官方说明处于电池优化豁免列表的 App 可在 Doze 中联网并持有 partial wake lock，但仍有其他限制。前台服务与电池优化豁免作用不同，不能只显示一个常驻通知就认为锁屏联网已解决。[A1]

服务类型应按真实的持续告警监听选择及声明；可沿旧原型评估 `specialUse`，不把它视为保活特权。不要套用目标 API 35 的 `dataSync` FGS 作为全天监听，后者有后台时长限制。短时 wake lock 只用于必要的消息处理/响铃，常年持锁、频繁精确闹钟、伪装音频播放不作为默认保活方案。[R3][A3]

代价是常驻通知、后台网络活动和一定耗电；低电量/超级省电、设备离线、设置中强行停止都应独立评估。客户端完全不运行或系统暂停其网络的这段时间，不存在能立即显示服务器新消息的普通长连接代码；可以做到恢复后补收，并让服务器以设备最近回执/心跳提示监听离线。这是范围边界，不是回到厂商推送的建议。

## 建议先验证接收端

先做最小原生接收版本，仅含开启/停止监听、连接状态、通知、确认和诊断。初步量级为 3–5 工作日出可安装接收原型，另留多日真机观察；不是已开工或承诺该时间能完成可靠性验收。

Find X8 应覆盖锁屏数小时/过夜、Wi-Fi 与移动网络、网络切换、服务器断开、离线恢复、页面退出、最近任务清理和系统回收后的恢复；设置页强停作为单独停止场景。观察时使用带事件 ID 的已授权测试消息，记录服务端入库、客户端接收、通知处理和确认时间，以及耗电和重复/遗漏。运行证据不足时不宣称“已保证收到”。

先满足既定条件下的接收和恢复，再把自选、单图、指标与数据中心接入同一 App。五项功能的原资源复用判断不变，厂商审核等待从本路线排期中移除。

后续服务器开发/验收只用 Ubuntu 本机隔离实例及仓库规定构建入口，不在 unraid 创建测试服务。此次研究不需要新部署或用户审批。
