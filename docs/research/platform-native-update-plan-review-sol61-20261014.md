## 结论

**有条件可实施。** 正常完整 bar 回调、旧柱真实修订重取与现有连续拖动机制可以兼容。v1 的方向、范围及生产授权边界正确，但正式实现前需要补齐三个 P1 数据合同：消费基线如何成为后端判定依据、平台恢复版本如何固定、平台 Python 指标如何读取并提交价格相同版本。分页凭据合并和恢复取消也需要明确状态转换。

必要恢复时的画面连续性仍是 **Ubuntu 原型门槛**，当前源码和公开类型不足以证明全窗口、全指标绘制完成可被一个公开回调可靠识别。该门槛不能用减少 reset 或现有视口恢复通过代替。

以下发现针对可执行合同缺口，不要求 v1 列出全部函数、数据表或实现细节。

## P1 发现

### P1-1：需要定义消费确认与修订判定的责任边界，否则“已接受基线”仍可能是发送进度

**方案位置：第 33–35、41–43 行。** 已提出“接受后作为基线”，但没有说明浏览器的接受记录如何影响共享流中的逐消费者历史检查，也没有区分收到事件、适配器交付和完成绘制。

**源码事实：**

- `backend/alerts/market_stream.py:351–358,382` 在构造 SSE 输出时运行 `delivery` 并推进输出 sequence；`564–568` 随该次输出推进消费者 cursor、loaded_before 和组合 snapshot，未等浏览器接受。
- `backend/alerts/market_stream_api.py:26–49,113–145` 提供注册凭据与 SSE，但没有逐次消费确认接口。
- `advanced-host/bridge.js:109–118` 在调用实时 callback 后记录最后柱和凭据；历史 `1129–1135` 以 callback 返回非 false 作为接受。`native-navigation.js:455–467,495–510` 能证明当前 cache/source generation 下进入适配器成功回调，不能证明已绘制。
- `market_stream.py:267–292` 对共享任务生成 changed/new bars；下一分钟事件不保证携带上一柱完整值。前端不能仅调整回调顺序，就保证完成方案第 41 行的上一柱交接。

**失败场景：** SSE 已输出新柱，消费端因旧世代或恢复状态未交付，服务端却已经将上一柱归为历史；稍后最终值到达，按发送边界误判为必须 reset。反向情况是消费端已经交付新柱，服务端仍按较早的 HTTP 凭据判定，从而漏掉真正旧柱修订。分页重新注册和带指标批次延迟都会使两端进度不同。

**建议补充：** 明确每个 listener / generation / result epoch 下的“适配器已接受”游标、展示投影凭据及更新时机；选择有界消费确认，或把 reset 候选交由前端按接受基线复核的合同。确认仅证明交付，绘制验收另行处理。保留共享计算任务，不按客户端复制任务。规定何处取得上一柱最终完整 bar、先交付旧尾柱再追加的排序，以及缺证据、超预算和断线后的核对方式。展示投影遵循 `bridge.js:598–608` 的 chart_time、数值转换及实际 volume 交付规则；不能直接复用包含 complete 的 `provider_cache.price_input`。

### P1-2：平台“固定本次版本”的恢复缺少现有可调用能力，需要明确新增合同及预算

**方案位置：第 55 行，相关第 57、59 行。** “固定版本，先准备覆盖历史及指标前缀，再失效重取”目前不能靠平台既有 cache_revision 参数完成。

**源码事实：**

- `backend/alerts/storage.py:1282–1293` 的 ProviderBar 以 dataset_id/start 为主键，仅存当前 payload；`provider_cache.py:374–388` 原地覆盖，`322–328` 直接删除历史行。
- `provider_cache.py:152–162,191–235` 的 REPEATABLE READ 只保证一次短事务中的观察一致；事务结束后无法凭返回的 cache_revision 重读该版本。
- `chart_api.py:94–121` 没有平台预取包或版本固定字段；`provider_cache.py:716–758` 不使用 input_revision/display_snapshot_id 固定平台读取。`snapshot()` 是当前缓存读取函数，不是可持有的历史快照。
- 组合已有固定 DisplaySnapshot 路径，例如 `bridge.js:1153–1169`，不能据此认为平台已经具备同样能力。

**失败场景：** 预取价格窗口得到 R，实时提交把旧柱改为 R+1；指标前缀或 reset 后第二次 getBars 得到 R+1。前端声称本次恢复为 R，但价格、指标和排队事件无法归属于同一份输入。仅在每个 HTTP 请求各自使用 REPEATABLE READ 不能解决跨请求问题。

**建议补充：** 选定一种足以实现的方案：在同一快照中准备包含价格窗口与计算前缀/结果的有界不可变恢复包，随后按恢复 token 服务 getBars 和指标；或新增短期平台快照接口并明确读取合同。无需提前设计所有存储细节，但应说明身份、覆盖范围、token 归属/过期、最大条数与字节数、共享多图成本、失败重建、后续版本接续及容量拒绝。缺少预取覆盖时应扩大或重建同版包，不能静默混入当前缓存版本。不得为等待供源或绘制而持有长时间数据库事务。

### P1-3：平台 Supertrend 与价格同版需要专门协调，当前同一次指标读取也可能混用两个版本

**方案位置：第 63–65 行，相关第 55、73 行。** 稳定起点与递归后缀要求正确，但现有平台协调不能证明结果与主价格相同版本。

**源码事实：**

- `bridge.js:267–275` 只为组合指标传入 display_snapshot_id；平台仅传 calculation_origin。平台 bars 在 `2608–2613` 直接交付，不经过组合展示批次。
- `provider_cache.py:757–766` 先读取价格与版本；`767–785` 再开启事务读取计算前缀。仅 SWING_SR 分支重新对齐 visible bars 和 cache_revision/as_of，Supertrend 使用第二事务前缀计算、却仍可携带第一事务的 visible bars 与版本。
- `indicator-coordinator.js:120–150` 隔离前端 binding 变化并核对组合 snapshot/input_revision，但没有核对平台返回 cache_revision 与主价格已接受版本相同。`175–192` 只检查指标分页间版本一致并把返回版本交给适配器，这不足以绑定主价格。
- `supertrend_pine.py:44–91` 明确依赖 previous close、ATR、上下界与 direction；仅补 period 根前缀或替换末点不足以修复历史影响。平台目前 `provider_cache.py:773–788` 可从固定 calculation_origin 重读完整前缀，不必为了此改动强行引入新的持久 checkpoint 系统。

**失败场景：** 价格已显示 R；Supertrend 请求进行时，供源修订历史为 R+1，而主价格 binding 还没变化。指标以 R+1 前缀计算且被当前结果通道接受，图上出现 R 的价格与 R+1 的趋势线。甚至同一响应内也可能把 R 的 visible bars 与 R+1 的指标结果标成 R。

**建议补充：** 定义价格交付 token → 指标请求 token → 返回输入身份/版本 → applyBatch 的核对接口，并让平台 visible、递归前缀和返回凭据来自同一观察。与 P1-2 的固定包可共享能力。说明价格先推进时，旧指标是撤回还是明确标旧，何时允许标为 ready；当前组合批次也只提供有界协调，不能宣称原子绘制。重算允许同版完整固定前缀，或验证过的修订点之前状态；checkpoint 若采用，须绑定数据集、参数、算法、origin 和已验证输入版本。complete/coverage/gap 变化即使绘图价格相同，仍须按计算依赖处理（`chart_indicators.py:403–433`、`indicator_state.py:45–84`）。展示计算不能推进确认计算与告警状态。

## P2 发现

### P2-1：分页凭据不能只“取较新值”，需要描述范围与版本的合并规则

**方案位置：第 51 行，相关第 33、74 行。** v1 已识别旧响应覆盖问题，但需要补上一个关键不变量：左侧分页接受不等于全部已加载历史已接受该页的全局 dataset 版本。

**源码事实：** `bridge.js:369–376` 合并 first/last，却直接替换 observed_at、input_revision、history_revision/tail_revision 和 display_snapshot_id；之后 `380` 重新注册。平台旧响应复核在 `1076–1115` 保护另一套 providerHistoryState，不能自动保护 marketHistoryState。共享平台检测 `market_stream.py:503–508` 使用全局 observed_at，且只查询 revision > 1 的行；新补入旧时间范围的行以 revision=1 写入（`provider_cache.py:351`）。

**失败场景：** 左页在旧版本返回，会回退实时凭据并引发重复更正；即便改成 max，也可能失败：尾部旧柱已在 R+1 修订，左页只包含远处历史，却带 R+1 的全局 as_of。把它推广到整个已加载范围，可能掩盖尚未交付的尾部修订。另有旧范围补入一根新 bar，revision=1，不会被现有 revision>1 筛选识别。

**建议补充：** 用同版快照覆盖证明，或有界的分区间接受凭据，区分左侧范围扩展与实时尾部推进；重叠范围需逐投影验证，不能无条件推广全局 observed_at。重订阅从最后实际交付游标接续，并证明新世代快照/重放覆盖切换间隙。修订证据应覆盖历史插入、删除及时间标签改变，不能只过滤已有行 revision>1。验收注入“旧左页迟到”和“新左页不含尾部”两种相反竞争，以及已接受范围中的首次插入。

### P2-2：需要分开取消视图动作与履行数据更正，并规定缓冲的世代归属

**方案位置：第 55–59 行，相关第 74 行。** 取消、排队和最终更正均已列出，但它们之间的状态转移尚未闭合。

**源码事实：** `bridge.js:2594–2605` 在恢复前改变 generation、清接受状态与游标；旧世代事件在 `2568–2569` 被直接丢弃。`recoverMarketBar:389–396` 仅成功后重注册，失败则定时重试。`reloadHistory:1471–1473` 避让交互；`viewports.js:324–350` 在 reset 已发出后因交互取消视口恢复并返回失败。当前不存在方案承诺的实时恢复缓冲。

**失败场景：** reset 已开始，用户拖动导致返回 false；后续 bars 被旧 generation fencing 丢弃，重试再次 reset。持续交互可造成反复重取或实时冻结；如果“取消恢复”同时丢掉修订责任，则旧柱一直错误。如果只新增队列但未定义取消后的去向，队列也可能被错误回放到新系列。

**建议补充：** 描述 preparing、resetting、applying、catching-up、ready/error 的最小状态机。用户交互立即取消旧画面保留与视窗回写；同一数据身份下仍保留更正责任，按最新需求完成或重新准备；切身份则废弃旧责任和队列。明确缓冲在何层、按什么 identity/generation/epoch 分组、如何合并同柱更新、如何处理缓冲内历史修订及 sequence 缺口。超上限/超时转为明确核对与重新取数，成功后从真实接受游标补齐。规定最大等待/重试或明确错误出口，不能靠每 500/1000ms 再调用现有恢复函数保证最终完成。

## 原型门槛与验收补充

这些是需要实验解决的假设，不是已证明不可实现的缺陷。v1 第 57–59 行已经正确提出验证与失败披露，建议把下面内容写成实施门槛：

1. 本地 v31.1 公开类型存在客户端画布截图能力（类型定位 `charting_library.d.ts:12216`）以及 chart/study 的加载事件（`10730`、`14474`）；未找到能证明全部目标窗口与指标已绘制完成的公开 barrier。`dataReady` 描述数据加载，不是完整绘制承诺。现有 `viewports.js:336–346` 的首次加载事件加两帧等待不足以证明全窗口完成。
2. 原型先证明截图范围能覆盖目标 pane/图格并保持正确尺寸，旧画面可明确标旧、用户可继续操作、交互后立即移除；覆盖层不能遮住有效交互或把过期十字线/报价当作当前状态。单张 widget 截图不自动等于可独立处理任意图格恢复。
3. 定义撤除旧画面的可观察条件：恢复 token 对应的目标历史范围、必需 countBack/边界、每个必要指标的接受范围与同版结果均齐备；再以实际录屏验证展示完成。`indicator-coordinator.settle:260–271` 可等待接受，但不是公开 paint barrier；现有 `native-indicator-results.js:191–211` 是项目既有、固定版本的内部适配 seam，不应包装为公开原生能力。
4. 如果公开能力无法达到必要恢复的连续画面目标，止于明确的未通过原型结论，保留真实历史纠错。后续是否接受短暂视觉变化由用户决定，不能自动将验收条件降为“reset 少了”。本轮无需原型、实现或生产发布。

v1 第 71–75 行已有合适的联合验收框架。补齐合同后，建议加入确定性的版本化输入样本：可见范围外但在固定 origin 之后的真实修订、同价确认/覆盖状态导致指标依赖变化、分页两种竞争、取消前后接续、恢复包过期/容量拒绝、多参数与多图同源。Supertrend 参考值应由**同一冻结输入与固定 origin**完整重算，覆盖 direction/Buy/Sell、空值及断点；不能用当前缓存或仅末点作为 oracle。连续 M1 视频仍需无指标、带 Supertrend 两组，且与事件/版本证据关联。此前生产没有带 Supertrend，不应引用为带指标通过。

## 已确认可保留的部分与审阅界限

- 当前是 continuous 真实序列身份；`native-navigation.js:402–406` 的 chartWindow/historical/takeSeed 为空或 false。遗留 window 分支不应成为新的恢复架构依据。
- `native-reserve.js:43–51,83–119` 的普通/快速储备、前缀保护、cache generation 检查及 `provider_cache.py:687–713` 的 PG-only reserve/后台 interest 与正常增量兼容。减少普通 reset 无须撤销这些机制。
- 组合 `display_changes.py:12–16,19–46` 已按真实 OHLC/volume 投影检查，不能把组合重置统一解释为元数据误判；共享流修改仍需组合回归。
- 不把 volume 一概忽略、不无限等待最终确认、不制造分钟柱、不重改绘图工具可见范围，均是正确边界。
- 未发现额外 P3 问题。权限、隔离主机、私有明细与许可保密边界符合 AGENTS.md；若新增快照/token，仍需沿用既有认证、身份隔离和有界资源合同。

以上源码事实支持修改方向及五项合同补充。逐次生产 reset 的实际成因、方案的性能改善幅度和连续画面能否通过，只能由后续获授权的 Ubuntu 实现/原型及联合验收证明；本报告不把推断表述为实测结果。
