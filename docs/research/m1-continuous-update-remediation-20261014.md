# M1 连续更新与历史更正处理方案

2026-10-14。分析基线 v1.25.3 / 6679a70；仅提出方案，没有修改应用或生产。依据：[原生更新合同](native-chart-update-contract-20261014.md)、[生产实测](../verification/m1-production-20261014/README.md)。

## 结论

平台和组合统一采用原生增量交付：当前柱更新／新柱追加不 reset；确认和审计信息变化不自动主图 reset；真正旧柱绘图数据变化保留受控重取。必须重取时先准备新数据、保持旧画面，再在价格与指标接受同一版本后撤下旧画面。不能只禁止 reset，也不能用短暂延迟保证来源最终数据永不迟到。

正常增量、历史一致性和绘图连续性是三个独立要求。使用原生公开 API 时，已经落后于最新柱的价格更正无法通过 subscribeBars 回写。若来源每分钟都有真实迟到更正，及时追加新柱、立即应用全部旧柱更正和从不执行历史重取不能同时保证；要保持自动正确性及实时性，需要改善重取的展示过程，而非声称单纯调整事件判断即可永久消除 reset。

## 已知事实与未证实原因

组合 EURUSD M1 约 7.5 分钟接续 7 个分钟、113 次尾柱变化，6 次 resetData；录屏确认 6 次短暂清空（0.1–0.7秒）。平台约 5.4 分钟接续 5 个分钟、22 次尾柱变化，5 次 resetData；录屏确认 5 次清空（0.2–0.4秒）。均无时间倒退、视窗跳回或柱宽变化。生产接收到 history_changed，组合 affected_start 为已过去一分钟。没有添加 Supertrend，不能宣称本轮带指标实测通过。

平台按整个 ProviderBar.payload 的变化推进 revision/changed_at，存在元数据也被判成旧柱修订的可能（provider_cache.py:340–369；market_stream.py:497–508）。组合已经比较 OHLC/volume 的展示投影，不能把组合问题也归为纯完成状态变化（display_changes.py）。尚未逐次证明旧新 OHLC 具体差多少、量变化或交付顺序分别占比。

## 1. 先记录真正交付给图表的版本

每个数据集身份／周期／订阅世代保留有界的已交付 bar 投影：图表 time、OHLC 和实际供应的 volume，以及数据来源版本、DisplaySnapshot、最新已交付柱时间。来源版本与展示版本分开。历史检验与这个实际交付基线比较，不把数据库 revision 变化或 SSE 已发送当成图表已接受。

增加局部时序证据：受影响柱的旧新投影、仅改变的元数据字段、最终值到达时刻、下一柱交付时刻、订阅确认、缓存重取与原生绘制完成时刻。数据只保留本任务私有材料，公共证据输出分类与计数。生产不增设测试实例。

此阶段验证：元数据误判、真实 OHLC/volume 更正、确认交接乱序、缓存观察凭据落后分别有多少。实时与历史浏览分开；不同来源、周期、账户、绑定和世代不合并。已交付基线有容量上限，超出或证据缺失时走明确的一致性恢复，不能默认无变化。

## 2. 将事件区分为不同动作

| 已验证的变化 | 主图动作 | 指标／状态动作 |
| --- | --- | --- |
| 同时间的最新柱 OHLC/volume 更新 | subscribeBars 更新完整 bar | 原生指标自然更新；Python 指标跟随同一快照更新 |
| 更大时间戳的新柱 | subscribeBars 有序追加 | 按同一展示版本延伸指标 |
| 仅 complete/source_confirmed/coverage 等元数据变化 | 不主图 reset | 更新状态和凭据；依赖这些字段的算法仍需重算 |
| 来源 revision 变，但 time/OHLC/实际供应volume 相同 | 不主图 reset | 推进来源观察凭据，验证指标实际依赖 |
| 旧柱的 time/OHLC/volume 确实改变、柱新增／删除或真实缺口修复 | 合并受影响窗口，执行针对该源的历史更正 | 从最早受影响依赖重算；同时提交展示版本 |
| 旧递归输入或确认状态影响 Python 指标，而已绘制价格不变 | 不强制价格序列 reset | 撤回受影响的旧指标结果、重算并更新自有指标结果层 |
| 断线、sequence/result epoch 改变，但历史相同 | 恢复订阅并核对，正常续接 | 重新建立快照凭据，不凭断线推断旧柱修订 |
| 数据集绑定、账户口径或实际系列改变 | 完整失效并重建相关序列 | 隔离旧结果，不能沿用旧数据 |

volume 是图表输入，且 OBV 等算法依赖它，不能普遍忽略；哪怕主图只画价格，也不能改变 Volume 或依赖指标语义。价格不变但指标变化的判定须按实际依赖，不能把“价格没变”推成“Supertrend/其他指标都不用算”。

## 3. 尾柱交接尽量用实时回调完成

若最终确认已经可用、上一柱仍是最新柱：先完整更新上一柱，再追加新柱，整个过程用 subscribeBars。新柱的 open 也必须来自实际来源，不能自行补造。

若最终确认尚未到达：不能无限等待确认而让新分钟停住，也不能设置一个短延迟就宣称保证不会迟到。维持实时新柱交付和可观察的确认状态；稍后真实更正已变成历史的柱，进入受控历史更正。来源异常、休市、稀疏分钟和断线同样不得凭时间到点制造新柱或完成状态。

当前平台与组合修订检测边界都应由实际交付游标推进：不能拿服务器最新柱边界替代图表已经接受的最新柱。交付时需确保同品种／周期顺序、世代 fencing，旧响应不覆盖新状态。

## 4. 必须重取时保留画面，再完成切换

当前 refreshChartHistory 已保存和恢复视口，但 resetData 会先清空原生序列；因此“恢复视口”与“没有闪烁”不是一件事（viewports.js:318–357）。

推荐在针对旧柱的恢复期间：

1. 固定本次修订快照，预取足够覆盖当前原生请求窗口与指标预热的历史，先校验数量、顺序、边界和依赖；持续收到的后续更新有界排队，不丢、不混入另一快照。
2. 保留最后一个完整有效的图格画面，显示简短更新状态。新历史尚未准备好时，不先调用 resetData。该画面仍是旧版，不能冒充已完成修订；报价或指标展示也不能假称与旧画面同版。
3. 数据准备后失效对应订阅缓存、reset 对应图格，并用准备好的同版结果服务 getBars；不因一个周期变化全局清掉无关图格缓存。
4. 确认所需历史窗口及依赖指标完整接受、原生绘制就绪后，撤下保留画面，再按顺序交付排队更新。不能只等第一次 onDataLoaded：实测重取期间出现63→126→189根分批加载。
5. 用户操作、切品种／周期、绑定或窗口变化取消旧恢复；新修订合并而不是并发反复reset。超时／失败结束等待，显示错误并可重试；不能无限冻结或宣称修订成功。

保持旧画面的实现需先在 Ubuntu 做小型验证，评估覆盖层的点击／十字线、主题、多个pane、指标状态、内存和取消行为；不修改许可库内部存储。不预先承诺原生缓存重取本身完全不空白，目标是让用户看到的画面连续。若覆盖层无法可靠实现，应明确保留必要重取的短暂视觉变化，而不是掩盖失败。

## 5. Supertrend 与价格必须同版

沿用并加强 DisplaySnapshot 绑定：当前柱及新柱增量用价格相同快照的 Python 结果；真实历史更正从最早受影响点之前的有效 checkpoint 顺序重算后缀，因为 ATR／方向有递归依赖。只替换最后一点不足以保证正确。

价格重取与 Python 结果准备应共享同一来源身份／快照／修订世代。旧结果只能标为旧或撤回，不能放在已经切到新版的价格上当成最新结果。超时保留明确的 pending/error；不将后台 confirmed checkpoint 或告警输入改成临时展示值。自有Python结果层能否不重建主价格序列独立更新，要按真实native study seam验证，不等同于普通第三方原生 study 的历史回写能力。

## 实施顺序与验收

先完成逐事件旧新投影及交付时序证据，再统一平台／组合的变化分类和交付游标；之后验证必要历史更正的预取／保留画面／切换，最后把 Supertrend 和共享多图放入同一恢复事务。每一步独立回归，Ubuntu 独立实例完成后才另行生产发布。

验收至少覆盖：当前柱反复更新、连续10–15次M1接续；同价确认／元数据变化；最终OHLC在新柱之前与之后到达；volume变化、真实旧柱更正、删除／新增历史；断线重连与result epoch；视窗之外的递归前缀修订；Supertrend多个参数、多图同源、切周期／滚动取消、错误重试。

通过条件：普通tail/append/metadata事件零reset，柱时间不倒退、不重复，视窗及柱宽保持；真实旧柱更正后价格与来源相符、指标与同快照完整重算相符；必要恢复无可见K线／指标消失、无无限等待，修订期间不会显示混合版本或忽略缺口。用视频逐帧及事件时序双重验证，最终截图和dataReady=true不足以证明无闪。无指标与带Supertrend场景必须分别验收。

这不是降低数据正确性的方案。若验证证明来源每分钟都真实修订上一柱，预计仍有必要历史重取；优化应落实到画面切换和指标一致性，而不是用“正常一分钟零reset”作为无法满足的绝对指标。
