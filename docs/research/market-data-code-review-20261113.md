## 结论

2026-11-13 后续产品方向：用户希望“组合行情”收进自建行情，成为可选扩展。底层原生读取、固定历史与接续三种数据职责仍应保留；用户入口可收敛为两类。优先删除重复查询、解码和事务准备，避免通过减少数据、降低展示刷新频率或弱化告警语义来省 CPU。

收益取决于使用场景，不能用同一个排名代表全部场景：

| 场景 | 最值得先做 | 直接收益 | 当前证据边界 |
|---|---|---|---|
| 打开数据中心 | 列表摘要与详情分开；批量查询；翻页只取新增页 | 页面响应与数据库查询量 | 重复读取路径已确认，未测当前延迟 |
| 执行自建历史维护 | 原生周期历史按月顺序合并；未变化周期直接继承 | 减少重复解压、解析和历史重写 | 算法重复已确认，未测真实数据规模 |
| 无浏览器但维持三条组合实时流 | 组合多周期复用同一次确认输入；到期调度减少空扫描 | 持续后台 CPU 与事务量 | 调用链已确认，当前占比需要重新采样 |
| 打开多图和指标 | 展示快照限量清理、历史块解码复用 | 交互尾延迟、重复解码和锁竞争 | 路径已确认，竞争程度尚未实测 |

四项优化已记为待办，当前不实施。未来若用户要求推进，可先做列表与原生历史合并；如果目标专注无人使用时的 CPU，则优先验证组合聚合。到期调度和报价路径是额外后续分析项，不属于本次已认可的四项。

## 2. 优先项：列表查询和前端翻页

### 已确认的重复工作

- [MarketList.tsx:125](../../web/src/market-data/MarketList.tsx:125)：请求第 k 页时，从第 1 页重新请求到第 k 页。每轮自动刷新也重读整个已加载前缀。
- [MarketList.tsx:172](../../web/src/market-data/MarketList.tsx:172)：每轮完成后 10 秒再次读取。代码没有页面可见性判断，浏览器自身可能另有后台节流。
- 因此，在没有刷新、重试的理想顺序翻页中，加载 10 页需要 55 次分页请求，而单纯追加应为 10 次。这是代码推导，不是实例采样结果。
- [data_center.py:125](../../backend/alerts/data_center.py:125)：自建列表逐条调用完整 `dataset_detail`，其中包含发布周期排名、维护与来源能力查询。
- [composite_center.py:153](../../backend/alerts/composite_center.py:153)：组合列表逐条调用完整 `detail`。每条重复发现全局需求、读取活动告警，再在 Python 中筛选当前组合；还读取映射校验、周期任务和详细规则健康。
- [PlatformMarket.tsx:65](../../web/src/market-data/PlatformMarket.tsx:65)：平台列表从管理页返回时，顺序恢复此前全部分页。此项属于返回加载成本，平台列表没有复用上述 10 秒列表轮询。

### 建议

1. 列表接口只返回行展示和打开图表所需的摘要，包括可用周期及对应版本。详细规则、映射证明、完整维护详情在展开时读取现有详情接口。
2. 后端按一页 ID 批量读取关联数据；`wanted_instruments` 同一请求计算一次。告警在 SQL 中限定相关组合，避免每行读取全部活动规则。
3. 分页追加只请求新页；已加载行的状态用批量 ID 查询刷新。保留可见状态目前的刷新节奏，避免改变用户已接受的状态展示体验。
4. 搜索增加短防抖并取消过时请求；保留输入的即时反馈。页面隐藏时可以暂停管理列表刷新，恢复后立即补读，不影响后台行情和告警。
5. 返回平台列表时先呈现缓存的已加载行和滚动位置，再校验目录版本；避免每次从第一页等待全部恢复。

实施分类预计 F0。验收关注连续翻页、返回位置、筛选后重新从第一页开始、展开详情最新状态，以及列表摘要与当前可打开版本一致。分页必须处理状态筛选成员变化，不能只更新行而永久保留已不符合筛选的记录。

## 3. 自建行情：原生历史合并存在按月份重复全量解码

### 已确认的路径

[native_history_archive.py:138](../../backend/alerts/native_history_archive.py:138) 的 `_rows_from_pages` 每次遍历都会读取来源 blob、解压、校验、解析 JSON。

[native_history_archive.py:147](../../backend/alerts/native_history_archive.py:147) 的 `_merge`：

- 首先遍历全部 incoming rows，发现月份。
- 对每个月，再遍历全部 incoming rows，仅选择该月数据。
- 每个月还遍历父版本 chunk 列表，查找该月内容。
- 随后重新排序、序列化并调用 `store_blob`。底层 blob 有去重能力，但去重前的解码、编码和数据库检查仍然发生。
- `_publish` 对 `inherited` 周期同样调用 `_merge`，即使该周期本轮没有更新；发布时再验证所有 chunk 引用。

若涉及 M 个月、N 条 incoming rows，仅 incoming 数据遍历就接近 `(M+1)×N`，并伴随重复解压。十年日线月份多；分钟历史则单月数据量大。实际收益需用当前数据规模验证。

### 建议

1. 对有序来源页执行按月顺序合并：每页解压一次，父块按月索引或顺序前进。只保留当前月和有界来源页，避免把十年分钟历史全部装入内存。
2. 如果来源页没有已验证的全局顺序，先建立有界的月份分段暂存，再逐月处理；不得直接假定全部来源天然有序。
3. `inherited` 周期直接继承已验证 chunk 引用和事实，校验来源、价格规则、版本范围及回收保护。对真正更新的月份才进行合并。
4. 原生周期产物后续再评估跨版本复用。当前 [history_mode_artifacts.py:106](../../backend/alerts/history_mode_artifacts.py:106) 会重新生成；旧 M1 路径已有 `_reuse_period_block`，不能把两条路径当作都没有复用。
5. 暂不更改供应商历史复查窗口。原生版本有意重新核对供应商当前可用窗口，以发现历史修订；缩小为最后几根会改变数据语义。

另一个配置一致性问题：[history_mode_maintenance.py:29](../../backend/alerts/history_mode_maintenance.py:29) 保存并校验 `overlap_bars`，但本轮全后端检索只找到配置处引用，实际原生抓取路径未消费它。应先明确为兼容字段并说明当前行为，或在独立需求中实现；不要让用户误以为它控制了实际复查范围。

实施预计 F1，先做不改持久格式的合并算法与继承优化。验证旧数据保留、历史纠正、失败周期继承、去重、乱序来源处理、复权因素变化、产物和清单一致，以及任务中断后重试。

## 4. 组合行情：在已有增量聚合上减少重复准备

### 已经具备的优化

- 持久 `CompositeInputEvent` 和按周期任务，不是每条 tick 都重建全部历史。
- [composite_aggregate_worker.py:30](../../backend/alerts/composite_aggregate_worker.py:30) 已有提交唤醒和空闲兜底等待。
- [composite_realtime.py:130](../../backend/alerts/composite_realtime.py:130) 已有当前桶、日历结果、极值结构和确认增量复用。
- [composite_chart.py:67](../../backend/alerts/composite_chart.py:67) 优先读取物化结果，历史部分复用固定版本周期产物。

### 剩余空间

[composite_aggregates.py:63](../../backend/alerts/composite_aggregates.py:63) 每次领取一个周期，再通过独立 build、commit 处理。同一条确认分钟影响九个周期时，会重复读取修订、历史版本、目标来源、日历和确认事实。

[composite_realtime.py:156](../../backend/alerts/composite_realtime.py:156) 先找出 changed 分钟，再对每个分钟单独调用输入读取。正常逐分钟确认时集合很小；重连补齐时会放大。

建议：

1. 先记录领取、元数据、输入读取、日历、聚合、提交的独立耗时和 SQL 数；据此决定是否值得合并领取。
2. 以同一修订、同一输入版本为单位，共享不可变元数据和变动分钟读取，再更新各周期现有桶。不要重建一套聚合器。
3. 补齐路径一次读取有界变动分钟范围，替代逐分钟查询；保留每个分钟选择不超过目标输入版本的最新修订语义。
4. 保持周期水位、租约、失败隔离和告警唤醒。某一周期失败不能把其他周期全部拖住，也不能把未处理版本标记已完成。
5. 暂不把九周期维护改为只维护当前展示周期。那会影响首次打开、告警依赖和现有周期就绪约定，需要另行定义产品行为。

实施预计 F1。最有意义的比较是同样三条实时身份、同样确认事件和九周期产物，事务量、CPU 和确认到可判定时间是否改善。

长期运行还要核对 30 天窗口：[composite_aggregates.py:211](../../backend/alerts/composite_aggregates.py:211) 在 seam 早于实时可用下界时放弃物化读取；[composite_realtime.py:201](../../backend/alerts/composite_realtime.py:201) 同样放弃页面缓存。建议先验证现有基线影子准备与切换是否正常覆盖，不能直接删去保护条件；它防止展示已越过可用范围的输入。本轮没有证据表明开发实例已触发此条件。

## 5. 平台行情：快照清理和缓存命中后的成本

目录检索已在 SQL 中过滤、去重、分页，再只取当前页元数据：[instrument_directory.py:172](../../backend/alerts/instrument_directory.py:172)。不建议改成每次把全目录加载到 Python。

读取缓存、供应商租约、历史修订和指标前缀共享也已存在：[provider_cache.py:736](../../backend/alerts/provider_cache.py:736)、[provider_indicator_inputs.py:61](../../backend/alerts/provider_indicator_inputs.py:61)。当前问题不能概括成“加缓存即可”。

### 展示快照

[provider_display_snapshots.py:51](../../backend/alerts/provider_display_snapshots.py:51) 的 `publish` 对新快照或需要续期的快照：

- 获取全局事务锁。
- 加载整个 `provider-display:` 快照集合，在 Python 选过期和超限项。
- 写入本次快照。集合上限为 2048，属于有界扫描，但在新尾部和多图更新时反复发生。
- 锁号 `8675311` 与 [display_observations.py:17](../../backend/alerts/display_observations.py:17) 的临时分钟容量准入锁相同。平台快照清理因此与新临时分钟准入可能互相等待；不是每条普通报价都会进入容量准入。

建议保留价格与指标共享同一快照的合同，将过期筛选、排序和有界删除推到 SQL；普通发布走幂等写入，只在配额边界做必要串行化。清理可定期执行，但硬容量不能只依赖清理线程。若拆分锁，需先确认两个独立容量约束不依赖彼此，并做并发验证。

平台全周期原生路由、qfq 与不复权身份、错误 OHLC 审计隔离继续保持。本项改善主要在有图表请求时；没有平台请求时，不应把它当作当前空闲 CPU 来源。

### 自建/组合共用的历史块读取

[history_artifacts.py:383](../../backend/alerts/history_artifacts.py:383) 每次读取产物块都会解压、校验并解析；相邻拖动、多图和指标可能读取同一块。可添加按数据库身份、产物块 ID 和校验和索引的有界解码缓存。

缓存命中前仍执行发布版本和回收保护校验，不允许已回收内容因内存命中继续可读。已有生成侧 `_page_input` 缓存不等于此读取侧已缓存。先测解码占比，再决定缓存大小，避免为了 CPU 无上限增加内存。

## 6. 持续后台成本：到期调度和报价事务

### 历史调度

[history_versions.py:408](../../backend/alerts/history_versions.py:408) 一个 tick 会检查多个角色；网络与计算两个循环无工作时各以 5 秒等待兜底。当前已有通知唤醒，不需要再新增一套通知系统。

建议共享一次轻量到期发现，根据每日维护、重试、租约和产物准备的最早时间决定下一轮等待；新任务仍由原提交通知立即唤醒，丢提示或重连仍有有界扫描兜底。健康心跳保持单独约束，不能因工作长睡眠被误判故障。

这项直接面向无人使用时的固定开销。先区分真正待办和空扫描，避免只把所有 `wait(5)` 换成更大的数字。

### 报价持久化

[test_pricing_transaction_cost.py:11](../../backend/tests/test_pricing_transaction_cost.py:11) 已约束无活跃价格规则、完成 handover 后的正常稳态：4 SELECT、4 UPDATE、1 flush、1 commit。分钟切换、续租和活跃价格规则会有额外开销。本轮未重新运行该测试。

因此，建议将报价优化放在上述重复工作之后：

- 先测 [price_alert_inputs.py:48](../../backend/alerts/price_alert_inputs.py:48) 的 `has_consumers`，确认是否值得将价格规则分类变成精确 SQL EXISTS，避免逐报价加载规则 JSON。该字段化或谓词调整必须保持完整价格规则判定。
- 保留 owner/epoch、dataset 锁、首个规则注册与下一条报价的顺序保证。
- 继续每条接受报价独立提交，保存中途穿越、分钟高低点和告警输入。
- 不建议先做跨事务“无告警”TTL 缓存、报价降采样、批量延迟提交，或移除 Instrument 镜像字段。这些方案影响更广；收益尚不足以支撑额外复杂度。

历史记录 [pricing 验收](../plans/pricing-optimization-evidence-20261112.md) 中的 CPU 是 2026-11-12 的旧测量，不是 v2.0.9 本轮实测。此文不承诺可以达到单核 3%，也不预估未经测量的下降百分比。

## 7. 一致性和个人维护成本

[ManagedMarket.tsx:83](../../web/src/market-data/ManagedMarket.tsx:83) 的来源筛选未列出 akshare，资产筛选缺少股票、基金和期货，聚合日界筛选也只有 NY17/UTC0。后端已有对应自建模式和 source_date 身份，界面筛选能力落后于实际模型。

建议让前端筛选选项来自后端已支持或当前可用的元数据，补齐现有能力；不要因此放开尚未接入的来源和周期。平台、自建创建和维护页面共享“来源 × 模式 × 周期 × 复权”的能力查询，减少散落白名单。不同模式的策略仍保留各自边界，不将三类行情强行合并为通用大类。

这是功能可发现性和维护一致性改进，不是显著 CPU 优化。

## 8. 后续验证建议

每项分别修改、分别比较，避免一次重构全部行情系统：

| 改动 | 最小有效证据 |
|---|---|
| 列表摘要、批量刷新 | 1/5/10 页请求次数和 SQL、首屏与返回时延；筛选成员变化、版本和详情一致 |
| 原生历史合并 | 相同历史输入、跨月和历史修订；结果与清单一致；解压次数、CPU、内存及事务时长 |
| 组合多周期共享 | 固定确认输入，九周期 OHLC/覆盖事实/版本一致；旧修订、断线补齐、单周期失败；SQL 和就绪时延 |
| 平台快照 | 价格与指标同快照；过期/修订拒绝；并发容量上限和清理；多图 P95 |
| 历史块解码缓存 | 冷热读一致；内存上限；回收并发后不可继续读取；拖动时解码次数 |
| 到期调度 | 新任务立即唤醒、未来重试、丢通知恢复、健康与停止；同窗空扫描数 |
| 报价路径 | 相同报价逐条回放；首规则注册并发；回滚、重连、分钟 OHLC、穿越告警和提交 P95 |

如进入实施，按仓库要求使用独立 Ubuntu Docker 验证环境，重要持久化与 worker 链路按 F1 验证。性能窗口分为无浏览器/无告警但保留三条连接、活跃价格告警、单图、多图和历史维护五类。记录同窗报价数、确认输入与产物数、服务 CPU 秒、SQL 和事务数；相同输入回放才用于判断代码收益。一次性定位开销可使用已有工具，无需为个人项目新增独立监控服务。

## 9. 产品命名建议：将“平台行情”改为“原生行情”

当前“平台行情”的实际含义是供应商直接提供其支持周期的原生 K 线。新浪、腾讯 A 股八周期及腾讯港股 D/W/M 直接使用供应商周期，并非本应用把更低周期重新聚合；OANDA 等也由各自原生能力提供周期。

候选：

| 名称 | 准确性 | 局限 |
|---|---|---|
| **原生行情（推荐）** | 明确周期与 OHLC 来自供应商原生返回；与自建派生周期相对 | 首次使用者需要在详情看到来源说明 |
| 供应商行情 | 明确数据来源在第三方 | 不强调周期未在本地聚合 |
| 直连行情 | 强调直接获取 | 可能误解为浏览器直连 |
| 平台品种 | 适合目录 | 不描述价格序列如何形成 |

建议主标签采用 **原生行情**；详情和图表来源行继续显示 `新浪 / 腾讯 / OANDA`、原生周期、复权口径及缓存状态。英文内部 `provider` 先保留。换的是产品术语，不是数据集身份。

“原生”不是“不复权”或“保证实时”；原生行情可能包含供应商提供的前复权、延迟或有限历史。自建也能保存原生周期，所以两个入口的根本区别是 **直接浏览供应商数据** 与 **由用户建立并维护版本化数据**。若用户更偏好非技术措辞，“来源行情”是另一个可选名；“原生行情”更能体现此前强调的原生周期直取要求。用户已认可“原生行情”作为替代名称，当前仅记录决定，未修改现有业务标签。

## 10. 产品模型建议：自建行情提供可选“实时接续”

### 代码与用户目标的对应

- 自建身份、来源绑定、维护计划和不可变历史版本已经属于 `MarketDataset`、`DatasetMaintenance`、`HistoryVersion`。
- 实时映射本来就是自建数据集的子资源，以 `RealtimeMapping.dataset_id` 关联自建数据集，并记录历史品种与实时品种的产品关系。
- 通用实时开关按历史 `Instrument` 打开或关闭，接口文案已经写明“仅适用于自建行情”。
- UI 仍把组合列表设为独立主分区，详情另有“组合与引用”页面，候选、映射、基线、拼接点和组合修订形成另一套入口。这是概念分裂的主要来源。

### 推荐的产品概念

只保留 **自建行情** 一个管理主对象。它表示历史数据集、来源、复权、周期和版本。详情中提供一个显式可选扩展：

> **实时接续：关闭 / 开启**  
> 来源：OANDA Practice · EUR_USD  
> 历史与实时品种的对应关系已核对

用户流程收敛为：选择历史品种 → 创建自建历史 → 按需维护周期 → 主动打开“实时接续” → 选择并核对实时来源 → 自建图表在固定历史基线上显示确认尾部和临时观察。

实时接续关闭时，自建数据仍可独立用于历史查看、研究和固定版本回测，不创建实时订阅。关闭应停止新增实时采集需求，不删除已确认接续输入、映射、审计或已保存告警。再次启用从当前基线与已记录尾部恢复，不重写过去告警证据。

关闭的是该自建行情对共享来源的需求，其他数据集或原生图表可能继续使用同一来源。依赖该扩展的告警须显示“实时接续已关闭，暂停判定”，已有提交输入的必要结算保留；开启后重新建立有效价格基准，不把关闭期间跨越阈值误报为当时实时触发。具体规则恢复沿用既有告警生命周期，不能无条件批量恢复所有规则。

暂停每日历史维护和关闭实时接续必须是两个开关：前者影响历史版本更新，后者影响实时尾部采集。

建议只保留一条自建列表记录，例如 `EURUSD · Dukascopy · NY17`，同一行显示 `历史可用至…` 与 `实时接续：运行中`。详情包含“概览 / 历史维护 / 实时接续 / 发布版本 / 引用”，原有映射核对、基线与接续修订迁入“实时接续”页；不要求用户再创建一条独立“组合”。图表可标为 `EURUSD · 自建 · 实时接续`，来源详情明确 `历史 Dukascopy / 接续 OANDA`，不能只写历史来源而隐藏实时价格来源。

首次点开启时，未配置就进入来源选择与核对，完成后创建或复用已有接续配置并记录开关。配置失败保留原历史可用；普通浏览或展开详情不启动采集。开关表达用户意图，旁边的状态表达实际情况：准备中、运行中、闭市、异常、已关闭。开关已开不等于已就绪。

这种收敛首先减少入口、重复列表与维护路径，不自动减少实际行情计算。此前四项性能优化仍需独立实施和测量，不能把 UI 改名当作 CPU 优化结果。

### 数据与身份迁移边界

建议分层收敛，避免以改名为由做大范围迁移：

1. **先收敛入口和术语。** 把实时映射、健康和开关放进自建行情详情；组合修订作为高级诊断/审计展开项。候选不再作为独立用户业务类别。历史 `MWC:`、保存的告警配置和旧路由保留读取兼容。
2. **将图表表达成自建数据集的显式视图。** 默认“打开图表”在接续已开启且选定配置时进入接续视图；“发布版本”里始终可打开固定历史。已打开或已保存的接续视图在关闭后保留确认尾部并停止更新，不能静默换成最新历史，造成价格和指标跳变。固定版本图表也不能因开启接续而自动切换。历史基线、接缝和输入修订仍保留版本证据。
3. **保留底层映射、组合修订与独立运行状态。** 它们表达来源匹配、固定基线、接缝和告警回放证据。第一阶段不合并表、不重新生成身份、不迁移 ChartAlert version、不删除 `MarketComposite` 或 `CompositeRevision`。
4. **稳定后再评估图表身份统一。** 新保存工作区可采用“自建数据集 + 实时接续选项”的显式身份；旧 `MWH:` 发布版本、`MWC:` 组合及 API/MCP ticker 继续解析原对象。不要把组合运行时身份直接重用为发布版本身份。

### 边界场景

**能力限制不是增加开关就能消除。** 当前映射校验只放行明确支持的 Dukascopy/OANDA 历史与当前 OANDA Practice Bid 产品组合：`EUR/USD → EUR_USD`、`USD/CAD → USD_CAD`、`XAU/USD → XAU_USD`，以及当前账户 OANDA 同品种路径。黄金明确记录跨来源产品差异。其他历史来源、股票/期货、D1 基础与原生周期数据集不能仅因同属“自建行情”就显示可用开关。应由能力接口返回 `supported`、`reason`、当前配置和可选来源。

同一个自建数据集可有多个映射与接续对象：`MarketComposite` 的身份包含 `dataset_id + mapping_id + rules`。建议普通操作只选择一个“默认接续配置”，其余保留在高级配置与历史引用里；不要自动取第一条或合并旧对象。现有实时开关作用于该数据集下相关接续修订，需要明确这一范围。逐配置独立启停属于新的后台调度行为，另行评估。

| 场景 | 统一产品概念的显示 |
|---|---|
| 未启用实时接续 | 固定历史周期、最后发布版本；无实时订阅 |
| 已配置但关闭 | 已核对映射与关闭状态；显示已保存确认尾部，不收新观测 |
| 开启但闭市 | 历史与确认尾部可读；显示闭市，不报采集失败 |
| OANDA 账户变化 | 保留旧映射作审计；重新核对当前账户，不能静默换品种 |
| 历史每日发布新版本 | 发布不原位改写接续基线；经基线切换流程校验并产生新修订，保留既有自动切换能力 |
| 一品种多日界或多数据集 | 每个数据集有独立开关和映射，不能按裸 symbol 全局切换 |
| 删除或回收历史版本 | 先检查工作区、告警、组合修订和派生引用，不能绕过回收保护 |

### 结论

建议用户术语为 **原生行情**、**自建行情**；不再把 **组合行情** 作为并列主类型，改称 **自建行情的实时接续**。审计文本使用“接续修订”“历史基线”“接续来源”和“拼接点”。底层可以继续保留 `composite` 作为实现术语和兼容协议。

这会把用户认知从“三种互不相干的行情对象”调整为“原生读取，或创建可维护的自建数据；自建数据还可选接续实时来源”。它与当前 `RealtimeMapping` 和 `realtime_switch` 的代码归属更一致，也保留组合修订解决的追溯问题。

用户已认可本节产品方向并要求记录；这不是迁移任务书或实施授权。若先做 UI 收敛，预计 F0/F1 混合：主页面与旧路由为 F0；共享图表身份、告警引用、MCP 或数据结构调整为 F1。应先定义图表解析与旧 `MWC:` 兼容合同，再实施。

## 11. 自建行情的替代名称（讨论归档，保留原名）

用户认可前述产品方向后，继续询问“自建行情”是否有更适合的名称。当时新增推荐候选为 **行情库**。用户随后决定维持 **自建行情**，本节保留取舍记录，不再作为待决项。

这个对象长期保存和维护来自明确供应商的行情，提供周期、不可变发布版本以及可选实时接续；“行情库”更强调持续使用的资料资产，能够同时覆盖固定历史与实时扩展，也不暗示行情价格由用户自行编造。

| 名称 | 适合之处 | 局限 |
|---|---|---|
| **行情库（推荐候选）** | 强调建立、保存、维护和复用；可以自然容纳历史版本和实时接续 | 单独看名称不能表达所有维护能力，需通过页面内容说明；也应与只保存品种列表的自选区分 |
| 自建行情 | 与当前叫法一致，能表达用户主动建立和配置 | 容易让人联想到自行生成价格；较强调创建动作 |
| 托管行情 | 突出建立后由系统定期维护 | 可能误解为第三方云托管或收费服务 |
| 定制行情 | 突出周期、日界和来源配置 | 容易误解为公式合成、价差或自定义指数 |

“本地行情”会额外承诺数据所在位置；“历史行情”不能覆盖实时接续；“自有行情”容易暗示数据权属，因此均不优先。

推荐入口为 **原生行情 / 行情库**。进入行情库后，一条记录仍称“行情数据集”，例如 `EURUSD · Dukascopy · NY17`；使用“新建数据集”“历史维护”“实时接续”“发布版本”等操作。行情库表示集合，数据集表示单个管理对象，实时接续表示可选能力，自选只是品种引用列表，不保存或维护这些历史版本。

若要求两个标签形式一致，并希望尽量少引入新词，继续使用“原生行情 / 自建行情”也合理。最终决定保留“自建行情”；下列取舍为讨论记录，不修改代码或接口。
