# M1 与 Python 指标连续刷新修复方案

依据 [根因记录](chart-reload-root-cause-20261013.md)。本文为实现方案，除已完成的准备提示静默改动外，尚未实施业务修复或生产部署。

## 目标与边界

已接受的同源临时 OHLC 不因报价年龄达到 15 秒或跨分钟而消失。来源新鲜度、连接有效性、REST 确认及覆盖仍分别判断。固定历史、固定 input_revision 查询只返回已确认输入；不填造空分钟，不让临时观测成为确认告警依据。

## 1. 持久化待确认的实际分钟观测

当前 LiveState.forming 是单槽位，适合最新分钟，不适合 REST 确认前的分钟队列。引入以 dataset / connection epoch / minute start 标识的有界观测存储，保留原始 OHLC、来源/接收时间和完整性证据。跨分钟时把已接受 forming 移入待确认区，再创建新 forming；无新报价超过 15 秒时，保持此前观测，更新新鲜度状态。

不要把所有 tick 再写一次独立表：最新分钟继续沿用已有 forming 发布事务，主要在换分钟保存已结束的观察快照。跨进程读必须从共享持久存储获得相同结果，不能只让 CurrentBuckets 或浏览器保存副本。重启、初次登录和刷新都需重现相同分钟集合。

待确认分钟不能因时间流逝标 complete/source_confirmed/coverage_complete=true；volume 仍 unavailable。保留真实观察到的分钟，未观察到的时间仍为 gap。图表有界读取，确认后只在固定输入与指标计算已能接手时释放临时副本；长期未确认进入显式降级与补采路径，超过资源边界应有明确状态，不能静默删柱造成回退。

来源、账户、修订和连接世代均须绑定。旧世代观察可以作为明确标识的过去观测留存，不能拼成当前世代 forming，也不能恢复 current quote_ready。新来源不得继承旧来源临时 OHLC。

## 2. 统一图表读取和 REST 交接

composite_chart、composite_series 和 CurrentBuckets 使用同一套观测合并规则：选定 input_revision 中的确认分钟优先，缺少确认的实际临时观察其次，当前 forming 最后。去重键为实际来源分钟，不以高周期标签推断身份。全部周期按既有日历聚合，HTTP、分页和 SSE 尾部结果一致。

REST 交接要以组合固定输入实际可见为准，不能仅在源 Bar 写入时移除临时副本。一个读快照内完成“确认替换临时”，允许权威 OHLC 改动但分钟不能中间消失。涉及 H1/H4/D1/W1 时重新聚合受影响桶；不能把旧极值只做 max/min 合并，因为 REST 修订可能缩小高低点。

## 3. 临时指标链必须同步扩展

fixed_indicators.chart_results 当前临时支路只处理一根柱并 break，IndicatorState.step(provisional=True) 每次从相同确认状态复制试算。因此单独增加临时分钟队列，会让后续 Supertrend/EMA 丢失递归前序。

从已确认检查点复制出独立的临时工作状态，按时间依次计算所有待确认分钟和当前 forming。推进的是副本，固定 run/checkpoint/output 保持不变。REST 改变某个已预览分钟时，从该分钟之前有效的确认检查点重算受影响后缀，生成新的展示批次；不得把临时 checkpoint 写回确认状态。已结束但未确认的观察仍明确不完整，可用于图表试算，不用于确认告警。

尾部输入、固定修订、参数、计算起点和世代变化均进入版本标识。迟到响应在版本不符时丢弃，避免旧结果覆盖新结果。

## 4. 按事件原因处理，避免全量指标清空

区分普通形成柱更新、确认交接、真实历史修订和来源身份变化。图表库常规 subscribeBars 回调仅能更新最新柱/追加，不能直接提交时间早于最新柱的 REST 修订；禁止仅删除 reset 分支或对旧柱强行回调。

先保留正确的公共历史重载路径：已经在显示中的较早临时柱被 REST 修订时，若 OHLC/相关输出确有变化，做一次受控历史刷新。同价且身份/显示元信息可正确交接时减少多余刷新。普通新 tick 不做整图 reset，15 秒无报价只改新鲜度。

指标通道已有 replaceRange，可替换受影响的后缀；但 Supertrend 是递归指标，范围必须覆盖依赖后续，不能只替换被修订那一根。price 与 study 对同一输入版本绑定。真实修订无法即时提供新结果时，明确失效相关范围，不能让旧指标继续表现成新价格的有效结果。source/params/origin 改变保持完整失效。

若受控公共 reset 仍造成明显闪烁，再验证主价格序列的受控 snapshot/尾部替换适配，以原子方式发布价格和匹配指标、保留视区。现有私有适配只针对指标；主价格替换必须单独验证固定 v31 契约，不宜直接扩展假定可用。没有完成这一验证前，不能承诺像内置指标一样零闪烁。

## 5. 告警及自选报价隔离

quote_ready 与 15 秒新鲜度判断保留。报价过旧时实时报价/告警按既有规则降级；显示历史观测不等于可用实时价。固定收盘告警仍以 REST/source-confirmed 输入和原生确认凭据判断，保留此前稀疏 D1 修复。自选表显示来源状态与最后更新时间，不能为了图表稳定把过旧报价改为 ready。

## 验证与交付顺序

1. 准备提示静默作为小改动，保留 error/retry；已本地 build 和 JSX 验证。
2. 在独立 Ubuntu worktree/实例完成观测生命周期、确认交接、多临时柱指标试算和事件分类，先把诊断红用例变绿。
3. 验证：跨分钟；REST 延迟 5/20/90 秒；16 秒无新报价但心跳正常；真正断线和恢复；REST 修订缩小极值；真实历史修订；缺分钟；多图/多用户；API 与 worker 重启；来源/参数/世代切换；迟到响应；固定 input_revision 隔离；D1 稀疏确认与告警不补发。
4. 使用真实 Chromium，在包含多个整分钟边界的至少 10 分钟窗口记录价格和指标时间线。要求普通 tick 不触发 reset、同源未确认观察不消失、M1 不回退、Supertrend 有效结果不反复归零；确认修订结果与完整重算一致。真实修订的受控失效单独记录。
5. 通过后提交可审查实现，再按发布授权推 tag/部署；生产发布前后固定对照同样指标。不存在开发实例转移到 unraid 的步骤。

建议先完成共享观测与计算正确性，再评估主价格原子替换；同时做二者会放大改动，难以区分生命周期错误和原生适配错误。
