## 排序与黄色竖杠：初步调查记录（后续结论见 05–06）

用户询问列表靠前的黄色竖杠是否表示级别、是否因级别而置顶。后续用户明确：同一地址 `?panel=notifications`，换电脑/浏览器仍有约十几条，涉及今天 15 点、16 点。**此前直接把用户所见黄色条目判为本机待同步，证据不足；以下只是当前实现的代码含义，尚不能认定就是用户所指条目。**

当前核对结论：

- 黄色竖杠来自 `.nc-pending`，表示本机记录尚未成为服务端正式历史条目，不表示 warning 级别。具体文案分别是“仅本机待同步”“服务端已接收，等待投影”“服务端拒绝，本机证据保留”。
- 页面先渲染本机待同步/待投影/被拒绝证据区，再渲染服务端历史，因此这些条目会单独排在正式历史之前，未与历史按时间混排。其显示未套用服务端历史相同的筛选逻辑，这是现状观察，不在本次自行修改。
- 正式历史按 `occurred_at` 倒序（相同时间按事件 ID 倒序稳定排序），不按级别或未读优先。重复事故合并后选最新接收的代表事件，再按该事件发生时间排序。
- 核对依据：`Panel.tsx` 的 `pending.map` 位于 `rows.map` 之前；`notifications.css` 的 `.nc-pending` 左边框；`notification_center.list_events` 的排序条件。
- 本次 Playwriter 会话检查时黄色条目数为 0；用户会话可能保留其浏览器本机同步证据，不能据本会话没有黄色条目断言用户界面不存在。

- 用户浏览器 pending 数据是独立 IndexedDB，本会话无法直接读取。要定位具体条目，需先确认黄色条目下方状态文案/标题；不凭颜色猜测原因、不清理用户本机证据。

## 05 旧同步游标失效导致本机消息持续积压

**状态：已授权并修复；原始浏览器证据保留，不清理用户现场。**

### 已取得证据

- 用户[截图](verification/notification-joint-review-20261019/05-user-pending-109.png)明确显示黄色条目为“仅本机待同步”，底部“连接受限，本机待同步记录保留 · 109 条本机记录”。此前仅凭本会话无黄色条目，未能定位用户状态；以截图为准。
- 截图时区是 `Etc/UTC`，其中 `08:40:21 UTC` / `07:38:42 UTC` 对应北京时间 16:40:21 / 15:38:42，并非事件日期或小时异常。
- 最近 1 小时服务端日志限尾样本中，同一个变化流游标反复返回 400 共 113 次。只读验签确认该游标可解析、类型为 changes，但签名及 epoch 均与当前 stream 不符，seq=276；当前 seq 在检查时为 2176。未输出或归档游标、密钥、cookie。
- Playwriter 用日志中的旧游标发起只读 GET，返回 **400 “无效通知游标”**；获取当前历史基线后用新游标请求返回 **200**。投影健康 ok、pending_sources=0。见[脱敏诊断结果](verification/notification-joint-review-20261019/05-cursor-diagnosis.json)。
- 隔离 VM 运行当前真实 NoticeRuntime：旧游标连续 3 轮 400 后，本机上传尝试 **0 次**，待上传状态不变，底部文本与截图完全一致；仅在该隔离 VM 重新建立基线后，同条上传到 accepted。期望“自动恢复”的断言在现有代码中如期失败。临时命令：在 web 目录运行 `node /tmp/mw75-invalid-cursor-loop.cjs --expect-recovery`。
- 日志没有浏览器身份，不能据此声称已把该旧游标逐一绑定用户的所有 109 条记录；但失效游标→循环提前退出→本机上传饥饿这一缺陷已复现，且与截图症状高度吻合。

### 原因与建议修复范围

- 同步循环先读取 `/changes`，后上传本机记录。旧签名在服务端验签阶段被判 400；前端只对 `409/NOTICE_RESET` 自动重建基线，400 则当普通连接错误退避重试同一游标，于是长期跳过后续上传。
- 即使网络和当前服务端都健康，保留旧进度的浏览器仍可能持续积压；其他会话/先前已成功上传的记录仍能在正式历史显示，因此出现一部分已同步、一部分未同步。
- 后续应针对**明确的变化流游标失效**建立可识别的恢复契约，重新取得基线及消费进度；不能把所有 400、认证失败或内容拒绝都一概当游标失效。
- 本机待上传记录继续持久保留，恢复后幂等重试；不要要求用户清缓存，不丢失未确认交易告警，不因历史重新读取而批量追弹/响铃或自动确认。
- 需要减少变化流读取失败对本机上传的长期阻塞；同时保存可诊断的错误阶段，避免只显示笼统“连接受限”。上述方向已获统一授权；实际实施和验收见文末执行记录。
