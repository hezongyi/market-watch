# 修复是否减少慢首屏：144 样本配对对照

2026-10-02，以 v1.3.0 和 `c26deca` 修复实现进行同条件 A/B。**双图并发加载
有明确的局部收益；整体超三秒率虽下降，当前样本不足以确认总体概率显著下降。
单图未显示改善，修复版最慢尾部也没有消失。**

## 主要结果

“慢”定义为导航到原生公开 `dataReady`、再两帧的时间 ≥3000ms；显示失败也
计为慢。每版 72 次，全部成功取得完整首屏数据，没有删慢样本，没有失败或
数据有效性异常。每版 36 单图、36 双图；两家供应商和九周期各重复两轮。

| 场景 | v1.3.0 慢首屏 | 修复版慢首屏 | 相对慢率下降 | 配对检验 p |
| --- | ---: | ---: | ---: | ---: |
| 全部，单图/双图各半 | 21/72，29.17% | 14/72，19.44% | 33.3% | 0.1435 |
| 单图 | 5/36，13.89% | 5/36，13.89% | 0% | 1.0000 |
| 双图，同源不同周期 | 16/36，44.44% | 9/36，25.00% | 43.75% | 0.0391 |

整体下降 9.72 个百分点，配对 bootstrap 的 95% 区间为下降 20.83 到 0.00
个百分点，包含无改善。主要终点的 exact McNemar p=0.1435，不能声称已证实
整体慢概率显著下降。双图下降 19.44 个百分点，区间为下降 33.33–5.56，
原始 p=0.0391；这是预先区分的场景，但子组检验未作多重比较校正，不将其
解释为独立的大规模线上验证。

| 首屏耗时 | v1.3.0 | 修复版 |
| --- | ---: | ---: |
| 全部 P50 | 2385ms | 1950ms |
| 全部 P90 | 6493ms | 4130ms |
| 全部 P95 | 6860ms | 7553ms |
| 全部最大值 | 7156ms | 8340ms |
| 单图 P50 | 1777ms | 1820ms |
| 双图 P50 | 2652ms | 2096ms |

整体配对平均快 527ms，bootstrap 95% 区间为快 113–925ms。双图配对平均快
1127ms，区间为快 609–1604ms。单图平均慢 73ms，区间跨零，不支持改善或
恶化的确定判断。P95 和最大值在修复版更差，不能用 P50/P90 的改善掩盖尾部。

## 是否减少了重连

这里只观察**首屏 candles 请求中的 TCP/TLS 建连**，不把启动预热本身的连接
算成用户等待；启动预热等待在 API ready 前，不包括在导航秒表内。

| 导航中至少一次冷建连 | v1.3.0 | 修复版 |
| --- | ---: | ---: |
| 全部 | 41/72，56.94% | 24/72，33.33% |
| 单图 | 5/36，13.89% | 10/36，27.78% |
| 双图 | 36/36，100% | 14/36，38.89% |
| OANDA 双图 | 18/18，100% | 0/18，0% |
| Binance 双图 | 18/18，100% | 14/18，77.78% |

双图 36/36 都有真正重叠的首屏 API 请求，修复版 36/36 也都有重叠，确认
不是通过序列化取数避开第二条连接。OANDA 双图中位数由 2470ms 降至
1907ms，冷建连 18 次降至零，与连接预热的实现目标一致。

原日本02链路下 Binance 的修复版仍频繁新建连接；单图新建次数反而由
5/18 增至 10/18。启动总预算仍为四秒，两条预热必须在预算内完成，代码对
ConnectError/ConnectTimeout 会轮换池，后续后台恢复也受额度和超时约束。
本次没有采集每次 HEAD 的阶段 trace，**不能仅凭首屏 trace 确定每次重新
建连是启动失败、远端主动关闭或其他恢复路径**。但足以否定“修复后所有
连接都热”或“所有首屏重连都更少”的说法。

## 同条件设计与证据

- 两版分别固定到同一 API 镜像 ID：基线 `5f3ebe…`，修复 `56a233…`，完整 ID
  见 [预定设计](verification/provider-latency/ab-statistics/design.json)。基线 tag
  v1.3.0 的文档提交与实际构建源码之间产品行为一致，沿用已接受镜像。
- 两版均使用本机 Mihomo v1.19.31 固定**原日本02**和美国01出口，保持原
  DNS/嗅探配置、协议和目标入口，未换更快的 VMess 节点，未改 Unraid 选择器。
  由此隔离本次代码修复；不是拿更快出口加修复与旧出口作比较。
- 同一浏览器进程、相同静态资源缓存、同一前端和授权 chart 库、同一隔离
  数据库 `market_watch_provider_fix`。相同 CPU=1、512MiB、DB pool=1/overflow=0。
  原基线 worker 仍运行，没有增加 managed worker、构建镜像或并行跑浏览器。
- 每次样本关闭图表、停止隔离 API、清空该数据库 provider 缓存、以指定镜像
  重建 API、等待 ready，然后开始导航计时。准备耗时原样存于 `setup_ms`。
  样本考察的是**启动预热后的冷缓存首屏**，没有统计服务启动总时长，也没有
  统计闲置 60 秒后的概率；闲置保活另由真实 TCP 时钟回归证明。
- 每个配对使用同样的品种、周期、原生保存布局。单图为新 widget；双图用
  公开 widget API 生成并保存的两图布局，同源相邻周期，区间/周期同步关闭。
  没有修改 vendor 或拦截行情、缓存静态资源路由。原生 countBack 保留。
- 每个品种/周期/场景两轮，第二轮逆转先后顺序，基线先和修复先各 36 对。
  总计 72 对、144 次导航，采样约 30 分钟。每个首屏请求必须 cache_hit=false，
  有完整 countBack 或提供商边界证据。144 样本全部通过数据有效性检查。

[原始记录](verification/provider-latency/ab-statistics/raw.json)保留每条请求的
状态、countBack、cache_hit、完整根数、网络阶段和原生布局信息。
[统计汇总](verification/provider-latency/ab-statistics/summary.json)包含供应商、
场景交叉分组、Wilson 95% 慢率区间、exact McNemar 和配对 bootstrap。
P50/P90/P95 使用 nearest rank；bootstrap 固定 seed、10000 次、按
供应商/场景分层抽取配对，未改结果符号或排除不利样本。

统计区间仍假设配对相互独立；同机同路由短时段存在网络相关性。单图/双图
各半是实验权重，未知真实用户的场景占比，因此 29.17%→19.44% **不是线上
用户慢率估计**。要确认线上总体降幅，需要按实际使用比例在多时段/多主机
重复采样；本次不能外推为“概率一定降低三分之一”。

复现工具：`scripts/provider_latency_ab_fixture.py` 只操作固定隔离 Compose
项目和写死的隔离缓存 profile；`web/tests/advanced-provider-latency-ab.browser.cjs`
驱动浏览器；`scripts/summarize_provider_latency_ab.py`只统计原始记录。
结束后已恢复隔离项目的修复版镜像和之前独立 VMess/美国01出口配置，未更改
原 v1.3.0 项目或共享代理。

## 本轮结论

本次统计支持**两图并发加载通常更快、前台冷建连明显减少**，尤其是 OANDA
稳定链路。它不支持单图明显提速，不支持所有场景慢概率已经显著下降，也不
支持原日本节点长尾已经解决。若用户主要使用多图并发，这个修复有实际收益；
若主要打开单图，当前证据不足以承诺“大幅提升体验”。
