## 1. 目标与范围

让无输入变化、无可运行任务的发布 worker 进入低开销等待；发生变化时只处理受影响数据，同时保持快照、覆盖、修订、告警和故障恢复的正确性。建立 Ubuntu 开发/验收实例的归属、资源预算和停止流程。

本期包括旧 managed 发布链路、覆盖读取优化、必要的迁移与性能观测、开发实例清点。API 高 CPU 独立归因；只有证据直接支持的重复工作才纳入修复。三层行情业务重构由其现有任务负责，本方案只规定兼容与集成边界。生产发布、生产配置变更和资源删除仍需明确授权。

## 4. 发布结果与调度设计

### 4.1 显式结果

以结构化结果替代模糊布尔值，字段名称在实现时可调整，语义固定：

| 结果 | 定义 |
| --- | --- |
| snapshot_changed | bar 内容、观察元信息、覆盖边缘或读者可见初始化状态发生有效变化 |
| task_progressed | 消费任务、推进检查点或完成初始化；允许处理无差异任务而不改快照 |
| runnable_remaining | 当前仍有符合条件且未受聚合/重试阻塞的工作 |
| next_due_at / blocked_reason | 最早到期时间、等待来源或失败重试原因 |

检查过某个目标不算进展；任务记录存在不等于可运行。保持既有内容 revision / 历史修订合同，任务确认、心跳不能冒充历史价格修订。仅观察时间更新如何反映现有快照 revision，要先固定现行读者与告警合同，再决定是否需要独立元信息版本。

### 4.2 持久变化触发

沿用 PostgreSQL，建议增加按目标合并的发布状态（最终表名和迁移编号在 P0 确定）：目标身份、请求世代、已处理世代、原因集合、检查点、最早运行时间、失败信息。精确桶修订继续复用现有 `ChartPublicationJob`，无需新增外部消息系统。

| 输入变化 | 必须触发的工作 |
| --- | --- |
| 新建/恢复计划、扩大历史起点、旧数据纳管 | 初始化或历史边缘推进 |
| 新 M1、价格/量修订 | 对应源周期聚合及受影响发布桶 |
| 覆盖扩展或证据变化，即使没有返回 bar | 覆盖、完整性、初始化与相关聚合复核 |
| 聚合完成或阻塞解除 | 等待该源周期的目标重新就绪 |
| 仅观察时间变化 | 刷新对应价格快照的观察元信息，保持告警新鲜度 |
| 日历、来源口径、规则变化 | 按既有业务操作处理身份与失效，不静默混用 |
| 必要的收盘/到期时刻 | 对有证据的形成中桶复核；时间经过不能补出覆盖证明 |

调度循环从就绪目标中公平选择，每个目标每次工作有源行数/时间预算。实时、修订、回填均须获得服务机会，优先级结合等待年龄，不能让持续实时任务饿死回填，也不能让大回填拖住其他品种。

只有全局无就绪任务时才进行有上限退避，不对每个空目标单独休眠。根据最早到期任务缩短等待；若使用 LISTEN/NOTIFY，只作为唤醒提示，数据库持久状态是恢复依据，断连与漏通知由定时核对恢复。初版可先使用轻量、有界数据库轮询，轮询上限由延迟基线确定。

### 4.3 并发与恢复

- 写源数据与记录变化在同一事务提交；发布快照、计数、检查点及确认处理也在同一事务提交。
- 处理世代 g 期间出现 g+1，只能确认 g，不能无条件删除新任务。合并原因或区间同样必须避免清除并发新变化。
- 第一阶段保留既有品种锁及锁顺序，通过缩小读取范围缩短事务。只有锁等待实测仍是主要瓶颈时，才考虑锁外计算；该方案必须校验输入世代、覆盖和规则版本，变化时放弃旧计算。
- 崩溃前未提交的工作可重试，已提交快照保持可见；重复消费不得重复增加计数或制造修订。
- 异常与聚合阻塞按目标延后，失败目标不触发整个循环持续忙转。
- 保留分批低频核对用于新目标发现、旧数据纳管及漏标记恢复，记录核对耗时和扫描量，不在每轮执行全量纳管。

## 5. 增量发布设计

| 路径 | 工作范围 | 检查点 |
| --- | --- | --- |
| 初始化 | 从可发布近期数据开始，按页推进 | 初始化水位、已复制边界 |
| 历史回填 | 仅尚未发布且可连续接入的历史页 | 历史左边界 |
| 实时推进 | 新增数据与受影响的形成中桶 | 已处理输入世代和实时边界 |
| 历史修订 | 脏桶及生成它所需的完整源区间 | 修订任务及输入版本 |
| 观察时间更新 | 对应桶的匹配快照元信息 | 观察版本/时间 |

M30/W1/MN 读取目标桶的准确 M15/D1 范围，保留 DST、日界、周月边界和完整性规则。不要用固定分钟数替代日历桶，也不要将任意一个新观察时间附给未发布的新价格。

`BATCH=2000` 保留为现有上限参考，拆分实时/修订与回填预算；不得把上限当成每次必读行数。无变化目标不重读历史窗口、不重算高周期、不更新发布记录。

`complete_count` 按新增、完成状态改变及允许的移除做事务内增量更新；初始化和维护核对可使用全量统计。边界变化、空数据初始化、重复执行和回滚均需验证，不能简单累加本页根数。缓存按源数据、覆盖、规则及必要的观察版本失效，禁止仅以最大时间戳或 TTL 作为正确性依据。

## 6. 覆盖存储与迁移

优先复用 `market_data_coverage` 的来源隔离与区间能力；是否新增规范化区间投影，由 P0 的数据规模和查询计划决定。普通发布读取最终不应反复从审计 JSON 重建覆盖。

1. **对照**：按品种、source、basis 计算现有读路径与结构化路径的有效区间差集；包含历史缺少 range_start/range_end/source 的格式、重复区间和异常记录。
2. **补齐**：可重入、分批、持久检查点地补齐有效证明。遵守原始 received_at 的五秒安全余量和完整分钟边界，不以迁移当前时间延伸旧证明；异常记录隔离并报告，不猜测口径。
3. **并发一致性**：补齐期间保留新写入的双写；使用稳定扫描检查点与追赶步骤，避免并发插入落在已经扫描过的键范围而遗漏。按区间结果验证，不仅比较行数。
4. **验证与切换**：比较新旧有效区间及其下游 OHLC、complete、volume、初始化和 revision；一致后按完成标记切换读取。未完成目标仍使用兼容路径。
5. **控制增长**：按相同来源口径维护等价区间与覆盖版本；只合并重叠或相邻且语义相容的证明，不跨未知缺口。保留审计溯源，`observed` 等计数不能在重叠区间简单相加。

覆盖证明、实际观察、闭市、未知区间保持区别，沿用现行来源合同。覆盖移除/修正也须更新版本并触发依赖复核。

迁移采用加法方式。回退应用保留新表/列和审计，切回兼容读取；新旧 worker 不同时成为同一目标的发布拥有者。新代码确认任务若旧代码无法识别，回退前必须做就绪状态核对并补建旧代码可消费任务。迁移、升级、回退在 Ubuntu 独立 PG 库演练后方可进入发布准备。

## 7. API 与运行资源管理

API 内存在供应商预热、实时维护和告警线程，不能把无网页请求等同于进程空闲。按线程采样、请求流量、活跃订阅与告警数分解开销。

已发现 `chart_alert_worker.stored_rows()` 在 published 路径先计算 staging `chart_rows()` 再用 published 结果覆盖。可以作为独立小修复候选，需验证身份检查、历史起点、日历与观察时间一致，不能仅据此认定 API 高 CPU 根因。后台告警计算频率和历史扫描的进一步改造由测量决定。

2026-10-07 此候选已按准备期有实测依据的小范围修复实施：published分支直接read_rows，保留原身份/日历/标签/观察信息处理，普通managed分支仍chart_rows。真实stored_rows/evaluate缺陷探针先红后绿，staging读从每次1降为0，28个告警回归通过。[修复与原始证据](verification/issue-13/alert-read-fix.md)。尚未部署或证明现有API CPU收益，不属于P1–P3核心改造。

Ubuntu 本机 Docker 已通过 `sg docker` 验证可用；主机 `quant-server`，Ubuntu 22.04.5，4 CPU、约 16GB 内存。已有多组运行实例，容器名和运行时长不证明可以清理。

建立实例台账：Compose project、任务/issue、工作树、提交与镜像 digest、创建时间、端口、网络、volume、数据库、CPU/内存配置与实测值、保留原因、停止命令。核对实际 compose 标签和挂载，未知归属保留并列出待确认项。

本任务使用独立 project、网络、volume、数据库及空闲端口；环境脚本显式指定 project/compose/env，避免默认命名冲突。只启动当前实验需要的服务，通知投递关闭，重型浏览器验收默认单任务串行。单容器配额之外控制所有项目的总并发，生产与虚拟机 CPU 配置另行评估，不能直接套用固定配额。

任务完成先停止自己的后台服务；需要用户验收时登记保留期限与停止方式。删除只按明确 project/label 和核实归属操作，不执行全局 prune，不清理其他任务或生产资源。

## 8. 性能基线与验收合同

### 8.1 测量方法

在 Ubuntu 独立 PostgreSQL 实例上固定 schema、源码、镜像、数据种子、时钟/事件序列与配额；旧/新版本顺序运行相同负载，避免 A/B 同时争抢 CPU。记录其他任务与宿主负载，受明显竞争污染的样本单列并复测。

四类必测：真正空闲（无新观察）、实时更新（含同价新观察）、历史回填、区间内价格/成交量修订。至少覆盖 EURUSD、XAUUSD、BTCUSDT，以及不同周期；扩大到 10 个明确身份的合成负载用于公平性验证，不冒充 10 个真实供应商品种实测。

数据集包含空/稀疏区间、跨页历史和按 issue 表规模量级构造的负载，不读取生产数据目录。若使用已有备份，先核实授权与归属，恢复到 Ubuntu 独立数据库并保护敏感内容。

建议每场景预热后测量至少 5 分钟、重复 3 次；低事件频率场景延长至足够样本。记录冷缓存与热缓存边界。指标包括：

- worker/API/数据库 CPU，主机 load、内存、swap 的实际换页活动及 CPU throttling；Docker 100% 表示一个逻辑核。
- 每轮耗时、SQL 数、返回/扫描行数、覆盖审计查询次数、快照写入数、有效变化数与事务/锁等待。
- 队列年龄、各品种/周期最长等待、输入提交到发布可见的 p50/p95/p99、回填吞吐、API 和告警延迟。
- PostgreSQL 使用受控 EXPLAIN (ANALYZE, BUFFERS) 与查询统计，区分计划估计、实测行数和耗时。仅在本任务库上执行测试查询。

P0 报告必须在修改优化逻辑前填入数值目标：空闲 CPU/SQL 降幅、允许的发布/API/告警延迟、回填吞吐下限、最长目标等待和资源预算；依据基线及既有产品要求确定，不在看到修复结果后放宽目标。

### 8.2 不依赖硬件的通过条件

- 无变化且无到期工作时，除明确标记的低频核对外，调度只进行有界就绪检查，不调用完整历史发布、覆盖审计重建或写发布记录。
- 价格/量未变化而观察时间更新，仍正确维护匹配快照和告警新鲜度。
- 无差异任务消费后不再反复执行；失败、聚合阻塞和无数据初始化都有可恢复且不忙转的状态。
- 重复输入、重启及并发更新不丢变化、不重复计数、不把旧世代标为最新；各目标在规定等待上限内获得执行。

### 8.3 正确性矩阵

| 类别 | 必测用例 |
| --- | --- |
| 快照 | OHLC、volume/volume_complete、complete、计数、边界、revision 与初始化一致 |
