## 1. 本轮确认及优先级

本方案取代 `chart-progressive-history-plan.md` 中由首次打开/视区/缩放自动扩展维护目标、三倍D1窗口自动预热、由原生请求等待缺失历史补齐的产品规则。自建行情采用用户指定起点、从近到远分段补齐并分段开放，已完成段在相应周期达到首次开放门槛后可以先看，不等待全部历史完成。旧文档和验证结果保留为历史证据，不再按其冲突条目实施。

1. 新品种搜索默认平台行情；已有工作区保持原数据系列，旧记录映射自建行情。
2. 自建行情不足时只询问是否加入后台维护，不提供转平台行情的建议或按钮，不自动替换数据源。
3. 拒绝维护：不加载或显示该未准备范围。已有有效图表可保留，但不得冒充新请求的结果；首次打开则显示范围未准备状态。
4. 同意维护：只填写“历史补数起点”，系统补齐该起点至当前的数据，并持续维护后续M1及派生周期。无需填写截止日期，也无需另行开启持续维护。从最新已完成M1向历史起点倒序分段补数，每段完成覆盖检查、相应周期派生及发布后计入可用历史，各周期首次达到三屏完整K线及指标历史要求后开放，之后逐段扩大可查看范围；不等待全部历史补到目标起点。尚未准备好的段不输出K线。
5. 两类数据系列、画线永久隔离；以后也不提供相互复制画线。继续保持同一工作区、同一品种、同一系列跨周期共享，以及不同工作区隔离。
6. 平台行情支持现有周期与原生/Python指标；预警、演练保持使用自建行情。
7. 自建行情从用户指定的历史起点持续维护至最新，并生成相应周期。W1/MN/缩放/翻页不会把历史起点自动向过去扩展；时间向前推进产生的新M1必须自动维护，不受此限制。W1/MN使用起点以后的完整数据派生。

## 2. 两种数据系列

| 维度 | 平台行情 | 自建行情 |
|---|---|---|
| 用途 | 首次探索、快速分析 | 数据一致的分析、预警、演练 |
| 来源 | 提供商直接返回对应周期K线 | M1事实数据按项目日历/分桶派生 |
| 请求路径 | 原生getBars→本机后端适配→缓存/上游 | 原生getBars→已发布区间的本地数据 |
| 未命中 | 按请求分页取得相应周期，受控重试和取消 | 不自动向更早历史扩展；用户指定起点，后续持续维护 |
| 数据结束 | 确认提供商历史边界后结束 | 当前已发布历史的左边界；右端随实时维护持续更新 |
| 历史新增 | 按需缓存 | 从近到远分段完成，每段原子发布、逐步扩大可查看范围 |
| 周/月 | 上游对应周期 | 已完整D1派生；不偷偷扩展M1范围 |

品种和系列分开标识：例如基础资产XAUUSD，series_kind=provider/managed。原生ticker必须区分两种系列；具体编码由适配层确定，不直接复用无区分的ticker。缓存键至少包含提供商、账户环境或目录命名空间、基础品种、系列、周期、Bid/Ask/Mid口径及分桶配置版本。

画线、比较品种、Python合成指标、工作区保存和订阅标识都保留系列身份，不允许decode时丢失系列。现有旧ticker按managed解释，迁移不复制画线、不覆盖原保存状态。

## 4. 自建维护流程

### 4.1 指定历史起点，持续维护至最新

维护表单只填写“历史补数起点”，不设用户截止日期。确认文案示例：“从2025-01-01开始补齐历史，并持续维护后续行情”。选择日期按品种交易日界线解析，展示所选历史起点及NY17/UTC0时区口径，避免自然日与交易日混淆。

系统保存目标历史起点、倒序补数游标、持续维护状态、最新已完成M1水位和各周期已发布覆盖。历史任务从最新已完成分钟向过去分段推进，直到目标起点；若已有连续可用历史，则从其历史左边界向更早处仅补缺口。实时新增M1独立向前维护，优先级高于历史回填。任务内部仍可按[start,end)分段、UTC存储；分段结束时间只是下载游标或进度水位，不是用户维护截止时间。日历和DST复用既有来源与zoneinfo。

用户指定的历史起点不会因访问、缩放、周期切换而自动前移；用户可以明确改为更早起点，后台仅补缺口并合并重叠任务。右侧目标随时间自动延伸，新M1及各派生周期持续更新，不需要重新申请。

加入维护即持久化开启该品种的持续M1维护，不附加第二个默认关闭的开关。关闭图表、退出网页、历史下载完成都不停止实时维护；进程恢复后补齐中断期间缺口。只有用户另行明确暂停/停止该品种维护才改变持续维护状态，不能以取消一个历史扩展任务代替停用实时维护。

历史补数任务的优先级严格低于实时维护与实时补数。适用于所有已加入持续维护的品种，不能仅保障原有品种而把新加入品种的实时更新归为历史低优先级。

1. 最高优先级：实时M1轮询、新增已完成M1入库、断线/延迟造成的近期缺口修复、相关聚合及预警处理。
2. 较低优先级：从当前可用历史边界向用户指定起点的历史回填、历史覆盖检查和历史聚合。当前查看周期可以在历史任务内部优先，但不得超过实时任务。

实时与历史采用独立执行通道，并在共享的上游请求额度、HTTP并发、数据库连接/写入及聚合CPU资源上预留实时容量。历史队列只使用剩余预算，避免仅调整队列数字却仍然占满共享资源。实时修复积压时，减少或暂停提交新的历史分段；已经开始的有界请求/短事务完成后让出资源，不中断事务造成半写入。实时与历史相邻/重叠范围进行覆盖去重，不能让低优先级历史任务的预留阻塞近期实时修复。

历史任务不能因带有“修复”标签就自动升级为实时优先级：只有影响近期实时连续性的缺口属于实时补数；旧历史缺口仍按历史优先级执行。实际近期范围和资源配额依据维护调度配置与延迟验收确定，不能以修复名义把整个多年回填提升到最高优先级。

### 4.2 任务状态

每段状态：待执行→M1下载→覆盖核对→相应周期聚合→原子发布→更新各周期可用根数并判断开放门槛，然后继续处理更早一段。整体状态可以同时显示“部分可查看、历史补数中、实时维护中”。到达目标历史起点后仅历史回填完成，持续维护继续运行。

就绪判定不要求先到达目标历史起点：检查当前段及其与已发布近期历史的衔接，覆盖完整且相应周期派生完成即可发布。首次达到下述三屏门槛的周期便允许查看已完成范围；已开放周期后续每完成一段，可查看的历史左边界向过去推进。右端以已完成M1水位持续推进，不以不断变化的“现在”作为无法结束的初始化门槛。断段不得拼接成连续完整历史。

下载分段和图表周期桶不一定对齐。M1及已完整的各周期可分别就绪，不要求等MN完成才开放M5/H1。跨分段边界的H4/D1/W1/MN历史桶，必须等组成它的M1/D1覆盖齐全后才发布；不能为每段凑出高周期bar而输出不完整历史。当前正在形成的桶与这种缺失历史桶严格区分。

历史任务失败/取消保留已存M1、进度和此前已发布的各段；重试只处理缺口。某段失败不撤销已经能看的近期历史，也不能把失败段标为已就绪。取消历史回填不会隐式取消已建立的持续维护。关闭网页后任务和实时维护继续执行；目标起点、已补到位置、各周期可看范围、实时水位与失败状态分别可查询。

有合法休市/上游无成交的区间，不要求每分钟都有bar；必须依照实际查询覆盖和交易日历证明处理完毕。供应商最早历史不足时返回明确不可达范围，不伪造成功。

派生M5/M15/M30/H1/H4/D1/W1/MN。完整历史bar必须有足够的原始覆盖；周/月随分段补数进度，使用已完整覆盖的D1生成。历史起点截断的桶不作为完整桶发布，也不为凑出第一根周/月线自动向起点之前下载。当前未收盘周/月线按形成中数据处理；到达收盘且覆盖完整后转为完整bar。

如果某周期或指标所需历史仍在已批准目标内排队，显示等待已有任务完成，不重复要求用户申请维护。只有目标历史起点本身太近、不足以生成该周期或指标时，才说明所需更早历史，让用户明确调整起点；Python指标lookback不得悄悄把起点前移。当前形成中bar在桶前段覆盖完整时正常显示，并标识未收盘。

### 4.3 发布与查看

下载/聚合期间只写待发布结果或不可见修订；读取接口以发布记录和覆盖范围决定可见性。扩展失败不能撤销此前已发布范围。发布由短事务更新范围/修订，不能持有长事务等待网络。

每段发布后立即更新该周期的完整可用根数和范围；达到首次开放门槛后允许进入或刷新查看，不等待全任务完成，也不强制跳转用户当前图表。向更早历史扩展已有会话的范围，通过明确操作重新载入，防止后台重置改变用户视区；已有可用图表的最新K线则通过实时订阅正常自动更新，不要求用户反复手动刷新。

自建数据集的历史左边界以当前已发布版本为准，分段发布后逐步向过去推进；当前展示版本的边界是真实的本地边界，noData可以如实终止向该边界之前的分页。右侧仍不断维护并实时更新，不得把本地水位误认为未来没有行情。未维护的远端历史不再伪装为“本次getBars稍后就会准备好”。

### 4.4 各周期首次开放门槛：三屏完整K线

用户已确认：下载分段是后台工作单位，不能用“完成一个下载分段”直接代表该周期适合浏览。

- 单屏容量 `N = ceil(实际图表绘图区宽度 / 用户柱间距)`，按各窗口实际尺寸独立计算，不使用整页宽度，也不通过放大柱宽降低门槛。
- 正常首次开放门槛为 `3 × N` 根已完整、已发布、连续覆盖的该周期K线：一屏显示、两屏作浏览缓冲。未收盘K线不计入门槛，但满足覆盖条件后可正常显示。
- 同时检查所选指标需要的前置历史；按各指标实际lookback和预热需求取足够范围，不能用三屏数量替代指标完整性校验。
- 例如绘图区960px、柱间距6px：N=160，M5正常首次开放需要480根完整K线，约40小时交易时间。休市不计为交易时间，不能直接换算成40小时自然时间。
- 各周期独立开放：M5达到条件即可查看，H4/D1/W1/MN尚不足时继续显示准备进度。目标范围内任务已存在时不重复询问维护。
- 门槛只是查看条件，不是下载授权。维护仍按用户指定历史起点执行，不能为了三屏或指标lookback擅自把起点提前。
- 例外：已经完整补到用户指定历史起点且相应周期聚合完成，即使不足三屏，也允许查看真实已有的K线，并显示实际根数、可用范围和历史边界。尚无完整K线的周期应显示“当前范围无完整K线”，不能制造K线；指标历史不足则单独说明，不伪造指标值。
- 开放后继续逐段扩展可查看范围，不要求每次扩展再凑出三屏。用户缩放/调整窗口不撤销已经显示的有效数据；允许在已发布范围内操作，但不得因此自动向用户起点之前补数。
- 状态分别显示目标起点、已补到位置、当前周期可用根数/首次门槛和实时维护状态，避免把“三屏已就绪”误报为“全部历史维护完成”。

### 4.5 原生界面限制的处理

独立验证已经证明：原生日期按钮在有限历史结束状态下不一定暴露目标日期。因此不能承诺对每次原生越界操作都精确弹出包含目标日期的表单。

自建图表持续显示可用范围与“维护历史”入口。首次进入或应用已掌握目标范围的跳转在读取前判断；原生拖动/日期跳转遇真实数据集边界，保留原生有限历史行为，并让用户通过明确维护入口填写历史起点。不得读取私有模型/拦截原生DOM来猜目标，不修改原生bundle。

此边界说明是实现约束：核心承诺是未准备范围不输出行情、补数必须明确提交；不能在接口方案中再次假定原生提供了它没有提供的导航事件。

### 4.6 图表内加载与补数文案

用户确认本项只更新方案，暂不修改代码。

- 图表绘图区不显示应用追加的“正在加载”“正在补数”“已补/已显示多少根”“历史后台准备中”等常驻或浮动进度文字。
- 没有可用行情、尚未达到开放条件或所选周期尚无完整K线时，绘图区保持空白，不显示“暂无数据”等占位文案，不绘制占位K线。
- 有可用数据时正常显示；后台补数不以文字覆盖、阻塞或打断当前图表。
- 维护申请仍按已确认流程询问；可用范围、实际根数、三屏准备门槛、维护进度及失败详情放在搜索结果状态、维护表单或用户主动打开的历史任务界面中，不在绘图区自动展示。任务详情需要的精确根数不因此删除。
- 前述“显示准备进度”“说明指标历史不足”“显示实际根数和边界”等要求均按上述位置展示，不能理解为在空白图表上叠加提示。
- 此项只约束加载/补数/无数据文案；真实错误与需要用户操作的维护确认仍通过独立消息或任务界面明确说明，不能以空白掩盖失败。
- 实施时通过原生公开配置处理可控制的原生加载/无数据提示；不得为清除文案修改原生bundle或依赖私有DOM。若该包的原生提示无法通过公开接口关闭，须记录具体限制，不把应用文案清理冒称原生提示也已全部消失。

## 5. 平台行情适配

复用后端OANDA认证、代理和HTTP客户端，新增参数化周期适配；浏览器永远不持有上游Token。

- M1/M5/M15/M30/H1/H4/D1/W1/MN映射到提供商正式周期参数。
- 现有M1基准是Bid、非平滑；平台默认尽量保持相同价格口径，明确配置适用周期的日界线/时区/周界线。
- 不承诺两系列OHLC完全相同，不后台互相覆盖。
- getBars按countBack和exclusive to读缓存/分页请求；日周月交易日期标签由单独适配处理，避免重复包含截止日期。
- 同键请求合并；按图表/请求世代取消旧等待；有上限的并发、超时、重试退避和速率预算。
- 网络失败走错误与重试提示，不能返回noData冒充永久历史边界。
- 缓存与自建Bar/覆盖记录分开命名空间或独立表。平台缓存不算作M1维护完成证明。
- subscribeBars更新当前周期形成中K线；不能用M1价格错误重建与上游口径不同的高周期OHLC。可复用实时价格提示，但蜡烛更新需要同系列一致的数据。
