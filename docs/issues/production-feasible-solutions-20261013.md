## 1. 复用原生范围控件

原滑动条设置某一周期类别的最小、最大范围。例如分钟 5～30，对当前支持的周期产生 M5、M15、M30 可见。它不调整图表滚动位置。

当前九个周期勾选由项目适配器替换了原生范围定义，并非宽屏把滑动条隐藏。现有库的定义模块提供 `createRangePropertyDefinition`：类别开关、起点、终点以及原生范围控件；多对象版本同时使用原生属性收集与撤销包装。这为恢复原生交互提供了明确接入点。

推荐在同一“可见范围”页复用这些原生控件，并保留九个周期的精确勾选。有效可见性继续以同一个 `mwMask` 为准，原生范围属性作为编辑入口，避免两个设置互相覆盖。

- 范围编辑只改变对应类别：分钟 5～30 选中 M5、M15、M30，小时和日周月的选择保留。
- 范围编辑后可以单独取消 M15，得到非连续选择 M5、M30。
- 非连续选择显示为“自定义周期”；原生滑动条显示的外边界不能被解释成区间内每个周期都已选中。打开窗口、保存、撤销时均不能自动补回被取消的周期。
- 再次实际拖动范围控件，才把该类别改为新连续区间对应的受支持周期。滑动过程中与勾选实时同步，使用原生属性与撤销事务。
- 原生可能允许 2～4 分钟等当前不支持的范围；应明确展示该范围没有可用的已选周期。不要把它悄悄映射成其他周期，也不要扩展本项目支持周期。
- 旧图 `mwMask=-1` 保留原范围语义，只有显式编辑才转换。多选对象的不同值保留混合状态，对每个对象只改用户操作的类别。

实施前需验证原生范围的混合值显示与撤销事务边界；不能仅恢复原生 HTML 后依赖异步监听去同步掩码，否则撤销、取消或多选可能失去原意。

验收覆盖单个/多个绘图、非连续选择、取消窗口、撤销重做、模板、复制、保存刷新、多图同步及窄屏。要求使用当前库的原生控件，项目只负责属性适配。

## 2. 组合告警：按证据选择修复路径

已核实的阻塞是最后收盘日线的 `coverage_complete=false`，时间结束与来源确认均已满足。2026-10-08 21:00Z 至 10-09 21:00Z 的日线有 1430 个观测分钟、10 个未知分钟。实时连接正常并不能使这根日线完整。告警没有指标预热依赖。

原“只有三根日线”不再代表当前总历史：活动修订查询返回 300 根、旧告警修订返回 30 根，均可继续分页。旧告警与活动图表绑定不同修订；活动修订也有覆盖不足，直接换绑定不能证明恢复。

下一步对缺口区间重新读取相同 OANDA Practice、账户范围、EUR_USD、bid、M1 口径，比较来源响应、确认分钟存储和组合输入记录。根据结果分三条路径：

| 来源核实结果 | 对应处理 | 恢复判据 |
| --- | --- | --- |
| 来源确实有完整 M1，本地未收或未应用 | 有界重新采集；通过 `confirmed_minutes.record` 与 `composite_inputs.apply_minutes` 登记不可变修订及输入事件，重新聚合受影响区间 | 同一固定组合修订读到真实补齐后的覆盖，且确认水位满足判定柱 |
| 来源没有观测，但有适用于该产品、账户、日期的独立闭市证据 | 建立经核对的来源会话/闭市规则；现有显式数据集日历不可原地改，需要新日历身份及显式选择相应修订 | 闭市区间与来源观测无冲突，告警版本明确，聚合完整性经验证 |
| 来源没有观测，原因或闭市证据仍不足 | 保留 unknown/stale；展示具体日期、缺分钟及核对状态，提供有界再次核对流程 | 新证据到位后再按前两条处理，不凭空响应登记完整 |

初始接续准备把区间查询完成后标为 `queried`，其设计明确不证明覆盖。补查应针对实际 unknown 区间，并设置重试预算、去重和审计；不能无限反复请求同一缺口。现有采集/确认模块可复用，但是否遗漏了真实来源观测仍待核实。

恢复告警时保留“先重新建立有效基准，再接收后续真实判定样本”的规则，避免断线/补查期间补造触发。细化 stale 文案是辅助可观测性，不能代替数据修复。正式验收同时验证补齐、真实缺口、日历冲突、旧修订读取、恢复基准及一次真实条件变化。

## 3. Swing 平均间隔移到图内

推荐复用现有 `bottom_left` 卡片。生产检查已证明顶部占用从 44px 变为 0，相同统计仍可查看。修改默认值和输入缺失时的兼容回退；旧 `below_name` 实例按这次显示要求迁移到左下角，保留 `show_average_spacing=false` 以及已使用左下角的实例。

## 4. LWMA 的新默认

后端目录与参数 schema 的周期默认设为 5，前端仅给 LWMA 默认白色 `#FFFFFF`。不能修改通用色表让其他 Python 指标一并变色。

已有保存的参数、样式和模板优先于默认值，不自动把用户的 20 周期改成 5。验收新建实例的实际计算参数、线色以及保存刷新即可。

## 5. 统一自定义指标与原生数据更新/绘图路径

### 目标与现有差异

用户希望以后的自定义指标复用内置指标的实现方式，获得相近的运行与绘图效率。方案从“局部优化 Python 独立分页”调整为“建立统一的原生指标接入能力”，以 Python 作为现有指标的计算来源，复用原生指标容器、数据更新、时间轴、样式、价格轴和绘图。

目前 Python 指标已经使用原生绘图和参数窗口。多出的主要环节是：每个输出通过 `ctx.new_sym` 建立 `MWPY_` 辅助系列，独立加载历史后再按时间与主图对齐。LWMA 一个输出，Swing 四个输出；多个输出不等于后端重复四次完整计算，现有相同请求和固定计算任务已经有复用。

生产同图对比已复现 Python 曲线等待分页时短暂消失，内置 WMA 保持显示；后台 `indicator_progress/indicator_ready` 还会触发主图及指标重载。约 142～375ms 的分页回调包含网络、队列、准备与读取，不能当作纯 Python CPU 耗时。

### 两种接入方式及选择

| 方式 | 计算在哪里 | 能复用的原生路径 | 条件与代价 |
| --- | --- | --- | --- |
| 原生主图计算 | 使用 `PineJS` 或项目的同步 JS 算法，直接读取主图 K 线 | 与内置指标相同的主图计算驱动、追加、分页和绘图 | LWMA 有公开 `PineJS.Std.wma` 可评估；与 Python 的缺口、预热、递归起点和实时语义必须逐项对齐。Swing 等需要第二套算法维护 |
| Python 计算＋原生结果更新接口 | Python 生成结果，适配层按指标提交到原生更新流程 | 主图范围驱动、原生指标数据容器、时间轴对齐、增量更新和绘图 | 保留图表、告警和回测的计算来源；需要补项目接口、协调异步结果和原生内部生命周期 |

当前推荐第二种作为通用接入方案。第一种可作为标准指标的独立对照实验，不作为用户已同意把 Python 计算迁到前端的决定。保持同一个计算来源可以减少图上数值与告警/回测分歧。

### 已核对的接口边界

原生公开接口的 `init` 和 `main` 是同步函数，`main` 返回数值/绘图结果，不接受等待 Python 网络请求的 Promise。`custom_indicators_getter` 返回 Promise 只用于注册指标定义，不是每根柱的异步计算接口。

公开 `IStudyApi` 提供参数、样式、显示和数据加载事件，没有“替换整段预计算指标结果”的方法；主图 Datafeed 的标准 Bar 只规定 OHLCV，不能假定增加自定义字段就会自动成为指标输出。

但当前原生内部已具备所需基础设施：

1. 指标计算完成后产生带时间和多 plot 值的结果行。
2. 原生时间轴为这些行分配对应主图索引。
3. 指标级 `onDataUpdate` 发送 `data_update`，包含指标身份及当前请求代次。
4. 指标消费者检查身份/代次，串行处理 plot 偏移和数据合并，更新价格范围、指标视图及数据事件。

受控浏览器中，用当前未修改的许可库、现有原生历史 fixture 与内置 WMA 读取运行结构，确认上述缓存、时间轴映射及消息方法实际存在，读取到 300 行 WMA 结果，页面错误为 0。该实验没有提交外部 Python 结果，也没有运行新接口；**证明接入点存在，不证明新方案已经可用或达到性能目标**。脱敏结果见 [接口可行性核对](evidence/native-indicator-interface-feasibility-20261013.json)。

### 推荐接口及更新语义

在项目的原生适配层增加一个窄接口，例如 `MWNativeIndicatorResults`。名字仅为方案示意，所有指标共享同一份实现。业务指标声明参数、输出、样式与计算规范；原生内部对象和字段仅由这一层访问。

| 接口操作 | 作用 |
| --- | --- |
| `attach` | 将一个指标实例绑定到具体图格、主图身份、周期、参数与算法版本，建立当前代次 |
| `applyBatch` | 校验并提交 snapshot、prepend、append、replaceRange 等结果批次，更新对应原生指标 |
| `invalidate` | 记录输入更正造成的失效范围；停止展示已无效值，安排相应重算 |
| `detach` | 指标删除、图格切换或工作区关闭时释放需求、缓存引用和订阅 |

批次必须带有：主图身份/固定修订、输入修订、计算起点、周期、参数指纹、算法版本、指标实例代次、批次序号、替换范围，以及按时间组织的值与有效性。先验证批次，再在原生更新队列中提交；不能让两套更新者竞争写同一个 plot。

接入时为已登记的项目自定义指标建立“外部计算结果”模式：原生负责指标容器和显示生命周期，协调器负责 Python 结果，不再启动这些指标当前的 `MWPY_` 辅助系列。普通内置指标继续使用其原生计算驱动。必须确认指标启动、暂停、删除、重新创建与原生父子依赖均正常，不能仅停止当前实例的引擎后直接写入数据，否则下一次原生重建可能恢复旧通道并覆盖结果。

重要语义：

- **缓存按时间保存。** 主图向前补历史会改变原生柱索引，不能长期缓存旧索引。提交时按当前主图快照重新映射，并处理日/周/月的交易日期标签。
- **追加与更正分开。** 追加最新柱、更新形成中柱、补更早历史各有边界；真实历史更正从最早受影响依赖开始重算。EMA/RSI/MACD 等递归结果的影响可能延续到尾部。
- **替换包含删除。** 原生 PlotList 的 merge 更新/合并已有行，空结果不会自动删除旧值；其 remove 是尾部移除。项目接口必须定义区间替换、旧值变 null、尾部回撤和完整快照缩短，不能只把新数组合并进去。
- **批次提交避免空白帧。** 有效旧区间在单纯补页/准备新范围时保留；新范围完成后一起提交。已失效结果须标记/撤下，不能为了“不闪”继续展示错误值。具体提交顺序需经过浏览器实验确认。
- **保留原生事件。** 更新经过数据合并、最值/价格轴缓存、视图及完成状态的流程。直接改私有数组不会自动维护这些依赖。
- **保留多输出。** Swing 四个输出作为同一批次，含左右偏移；SuperTrend 的线、颜色、填充及信号也按同一版本提交，避免各输出错开。
- **拒绝过期响应。** 切换品种/周期、改参数、删除指标后，旧批次不得影响新实例。输入修订不能单靠网络到达顺序排序。
- **真实缺口仍断开。** pending、warmup 和真实 gap 与有效数值区分；0 和负数仍可能是有效输出。保留 Python 既有完整性及预热要求。

### 主图驱动与共享准备

目标流程：

```mermaid
flowchart LR
    A[主图接受的历史范围与修订] --> B[自定义指标需求协调]
    B --> C[Python 共享计算任务与结果块]
    C --> D[指标结果批次与版本校验]
    D --> E[项目原生指标结果接口]
    E --> F[原生指标缓存和时间轴对齐]
    F --> G[原生价格轴和绘图]
```

主图接受数据、切换周期、增加指标及修改参数时，协调器登记同一身份和范围的需求。后端已有 `DataQuery.indicators` 多指标参数、不可变输出块和检查点复用，应在这些基础上批量准备和读取；多指标仍是各自算法任务，复用的是输入、请求和可共享结果。

按主图分页边界预取指标输出，一次读取某个指标的所有 plot；已有相同输入/参数的结果供多图共享。固定历史缓存与可变尾部区分，缓存有内存/条数预算，隐藏或删除的消费者释放需求。

异步冷启动不会因换了绘图通道消失。主图可以先呈现已就绪 K 线与已有有效曲线，自定义指标在所属图格显示准备状态，完成后提交结果。不得为了等待一个昂贵指标而让整个主图长期空白。准备过程只报状态；只有实际依赖更正触发必要的失效/重算。

### 接入内部接口的维护方式

项目已有针对固定许可库版本的校验与适配机制。新增能力也集中在一个可撤回的适配入口，对构建指纹、内部方法和数据结构做精确核对；其余指标代码只调用项目接口。

接入点优先复用原生指标输出阶段。可能需要一个小型、可审计的构建适配钩子来登记外部计算的指标生命周期；具体选择运行期包装还是构建钩子，需要后续最小实验比较。不能在各个指标内散落对私有模型的读写。

原生升级时先运行契约与行为回归，再开放新接入。若不兼容，明确停止该通道或使用已验证的旧通道，并完整撤销当前绑定；不得在同一个实例上同时运行两条写入路径。

### 后续验证阶段与成功标准

| 阶段 | 要验证的内容 | 通过条件 |
| --- | --- | --- |
| A 最小接入实验 | LWMA Python 结果进入原生 WMA 类似的更新流程；历史、当前柱、空值、更正及回撤 | 数值与 Python 一致，已有线不因单纯等待消失，主图无需 reset，过期批次被拒绝 |
| B 主图范围协调 | 初次添加、改参数、前向分页、周期切换、模板/工作区恢复 | 指标需求与主图身份一致；保留已有有效区间，缓存和订阅正确释放 |
| C 多输出与多图 | Swing 偏移/统计、SuperTrend 填充与信号、单图/五图并发 | 同批次输出一致，价格轴、样式、隐藏和最大化正常，内存有上限 |
| D 性能与正确性比较 | 相同数据的内置、当前 Python、新通道；冷/热缓存，1/4/8 指标 | 给出首个有效绘制、分页 p50/p95、整条消失次数、重载次数、网络/DB/CPU/绘图分段及内存峰值 |

首要行为目标：往返拖动已缓存有效区间时整条曲线消失次数为 0；后台普通进度和正常尾部追加不引发整图清空；历史更正、真实缺口、参数改变及尾部回撤仍正确。

绘图可复用与内置相同流程，减少额外序列装载、同步和重载开销。Python 首次计算、网络和队列延迟仍存在，不能据此承诺与本地内置指标的端到端耗时完全相同。性能比例或具体毫秒目标在同场景实验后确定。

## 6. 右下角通知与故障处理

普通“图表提示”改为右下角非模态通知，不抢焦点、不要求点击确定。推荐默认同时最多 3 条；同一故障更新已有卡片和次数。短暂网络失败在约 30 秒合并窗口内去重，避免多个图格和短暂恢复把同一故障反复弹出；这些数值是待验证的初始建议。

短暂提示可自动收起，长期数据不可用时保留所属图格的状态及手动重试入口。通知关闭不会清除故障本身。窄屏适配宽度，避开价格轴/原生窗口的主要操作区；需要用户决定的草稿恢复继续使用相应确认流程。

错误分类区分用户操作主动取消、真实超时、HTTP 失败与通用网络失败。对可重试读取采用有限次数、退避和抖动，避免每个图格各自重试同一请求；配置或鉴权错误不按网络故障无限重试。

真实 `TypeError: Load failed` 的失败请求、时刻和浏览器网络原因尚未自然捕获。需要有界记录请求路径、耗时、取消/超时来源及恢复结果，不收集凭据和完整布局。第 5 项可减少请求压力，但不能据此宣称已查明第 6 项网络根因。

## 7. 详情打开后的列表

当前 920px 列表被 360px 详情缩到 560px，仍沿用四列布局，主列被操作说明挤到 0。临时两列方案已将主列恢复到 324px，验证问题在空间预算。

推荐按实际列表容器宽度切换：空间充足保留常规布局；紧凑时左侧放品种/来源及状态，右侧放受限宽度的操作。长操作说明移到对应提示入口，或仅在实际会关闭同步时展示，避免每行说明参与无限宽度竞争。

侧栏是否显示由“列表实测最小可读宽度＋详情宽度＋间距”决定。560px 在紧凑布局下可读，不必一打开详情就隐藏列表；更窄时使用现有完整详情与返回列表。保留筛选、滚动位置、选中行及键盘焦点。

验收覆盖阈值两侧、窗口缩放、长来源名称、打开/切换/关闭详情及两种组合标签页。
