## 1. 绘图可见范围：滑动条被替换

原滑动条用于设置一类周期的最小、最大范围。例如分钟范围为 5～30 时，绘图在支持的 M5、M15、M30 周期显示，M1 不显示；它不用于调整线条位置或图表横向滚动。

生产宽屏设置窗口实测为九项 M1、M5、M15、M30、H1、H4、D1、W1、MN 复选框，滑动条及 range 输入均为 0。原生图表实际宽度为 1900px，`max-width:460px` 规则未命中，因此不能归因于窄屏隐藏。

**直接原因：** `advanced-host/drawing-visibility.js:32–47` 包装原生可见范围属性定义，绘图存在 `mwMask` 时返回九个 `createCheckablePropertyDefinition`，替换原周期范围定义。引入记录为提交 `3f14266`。`mwMask=-1` 时兼容旧范围；编辑复选框后以九位掩码决定可见性。

建议保留与当前九个支持周期一致的独立选择，并说明原范围功能如何对应。若要恢复原滑动操作，可增加“范围选择”入口，将结果转换成同一个 `mwMask`；不要让旧 `minutesFrom/To` 等范围与掩码成为两个互相覆盖的保存来源。需覆盖旧图恢复、勾选／范围转换、撤销重做、多对象选择及刷新后可见性。

## 2. 组合告警：覆盖缺口与版本绑定

已核对 EURUSD 组合行情的唯一现有日线告警，条件为收盘价格下穿常量 `1.11546`，没有指标预热依赖。告警仍为 `active/stale`，原因与用户报告一致。

| 对象 | 核实结果 |
| --- | --- |
| 告警固定组合修订 | `a3c66706…`，历史版本 `cc612676…`，历史从 2026 年开始 |
| 当前图表活动修订 | `9959ebb0…`，历史版本 `7fc29e0c…`，历史从 2021 年开始 |
| 当前活动修订日线查询 | 返回 300 根且仍可继续分页 |
| 旧告警修订日线查询 | 返回 30 根且仍可继续分页 |
| 实时来源状态 | 连接及报价正常，确认尾部正常；这不等于每根历史判定柱覆盖完整 |

“日线只有 3 根”已不符合当前查询的总历史数量。旧修订接续来源之后的尾部日线确有少量柱，不能将这个数量与整个组合历史混为一谈，也不能把缺少指标预热认作这条价格告警的原因。

**直接阻塞条件：** `backend/alerts/composite_alerts.py:225–242` 在收盘模式排除未结束柱，再检查最后判定柱的 `time_closed/source_confirmed/coverage_complete`。最后已结束柱为 **2026-10-08 21:00Z 至 2026-10-09 21:00Z**：时间已结束、来源已确认，但覆盖不完整，观测 1430 分钟，未知 10 分钟。上一日也有 5 个未知分钟。当前形成中的日线尚未结束，不能代替上一根收盘柱。

读取旧修订的 M1 核实，这 10 个时间点确实没有观测：纽约时间 10 月 8 日 **17:00、17:01、17:02、17:03、17:06、17:07、17:08、17:09、17:13、17:19**。目标数据集的 `calendar_profile` 当前为空。`composite_series.py:55–76` 对没有观测、又未被适用日历证明闭市的分钟保留 unknown，因此整根日线不完整。

这解释了当前 stale；**这些分钟在真实来源中属于无报价、采集缺数还是适用休市，仍需要来源侧证据**。缺口集中在日界附近是一条排查线索，不能仅因“没有 K 线”就登记休市。当前活动修订的最后闭合日线也显示覆盖不完整，所以仅把告警改绑新版本并不能证明恢复。

建议按以下顺序处理：

1. 只针对具体缺分钟核对 OANDA Practice `EUR_USD/bid/M1` 的确认响应及该账户适用日历。可补的数据补齐；已证实闭市的分钟通过明确、可审计的来源日历处理。
2. 核对固定修订重新聚合及告警读取的一致性。旧告警固定修订属于防止历史语义被静默改变的设计，应展示“告警版本”和“图表版本”，通过显式编辑／新建选择版本。
3. 把泛化的 stale 文案细化为判定柱日期、哪项条件失败、未知分钟数及恢复阶段，避免“来源正常”被理解成“可以判定”。
4. 修复后验证连续有效收盘样本、恢复基准与下穿判定，保持断线期间不补造触发。不能强制改为 ready，也不能用最新报价或形成中日线绕过覆盖要求。

## 3. Swing 平均间隔：复用左下角卡片

实测默认 Swing 显示“平均间隔：高点 10 根 · 低点 10 根”，顶部占 44px；图表起点 y=44、可用高度 956px。仅在检查会话把 `statistics_position` 改为 `bottom_left` 后，顶部占用变为 0，图表 y=0、高度 1000px，同一统计继续显示在图内左下角卡片。

**直接原因：** `backend/alerts/swing_sr.py:208–212` 默认位置为 `below_name`。`advanced-host/swing-sr-display.js:89–118` 将信息区域插在图表容器之前，并把页面设为纵向 flex；`178–215` 根据位置把平均间隔放入顶部区域或图内卡片。`58–59` 的旧输入修复回退也为 `below_name`。

推荐默认改成现有 **左下角卡片**，同时修改旧输入缺失时的回退。新默认不会自动改变已保存实例；若迁移顶部实例，应明确只迁移 `below_name`，保留已经隐藏平均间隔及已选左下角的用户设置。也可保留 `show_average_spacing=false` 作为完全隐藏选项。

该方案只改显示位置，不改计算、Swing 确认及平均间隔口径。验收覆盖多图、多 Swing、折叠详情、缩放和不同主题，确认统计更新不再改变图表外部尺寸。

## 4. Python LWMA：默认周期 5、白色

生产目录及新添加实例的周期均为 20，颜色为 `#42a5f5`。

**原因：** `backend/alerts/chart_indicators.py:12` 为 LWMA 定义 `period=20`，参数 schema 默认也由目录生成；`advanced-host/indicators.js:68–109` 使用通用线色数组，首条线为蓝色。

建议后端 LWMA 默认周期改为 5，前端为 LWMA 单独定义白色 `#FFFFFF`。避免修改通用颜色数组导致其他 Python 指标一起变白。已有保存的周期、颜色和模板以用户设置为准；仅对新的默认实例生效。验证新建实例、服务端实际计算参数、颜色及刷新恢复即可。

## 5. Python 指标：先修加载与刷新，再衡量计算

### 已复现的拖动问题

使用同一 EURUSD 组合 H1 图表、周期 20 的 Python LWMA 与内置 Moving Average Weighted，开启自动价格轴。检查会话把 Python 线设为品红，内置线保持蓝色，采样图内 canvas，排除顶部文字与价格轴标签。

| 有效场景 | 采样结果 | 同期事件 |
| --- | --- | --- |
| LWMA＋Swing＋内置 WMA，往返拖动 | 153 次采样中 Python 线整条不可见 11 次，内置线不可见 0 次；两段约 472ms／252ms | Python 补历史，LWMA 回调 375ms／169ms；该段没有 SSE reset |
| 仅 LWMA＋内置 WMA，往返拖动 | 109 次采样中 Python 线整条不可见 9 次，内置线不可见 0 次；三段约 176ms／158ms／176ms | LWMA 分页回调 142ms／152ms／167ms；后段另有 indicator_progress 重载 |

两次有效观察均出现等待指标分页时曲线短暂消失。普通小幅拖动、已缓存区域也存在不闪的情况，所以不能概括成每次拖动必闪。

**路径原因一：独立历史序列。** `advanced-host/indicators.js:136–185` 给每个 Python 输出创建 `MWPY_` 合成符号，再将各自历史按时间映射回主图。LWMA 一个输出，Swing 四个输出；内置均线直接使用已加载主图数据。拖动进入主图已经有数据、Python 序列尚待补取的区域，Python 仍要经过独立数据请求与原生序列装载，已有图形在等待期间也会被重新计算／短暂撤下。有效采样显示消失与分页请求、回调对齐。

**路径原因二：后台进度引发整图重载。** 实际消息捕获到 `indicator_progress/indicator_ready` 后历史重新加载。

- `fixed_indicators.py:84–117` 以输入修订及目标范围形成不可变指标任务，并复用之前的检查点。
- `market_stream.py:483–489` 比较进度的任务 id、cursor、status；变化即产生 reset，包括任务切换／完成状态变化。
- `advanced-host/bridge.js:2365–2377` 收到 reset 清理历史接受状态和缓存，进入恢复；`1277` 起的刷新路径定位含该指标的图格。
- `advanced-host/viewports.js:318–350` 调用 `chart.resetData()`，触发主图及关联指标重取、重绘。多输出、多指标可能扩大重复恢复成本。

上述机制具有重绘和额外取数成本。并非每次 reset 都不必要：真实历史更正、来源修订、回撤等必须重新验证；应根据受影响的已接受范围区分，而不是整体禁止 reset。

### 耗时与正确性边界

本次有效指标分页回调约 142–375ms，后台重载后首屏回调还出现约 524ms。它们包含网络、排队、数据准备、读取和计算，**不等于 Python CPU 计算耗时**。因此“Python 比内置慢”的体验成立，但主要计算瓶颈尚未通过 CPU 分段测量确认。

后端已经有固定历史结果共享、不可变输出块和检查点复用，不能以“没有缓存”为前提重建缓存。平台行情另有 `provider_cache.py:754–791` 读取固定前缀后计算、再裁剪输出的路径；较长历史、多指标时可能有优化空间，但本次组合拖动测量不能直接证明平台路径的 CPU 瓶颈。

此外，两种指标的数据有效性口径并不完全相同。Python 会因真实覆盖缺口重置预热并输出 null；例如本轮一页 218 个时间点仅 14 个有效 LWMA 点，另一页 51 个点均为空。`barsOf` 把空值包装为 close=0、volume=0，指标再恢复为 NaN。不能把 close 数值有限当成“全部有效”，也不能为消除闪烁而跨越真实缺口补线。

### 推荐分阶段方案

1. **稳定显示优先：** 主图与关联指标按同一固定身份、修订和历史范围协同准备；向前分页时保留已接受区间的旧输出，新区间准备好后追加。真实历史修订需作废对应范围，不能继续展示已失效结果。
2. **缩小重载：** 区分 job 进度、尾部追加与已展示依赖更正；不因新任务 id／status 单独改变就清空不受影响的历史。按图格合并多个指标、多个输出的恢复，保留视口。
3. **共享请求与预取：** 同图主数据和指标输出共享取数范围、预取边界及结果批次。现有相同 spec 的请求已存在复用，优化应针对剩余不同 spec、独立分页和订阅恢复，不能简单计算为“四个 Swing 输出等于四次完整计算”。
4. **测量后优化计算：** 记录数据就绪、队列等待、数据库／块读取、算法 CPU、序列化、首个有效绘制的阶段耗时；比较冷／热缓存、历史长度、1／4／8 个指标、单图／五图。随后针对固定任务复用边界、平台前缀重算等已证实瓶颈优化。

建议验收目标：往返拖动已有有效区间时保留原曲线；正常尾部追加不清空整图；修订及真实缺口仍正确；给出相同场景优化前后首屏／分页 p50、p95 和 CPU 分段，避免只用添加指标 API 的返回时间作对比。

## 6. TypeError: Load failed：重复提示机制确认，网络触发待定位

Chromium 有效检查阶段未自然出现用户描述的 `TypeError: Load failed`。本机 Linux WebKit 尝试没有完成 HTTPS 页面加载，连独立控制站点也失败，属于检查环境限制，不能据此认为生产 Safari 存在同样问题。用户实际浏览器／设备尚未确认。

这类 `TypeError` 是 fetch 没有得到可用响应的通用表现，仅凭文字不能区分断网、连接重置、TLS、跨域或其他浏览器网络失败，也不能认定由 Python 计算引起。用户真实失败请求 URL、时刻和网络错误仍缺失。

**已确认的提示放大机制：**

- `web/src/api.ts:22` 起使用 fetch，网络失败继续作为原始错误传递。
- `AdvancedWorkspace.tsx:141–165,761–769` 按来源键维护错误，并作为 notices 发给图表。
- `advanced-host/bridge.js:24–38` 将这类 notice 放进“图表提示”模态窗口。`2312–2320` 仅在错误持续存在时保留已确认去重；错误清除后删除去重记录。

仅在检查会话注入同一 `feed-poll-state` 模拟错误验证：确认后再次发送相同未清除错误不弹；先清除错误、再发送同一错误立即重弹。**此实验证明弹窗机制，不证明真实网络错误的起因。** 间歇失败／恢复，或多个图格以不同键报同一故障，会反复打断用户。

建议补齐真实浏览器的失败请求时刻、路径、取消／超时标识和恢复情况，再分别处理网络根因。界面可独立改善为来源旁非模态状态与有上限的退避重试：切换图表主动取消不算故障；同一网络故障跨短暂恢复仍合并；长期失败保留可见信息及手动重试入口。不要通过全面屏蔽报错宣称已修复。

## 7. 组合详情后列表：空间预算错误

已在 1900px 宽屏复现“数据中心 → 组合行情 → 查看详情”。

| 实测尺寸 | 打开前 | 打开详情后 | 浏览器内候选样式 |
| --- | ---: | ---: | ---: |
| 列表宽度 | 920px | 560px | 560px |
| 品种／来源主列宽度 | 314px | **0px** | 324px |
| 条目高度 | 75px | **543px** | 151px |

**直接原因：** `DetailPanel.tsx:61–75` 在内容区不小于 900px 时使用 360px 侧栏；`window.css:375` 用右侧 padding 给详情腾位置，使列表剩 560px。列表 `window.css:305` 仍使用四列 grid，紧凑布局仅在 `max-width:550px` 生效。操作列含两个按钮和长说明（`OpenChart.tsx:16`），其内在宽度与其余列挤掉了 `minmax(0,1fr)` 主列；来源文字设 `overflow-wrap:anywhere`，因此逐字竖排，整行拉高。

只在浏览器临时应用“列表容器 ≤700px 切两列、操作说明限制 180px”后，主列恢复 324px，行高降为 151px，说明能够正常换行。它验证了空间分配方向，**不是正式修复或已验收成品**。

## 补充：Swing 为什么有四个价格轴标签

这是前面用户提出的解释问题，不增加为第八项待处理需求。`backend/alerts/swing_sr.py:14` 定义 `high/high_left/low/low_left` 四个绘图输出；后两项用于按确认强度左移显示原始拐点位置。前端建立四个 plot，原生指标默认显示各 plot 的价格轴值，所以可出现四个标签，并不是算了四种平均间隔。
