# 原生连续历史与有限窗口：性能验证及方案复评

2026-10-04。工作分支 `fix/native-chart-window-sync`。本轮只研究、测量和归档，没有实施新的产品方案、改生产配置或合并。先前的闪烁候选修改仍保留，未因本轮研究发布新版本。

## 决策结论

1. **不应继续把 20,000 当作 Advanced Charts 的固有极限。**它是应用限制。官方允许按原生 `countBack` 返回、服务端自行分页；历史范围仍连续取到当前日期也是官方记录的行为。原生 v31.1 实测能保留 60,000、200,000，甚至百万根。
2. **用户提出的“第一次加载到 PG，以后更快”成立，但分两层。**PG 命中省去上游取数；浏览器已加载的同区间再次定位则进一步省去传输、解析和数据处理。本轮后者常为亚毫秒至数毫秒，前者 60,000 根仍需数秒，200,000 根仍需十几至二十秒。
3. **不建议无限制满足任意原生数量。**百万根无指标单图能加载，但处理阻塞约 8.7 秒，旧侧追加几十根又阻塞约 10 秒。四图各 200,000 根、三个指标的 JS 堆约 1.9 GiB。能容纳不等于体验可接受。
4. **建议优先重新设计原生连续加载路线，减少自定义窗口状态，但必须一起处理后端热读取、长任务、取消和错误恢复，并保留经测量确定的资源预算。**不建议简单删掉三个上限，也不建议仅为了闪烁直接把用户迁回原始错误生命周期。
5. **有限窗口应被视为极远定位的性能选项，而不是“超过 20,000 自动切窗”的唯一答案。**它确实避免整段走廊及指标重算，但有窗口边界、源隔离、订阅与恢复的维护成本。最终是否保留，取决于产品对极远跳转和多图内存的要求；本轮没有实施新的混合策略或阈值。

## 证据与实验边界

- [官方资料核查](native-large-history-official-research.md)：官方现行文档、匹配版本的本地 v31.1 接口声明、供应商第一方资料。没有找到总 bars 上限或大数据量性能保证。
- [精简实验数据](verification/native-large-history/evidence.json)、[热缓存 profile](verification/native-large-history/hot-profile.txt)。私有完整轨迹与截图留在 Ubuntu `.acceptance/chart-sync-ubuntu-20261004/large-history`，许可原文件和完整行情不入 Git。
- 浏览器 Chromium 153.0.8010.12，1600×1000，Ubuntu 4 逻辑 CPU、约 16 GiB 内存，共享宿主。正常 CPU 与 CDP 4 倍 CPU 降速分开报告。降速是压力代理，不代表某个具体电脑。
- 真正远跳测试使用恢复原始 SHA 的许可 v31.1 bundle。未载入产品 `MWNativeNavigation/MWNativeReserve`，只加观测 hook。按公共 `setVisibleRange` 触发原生需求，正常异步 `getBars` 回调交付，并检查内部实际保留数量、目标视区、真实鼠标移动和指标数量。
- 合成数据用 24×7 M5；四图混合布局为 M5/H4/D1/W1，原生交易日历转换允许高周期 bar 标签差异。多图同周期使用不同实验商品，避免共享线程去重掩盖最坏成本。
- 每图三个原生指标：MA200、RSI14、MACD。指标与请求完整处理结束才计时；`dataReady()` 单独为真不作为完成证据。
- 后端使用原有 API 镜像和 Ubuntu 独立 `chart_sync` PG。在一次性容器进程内绕过请求模型容量、放宽内部容量与预算；正常 API、web、用户验收入口未改。HTTP 研究服务只绑定 `127.0.0.1:16145`，实验后已删除。未启动新的生产/通知 worker，没有保存用户布局或偏好。
- 后端只进行正常行情缓存 backfill，不删除缓存伪造冷态，不改写历史 bar。实验日期选择原来未覆盖范围；首轮失败留下的已取数据在下一轮复用，按实际冷/部分热/完全热标注。
- JS 堆为采样时 `JSHeapUsedSize`，不是浏览器总 RSS 或内存峰值。帧间隔会随采样时机漏掉较晚的处理，结论同时使用 long-task、同步回调耗时以及追加完成后的 RAF 间隔，不能只引用 p95。
- 原来的“小请求额外返回 200,000 根”实验只表示适配器缓冲，不证明图表实际保留和重算全部数据；它约 40 MiB 的结果不用于容量判断。真正远跳时内存明显更大。

以下是合成 JSON 经 HTTP/拦截传输、正常原生回调后的成本，**不含行情商/PG 等待**。60,000、200,000 单图三指标、四图 60,000 三指标和混合图 200,000 各有三次有效样本，下表这些项取中位数；其他项为单次观测。

| 单图，无指标 | 60,000 | 0.86 s | 0.55 s | 68 MiB |
| 单图，无指标 | 200,000 | 2.63 s | 1.68 s | 199 MiB |
| 单图，无指标 | 1,000,000 | 11.55 s | 8.74 s | 941 MiB |
| 单图，三个指标 | 60,000 | 1.34 s | 0.96 s | 165 MiB |
| 单图，三个指标 | 200,000 | 4.13 s | 2.92 s | 477 MiB |
| 两图各三个指标 | 每图 60,000 | 2.67 s | 1.05 s | 307 MiB |
| 四图各三个指标 | 每图 60,000 | 5.03 s | 1.07 s | 585 MiB |
| 四图各三个指标 | 每图 200,000 | 19.42 s | 3.99 s | 1,907 MiB |
| 八图各三个指标 | 每图 60,000 | 11.58 s | 1.84 s | 1,103 MiB |

### 交互与继续加载

- **已加载数据内**的拖动、向新侧返回、重复定位大多流畅，无新增请求；重复定位典型约 0.5～1 ms。原生大缓存确实有收益。
- **触及旧侧边界并补入新历史**时，当前原生模型处理与已加载数量明显相关。单图三指标 60,000 根补约几十根后可停顿约 0.9～1 秒；200,000 根约 2.8～3.2 秒；百万根无指标约 10 秒。真实 OANDA 会返回额外储备，减少边界请求频率，但这次发生补数时仍观察到长任务。
- 这是新增代价，不是当前“无关 reset 反复重建”这一缺陷。换回正常 getBars 会避免一类重建，却可能把体验问题变为大序列追加的停顿。
- 原生实时订阅连续更新同一尾 bar 100 次：60,000 和 200,000 根单图三指标，回调中位约 0.3 ms、最大约 1.9/3.4 ms，没有新历史请求。不能把旧侧追加的成本推广到所有实时 tick。
- 4 倍 CPU 降速：单图三指标 60,000 根约 4.17 s、最大阻塞 3.27 s；200,000 根约 12.92 s、最大阻塞 10.46 s。混合四图 60,000 根约 5.09 s，旧侧补数出现约 3.73 s 帧间隔。较慢客户端的成本不可忽略。

## 真实 OANDA / PG / HTTP

### 取数与缓存收益

| 必需数量 | 冷/部分热 | 完全 PG 命中，内部 data 调用 | 完全 PG 命中，真实 HTTP 含编码与传输 |
|---|---|---|---|
| 20,000 | 5 页，18.13 s | 1.14～1.40 s | 1.71～1.74 s，约 3.85 MB |
| 60,000 | 15 页，78.20 s | 4.12～4.33 s | 4.82～5.34 s，约 11.55 MB |
| 200,000 | 首轮 300 s 预算后约 308 s 退出，已取 42 页；下一轮补 8 页，114.80 s 成功 | 13.24 s | 15.25～15.35 s，约 38.47 MB |

200,000 第一轮后缓存可复用是用户提出方案的正面证据。但冷请求时间不能只按单页网络速度线性外推：60,000 的上游 HTTP 约 12.6 s、写入约 15.1 s，其余大部分在反复快照读取和处理；200,000 放大更明显。

对 60,000 完全热请求做 profile：总约 4.4 s，数据库结果中的 JSON 解码累计约 3.4 s。`snapshot_transaction` 把 dataset 的 coverage/metadata 和每根 bar 一起返回，结果重复解码；冷分页还反复扫描逐渐增长的结果。这是**当前读取实现的成本**，不是 PostgreSQL 缓存的理论下限。未来可以在保持一致快照合同的前提下优化，但本轮没有改变 SQL 或算法。

### 真实原生端到端

原始库 + OANDA NY17 交易日历 + 本地 HTTP 研究服务 + 同一 PG + MA200/RSI/MACD：

| 目标需求 | 完全热缓存请求至原生定位完成 | 实际库内保留 | 最大浏览器长任务 |
|---|---:|---:|---:|
| 约 60,000 | 6.42 s | 58,961 | 0.94 s |
| 约 200,000 | 21.00 s | 195,977 | 2.91 s |

实际原生需求和保留量受交易日历、估算、已加载储备及指标影响，并非恰好整数量。两例从启动、远跳到追加均 `cache_hit=true`。此前目标边缘未完全缓存时为约 12.26 s/36.29 s，不能把那轮称为完全热。

### Python 指标

使用真实后端 Python SMA200（包含 199 根前缀）：60,000 热调用约 3.68～3.79 s、响应约 14.52 MB；200,000 约 11.37～11.93 s、响应约 48.36 MB。首次缺前缀需要额外分页，约 8.11/24.54 s。Python 计算本身只占其中一部分；更多序列会增加传输、前端数据源和内存成本。本轮验证的是后端真实数值与原生指标的独立成本，未将 Python 指标叠加到 200,000 根真实原生图表中，不能声称该组合已验收。

### 当前合同和供应商边界

- 未变更的 Ubuntu 正常 API 对 60,000/200,000 返回 422；正常 web 同样拒绝超限。完成实验依赖一次性研究进程，不能宣称产品已经支持这些数量。
- OANDA 直接只读请求 `count=5001` 返回 400，`Maximum value for 'count' exceeded`，证明供应商单页有限；现有适配器使用 4,000。单页限制不等于整段 getBars 必须同样受限。
- Binance 官方单页最多 1,000；Yahoo 还受历史保留窗口限制。PG 已缓存更早数据可保留，但不能仅扩大 `countBack` 让供应商提供已经不可取的历史。详见官方研究。

## 加载状态、取消与错误恢复

- 模拟 2 秒网络等待，原生显示 legend 三点 loader / `data-status=loading`，RAF 大多约 16.7 ms；等待并不必然卡死。此时 `dataReady()` 仍可沿用旧数据返回 true，因此必须用请求完成和目标定位判断。
- 数据进入原生回调时的大长任务与网络等待不同；能显示 loader 不代表输入响应或动画一定持续。用户愿意接受首次等待，不能消除 200,000/百万根后的 CPU 停顿。
- 后端真实 HTTP 在 0.81 s 被客户端取消：约 0.83 s 检测断开、约 0.87 s worker 结束；随后小请求 HTTP 200。1 s 预算超时返回 503，约 1.9 s worker 结束，下一次小请求正常。已发出的页允许填充共享缓存，取消不承诺立刻中断所有已发送 I/O。
- 原始库 60,000 远跳中切商品：新商品约几十毫秒恢复，旧回调没有覆盖新商品；旧导航 Promise 仍等到配置的 5 s 超时。
- **同商品远跳尚未完成时再跳回最新**：原始公开 `setVisibleRange` 新导航报 `Value is null`，旧导航随后完成并把视图放在旧目标。需要应用协调导航代次，不能依赖正常 getBars 自动取消旧意图。
- 注入一次 getBars 503：原生 thread 保留 `_errorMessage='injected 503'`；再次远跳没有新 getBars，返回 `Value is null`。因此错误收尾修复需要保留，与是否窗口化独立。
- 公开 `resetCache + resetData` 探针重置后回到近期范围，丢失此前远历史位置；重新定位再次请求约 59,788 根。启用 `request_only_visible_range_on_reset` 在本探针中没有避免这一行为。它不是已经验证的“直接免窗口远跳”替代方案，真实更正时的定位保存仍需处理。

## 闪烁与窗口方案的得失

此次用户闪烁的具体链路：历史窗口尾游标与 latest 不连续，后端将缺口/积压提示为 reset，前端无条件 `reloadHistory → refreshChartWindow → rebase`；此外导航中可见范围变化误触发较新侧换窗。历史模式本身并不要求几秒一次重建。

本轮只复测已部署的候选修复，没有继续部署：用户原 EURUSD 混合布局，点击 D1 后静止 16 秒、只 hover 另一个 bar 再等 16 秒，M5 恰好一次必要切窗，无后续重建或无关 reload。实际保留约 2,759 根 M5，图表宿主页 JS 堆采样约 45 MiB。与上面的三指标合成测试**不是等条件 A/B**，只能证明窗口能保持有限数据和候选版本去掉了重复重建，不能把所有性能差异归因于窗口方案。

| 维度 | 原生连续加载 | 有限窗口 |
|---|---|---|
| 首次远跳 | 获取目标到已有边界的走廊；冷请求可能很长 | 获取目标附近与必要前缀 |
| 同浏览器复用 | 好，已载入区间近乎立即定位 | 当前窗口好；远切需要重建，PG 仍复用 |
| 多图/指标内存 | 随实际保留数量增长 | 更容易保持有限 |
| 向新侧拖动 | 连续历史自然支持 | 自定义边界延伸与过渡 |
| 向旧侧追加 | 当前原生大序列可能产生长任务 | 单次参与处理的数据较少 |
| 订阅、更正与生命周期 | 接近供应商合同；取消/错误仍需协调 | 多了身份、源代次和范围相关 reset 判断 |
| 维护/升级 | 私有挂钩可缩小 | 多个私有原生挂钩需要逐版本核查 |

## 建议的下一阶段（尚未实施）

1. 把十字线重放、错误收尾和导航代次保留为独立修复，不和取数策略一起回退。
2. 优先优化 PG 热快照的元数据重复传输/解码和冷页反复扫描，保持一致观察版本、覆盖证明与更正合同。否则放宽上限后“缓存以后快”收益会被读取成本吃掉。
3. 让正常 getBars 在资源预算内按原生需求完整满足，上游分页与整段容量解耦。长冷请求采用可观测、可取消的取数生命周期；必须独立解决 HTTP/代理/任务预算，不能只把默认 8/25 秒任意调大。
4. 容量判断同时考虑单图实际保留量、总图数、指标和客户端处理成本。60,000 适合进入候选验证范围，**不是已经建议的无条件新上限**；200,000 三指标追加停顿、多图近 2 GiB、百万根十秒阻塞均应进入保护条件。
5. 对极远请求明确选择：接受加载等待和大前端成本、提示缩小跨度，或保留经专门验收的有限窗口作为性能选项。不要为了降低等待而静默截断 countBack，也不要把供应商不可取范围伪造成历史起点。
6. 沿用现有合理储备减少追加频率，不减少拖动缓冲。追加一次就重算大量已载入序列的问题需要单独确认可优化的公开能力或原生行为，不能靠 PG 命中解决。

本轮证据支持用户对方案复杂度的担心，也确认大序列本身有真实性能代价。选择原生为主要路线有依据，但实施前必须明确容量预算和极端需求的体验取舍。没有将研究结果当作生产验收或自动批准重写方案。

## 复跑入口

浏览器实验：[advanced-native-large-history.research.cjs](../web/tests/advanced-native-large-history.research.cjs)。需要合法许可分发和已验证原始 bundle 私有副本，不将许可文件放入报告或 Git。副本可由现有 installer 的 `--disable` 恢复，再校验 SHA；不对正在运行的许可副本执行 disable。

```bash
LARGE_HISTORY_OUTPUT=/tmp/native-large-history-research \
LARGE_HISTORY_ORIGINAL=/private/original-library.js \
LARGE_HISTORY_CASES='[{"size":60000,"charts":1,"studies":3},{"size":200000,"charts":4,"studies":3,"mixed":true}]' \
```

真实缓存实验：[native_large_history_probe.py](../scripts/native_large_history_probe.py) 和 [native_large_history_http_probe.py](../scripts/native_large_history_http_probe.py)。只在使用独立 `chart_sync` 数据库的临时容器执行；脚本断言 PG hostname/database 和通知关闭，不适用于生产。HTTP 服务端口只能绑定 localhost，结束后删除容器。`provider:true` 浏览器实验需先启动该本地研究服务；原生正常 API 仍保持原容量限制。
