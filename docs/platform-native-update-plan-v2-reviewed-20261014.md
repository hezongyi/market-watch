# 平台行情原生更新与历史拖动保留方案

日期：2026-10-14。代码基线：v1.25.3 / 6679a70。方案版本：v2，已根据 GPT-6.1 Sol（max）首轮审阅补充数据合同，待针对性复审。尚未实施、未修改生产。

审阅依据：[首轮报告](research/platform-native-update-plan-review-sol61-20261014.md)。原始 [v1 审阅基线](platform-native-update-plan-v1-reviewed-20261014.md) 完整保留，SHA256 为 `d37c6f1890708bf65235b5e137c82f6e0ce88ba38b2368353fe2fc9af2925472`。

## 目标和已确定的边界

平台行情的当前 bar 更新、新 bar 追加使用原生 `subscribeBars` 回调；历史加载继续通过 `getBars`。保留现有历史缓存、后台预热、动态左侧储备、连续导航、多图联动和指标预热，不退回等待拖到边缘才取数的方式。

“原生更新”指图表交付方式，不指浏览器绕过后端直接连接供应商。预热可在图表静止时运行，正常历史扩展不需要 resetData。真正已加载旧 bar 的修订、删除和缺口修复仍须处理，不能用忽略修订换取不闪。

此次首先落地平台行情；修改共享流或恢复通路时，组合行情必须回归，保留它既有的组合规则与展示快照机制。Supertrend 属于同轮验收范围。绘图工具可见范围不在此方案中再次调整。

依据：[原生更新合同](research/native-chart-update-contract-20261014.md)、[拖动兼容性](research/platform-native-update-pan-compatibility-20261014.md)、[历史更正详细分析](research/m1-continuous-update-remediation-20261014.md)、[生产实测](verification/m1-production-20261014/README.md)。

## 更新决策

| 已验证的事件 | 价格序列动作 |
| --- | --- |
| 最新 bar 的同时间戳更新 | 回调完整 bar；不 reset |
| 新时间戳的 bar | 有序追加；不 reset |
| 正常向左分页、历史储备补充 | 继续现有历史扩展；不因补充本身 reset |
| 仅完成、确认、覆盖状态或 revision 改变，绘图输入相同 | 更新观察凭据；不 reset 价格序列 |
| 已接受的旧 bar 时间、OHLC、实际供应 volume 改变，或历史新增/删除/缺口修复 | 验证并合并更正，进入受控恢复 |
| 断线重连、结果 epoch 改变 | 先核对已有序列及缺口；不能仅凭连接变化推断历史已改 |
| 账户、来源口径、品种/周期或系列绑定改变 | 隔离旧订阅及结果，重建相应序列 |

主图无需 reset 不等于所有指标无需重算；按指标真实依赖分别判断。不能普遍忽略 volume，也不能仅比较数据库 revision。

## 实施步骤

### 1. 建立逐事件的修订证据和交付基线

按实际数据集身份、周期、订阅世代记录有界的已交付 time/OHLC/volume，以及历史接受范围、实时游标、来源版本和指标依赖身份。以接受后的数据为比较基线，不把后台缓存更新或 SSE 发送直接等同于图表已接受。

采用“服务端提供修订候选、主机按交付基线复核”的责任划分。现有服务端发送 cursor 仅用于传输去重/接续，不能作为图表消费证明。主机在当前 source/cache generation 的原生适配器成功回调之后提交交付账本；它证明接口接受，不证明已经绘制。候选核对请求携带 listener/generation/result epoch、接受区间及绘图投影凭据，由同一观察下的数据返回明确差异/无差异/证据不足；异世代响应不采纳。共享计算任务继续按数据集复用，不为每个浏览器复制计算任务。是否复用已有 history_observation 或增加专用核对字段按接口验证决定，但必须落实此合同。

投影使用最终供应给原生图表的 chart_time、数值转换和实际 volume；不能直接复用带 complete 的 price_input。主机账本按现行单源/工作区条数与字节容量上限约束；覆盖被淘汰、缺少插入/删除证明或核对超预算时，进入明确的一致性恢复，不推断相同。

对记录到的 reset 候选比较旧新投影并分类：状态变化、真实数值更正、交付乱序、缺口或凭据失配。基线不足或无法验证时进入明确的一致性核对，不默认为无变化。私有明细不提交，公共证据保留分类计数和时序结论。

此步骤解决现存证据缺口：尚不能断言生产每分钟 reset 都是状态误判，也不能把组合的真实展示差异归为纯元数据变化。无需用户额外说明。

### 2. 收敛平台 reset 条件并保持分钟交接顺序

在共享 market stream 中使用上述分类。仅状态变化推进凭据，不触发价格恢复。若上一 bar 的最终值在追加新 bar 前已到达，先更新上一 bar，再追加新 bar；不能为了等最终确认无限阻塞新分钟，或凭时间到点制造 bar。

分钟交接事件在同一观察中显式提供旧尾柱的最新完整投影、后续新柱和来源凭据，不能依赖现有 delta 恰好带旧尾柱。主机按自身接受游标决定旧尾柱仍可实时更新还是已成为历史，按时间顺序交付；若最终值尚未到达，立即按真实来源交付已有新柱，迟到更正再核对。重连按真实交付游标补齐，超出有界重放范围则修复缺口。

最终值在新 bar 追加后才到达且实际有差异时，按历史更正处理。保持订阅 generation/sequence、迟到响应隔离和断线补齐。

### 3. 保留无感拖动机制并修好分页与实时交接

保留 provider cache/service、PG 连续历史证明、后台历史 interest、原生 countBack/from/to 分页、储备请求调度、容量保护和取消逻辑。

保留现有储备策略：普通约 2 屏阈值/1 屏批次，快拖约 3 屏阈值/2 屏批次；这些是当前策略，不是无限无等待承诺。首次加载完成、拖动或缩放后均可检查不足并提前补充。

历史分页扩展已接受范围时，保留 acceptMarketHistory/registerMarketBar 协调，但须确保旧历史响应不回退实时游标、不覆盖较新的接受凭据，重新注册订阅不漏新 bar。历史浏览不得被实时更新强行拉回尾部。

接受凭据按有界区间记录：左页仅证明该页接受范围，不把该页全局 as_of/revision 推广到全部已加载历史，也不能靠全局取 max 合并。重叠区域逐投影核对，同版包完整覆盖时才可合并证明；实时尾部游标单独维护。历史首次插入、删除及时间标签变化都属于候选，不能只查 revision>1。换订阅世代时以最后实际交付游标衔接新快照/重放，并拒绝旧响应；区间或重放容量不足转为受控核对。

### 4. 将必要历史恢复做成受控事务

合并同源同周期更正，固定本次版本，先准备覆盖所需历史及指标前缀的数据，再失效和重取。只恢复相关序列，保留视窗、间距及无关图表缓存。恢复期间后续实时更新有界排队，按版本和时间顺序接续。

平台 ProviderBar 当前原地覆写，不能凭 cache_revision 重读旧版本；本方案新增“有界不可变恢复包”能力。价格窗口、稳定 origin 起的计算前缀和版本凭据必须在同一短 REPEATABLE READ 观察中获取；结束事务后用这些冻结输入计算并生成包，不为网络/指标/绘制持有长事务。多页或大前缀准备采用有界冻结存储与可验证覆盖，未齐备时不能 reset 或将不同事务的数据冒充同版。

恢复 token 绑定已认证会话、实际来源/账户口径、品种/周期、图表消费者、恢复世代及覆盖区间；同源多图可共享只读输入，提交状态按消费者隔离。准备好的价格页和同输入指标结果由主机不可变种子缓存服务此次 getBars/指标需求，不再回读当前 ProviderBar 冒充旧包版本。新增接口字段必须显式支持/拒绝，不能被旧接口 extra=ignore 静默丢弃。

恢复包条数、工作区加权容量、响应字节、计算资源、TTL及并发准备数复用/纳入现有能力预算，原型记录明确生效值；超预算或过期返回明确错误并保留原图，不先清空。不缓存无界完整历史，不长期持有连接。原生 reset 默认可能重新请求全部已加载范围，因此准备范围按实际消费者需求及指标前缀验证，不能只覆盖可见屏幕。缺少覆盖时在重置前扩大/重建包；重置后出现意外需求则进入明确失败/重建流程，不混入当前版本。包完成、切身份、过期或失败后释放，后续版本从接受游标验证并接续。

先在 Ubuntu 验证通过公开能力暂时保留最后完整画面的可行性。准备和绘制过程中明确标记待更新；撤下旧画面必须等待所需历史和指标全部接受并完成绘制，不能只凭首次 onDataLoaded。用户拖动、缩放、切品种/周期或布局变化应取消过期恢复和视窗回写；最终需重新核对并完成更正，不能无限延后。

异常恢复包含超时、取消、重试和缓冲上限。保留画面不能无限冻结、假称最新或挡住用户操作。若公开能力无法满足必要恢复时的画面连续性，应记录为未达到的验收项，不能把减少 reset 等同于彻底修复闪烁。

最小状态机为 ready → preparing → resetting → applying → catching-up → ready；任何阶段可进入 error，明确取消/重试出口。更正责任与视图动作分离：拖动/缩放立即移除旧画面并取消旧视窗回写；同一数据身份继续按最新需求准备或完成更正，不因视图取消丢掉责任，不盲目反复 reset。切身份则废弃旧责任及队列。

主机维持独立于显示提交的恢复输入通道，队列按 identity/listener/generation/result epoch 分组。旧世代事件不混入新队列；同柱更新可合并，但最早历史更正和缺口证据不能丢。世代切换从实际交付游标重新注册/重放补齐，不宣称被 fencing 丢弃的事件已成功缓存。队列超条数/字节上限、序列缺口、epoch变化或包版本无法衔接时，废弃待提交包并重新核对，不直接回放。原型明确准备/恢复的有限超时和重试次数，达到上限转 error/可重试并释放旧画面；不能用现有 500/1000ms 重试循环无限冻结。

### 5. Supertrend 与价格版本一致

维持稳定计算起点，拖动加载更多价格历史不能随意改变递归计算种子。当前更新和新增随同一价格版本计算；真实历史修订从最早受影响输入之前的有效计算状态重算后缀，不能只替换末点。

隔离旧计算结果，避免新版价格配旧指标并宣称已同步；计算待完成时显示明确状态。保留确认计算与告警语义，测试不新建通知或告警。

平台 visible bars、递归前缀、返回版本统一从冻结观察读取，修复非 SWING 指标第二事务读取前缀却沿用第一事务价格凭据的路径。交付合同为价格接受 token → 指标请求 token → 返回输入身份/范围/版本 → applyBatch 核对；异 token 结果拒绝，不能仅凭指标页之间 cache_revision 相同就提交。正常增量也须绑定实际价格输入身份和前缀版本；后台读取更新了版本而价格未接受时不得假称同版。

价格先推进时受影响旧指标标记为旧/待计算，无法清晰标旧时撤回；同版结果接受前不得 ready。这属于逻辑版本协调，不宣称原子绘制。重算可直接使用同版稳定完整前缀；不强制新增持久 checkpoint。若采用计算 checkpoint，必须绑定数据集、算法、参数、origin 和已验证前缀版本。complete/coverage/gap 变化即使价格相同也核对指标依赖；展示路径不得推进确认计算或告警状态。

## 原型门槛

先验证消费基线/候选核对和恢复包合同，再验证画面连续性；通过之后进入完整应用实现。客户端截图、chart/study 加载事件以及现有 indicator settle 能提供证据，但没有已证明的公开“所有历史和指标已绘制”屏障。

撤除旧画面的门槛同时包含恢复 token 对应的历史覆盖/countBack/边界、每个必要指标同版接受范围及实际录屏绘制验证；不能凭一个 onDataLoaded、dataReady 或两次 RAF 代替。分别验证多 pane/多图、尺寸主题、用户操作立即移除、旧报价/十字线标识及内存限制，不修改许可库内部存储。

若必要恢复仍可见空白，原型结论为该目标未通过，保持真实纠错；不自动将验收降为“reset 少了”，也不把此方案标记为完全修好。

## 验收与完成条件

开发和验收在 Ubuntu 独立 worktree/Compose 实例进行；此方案不授权新的生产部署。

1. 普通更新：静止图表连续跨至少 10–15 个 M1 边界，正常尾柱更新、新柱追加和纯状态变化零 reset；时间有序、无重复/倒退、无 K 线消失。
2. 拖动保留：在持续更新期间普通/快速左右拖动、缩放、返回尾部和多图联动；对照基线确认缓存保留、请求优先级、视窗/柱宽和指标起点。已预热历史的等待和卡顿不得退化；冷历史、真实边界及容量不足有明确处理。
3. 真修订：分别覆盖最终值在新柱前/后到达、volume 修订、旧 bar 新增/删除和缺口。更正后价格符合供源、Supertrend 符合同版本完整重算；仅状态变化不触发价格恢复。
4. 并发和失败：分页与实时更新竞争、断线/epoch、切换取消、拖动中更正、预取失败、指标超时及多次修订合并，不丢 bar、不接受旧结果、不无限冻结。
5. 视频和事件双证据：无指标与带 Supertrend 分别录屏和记录事件；截图、dataReady=true 或 reset 计数单独不足以证明不闪。组合行情回归，既有布局/绘图工具行为不退化。

确定性回放另含：旧左页迟到、新左页带新版本但不含尾部、已接受范围首次插入/删除、适配器延迟接受与旧世代拒绝、可见范围外且 origin 后的修订、同价状态变化影响指标依赖、包过期/容量拒绝、恢复取消前后接续及多参数/多图共享。Supertrend oracle 使用同一冻结输入和固定 origin 完整重算，核对方向/信号、空值和断点，不能拿当前缓存或仅末点对照。

若上游每分钟真实更正已过去的 bar，公开实时回调无法同时保证及时追加、立即修正全部历史和永不重取。方案保证正常增量不重载，并以必要恢复的画面连续性作为独立验收目标。

交付包含实现、适当自动回归、Ubuntu 联合验收证据和 PR；生产发布另按明确授权执行。
