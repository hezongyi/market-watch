# 自建实时行情：历史基线自动轮换与实时数据定期清理

日期：2026-11-13。状态：**需求与默认规则已明确，待实施**。本文件形成方案，不代表已修改调度、开启自动切换或执行数据删除。

## 1. 目标与实施基线

用户确认的目标：自建行情已开启实时后，定时维护或点击“立即更新”发布了新的可用历史版本，系统自动准备并轮换历史基线；实时分钟数据滚动保留 30 天，满足条件后定期清理。

- 当前分支：`feat/mobile-data-workflow-20261113`。
- 代码参考：`afe9ebc8bbbd80d0c06fdb0f3b773ed56aaeef47`，基于 v2.0.11，含手机数据页全流程实现与验收修复。
- 当前验收：Ubuntu `quant-server`，独立 project `mw-mobile-data-workflow-20261113`，HTTPS 18446。自动激活关闭，retention_mode=off；六个供应商开启。
- 后续实施使用独立 worktree/branch，例如 `feat/managed-live-rollover-20261113`，从上述代码或明确包含其改动的后续基线开始；不覆盖当前 APK 验收环境。
- 风险 **F1**：涉及持久修订激活、告警绑定及后台物理清理。需 PostgreSQL 并发/恢复验证、Ubuntu 隔离实例真实流程及适用 R2；按 AGENTS.md 完成独立 Standards/Spec review。方案编写本身只改文档。
- 当前无需再向用户澄清；以下默认规则均落实已讨论的行为，运行参数由实施者按本方案设置。

## 2. 产品规则

### 2.1 何时轮换

1. 对支持接续、实时开关已开启、默认实时映射有效的自建行情生效，包含已有接续配置。
2. 定时维护和手动“立即更新”同样生效。保存维护设置本身不强制生成版本或切换。
3. 维护运行完整成功、所需周期发布后，后台寻找最新合格版本。HTTP 更新请求只提交任务，不等待轮换完成。
4. 轮换依赖已有维护计划，不替用户打开实时、恢复暂停的计划、改变维护时间或下载范围。
5. 暂停维护但手动更新成功仍可轮换；实时关闭时不自动激活候选，再次开启后后台重新核对最新版本。
6. 同一版本重复事件只处理一次。连续发布多个版本时优先最新合格版本，合并未开始的重复工作；同日历史修正也可触发，不限制为每日一次。轮询不能使相同版本反复重载图表。

### 2.2 新版本的资格与接续点

- 同一自建行情、历史来源、品种、价格口径、日界规则，继续使用当前明确选择的实时映射；不能采用“任取第一个已审核映射”的策略。
- 新版本 published、非回收、M1 产物非空且可读；维护请求的周期完成，不能仅凭 HistoryVersion.status=published 判定成功。
- 新版本历史起点不能晚于当前基线起点，历史终点不能倒退；部分发布、不可用必需产物、失败或取消任务均不自动接管。
- 按新品种历史末端支持的最近日界计算 T，沿用现有 ny17/utc0 及 DST 规则；T 不早于现有接续点，且在实时可用窗口内。历史日界之前必须有实际基线。
- T 之前使用新版固定历史；T 起使用同一实时来源的确认分钟和当前报价。补齐必要的来源分钟，保留真实缺口及来源标记，不补价、不平滑两个供应商的价差。
- 外汇常见少量 M1 缺口按实际有效数据聚合，不要求每分钟齐全。显著退化、无法提供原有最新数据或不可服务指标/告警时暂缓，并记录具体原因。

### 2.3 用户体验

旧行情持续运行 → 后台准备候选 → 校验通过 → 一次激活 → 自选/普通实时图表刷新到新基线。

- 自选和普通接续图表继续使用相同 MWC 身份；不需要退出、改品种或关闭再开启实时。
- 后台准备候选不会中断原有采集，也不清空共享实时报价和分钟缓存。相同来源采集需求去重。
- 切换前候选需追到明确的激活水位，覆盖旧修订当时已确认尾部；重新读取当前源报价形成当前 bar，避免丢失/倒退。切换不能把数分钟前的候选截止直接当成当前状态。
- 图表保留周期、视区、绘图与指标设置；历史值或指标因新历史修正而改变是允许的，但版本不能混用。使用已有 stream reset/代际隔离机制，旧响应不得覆盖新结果；保留旧画面至新结果可用，失败有明确反馈。
- 明确打开的 MWH 固定版本、固定回测输入继续固定。冻结旧修订和“固定版本仍可访问”是不同概念，不能暗示旧实时修订永久保持供数。
- 手机详情轻量显示当前基线时间、准备中/已更新/暂缓原因；详细失败和清理统计进已有任务/记录入口。无日常确认弹窗、无新增必填配置。
- 属于共享后端行为，网页端同一接续行情也会跟随轮换；保留网页已有维护表单、图表拉取和预取策略。

### 2.4 告警与旧引用保护

现有 `switch_activation.publish` 会冻结旧修订；`composite_alerts.rebind_active` 对固定价格规则保留旧绑定并可能置为 blocked。每日轮换不能直接照搬这一副作用。

本轮采用已讨论的保守规则：

1. 激活前列出当前绑定规则。能够保持语义且可安全迁移的规则复用既有修订迁移能力，明确切换事件边界，重建判定基准，不把历史价格修正当成一次新穿越。
2. 对固定价格绑定、几何/指标无法保持或其他会因激活而停用的规则，**暂缓该品种的自动轮换**，保持旧运行与告警，不先切换再报告告警被阻断。
3. 激活事务内再次检查规则/版本，防止预检查后新增或编辑告警的竞态。现有手动修订接口的显式语义保持不变。
4. 手机显示“基线轮换暂缓”及原因。接续点接近 30 天窗口时提示需要处理，不能静默无限挂起。
5. 暂缓不等于永久满足自动轮换：交付必须清楚展示此保护性例外。为所有固定告警新增“跟随基线”语义、永久并行维护旧实时修订不属于本轮默认范围。

## 3. 实时数据保留与清理

### 3.1 时间与数据边界

- 原始确认 M1、其来源修订及相关接续输入滚动保留最近 **30×24 小时**，按数据所属 UTC 时间计算；基线轮换不重置年龄。
- 只选择 `start < now - 30 days` 的分钟；边界分钟保留。跨越边界的聚合桶、响应 blob 要完整核对 end/全部内容，不能只按创建时间或主键删。
- 新接续点之前的长期行情由固定历史提供；最近 30 天实时来源数据继续保留用于补齐、排查。固定历史与实时供应商可能价格不同，清理后不承诺还原被删除的实时原始输入。
- 当前报价用于当前 bar；本轮不新增全量 tick 永久归档，也不扩展其他供应商平台缓存的 TTL。
- 不删除本轮之外的历史版本/历史分块、行情身份、来源映射、告警配置、切换审计与引用记录。历史版本物理回收继续走原有独立流程。

### 3.2 允许删除的条件

同时满足：

1. 对应来源有可核对的 succeeded 基线切换记录，新活动基线能够服务所需长期历史；失败/部分激活不解锁删除。
2. 数据已经超过 30 天；没有运行图表/固定读取、告警、回测/策略、活动候选、任务或历史内容引用。先盘点仓库实际引用模型，事务内复核，不能把外键可删除当成语义无引用。
3. 共享 source 的其他自建行情、原生读取和未完成任务均已检查。不能按一个 dataset 的日界直接删除整份公共来源缓存。
4. 最近 30 天、当前活动基线/接续所需数据、未确认有无引用的数据均保护；引用解除后再纳入后续批次。
5. 保留现有恢复验证门禁。首次 execute 必须有实际备份恢复证据及有效 marker，不能手工伪造通过标记。

### 3.3 调度与中断恢复

- 轮换成功后唤醒现有清理 worker；低优先级周期巡检继续处理到期数据，不依赖用户下次打开 App。
- 复用现有每批上限、分块事务、外键顺序、游标与运行记录。清理失败或进程中断可恢复，不阻塞实时采集或下一次历史维护。
- 同一清理批次重试幂等；**不同巡检日期必须能创建新批次**。现有“一次切换一个完成批次”的机制不可直接作为永久定时清理，否则只清理一次。
- 同一来源和 UTC 日期合并重复清理唤醒，不为每个图表/品种重复扫描整库。成功切换记录是授权依据，日期批次是进度身份；不能伪造成功切换来驱动每日清理。
- 即使该日没有新版本，仍可清理已有成功接续范围内新到期且无引用的数据；当前运行/阻塞候选仍有引用的数据继续保护。
- 当最近若干条全是失败/已完成运行时，仍应找到合法待执行来源；修正现有 `tick()` 只检查最新 20 个 run 可能饿死旧来源的问题，用有界分页/明确待执行索引，不做无界全表循环。
- 每批记录边界、来源范围、删除量、跳过量和原因。模式保留 off/dry_run/execute；dry_run 与 execute 分别幂等，不能混淆报告与实际删除。

自动候选身份至少包含 composite、父修订、目标历史版本、当前映射和接续点；激活时 compare-and-swap 当前修订。并发手动改映射/日界/激活后，旧候选不得覆盖新选择。准备阶段可有界重试瞬时错误；已实际失败的激活保持记录，不无限自动重放有副作用动作，明确重试才新开 attempt。

运行默认采用现有 worker：后台最多每 60 秒核对遗漏的成功维护，已有激活循环最多每 5 秒检查就绪候选；提交后提示只缩短等待。清理循环每 60 秒检查，每个来源按 UTC 日期建立一个可恢复批次，轮换成功可立即唤醒当日批次；完成后该日期不重复扫描。

配置建议新增 `ALERTS_MANAGED_ROLLOVER_ENABLED`（代码默认 false，发布时显式设置），专门控制维护触发；保留 `ALERTS_SWITCH_AUTO_ACTIVATE_ENABLED` 作为自动激活总开关。新隔离验收显式开启这两项；对开启日更轮换的托管行情，每周流程与日更共享候选，不能另开竞争激活。保留 `ALERTS_RETENTION_MODE`，先 dry_run，再在恢复验证通过的任务测试库 execute。普通用户只操作既有维护与实时开关，不需填写这些运行配置。

## 5. 有序实施步骤

1. 固定新 worktree 基线，盘点 runtime 接线、实际引用模型和现有测试；形成 F1 改动清单。当前验收实例保持原样。
2. 实现维护成功→可恢复候选核对；补重复事件、同日修正、连续发布、重启补偿和精确映射测试。
3. 接入现有准备/激活链路，先完成告警保护、尾部追赶、CAS 与旧写入 fencing，再允许自动激活。
4. 打通共享 stream、手机自选/图表及桌面跟随；验证固定版本不漂移，当前 bar 与指标刷新正确。
5. 实现每日清理批次和公平巡检；补引用保护，先用 dry_run 验证来源与候选边界。
6. 用任务专属 PostgreSQL 和夹具数据完成 30 天边界/并发/中断恢复；执行真实备份恢复校验后，才在该隔离测试库运行 execute。不能调整宿主时钟制造数据年龄。
7. 在独立 Ubuntu 全服务实例用真实供应商完成历史更新→自动轮换→继续实时；清理的旧数据场景用明确夹具补验，两类证据分开。
8. 独立 review、必要修复和最终截图/运行证据；按用户当前指令处理 PR/CI。生产启用、正式 tag 和 Unraid 操作仍需本次明确授权。

| 恢复与开关 | dry_run 不删除；无成功切换或恢复 marker 不删除；执行中断恢复且计数正确；off 真正停止调度/删除 |

## 7. 停止条件与交付

出现数据来源变化、切换后当前 bar/确认水位倒退、告警被自动停用、固定读取漂移、跨来源/引用误删、恢复失败或隔离资源不足时，保留证据并停止受影响的自动激活/清理；保持能运行的原基线，不扩大到生产或其他任务。

交付必须包括：实现提交、实际 schema 变化、测试结果与 skip、真实 Ubuntu 地址/启停命令、旧新历史版本与 seam 证据、连续实时报价与当前 bar、告警保护案例、清理 dry_run/execute 差异及恢复记录。只完成轮换而未证明周期清理，或只有清理报告未执行隔离库验证，均不能声明需求完成。

停止轮换/清理开关能阻止后续动作，但不会撤销已删除数据。清理后的恢复依赖已验证备份；切回旧基线也必须重新确认其必要输入仍在且准备完成，不能仅回写 active_revision_id。

当前 APK 真机仍需用户协助验收；本方案不要求为纯 Web/后端改动重装 APK。当前任务未取得生产发布或生产数据删除授权。
