# 原生连续历史加载实施方案

日期：2026-10-04；实施状态更新于 2026-10-05：P1～P4 已形成 Ubuntu 隔离候选，P5 自动验收证据已归档，原用户人工验收待反馈。详见 [逐项审计](native-history-completion-audit.md) 与 [验收交付](native-history-acceptance.md)。本文件保留技术路线和验收合同，未获得生产发布授权。

依据：[独立复评](native-history-decision-reassessment.md)、[性能证据](native-large-history-analysis.md)、[官方合同核查](native-large-history-official-research.md)。原问题规格中的静止光标、失败恢复、交易日历、指标、布局保持要求继续有效；其中“远跳默认有限窗口”的技术路线由本方案替代。

## 1. 方案决定

默认采用**原生连续历史加载 + 后端分页持久缓存 + 有限资源预算**。

正常 `getBars` 按原生必需数量取数，允许在通过验收的预算内超过现有 20,000 根。供应商单页限制只决定后端分页方式。首次缺失历史写入 PG，后续请求复用；当前 widget 已载入区间继续直接复用原生缓存。

撤除默认按约三屏距离切窗的策略。保留十字线重放、导航竞争处理、失败恢复、历史修订核实；这些能力与是否切窗独立。

本期不实现自动混合切窗，不在超时或 hover 时切换数据模式。现有有限窗口候选保留在隔离分支/构建中作为比较材料，未完成验收前不作为可发布回退版本。超出预算时保留有效图，解释原因并允许调整周期或跨度。

产品范围：优先解决原 EURUSD 四周期布局超过 20,000 根的实际远跳，以及点击后鼠标静止的光标错位。任意年份的分钟历史、百万根多指标并不属于无条件支持承诺。如果预算验证无法覆盖原问题实际目标，本期不能以“已加超限提示”宣告问题解决，必须转入有限历史浏览模式的专项设计和验收。

## 2. 用户操作合同

| 场景 | 应有行为 |
| --- | --- |
| 目标已在原生缓存 | 直接定位；最终视区就绪后重放十字线 |
| PG 已覆盖目标走廊 | 一致快照读取、正常历史回调；不切窗 |
| PG 覆盖不足 | 后端分页补齐并持久化；图表保持加载提示，可继续改变导航意图 |
| 加载较长 | 显示正在加载历史及可取消状态；有真实阶段/页数才展示，不伪造百分比 |
| 加载中点击另一目标、切周期或回最新 | 旧导航失效，新导航优先；旧结果不改变新视区 |
| 仅移动鼠标 | 更新语义光标，不启动窗口重建或取消有效导航 |
| 超时、503、繁忙、预算不足 | 结束本次等待，保留已有有效图，提示可采取的操作；后续操作可恢复 |
| 真实历史修订 | 刷新受影响的数据源并恢复视区、指标、画线与光标 |
| 流 gap、重复通知或范围外更新 | 核实已交付历史是否变化；未变化不重建 |

网络等待可取消不等于同步图表计算可立即中断。浏览器交付前必须执行预算准入，不依赖卡顿发生后的取消按钮保护本次操作。

## 3. 历史读取模块

### 3.1 需求与快照

输入保留商品身份、周期、`from/to/countBack`、指标前缀和观察版本。数量合同为：满足真实 `[from,to)` 范围与 `countBack` 两者中的较大需求，再满足指标前缀；可选储备另计。

把当前 `CAPACITY` 的职责拆开：输入安全上限、实际必需量、查询行数、可选储备。禁止每次小请求按全局最大容量读取完整缓存。

快照采用短一致性事务：优先验证 PostgreSQL REPEATABLE READ 下分别读取一次 dataset 元数据和有界 bars 的方案。bars、coverage、revision、修订判断来自同一事务快照；上游 I/O 全部在事务外。访问时间等 housekeeping 尽量在快照外处理；若现有事务调用者不允许这种拆分，采用保持同一语句快照的查询重写。最终以并发修订测试和 profile 决定实现，不以降低解码时间牺牲观察一致性。

冷分页循环只查询规划下一页所需的覆盖、游标和有界数量，避免每页反复解码全部历史。数据齐备后读取最终一致快照；期间发生修订时重新核实，不拼接多版本页面冒充单一观察。

替换固定 80 轮循环为显式的页数、时间、并发预算和无进展检测。页数预算由实际需求和供应商分页能力计算并受硬上限约束；每轮检查覆盖/游标进展，无进展按有界重试后失败，不能无限循环。

### 3.2 快路径与长加载

热缓存/可快速完成的请求继续使用现有 `/charts/data` 成功结果合同。大冷请求使用历史加载任务，避免一个普通 HTTP 请求承担分钟级分页。

建议增加以下逻辑 interface，具体路由与现有鉴权风格一致：

| 操作 | 请求/结果 | 约束 |
| --- | --- | --- |
| 提交历史需求 | 查询参数及幂等请求标识 → 已完成结果或加载句柄 | 先验预算；同一客户端重试不重复排队 |
| 查询加载状态 | 句柄 → waiting/filling/ready/failed/expired | 只返回真实进度；等待轮询有退避和总截止时间 |
| 取得历史结果 | 句柄 → 当前一致快照，或继续等待/明确错误 | ready 表示覆盖齐备，交付仍须验证最新观察；不能沿用过期 revision |
| 解除等待 | 客户端自己的句柄 → cancelled | 幂等；不取消其他消费者所需工作 |

任务状态存 PG，执行采用独立行情历史 worker，复用供应商限流、dataset lease 和单页提交。优先扩展已有 provider 调度能力，复用前先核查其固定数量/时间窗口限制；不直接把大 countBack 塞入现有预热兴趣记录。

历史 worker 与业务通知 worker 分离，验收环境仍关闭业务通知。任务应有所有者、截止时间、消费者租约、执行租约和终态回收；进程重启后能继续利用已提交页面，过期消费者不能留下无限后台下载。

重叠需求通过现有 dataset lease 和 PG 覆盖共享已完成页面，不要求首期实现复杂区间合并算法。单个消费者取消后停止其后续分页；其他消费者继续自己的需求。已发出的页可完成写入，旧 worker 不得在租约被接管后提交。

该协议由宿主/bridge 包装，原生库仍看到一次 `getBars` 的最终异步成功或失败回调。进度单独传递；不以多次调用同一个历史 callback 模拟流式数据。

### 3.3 错误语义

保留结构化错误通过后端、宿主、postMessage、bridge 传递，至少区分：参数无效、预算不足、服务繁忙、供应商失败、超时、取消和数据暂时不可得。沿用现有错误码时保持兼容。

只有已经核实的历史耗尽才返回历史终点。预算不足、超时、缓存未齐、供应商暂时不可取不得转成 `noData:true`。行情商保留范围需单独表达，PG 已有更早历史仍可复用。

## 4. 导航、光标与原生适配模块

维护三种互相独立的版本：导航代次、数据源代次、光标版本。所有异步完成事件先校验所属代次，再提交视区或状态。

导航状态依次为 `idle → loading → applying → idle`；失败或取消必须回到可操作状态。新导航使旧导航失效，清理其 HTTP/任务消费者和原生 deferred/subscriber；不能只丢弃响应却让原生继续永久等待。

共享数据源有多个图表消费者时，取消一图不能清空仍被其他图使用的缓存或请求。布局销毁、商品/周期变化、恢复布局都走统一释放流程。

光标保存源图、语义时间和必要的价格信息，不保存最终像素或旧 bar 索引。在有效导航数据完成、最终视区绘制后，按最新仍有效的光标重放。关闭同步、源图离开或销毁后不得重放旧光标；沿用原生日历映射。

现有 `native-navigation.js` 按职责拆分/收缩：默认路线去掉窗口锚点、窗口身份修饰、向新侧切窗及三屏阈值；保留并隔离必要的错误收尾、导航协调和光标挂钩。不得通过关闭整个现有总开关同时关闭这些修复。

私有挂钩继续用许可库 SHA、唯一锚点及幂等安装检查。修改库字节后生成新内容版本 URL，验证旧缓存浏览器更新。许可资源保持 Git 忽略。

## 5. 历史修订模块

观察记录覆盖已实际交付的历史及指标依赖前缀。分页扩展时保守合并观察，核实完成时处理并发扩展，不能用较新版本号掩盖较旧页面的未核实范围。

SSE reset/gap 触发范围核实：未变化只推进已验证观察；真实更正才刷新。重复通知合并，旧数据源 review 取消；核实失败保留有效数据并标记待重试，不能默认为未变化。

刷新保存商品、周期、可见范围、柱宽及有效光标；采用经测试的定向原生失效流程，避免 widget 级清空连带其他图。相同原生数据源共享图需要一起获得一致修订。

`resetCache/resetData` 可能丢失远历史位置，因此恢复位置及重新加载成本属于正式验收项。`request_only_visible_range_on_reset` 不作为已证明可行的捷径。

## 6. 资源预算与性能验收

后端预算包括必需 bars、指标前缀、响应 bytes、任务存活时间、页数和供应商并发。前端预算包括各独立数据源累计常驻量、指标、正在处理的响应及切换重叠内存；共享关系未知时保守计数。

前端对同一工作区同时发起的导航预留预算，完成、失败或取消时释放预留，防止多图同时通过单图检查后超额。预算在追加历史、切指标和恢复布局时重新校验，不只在首次远跳执行。

先减少可选储备；必需需求仍超过预算则明确拒绝并完整结束生命周期，不静默截断或自动改变用户缩放。预算由后端提供版本化能力配置，宿主与 bridge 采用相同合同；后端始终独立强制校验。

本方案不把 6 万或 20 万直接指定为正式上限。实施必须产出一份随候选版本归档的预算配置与性能验收记录：参考硬件、原布局与指标、支持的请求/常驻范围、bytes/并发/截止时间、点击至可交互耗时和最大输入阻塞。数值须在隔离候选实测后固化，未固化不得扩大发布容量。

性能验证分三层，不能用一层结果代替另一层：

- 后端：相同缓存和需求下 profile 对照；小请求面对大缓存不再按硬上限读 bars；冷分页解码工作量不随已完成页反复全量增长。
- 完整产品：真实 HTTP、宿主 postMessage、bridge、原生指标及 Python 指标组合；冷 PG、新页面热 PG、同 widget 已载入分别记录。
- 长期使用：旧侧追加、2/4/8 图、多次导航/取消后的常驻量及浏览器进程内存；资源最终回落，无持续泄漏或无界累积。

如果后端优化后，原问题目标仍因原生处理产生不可接受的持续交互阻塞，不继续提高容量。转入单独的有限历史浏览模式方案；这属于明确的后续分支，不在本期暗中加入自动切窗。

## 8. 必须通过的正确性检查

| 检查 | 成功标准 |
| --- | --- |
| 原 EURUSD H4/W1/D1/M5 布局 | 原超 20,000 目标成功；点击后静止光标准确，无后续无关重建；hover 不重建 |
| 新意图覆盖旧意图 | 远跳未完成再点另一日期/回最新，最终停留于新目标，旧回调不反向覆盖 |

| 共享与生命周期 | 同商品同周期不同图位置正确；取消一图不破坏另一图；销毁后无消费者残留 |
| 操作与日历 | 日期跳转、范围同步、布局恢复、切周期；OANDA/Binance/Yahoo 适用范围及 D/W/M、DST 映射 |
| 指标与几何 | 原生/Python 指标前缀正确，柱宽、价格轴、画线、用户同步开关保持 |

测试应通过公开产品操作和模块 interface 检查可见结果；必要的原生内部观测仅用作定位/证据，不能用内部标志代替最终视区、光标及可操作性。

## 9. 验收环境、交付和回退

使用 `/home/quant/repos/market-watch-chart-sync` 所属独立工作区，不改主仓库其他工作。开发、验证、验收全部在 Ubuntu 本机独立 Compose project、网络、volume 和数据库中运行；新候选使用独立于现有人工验收实例的项目名称与端口，保留原候选便于同条件比较。

Compose 明确包含 API、web、chart、PG 和按需启用的历史 worker；业务通知关闭。项目名、实际地址、镜像版本、启动/停止命令、验证结果在实例真实启动后记录到验收文档，本方案不虚构运行地址。凭据只放私有配置目录。

新数据库字段/表采用增量兼容迁移；本期不删除行情缓存，不以清空 PG 制造回退。验收和后续发布保留上一完整构建及配套配置，回退时结束新任务消费者、停止新历史 worker、恢复匹配的前后端构建并重载 widget，不能在运行中的图表上热切换数据模式。

现有有限窗口候选未完成验收，不作为生产回退目标。未来生产发布另行记录可用的已发布版本及其已知限制；不以回退掩盖原缺陷。生产不属于本轮实施/验收环境，不在 Unraid 创建任何开发或临时调试实例。

最终交付包含：实现提交、预算配置、完整产品测量与正确性证据、Ubuntu 访问和启停说明、人工验收结果、仍有限制及对应回退步骤。缺少原问题成功复现对照或真实修订链路验收，不标记完成。
