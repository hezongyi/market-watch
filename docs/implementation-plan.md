## 2. 交付范围

### 2.1 第一版完整范围

1. EURUSD、XAUUSD、BTCUSD 或 BTCUSDT 行情、K 线和数据状态。
2. 普通价格预警：指定价格，向上/向下穿越，可选择即时报价或指定周期收盘确认。
3. H4 回落/反弹结束预警：连续阴线且低点下降后的上破，及对称卖出条件；N 默认 2，可改 3 或更多。
4. 前日高低点突破：默认 M5 确认、双向、跨日更新前一有效交易日。
5. 人工开启、仅对开启后的事件触发、一次触发即完成监控。历史数据可以建立策略准备状态。
6. 网页提示与声音、ntfy 强提醒、独立的确认状态和提醒历史。
7. 历史信号标记、指定日期范围、隐藏未来、手动开启及逐根/加速回放。
8. 页面修改常用参数，Python 扩展策略，版本固定到每条监控和演练。

### 2.2 分阶段交付但不删除的需求

先交付 ntfy 已验证的高优先级响铃，再补齐指定节奏、最大次数、静音与确认联动。原版不支持的功能由自动化适配或最小 Android 客户端承接；这些功能通过验收前不能声称完整第一版完成。

自动下单、盈利回测、多用户、任意网页 Python 执行不在当前范围。

## 5. 行情方案与验证门槛

### 5.1 数据源选择

- EURUSD、XAUUSD 优先验证 Dukascopy；BTC 先验证同源 BTCUSD，若不合适采用可达交易所 BTCUSDT 现货。
- 仅在有可用账户和权限时采用 OANDA；不将开户或三品种免费权限视为现成条件。
- 三品种必须分别记录数据源、真实交易对、市场类型和报价口径。运行中的监控不自动切源；切源需重新建基准和监控。
- 第一版以完整 M1 OHLC 自合成 M5/H4/D1；最新报价另用于当前价格及即时价格预警。
- **价格口径默认优先 FX/黄金 bid、现货 last，最终跟随实测接口确认并显式展示。** 若源提供准确 mid 可选用，但不能把 bid/ask 两套 OHLC 的高低点简单平均，冒充真实 mid 高低点。要从同步逐笔 bid/ask 求 mid，再聚合。

### 5.2 抓取与质量控制

初始默认拉取最近 180 天 M1，日期范围回放可按需补历史。实时每分钟检查新完成 M1，短时重试遵守供应商限速；现价刷新周期由接口实测确定。历史补数限并发，不能挤占实时请求。

基础记录包含 source_timestamp、received_at、finality、revision、质量标记。只在供应商确认完成或适配器满足经实测确定的完成判据后发布收盘事件；不只凭本机时间推定数据已完整。

区分闭市、无成交和断线。适配器必须解释稀疏分钟：仅凭“这一分钟没记录”不能区分无报价与断线。不能验证完整性时将相关 K 线标为未知/不完整，阻止依赖它的判断。

首轮门槛：三个品种实际可读历史及实时数据，观察一个覆盖活跃交易时段的连续运行窗口，记录完成 M1 的延迟分布、缺口、补齐和接口错误。建议目标为收盘后 30 秒内可确认多数信号；这是测量目标，未实测前不承诺。

### 5.3 自定义时间

数据库存 UTC；FX/黄金以 America/New_York 当地 17:00 切日，BTC 以 UTC 00:00。H4 从相应交易日开始时间划分，区间为 [start,end)。日历区分正常休市、周末、假日及维护时段；夏令时切换采用 zoneinfo，不写死偏移量。

先按本地交易日边界确定区间，再转换 UTC。日历异常造成不足 4 小时的尾段显式标记，默认不用于 H4 策略，避免悄悄当作标准 H4。FX 通常在周末切夏令时，仍需覆盖边界测试。

## 6. 策略模块与确定性

策略插件公开三个接口：参数 schema、warmup(history)、on_event(state,event,context)。context 仅能读取事件时刻已完成的数据；策略返回新状态和解释结构，不直接访问网络或发送通知。

具体两条 K 线规则沿用设计草案。补充统一实现约定：

- 时间判定是事件收盘时间严格晚于 armed_at；恰好等于开启时间的已收盘 K 线不触发。服务器接收请求时生成 armed_at，前端时钟不作为依据。
- 双向共用一条监控，先触发一侧后整条完成；两侧需要分别通知时建立两条。
- 等待突破的状态可无限持续，因此启动时不能仅凭固定最近 N 根就准确重建。为策略版本/参数维护状态检查点；首次从可用历史起点重放并记录起点，若历史不足以判断初始状态，标为未知，等待范围内新形成的准备序列，不编造已准备状态。用户可选“仅从开启时开始累计”。
- 历史上已触发的准备状态被消费；历史重建可寻找后续新准备，绝不补发开启前信号。
- 修改活动预警视作创建新版本并重新开启，展示新起点；已触发事件保存旧规则，不随编辑变化。
- 数据缺口暂停推进。补齐后按事件时间顺序恢复；开启后发生但迟到的有效信号仍记录并按一次性规则消费，通知明确标注发生时间与“延迟到达”，不能伪装成当下机会。
- 数据修正保留审计，不撤回或重复发送已发信号；需要按修正数据重新演练时创建新 replay run。

价格预警使用上穿 previous <= level 且 current > level、下穿 previous >= level 且 current < level；提供可配置“触及即算”的包含等号模式。开启时先取有效现价作为基准，不因为价格早已超过阈值立即补发。断线恢复跨阈值只能说明两次观察跨过了阈值，通知说明无法确定期间首次穿越时刻。

即时价格预警若只有 M1 历史，无法精确重现分钟内先后顺序。回放将其标为“分钟范围内触及，时间近似”，不与逐笔实盘宣称完全一致；K 线收盘策略可严格一致。

## 8. 通知、确认与重复提醒

### 8.1 服务端链路

行情事件推进策略后，在一个数据库事务内完成：锁定 watch → 创建 signal → 标记 triggered → 创建 notification 和 outbox。对单次监控的 signal 唯一约束防止重启或并发重复触发。

通知 worker 用有期限租约领取 outbox，HTTP 发布 ntfy；指数退避重试网络错误/限流，鉴权错误标记需处理。进程重启回收过期租约。

**HTTP 超时可能已经成功发布。** outbox 只保证至少一次尝试；ntfy 原版不一定基于业务 ID 去重，因此不能承诺端到端恰好一次。通知携带稳定 signal_id，记录各次发送；确认前重查服务端状态，客户端增强层负责重复事件合并。没有客户端回执时网页仅显示“推送服务已接受／手机送达未知”，不伪造设备在线和送达。

### 8.2 确认接口

- 网站登录会话可调用 `POST /api/notifications/{id}/ack`，幂等返回确认状态。
- ntfy 配“确认”HTTP action，使用只允许确认这一条通知的随机令牌；数据库仅存 hash，可吊销，有效期覆盖该通知生命周期。令牌放授权 header，不出现在 URL、公开日志或普通消息文字里。
- 通知正文点击只导航详情，不用 GET 自动确认，避免链接预览消耗告警。
- 原版点击停止本地铃声不等于服务端确认。界面明确要求使用“确认”，并验证它能同时清除通知/停止声音；若不成立，进入手机增强层实现。
- 服务端确认取消待执行提醒；已有在途请求可能仍到达，客户端需按 signal_id 的已确认状态阻止复响。原版不能满足时不可宣称竞态已解决。

### 8.3 两个提醒适配阶段

**基础适配：** ntfy 级别 5、用户选择 Android 通道铃声、网页声音（首次用户交互后才能启用）、确认 API、发送历史。保留即时投递、不划掉应用的实际条件。测试按钮必须由用户主动触发。

**完整节奏适配：** 优先验证 Tasker/MacroDroid 接收 ntfy intent 后驱动本地提醒。只有一个声音控制者，避免 ntfy 自身循环与自动化音频同时播放。本地保存 event ID、确认状态、次数和计时；收到后响 15 秒、停 30 秒再响，支持无限/有限次数、夜间静音、退出静音后恢复。网站确认通过控制消息及状态拉取停止本地循环；断网期间同步不了远端确认时如实显示等待同步。本地确认立即停声，恢复网络后重试上传确认。

自动化方案需交付可导入配置、版本与故障恢复说明，验收失败则改用最小 Kotlin 客户端，复用 ntfy 传输和相同协议。自定义客户端不自动消除 ColorOS 杀后台问题。通知节奏是否能仅用原版达到，以实测为准，不用每隔 30 秒服务器再发消息冒充准确本地响停。

静音时间按 Asia/Shanghai 默认，可改；服务端在静音期暂缓声音通知，保留站内事件；手机本地也执行静音，避免已收到循环跨入静音仍响。次数耗尽仍是未确认，状态单独展示。

页面：行情/监控、创建预警、信号中心、历史演练、设置。首页显示源延迟、数据缺口和策略等待状态；不用系统已发请求替代手机收到的状态。

| GET /api/instruments、/candles、/quotes | 品种、按区间分页 K 线、最新报价 |
| GET /api/strategy-types | 参数 schema 与策略说明 |
| POST /api/watches | 原子创建监控、规则与时间快照 |
| GET /api/watches；POST /{id}/cancel | 状态、取消 |
| GET /api/signals、/notifications | 解释和提醒历史 |
| POST /api/notifications/{id}/ack | 幂等确认 |
| GET /api/events | SSE；支持重连游标 |

单账号密码登录，密码用 Argon2 hash，HttpOnly/Secure cookie，CSRF 防护；部署初始化生成管理员凭据。API 不接受未鉴权的任意 ntfy topic 发布请求。

## 10. 历史回放

回放固定数据快照和规则版本，虚拟时钟只释放已到截止时间的完成 K 线。各周期独立按收盘时间合并事件，H4 未完成时不向策略开放其最终 OHLC；前日区间只能来自当时已完成的交易日。

图表隐藏未来；预加载数据也不得让策略访问未来索引。seek 向后时从检查点重建，生成新的分支/运行状态，不在旧状态上倒退时间。加速播放仍逐事件处理，不跳过中间信号。

实时和回放共享策略及日历模块；回放使用虚拟 outbox，仅显示模拟提醒，不连接真实 ntfy。保存创建监控时刻、规则、触发 K 线、原因，支持导出演练结果。初次导入的历史行情通常不含真实接收延迟，回放验证的是规则逻辑，不模拟已无法恢复的历史网络延迟。

## 11. 部署和维护

Compose 服务：reverse-proxy、api、market-worker、notify-worker、dukascopy-adapter、postgres；自建通知阶段增加 ntfy。沿用现有反向代理时不重复占用端口。

初步资源预算 2 vCPU / 4 GB RAM，磁盘按历史范围测量后确定；这不是性能保证。Python/Node/ntfy 版本固定，日志轮转、失败任务可见、每日数据库备份、升级前备份与恢复演练。密钥通过受限环境文件或容器 secrets 注入，不提交仓库。

生产自建 ntfy 使用 HTTPS、鉴权及专用 topic，发布/订阅权限分开；ntfy 服务地址从配置读取，不能自动悄悄切到公共服务器。迁移后做一次端到端验收。监控 worker 心跳、行情最新完成时间、任务积压和备份状态；ntfy 自身故障在网站明显展示，不能只靠同一条 ntfy 通道报告自身故障。

## 12. 开发里程碑与完成条件

| 阶段 | 产物 | 完成条件 |
|---|---|---|
| M0 数据与工程起步 | 独立仓库、版本锁定、Compose、行情验证报告 | 三品种历史/实时可读，明确口径、数据完成判据和补数路径；不可用则选替代源后再通过 |
| M1 时间与行情核心 | 存储、补数、日历、M5/H4/D1 | NY17/UTC0、DST、周末、缺口及修正测试通过；能图表抽查分桶 |
| M2 策略与监控 | 三类预警、状态保存、解释、一次性事务 | 规则矩阵、开启边界、双向、恢复和去重通过 |
| M3 网站与基础提醒 | 图表、参数页、信号中心、ntfy、确认 API | 网页关闭后策略仍运行；实际信号到手机；明确送达未知；确认及本地停止实测 |
| M4 历史演练 | 日期、隐藏未来、逐根/加速、信号标记 | 同数据下收盘策略实时模拟与回放完全一致；无未来数据访问 |
| M5 完整提醒与部署 | 精确节奏适配、静音/次数、生产部署、操作手册 | 15/30 秒节奏、最大次数、静音、确认、重启/重发、长待机和网络切换验收完成 |

M0 先记录真实接口表现，避免虚构行情可用性；M3 可先日常试用，完整第一版以 M5 通过为准。工期在 M0 后按实际免费数据接口和手机适配复杂度估算，不给无依据的固定天数。

### 必要验收矩阵

- 策略：N=2/3、十字星、等号、连续高低点中断、准备后等待多根、历史准备已消费、开启中途、买卖镜像、双向一次性。
- 突破：前日阈值、开启已在区间外、跨日统一阈值、周一/周五、缺失日不能当休市。
- 时间：纽约夏令时前后、BTC UTC0、日终 M5 归属、不同周期同时收盘。
- 持久化：进程在事务前后崩溃、租约到期、ntfy 超时但已接受、确认与发送竞态、重复行情。
- 手机：现有已通过测试保留；新增生产服务器、长待机、网络切换、完整节奏与确认。划掉应用会中断的已知条件写入使用说明，不写为通过。
- 回放：隐藏未来、向后 seek、新建监控、数据版本固定、无真实推送、即时价格预警近似说明。
