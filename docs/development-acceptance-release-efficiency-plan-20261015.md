## 1. 建议采用的路线

保留「Ubuntu 开发验收、Unraid 正式生产」边界，先把现有 `mw-docker` 补成统一入口：**分级验收、小数据基线、手动控制并发、最终镜像复用、任务退役闭环**。不先引入新的部署平台。

1. 多个 agent 继续使用独立 worktree、branch、Compose project、网络、数据库和 volume；代码可以并行，由用户手动控制验收并发；建议同时两个轻量 R1，第三个由用户结合实时内存/磁盘/负载决定。R1W/R2/R3、完整恢复及性能测试由用户安排错峰，不开发槽位或自动队列。
2. 日常验收复用版本化、无生产身份数据的种子包，不复制整库。生产规模恢复、迁移和查询性能验证只保留一个专用通道。
3. 最终集成提交构建一次发布候选；用这组实际镜像完成最终验收，再提升到生产。Unraid 延续现有的不构建原则。先沿用已验证的 SSH 镜像传输，私有 registry 后置。
4. 把备份、恢复演练、迁移验证和应用切换分开计时；兼容发布的恢复演练尽量移到停写窗口前。快速发布通道须有明确的备份时效、兼容性和恢复证据门槛。
5. 清理以归属、任务完成、实际恢复验证及引用检查为条件。TTL 用于提醒和调度，不能把仍在开发的任务变成可删资源。

共享 PostgreSQL 服务可以以后试点，但**不作为第一阶段前提**。现行 [AGENTS.md](../AGENTS.md) 要求每项任务独立 volume 和数据库；现有退役工具也只支持本项目独占 PG volume。共享服务需要同时解决规则、连接权限、资源争用和退役工具的变化。

### 1.1 后续每个需求的执行顺序

日常开发按下面的状态推进。agent 先根据改动自动选择最小风险路径，不要求用户逐项指定；状态只在证据齐全时前进，CI 通过不等于 Docker 验收通过，Docker 验收通过也不等于生产已发布。

```text
需求/缺陷
  → agent 自动判断 P0/F0/F1/F2 与最小验收级别
  → 需要时填写简短 Issue、创建独立 worktree/branch
  → 本地检查 → GitHub PR CI
  → 需要 Docker 时检查 Ubuntu 资源与任务隔离（并发由用户手动控制）
  → 本人自审；F1/F2 或 R2/R3 再做独立 review
  → 合并 main 后从准确提交构建 release candidate
  → 只有风险需要时做 R2/R3
  → 生成发布清单，等待本次生产授权
  → Unraid 预检、备份、迁移、切换、观察
  → 发布结案或按风险回滚，最后退役 Ubuntu task
```

1. **自动判定。** 先看改动文件和行为：仅文档/样式/纯局部逻辑选 P0；兼容的 API/UI/worker 选 F0；schema、持久格式、重要后台链路选 F1；PG 主版本、破坏性迁移、灾备选 F2。agent 在 Issue/PR 中写出判定理由和需要的最小检查；用户只在生产操作、真实数据或风险边界不明确时介入。
2. **建立隔离工作树。** 需要代码时从最新 `main` 建独立 branch/worktree 和唯一 task/project 名称；不在共享 `main` 工作树直接开发。代码可以并行；每个 session 启动验收前检查 project/端口冲突和实际余量，需要协调时报告用户，不自动停其他任务。
3. **本地快速检查。** 先运行改动相关的 pytest、`ruff check backend` 和 `cd web && npm run build`；涉及 adapter 时运行其 `npm ci`/检查。默认禁用真实通知和供源外连，禁止把 `.env`、完整备份、session 或许可库加入提交。
4. **打开 PR。** 当前 `.github/workflows/ci.yml` 会在 PR 和 `main` push 触发三个检查：`backend` 启动 PG14.24 服务并核对 `server_version_num=140024`，对后端相关改动运行 Ruff 和 pytest；`web` 执行 `npm ci` 和生产构建；`compose` 校验开发、生产和 acceptance Compose 展开配置。它只使用 CI 临时服务和无生产凭据，**不**构建/推送 Docker 镜像，不连接 Ubuntu Docker socket，不连接 Unraid。分支保护是否已将这些检查设为 required 仍需在仓库设置中单独核对。
5. **在 Ubuntu 验收。** CI 通过且判定需要 Docker 后，agent 只读检查资源、说明预算；按用户控制的并发安排，用选定 profile 和 `mw-docker build`/`mw-docker compose-build` 构建 task-owned acceptance 镜像，Compose 使用 `--no-build`。R1 默认只启动必要服务和 D1，可同时运行两个；R1W/R2/R3 才增加 worker、长历史、迁移、规模或恢复检查，由用户安排与重构建或完整恢复错峰。记录主机、project、镜像实际 ID、PG 实际版本、测试结果、资源峰值和可访问地址。
6. **合并与候选。** review、CI、对应验收证据和已知限制齐全后才合并。发布从合并后的完整 main 提交或明确 tag 构建一次 `purpose=release` 候选；API、web、chart-origin、backup 等组件的输入、基础 digest、dirty 状态和产物身份写入清单。分支 acceptance 镜像不能 retag 成 release，也不能用另一台机器重构建来“等价替代”。
7. **最终验收。** 用候选镜像直接启动 R2；只有 F1/F2 或明确规模/恢复风险时才排入 R3/D3。候选验收结束后只修复候选并重新生成新候选，不能把 Ubuntu 上临时改过的容器当作生产输入。前端图表地址、Yahoo、JIT、通知隔离和数据库版本都按生产目标逐项核对。
8. **发布授权与 Unraid 切换。** 生产发布必须获得本次明确授权。授权前只做只读预检和 Ubuntu 工作；授权后在 Unraid 本机生成/核对备份、固定镜像和 standalone Compose，先迁移再启动写入 worker，观察 ready、SSE、行情、队列和重启状态。GitHub CI 不自动 SSH、pull、stop 或修改生产。
9. **结案、回滚和退役。** 观察窗口通过后登记 active release、备份、镜像和回滚链；失败按 F0/F1/F2 规则回到已验证的旧镜像或专项恢复流程。Ubuntu 任务先 `mw-docker retire` 预览，完成归档和实际恢复/内容核对后才 `--apply`；release/rollback 镜像、数据基线、备份和其他任务资源继续受保护。

开发者日常只需要记住四条：**PR CI 先挡明显错误；Ubuntu 验收才证明容器和数据边界；生产只接收最终候选；清理必须在证据之后。** 现有 CI 是代码和 Compose 验证，不是镜像发布；GitHub 镜像自动构建和 GHCR 暂不加入这条默认路径，后续只有在镜像传输成为瓶颈时才为 release candidate 启用。

### 1.2 Issue、agent 对话和 PR 的分工

Issue 是需求的长期记录，agent 对话是本次执行指令，PR 是代码和证据的审查入口。仓库模板为 [`.github/ISSUE_TEMPLATE/market-watch-task.md`](../.github/ISSUE_TEMPLATE/market-watch-task.md)，在 GitHub 的 **New issue → Market Watch 需求 / 缺陷** 中可直接使用。除了一行拼写、单个文档链接等低风险改动，先登记 Issue 再让 agent 开始实施；如果用户直接在对话中提出较大的需求，agent 应先按模板填写 Issue 草案。需求清楚且不涉及生产时可按默认规则继续；只有仍有冲突或缺失的字段才列出待确认项并等待用户。不要只把关键需求留在聊天记录里。

模板由 agent 负责初填和维护。需求明确且不涉及生产时，agent 可以按默认风险规则直接建立 worktree/branch 实施；只有目标、范围、风险、验收级别、数据边界或生产影响缺失/冲突时，才停在范围检查点等待用户选择。确认前 agent 可以做代码/资源只读盘点和文档整理，但不修改代码、不创建验收数据、不修改生产。

可以直接使用下面的提示词：

```text
按 Issue #<编号> 实施，不扩大范围；先由 agent 自动判断最小流程，不要求我逐项指定。
目标：<用户可观察的结果>
范围：<允许修改的模块/文件>；明确不改：<生产/数据库/其他模块>
agent 判定：P0/F0/F1/F2；最小验收：无 Docker/R1/R1W/R2/R3；数据：D0/D1/D2/D3；写明判定理由
验收标准：
1. <功能结果和边界>
2. <回归/兼容性>
3. <部署或回滚要求>
先盘点相关代码和资源，给出实施计划；除文档或只读检查外不要改变生产。
完成后先自审和运行必要检查，再做独立 Standards/Spec review，最后汇报是否适合创建 PR。
```

Issue 至少保留：背景/问题、目标与不做事项、风险类别、验收级别和数据基线、生产影响、回滚条件、预期文件/模块、完成证据。Issue 不需要泄露密码、完整 env、生产备份或私有许可材料。

### 1.3 人工检查点：只在这些时刻停下

个人维护不需要用户盯住每个命令。agent 先把能自动完成的工作做完，只在会改变范围、合并历史、生产状态或永久资源的节点停下。用户看到的是一份短报告和一个可直接回复的动作。

| 检查点 | agent 先完成 | 用户决定 | 可直接回复 |
| --- | --- | --- | --- |
| 范围/风险不清 | 只读盘点、Issue 草案、冲突项和 P/F 选项 | 目标、数据边界、验收级别或是否允许真实生产行为 | `按选项 A，继续；不发布生产。` |
| 合并前 | 实现、必要测试、CI、适用 Ubuntu 验收、自审、Draft/Ready PR 和 review 证据 | 是否把 PR 合并到 `main`；合并不自动发布 | `合并 PR #<编号>，不发布。` |
| 正式发布前 | 从合并提交构建候选，完成 R2/必要 R3，核对 digest、备份方案、迁移和回滚清单 | 是否创建正式 tag，以及是否在 Unraid 备份、迁移、切换 | `授权候选 <digest/tag> 发布，按清单执行；异常立即停。` |
| 异常或永久删除 | 保留现场、日志、备份和当前镜像，给出继续/回滚/暂停选项 | 继续、切回上一稳定版、恢复数据，或删除 volume/工作树/备份/正式镜像 | `暂停，保留现场，不删除。` / `按方案回滚到 <digest>。` |

正常的 Issue 填写、worktree 创建、编码、测试、CI、轻量验收和 Draft PR 不需要停下来询问。健康发布完成观察窗口后 agent 可以先给出结案报告；只有指标异常、需要延长观察或要清理受保护资源时才再次等待。

验收并发由用户手动控制，不实现 `acceptance` 槽位或队列命令。agent 在已有任务授权内检查资源后可启动自己的隔离实例，不新增每次启动审批；发现容量不足、端口冲突或需要与其他 session 错峰时，再报告用户协调。

每次停下只报告五项：`节点｜风险/候选｜已完成证据｜建议下一步｜需要的唯一回复`。例如：`合并前｜F0，PR #123｜CI/R1/自审均通过｜合并到 main 后再构建候选｜回复“合并 PR #123，不发布”`。不要把已经由 `AGENTS.md` 规定的 profile 和常规命令逐项交给用户选择。

最短启动指令如下，适合直接发给 agent：

```text
按仓库 AGENTS.md 和 Issue #<编号> 的个人精简流程自动执行。自行判断 P/F 和最小验收，完成开发、测试、CI、自审、Ubuntu 验收和 Draft PR；不要逐步询问我。只有范围或风险不清、准备合并、准备正式 tag/Unraid、异常回滚或永久删除时停下，报告证据、建议和我需要回复的一句话；其他步骤自动推进。
```

没有 Issue 时，将第一句改为“先按需求建立 Issue 草案，再按仓库 AGENTS.md 的个人精简流程自动执行”。用户只需在检查点回复动作，不必重新描述整个需求。

### 1.4 创建 PR 前的自审门禁

可以先创建 **Draft PR** 让 CI 提前运行，但标记为 Ready for review 前必须完成自审。普通功能建议先自审再创建 PR，减少无效 CI；大任务若需要早期协作可以先开 Draft，但不能把 Draft 当成已验收。

自审至少包括：

- `git diff --check`、`git diff <base>...HEAD`，确认改动只在 Issue 范围内，没有调试代码、凭据、生产地址或未解释的生成文件；
- 运行与改动对应的 pytest、`ruff check backend`、`cd web && npm run build`，并记录未运行的检查及原因；
- 检查迁移是否向后兼容、默认配置是否安全、通知/供源是否误连生产、Compose 是否固定镜像和隔离 project；
- 检查文档、版本、回滚步骤和验收证据是否与实际实现一致；
- F1/F2 或 R2/R3 改动再做一次独立 Standards/Spec review；P0/F0 默认由本人完成自审即可，用户或 agent 明确要求时再增加第二次 review。

PR 描述应链接 Issue，写清问题、最终行为、测试命令/结果、已知限制、镜像/数据基线和是否需要生产授权。CI 绿灯只能说明自动检查通过，不能代替自审、Ubuntu 验收或生产核对。

### 1.5 个人维护者的精简默认路径

本方案的完整路径覆盖并行 agent、数据库变更、PG 升级、灾备和多人协作；个人维护不应让每个小改动都执行全套 R2/R3。推荐采用按风险升级的默认路径：

| 变更类型 | 个人默认必须做 | 只有这些情况才升级 |
| --- | --- | --- |
| 文档、样式、纯局部逻辑 | PR CI、本人自审；Issue 可省略 | 改动实际影响运行时或发布配置时升到 F0 |
| F0 普通功能/API/UI/兼容 worker | 简短 Issue、PR CI、本人自审、一个 Ubuntu R1 smoke 验收；从合并 `main` 构建候选镜像；生产前 Unraid 本机备份、健康检查和旧镜像回退链 | 只有完整 worker 链路、跨服务协议或性能问题才加 R2 |
| F1 数据库/schema/持久格式/重要 worker | Issue、CI、R1/R2、一次迁移预演和兼容性 review；使用匹配的 D2/D3 证据 | 需要生产规模、锁/耗时或恢复证明时才加 R3/D3 |
| F2 PostgreSQL 主版本、破坏性迁移、灾备 | Issue、CI、独立 Standards/Spec review、R2+R3、实际恢复与专项回滚方案 | 不再压缩门禁；必须安排维护窗口和明确 RPO/RTO |

个人建议同时运行两个轻量 Ubuntu 验收 project/PG；agent 可以并行准备代码和验收，是否同时运行第三个由用户按资源情况决定。R1W/R2/R3、完整恢复和性能测量由用户安排错峰。这样可以利用独立 PG 并行验收，又不会把三套完整 worker/恢复环境叠加起来。任务首次验收时创建独占 PG，后续重跑复用 volume；只有数据污染、schema 变化或明确要求 clean run 时才从 D1/D2 seed 重置。R3 始终是单独、按需的恢复通道。

### 1.6 多 session 的手动并发管理

多个 session **不会因为 worktree 独立就自动排队**。worktree 只隔离代码；Compose project、PG volume 和数据库只隔离数据。CPU、内存、磁盘 I/O、BuildKit 和端口仍由同一台 Ubuntu 共享。现有 `mw-docker ops.lock` 只串行构建、退役和清理，不能自动协调各 session 的 `docker compose up`。

用户已明确选择手动控制并发：不实现 `acceptance acquire/release/heartbeat`、FIFO、共享槽位目录或失联租约回收。agent 只需在验收记录中写明 task/project/worktree、profile、端口、资源预算和运行状态；存在冲突时报告用户，由用户决定哪个任务先运行。不要为执行默认开发流程再建立调度系统。

必须长期保留的安全底线只有六项：CI 通过、改动范围自审、合并提交构建候选、生产前 Unraid 备份、发布后健康检查、保留可验证的上一稳定镜像。共享 PG、私有 registry/GHCR、自动 promote/tag、任务域名入口、全量 D3 每次发布、复杂 dashboard 和第二套自动清理策略都先不做；只有实测瓶颈或风险需要时再增加。

如果把完整路径强制到每个任务，个人项目会出现明显的流程成本：小修复也要填完整 Issue、开多套容器、恢复大库、做多轮 review，等待时间可能超过编码时间。精简后的主要收益是保留 CI 和发布回退的安全性，同时把日常验收限制为一套可复用的小数据环境；完整恢复和 PG 专项只在真正有数据风险时付出成本。

## 2. 资源与流程现状

### 2.1 主机与磁盘

| 项目 | Ubuntu 开发主机 | Unraid 生产主机 |
| --- | --- | --- |
| CPU / 内存 | 4 核；15.61 GiB；可用约 11.28 GiB | 6 核；31.23 GiB；可用约 3.63 GiB，无 swap |
| 系统 / Docker | Ubuntu；Docker 29.1.3；containerd overlayfs；cgroup v2 | Unraid **6.11.5**；Docker 20.10.21；Btrfs；cgroup v1 |

### 2.3.1 当前备份到底是什么

当前生产数据库备份**不是 Unraid 文件系统快照，也不是增量备份**，而是「基于 MVCC 一致性快照的全量 PostgreSQL 逻辑备份」：

1. `backend/alerts/backup.py` 先在 `REPEATABLE READ` 事务中执行 `pg_export_snapshot()`，并在同一事务视图中统计表行数。
2. 它把这个 snapshot 传给 `pg_dump --format=custom --snapshot`，导出数据库对象和数据到一个 `.dump` 归档。
3. 导出结束后只做 `pg_restore --list` 归档可读性检查，并写入 `.json` 清单、SHA-256、字节数和表计数；这一步**不是实际恢复**。

所以这里的“snapshot”只代表导出时所有表看到同一个时间点的数据视图，不代表底层 XFS/Btrfs 做了瞬时复制，也不代表下一次只导出变化部分。每次运行仍要读取并写出全库逻辑内容；当前生产库约 11.56 GiB，最近 dump 约 2.78 GB，压缩归档较小不改变它是全量导出的事实。现有备份服务可以在线执行，但会消耗磁盘读写和 CPU，并在导出期间保持长事务快照；不能把它当成零成本操作。

当前 `.json` 清单记录的是 dump 完成后的 `created_at`、SHA-256、字节数和表计数，没有独立的 `snapshot_at`；文件 mtime 或 `created_at` 不能冒充快照时点。后续备份证据要显式记录 `snapshot_at`、dump 完成时间、SHA-256、`pg_restore --list` 时间、实际恢复完成时间、迁移时间和应用切换时间。

上次 v1.25.4 的 **934 秒停写**同时包含最终 dump 和完整恢复，不能把这 934 秒全部归因于 `pg_dump`，也不能据此承诺改成“快照”后就会变成秒级。先取得真实分段基线，再决定哪些步骤能移到停写前。

| 方式 | 当前状态 | 适用目的 | 成本与限制 |
| --- | --- | --- | --- |
| 全量逻辑 dump（`pg_dump -Fc`） | **正在使用**；每日及发布/升级按风险使用 | 跨主机、迁移、选择性恢复、跨同主版本验证 | 每次读取全库并生成完整归档；耗时和空间随数据增长 |
| 事务一致性 snapshot | **正在使用，但只是 dump 的一致性机制** | 让一个 dump 内的数据相互一致，并允许在线导出 | 不是物理快照；长事务仍会带来 I/O 和 vacuum 保留压力 |
| 物理 base backup + WAL 归档 | **尚未实施** | 同一 PG14 集群的时间点恢复、减少重复全量导出的压力 | 首次仍需全量 base backup；要设计 `archive_mode`、WAL 保留/监控、异机存储和恢复演练；不能替代逻辑迁移 dump |
| Unraid/ZFS 文件系统快照 | **不采用为当前默认** | 同一存储上的快速卷级回退 | 生产 PG 数据当前在 XFS，现场不是可直接套用的 ZFS 克隆方案；同机快照也不等于异机容灾 |

近期保持全量逻辑 dump 作为可移植的迁移和灾难恢复格式，但把它移出不必要的停写窗口：F0 兼容应用发布可使用最近 24 小时内**已经实际恢复验证**的恢复点，并另行在线生成/留存本轮 dump；F1/F2、PG 升级或无法证明向后兼容时，仍要按专项要求取得迁移前恢复点并完成实际恢复验证，不能为了缩短窗口跳过保护。长期若全量 dump 成为主要瓶颈，再单独设计 PG14 physical base backup + WAL/PITR；实施前要完成容量、WAL 归档失败告警、独立恢复和 RPO/RTO 演练，本轮不启用。

## 3. 对参考建议的取舍

| 建议 | 本项目选择 |
| --- | --- |
| 共享一个 PG，每任务独立库/schema | 暂缓。先减少服务和数据；若之后仍有明显 PG 内存重复，再在 Ubuntu 试点独立 database，避免用 schema 代替权限隔离 |
| Compose `-p` 隔离并限制 CPU/内存 | 采用；保留独立网络/卷/数据库，不只改项目名 |
| Traefik/Caddy 分支域名 | 第二阶段再评估。先由入口分配并登记端口，使用任务独立的 TLS 配置；域名问题先服务于镜像复用 |
| 24 小时自动销毁实例 | 暂缓。先手动 stop/retire；未来可按需加到期提醒，不实现租约、自动停机或按时间删库 |
| 分支只跑测试，合并后验收一次 | 改成分级。每个分支保留与改动相关的实际功能验收，最终集成做一次完整验收，不把分支缺陷全部推迟到合并后 |
| 小种子数据；PG template 克隆 | 采用小种子包。`CREATE DATABASE … TEMPLATE` 只能在同一 PG 集群内复制，要求模板无连接，耗时随数据量/存储变化；不能代替跨独立容器数据目录的复制 |
| 每晚在 Unraid 脱敏整库、ZFS 克隆 | 不采用为默认。生产侧每晚脱敏有额外负载和身份数据风险；现场 Unraid 6.11.5、PG 数据在 XFS，不具备此处假定的 ZFS 克隆条件 |
| 构建一次、原镜像发布、回滚旧镜像 | 采用；先解决最终候选的域名配置、镜像身份及清理保护，再增加 registry |
| 全局 container/image/builder prune | 不采用。保留现有精确归属边界；Docker 的“unused”也可能是保留的回滚资源 |
| 日志轮转、固定命令、可视化管理平台 | 先用 Compose 级轮转和 `mw-docker`；不为提效再部署 Harbor、Coolify、Dokploy、Portainer 等平台 |

## 4. 验收分级与并行资源预算

### 4.1 服务分级

| 通道 | 适用改动 | 启动范围 | 数据 | 并发建议（用户协调） |
| --- | --- | --- | --- | --- |
| R0 静态/自动测试 | 文档、纯函数、局部逻辑 | 本地检查；需要 PG 的测试才临时申请任务 PG | D0 | 轻检查可并行；编译和 DB 测试计入预算 |
| R1 轻量功能验收 | UI、API、交互修复 | 独占 PG + API + 小型网关；按需 web/chart/TLS；migrate/seed 一次性运行 | D1 | 建议 2 个；第三个由用户按实时资源余量决定 |
| R1W 后台功能验收 | SSE、历史、聚合、供源相关 | R1 加被测 worker 和必要上下游 | D1 或 D2 | 最多 1 个，可搭配 1 个 R1；性能测量时独占 |
| R2 最终集成 | 正式候选整体兼容性 | 与生产相同的服务拓扑，加 Ubuntu 专属 PG/TLS；通知隔离 | D2 | 1 个，暂停新增 R1 和构建 |
| R3 规模/恢复/迁移 | PG、迁移、索引、大数据性能及灾备 | 单个隔离恢复项目，默认不启动业务 worker | D3 | 1 个，与性能测试和构建错峰 |

R2 和 R3 都在 **Ubuntu** 做，不在 Unraid 生产机做：

- **R2 最终集成**：使用最终候选镜像，启动与生产相同的必要服务拓扑，但连接 Ubuntu 专属 PG14/TLS；使用 D2 合成或代表性数据，通知、真实行情外连和生产地址全部隔离。R2 一次只保留一个活动项目，验证通过的镜像才进入生产候选清单。
- **R3 规模/恢复/迁移**：使用 Ubuntu 的单独 `restore` project。需要生产规模、PG 升级或灾备证据时才恢复受控 D3；只做迁移、恢复、查询和性能检查，默认不启动业务 worker，不连接真实通知。R3 与构建、其他重任务错峰，完成后按恢复证据和引用规则退役。
- Unraid 只在获得本次发布授权后执行正式备份、对生产 PG14 的最终迁移和应用切换；它不是 R2/R3 验收环境。

轻量验收不能证明完整 worker 链路或生产规模性能；R2/R3 也不能替代分支实际功能验收。profile 选择写进任务清单和验收报告，避免少启服务后仍宣称全部通过。

### 4.2 初始预算与资源检查

下表是**待实测调优的初值**。CPU 是所有同时运行服务的 quota 之和；Compose 没有自动的 project 总限额，需要生成入口逐服务分配、检查总额。磁盘是计划新增峰值，包括数据、临时恢复副本和归档，使用量检查不是硬配额。

| 类型 | 内存上限合计 | CPU 合计 | 新增磁盘峰值预算 | 约束 |
| --- | ---: | ---: | ---: | --- |
| R1 单任务 | 1.25 GiB | 0.75 核 | 3 GiB | PG 512 MiB、API 512 MiB、网关 64 MiB，UI 的 web/chart 各 64 MiB；迁移与 API 错峰；API-only 为 1088 MiB / 0.65 核 |
| R1W 单任务 | 3 GiB | 1.65 核 | 6 GiB | PG 768 MiB、API 512 MiB、至多 3 个 worker 各 384 MiB，含 UI/网关时按实际拓扑核算 |
| R2 完整集成 | 6 GiB | 2.5 核 | 8 GiB | 含所有后端、PG、静态服务；浏览器另计；迁移与 API 错峰 |
| R3 完整恢复 | 4 GiB | 2 核 | **24 GiB** | 按约 12 GB 数据、约 3 GB dump、索引/WAL/恢复余量估算；新一轮先测实际峰值 |
| BuildKit 构建窗口 | 3 GiB | 1 核 | 3 GiB 临时增量 | 外部构建任务并发 1；内部并行度现为 2，变更需单独维护专用 builder |
| 浏览器验收 | 1 GiB | 约 0.5 核预算 | 1 GiB 证据上限 | 不与多个浏览器性能测试叠加 |
| OS、Docker、编辑器等预留 | 4 GiB | 约 0.7 核预算 | 根分区至少保留 20 GiB | 属于主机余量，不是给其他服务施加的新限制 |

两个 R1 加一个构建、一个浏览器和主机预留是个人默认预算；第三个 R1 建议在可用空间、`MemAvailable`、CPU 和 I/O 实测均达标后，由用户决定是否并行。这个预算适合正确性验收，不代表并行任务能得到生产级延迟。JIT/历史查询若超过额度，升级到 R1W/R3，不能为塞进预算而把全部 JIT 关掉。

资源估算公式：`预计剩余空间 = 当前文件系统可用空间 − 尚未兑现的任务峰值预留 − 新任务新增峰值`。已有占用不再扣一次；不同任务共享的镜像/缓存只登记一次，保守预留增长量。内存也按当前使用与未兑现预留计算，不能只看 `free` 的一刻读数。

- Ubuntu 当前 32.92 GiB 可用：建议运行两个 R1；两个 R1 的 6 GiB 加构建增量 3 GiB 后约余 23.92 GiB，启动前仍需检查实时余量。第三个 R1 建议在可用空间至少 **40 GiB** 且峰值实测通过后再由用户安排。
- R3 建议先具备 **50 GiB** 可用空间；当前不安排新的完整生产恢复。空间不足时报告用户安排错峰或扩容，不擅自删除现有任务。
- 预计余量低于 20 GiB 或 `MemAvailable < 2 GiB` 时拒绝新的重任务；负载持续 5 分钟超过 4 时报告用户推迟重构建。优先保留正在验证的数据，不通过清理其他任务腾空间。
- Unraid 只做正式发布所需操作。发布前建议连续 10 分钟可用内存至少 4 GiB、无持续 I/O/负载异常；本次约 3.63 GiB 的样本不能直接认定具备发布余量。不改其他业务或虚拟机设置来满足门槛。

Unraid 单次正式发布另预留约 5 GiB 的镜像导入/临时文件峰值，并以实测修订；Docker 所在文件系统扣除新增峰值后至少保留 10 GiB。备份目录所在实际磁盘另保留「两份最大 dump + 5 GiB」写入余量，检查 share 对应的底层磁盘，不能只看 `/mnt/user` 聚合空闲量。生产不增加用于验收的 PG 副本，镜像包与备份也不能混用同一个容量数字。

磁盘长期预算：专用 BuildKit 目标 8 GiB、已安装基础 OCI 缓存目标 1 GiB；两者单独统计且不等于硬配额。D1/D2 基线包合计目标 3 GiB，日常验收归档软预算 5 GiB，完整恢复通道另计。生产备份初始软预算 100 GiB，达到阈值先报告增长和受保护项，不按容量强删。

## 5. 数据基线与复用

| 基线 | 内容与上限目标 | 生成 / 更新条件 | 用途与限制 |
| --- | --- | --- | --- |
| D0 | 空库迁移 + 最小确定性 fixture；恢复后 ≤64 MiB | schema/测试模型变化时生成 | 单元、PG 连接、权限、迁移起点 |
| D1 | 合成账户/布局；FX、黄金、BTC、Yahoo 样本；candles ≤50 万行；dump ≤150 MiB、恢复库 ≤512 MiB | fixture、日历、指标协议或 schema 变化时发布新 ID | 日常功能验收；禁止生产 token、密码哈希、session、真实通知地址及待投递 outbox |
| D2 | 完整服务链路所需数据与队列；恢复库 ≤2 GiB、dump ≤500 MiB | 正式候选或业务协议变化；可复用匹配版本 | 最终集成；可加有代表性的长历史、分布及索引统计，不宣称等同生产规模 |
| D3 | 经过权限控制的实际生产备份及清单；当前原库约 11.56 GiB | 风险发布前/定期恢复演练；仅一个活动副本 | 迁移、灾备、规模性能；不是三个分支各复制一份 |

### 5.1 Ubuntu PostgreSQL 的创建、复用和重置

第一阶段不预建一个供所有任务共用的 PG，也不让每次验收都从零重建整套数据库。采用「**任务首次使用时创建，任务存续期间复用；需要干净状态时只重置该任务数据**」：

现有 Compose 已按独立 project 使用各自的 named volume；在不执行 `down -v` 或退役的情况下，`compose up --no-build` 会复用已有 PG 数据。本分支新增 `preview prepare/up/status/stop/reset`，命令及边界见 [Ubuntu README](../deploy/ubuntu/README.md#轻量验收与任务-pg-复用)。R1 首次用固定 D1 生成器初始化，普通重跑保留用户写入；下表中的 D2/R2/R3 自动化仍为后续目标。

| 场景 | PG 服务与 volume | 数据初始化 | 后续复用规则 |
| --- | --- | --- | --- |
| R1/R1W 分支任务 | 每个 task 独占一个 PG14 容器、volume、数据库和凭据 | 当前 R1 首次 migrate 后用固定副本 D1 生成器 seed；D2 dump 尚未实现 | 普通代码重跑、重启和浏览器重验直接复用同一 volume；只有测试写脏数据、schema 变化、迁移回归或明确要求 clean run 时才显式 reset |
| R2 最终候选 | 一个独立的 R2 project 和 PG volume，一次只允许一个 | 从匹配版本的 D2 初始化；候选清单记录 seed ID、PG digest 和 schema revision | 同一候选的功能重验复用数据库；候选迁移或测试改变 schema/关键数据时，丢弃该 R2 数据库并从 D2 重新恢复，不能继续使用已经被前一轮改过的库 |
| R3 恢复/迁移/规模 | 一个专用 R3 PG 服务，默认不复制给分支 | 对指定 D3 dump 做一次实际恢复并记录 SHA/行数/恢复时间 | 只读规模检查可复用已验证库；迁移或写入型实验必须新建隔离数据库/volume 或重新恢复同一 D3。R3 不长期保留生产副本，证据完成后退役 |

这里复用的是 **PG 服务、volume 和不可变 seed**，不是复用运行中的生产库，也不是让不同 task 共用一个可写数据库。D1/D2 dump 体量受控（目标分别 ≤150 MiB/≤500 MiB），首次恢复通常远小于复制 11.56 GiB 生产库；真正的 D3 恢复只保留一个 R3 通道，不让三个分支各自复制。

当前 `preview reset` 默认只预览；显式 `--apply` 才在本任务 PG 新建数据库，从固定 D1 生成器初始化并记录旧库。旧数据库和 volume 全部保留，失败不启动写入者；目前没有一键切回旧库命令。reset 不是备份，也不是零成本快照，重复 reset 会增长空间；退役归档必须覆盖所有非模板库。通用 `reset-to-dataset` 和 D2 选择仍待实施，禁止用 `down -v` 或全局 prune 代替。未来若实测 PG 进程重复占用成为主要瓶颈，再在 S5 试点共享 PG；共享集群不是当前默认方案。

D1/D2 应覆盖：1/2/4/8 图与手机视口，M1 与较大周期，跨交易日、周末、DST、维护/休市、历史缺口与修订、实时接续、SSE 确认、指标热身、保存/重载，以及 Yahoo、OANDA 等各自的数据语义。秒级任务用限定时段 fixture；月线/年跨度直接构造相应周期样本，不必铺满多年分钟数据。

**当前 D1 的实际范围较小：**四个禁用外部采集的合成品种，M1/H1 各 720 条，共 5760 candles + 5760 published bars；固定起点 2026-10-05 00:00 UTC，dataset ID 为生成器 SHA 的前缀。不覆盖上述全部日历、实时供源和完整业务链场景；不能把这次 smoke 视为 D2/R2 或生产规模验收。

每个基线发布清单至少记录：`dataset_id`、生成器版本、schema revision、PG 镜像 digest/实际版本、编码/locale/时区/扩展、业务配置/JIT 模式、每表精确行数与内容摘要、覆盖时间和品种、随机种子、压缩/恢复大小、SHA256、生成及实际恢复结果。功能场景固定时间与期望结果；时间敏感服务通过受控时钟或明确场景日期运行，避免老 fixture 被当作实时供源健康数据。

默认从合成数据生成 D1/D2。确需生产样本时，在 Ubuntu 的受限 R3 中抽样、替换身份、重建凭据并清空投递队列，再经过导出与泄漏检查；全量原备份和中间材料保留在私有目录，不进 Git、不挂到普通预览栈。不得通过直接裁剪生产表来制作小数据。

R0/R1/R2 的全部后端默认 `ALERTS_DELIVERY_ENABLED=false`，默认禁用真实行情外连，使用 fixture 和测试接收器。只有验证供源的任务才显式开启相应通道；仍使用独立测试配置，并阻断生产数据库、API 和投递目标。不能只在某个 worker 关闭通知，而让同项目其他服务继承生产投递设置。

跨任务复用的是**不可变的种子归档和生成器**，不是运行中的 volume。每个任务将种子恢复进自己的 PG。小库的导入和退役恢复验证都更快，也保留现行「归档且实际恢复校验后删卷」要求。PG 固定使用当前已审查 14.24 digest，验证 `server_version_num=140024`；后续升级通过新基线显式变更，不跟随 `latest` 或可变 PG14 标签。

## 6. 最终镜像复用的实施条件

### 6.1 区分分支验收与最终候选

分支提交和合并后最终提交不同，不能要求它们无条件共享一个镜像。分支保留 acceptance 用途构建；最终版本号、源提交、依赖和许可库输入确定后，创建一组不可变 **release 候选**，完成 R2 和所需 R3。生产只接收这组受测产物，不再按相同源码重构建。

候选清单记录：最终完整提交 SHA、dirty=false、各组件构建输入摘要、基础镜像 digest、许可库版本/摘要、构建参数、平台、产物身份、测试报告、数据基线和上一稳定版兼容性。只允许相同输入命中组件复用；复用旧组件时保留其真实来源，不能把旧镜像标成新提交构建。

### 6.2 前端跨环境地址

`web/Dockerfile` 的 `VITE_ADVANCED_CHART_ORIGIN` 编译进 JavaScript，`AdvancedWorkspace.tsx` 和 `market-data/Window.tsx` 直接读取它。仅在容器启动时设置另一个环境变量不会改变已构建页面。

建议把**非敏感的图表来源地址**改成受验证的运行时公开配置，仍强制 HTTPS、受允许来源、主站和图表不同 origin，且不把登录 Cookie/Authorization 交给图表静态域。配置只包含浏览器本来需要的公开地址，不包含代理凭据、数据库 URL 或 token；用配置版本和摘要与镜像版本分别登记。补齐已有窗口入口的统一读取及跨域/缓存验证后再启用。

若先沿用现有构建参数，则最终候选验收必须用隔离浏览器的 DNS/hosts/TLS 映射，把产物中的生产域名全部解析到 Ubuntu 验收端。必须拦截实际生产网络访问，使用全新浏览器状态，逐请求证明没有访问生产 API/图表/数据库，不能在日常登录生产的浏览器里修改全局 hosts。该方式复杂，作为过渡，不作为已实现能力。

### 6.3 镜像身份、传输与保护

现有 Ubuntu Docker 29 与 Unraid Docker 20 的镜像存储方式不同；v1.25.4 导入前后 Docker image ID 不同，但 RootFS DiffID 与有效 Config 一致。因此：

- 近期沿用已有 SSH `save/load` 流程；每个组件只导入一次，保存传输文件 SHA256，核对层及有效配置，再记录目标主机实际 ID。不要拿两端 `image inspect .Id` 字符串相等作唯一条件。
- 后续若使用私有 registry，固定平台对应 manifest digest，并记录 index/平台 manifest/config 身份；版本 tag 仅用于阅读，Compose 用不可变引用。registry 预算约 256 MiB 内存、0.2 CPU、20 GiB 存储，先证明增量传输收益；不在本轮安装或推送。含许可库的镜像必须保持授权范围内的私有访问。
- 当前退役工具会拒绝 release/rollback 用途镜像，`--retain-image` 也不能豁免。须先增加**项目资源归属与镜像消费引用分离**：最终验收项目拥有自己的容器、网络和库，但仅消费已登记并受保护的 release 产物；退役只删该项目资源，永不删它消费的正式/回滚镜像。
- 新保护索引覆盖活动项目、正式发布、回滚链、基线消费者及恢复任务；每次删除前重查实际 ID/digest 及全部运行和停止容器。不能通过 retag、重写镜像 purpose 或伪造完成状态规避现有保护。

### 6.4 Git tag、Docker tag 和自动发布门禁

现有 CI 没有“Ubuntu 验收通过就自动推送生产 tag”的步骤。`mw-docker build` 会给验收镜像写入 task、project、commit、用途和构建时间等归属标签，但不会自动创建 Git release tag、推送 GHCR、SSH 到 Unraid 或切换生产。`promote` 也只是规划中的命令，目前不存在。

建议把两个阶段分开：

1. 分支验收阶段只生成 acceptance 镜像，标签包含 task 和完整 commit；它不能直接 retag 成 release。
2. 合并到 `main` 后，从**准确的合并提交**在 Ubuntu 构建一组 release candidate，使用候选版本/commit 标签和不可变镜像 digest，写入候选清单。
3. R2/R3 通过后，候选状态变为 `validated`，但不自动变成生产 tag。先完成 PR review、发布清单和本次生产授权。
4. 获得授权后，才创建正式 Git tag（例如 `v1.25.6`）和对应的生产镜像引用；Unraid 导入/拉取的是 R2/R3 实际验证过的同一 digest，不重新构建。失败时只切回已登记的上一稳定 digest。

这样可以自动化“构建、记录候选、验收”，但把不可逆的正式 tag 和生产发布留在明确授权之后。未来可以让 Ubuntu 的 `accept/promote` 入口自动完成第 2、3 步，但第 4 步仍应要求人工授权；GitHub CI 和 GHCR 默认不承担生产发布。

## 7. 生产发布与回滚流程

### 7.1 按风险选择恢复工作量

| 类别 | 判定条件 | 发布前要求 | 应用回滚 |
| --- | --- | --- | --- |
| F0 兼容应用发布 | schema、PG、扩展、持久数据写入协议均不变；旧版可继续读写新版产生的数据 | 最终候选 R2；在线生成本轮一致性备份；另有匹配 PG/schema/备份工具、距发布 ≤24 小时的实际恢复演练证据（演练备份可与本轮新 dump 分开） | 切回上一组镜像及配置，保留当前数据 |
| F1 数据/结构变更 | 新迁移、索引、回填、持久格式或写入语义变化 | D3 上用最终候选完成实际迁移/业务验证，旧版对迁移后及新增数据的读写回归；耗时和锁预算 | 明确验证兼容才允许只换镜像；优先 expand/contract，不自动降级 |
| F2 破坏性/PG 变更 | 删列、不可逆数据转换、PG主版本/存储变化、无法证明旧版兼容 | 专项维护方案，最终恢复点的实际恢复校验、数据追补与明确 RPO/RTO | 按专项数据恢复方案处理，不能承诺秒回退 |

F0 快速通道是**待建立的新发布政策**，当前不据此降低任何已要求的恢复检查。实施先把完整恢复提前到停写前；验证稳定后，才允许在符合全部 F0 条件时复用最近恢复演练，免去每次重复跨机恢复整库。

必须区分两个保证：新备份的成功退出、SHA256、清单及 `pg_restore --list` 只能证明生成和基本可读；**不等于这份最新备份已实际恢复**。复用 ≤24 小时演练时，最新备份在本轮仍可能未恢复；灾难恢复的「已验证恢复点」只能指向那份实际演练过的备份。不能把快速应用回滚能力当成最新数据恢复保证。若要求每次最新备份都实际恢复，则保留该检查，但放在切换窗口前，并接受跨机恢复耗时。

### 7.2 预备与短窗口切换

1. **T−1 天至 T−1 小时：**确定风险类别、最终候选和上一稳定版；在 Ubuntu 完成 R2/必要 R3，提前导入镜像并验证目标身份。记录构建、传输、恢复、迁移、验收各段耗时。
2. **切换前：**在 Unraid 本机用现有 MVCC 一致性备份能力在线生成发布前数据库及配置备份。与每日 cron 共用已有互斥锁，禁止重叠重备份；备份失败不切换。当前工具会在同一快照下计数和导出，大表计数及长快照仍有负载，需单独测量和错峰，不能当作零成本。
3. **时效门槛：**F0 拟要求备份快照时点距切换 ≤15 分钟、配置与当前一致、恢复证据有效；补记真实 `snapshot_at`，不能直接将现有文件时间或清单完成时间当作快照时间。超时重新评估/生成。首阶段先保留最新备份的完整恢复，将其移出停写窗口；若因此超过 15 分钟，记录原因并使用更保守的发布窗口，不能静默放宽门槛。
4. **配置核对：**从当前 `compose.production.yaml` 生成 standalone release 文件，核对固定镜像、全部后端 Yahoo=true、既有代理/数据库/网络/端口/资源、按服务 JIT 策略及通知配置。生产不带验收用 `ALERTS_DATABASE_EXPECTED_VERSION`；保留当前 PG14.24 和生产私有配置。
5. **正式窗口：**获得该次生产发布授权后才停本项目必要写入者，记录用户业务状态指纹和服务状态。按风险执行迁移与镜像替换，避免两个版本的调度/投递 worker 同时写同一库。首版采用单生产实例受控切换，不另起全套蓝绿栈占用 Unraid 内存。
6. **切换门禁：**迁移成功、API ready、反向代理上游可达后再启对应 worker；核对网页、SSE、心跳、队列推进和供源读取。Compose `healthcheck` 本身不会自动完成切流或回滚，需要发布入口显式处理。当前主线 Nginx 已有 DNS 动态解析，仍需实测所用产物，旧版本必要时刷新 web/TLS。
7. **观察与结案：**至少 15 分钟真实行情和指标观察，明确是否跨到新分钟；错误率、reset、OOM/重启及用户状态指纹达标后结案。最新备份若走 F0 演练复用政策，应在后续固定演练窗口实际恢复，最长 24 小时；失败即标记备份异常并阻止下一次发布，不自动覆盖生产库。

先以「停写时间较 934 秒减少至少 50%」为试点目标，F0 成熟目标为 **≤120 秒**。这不是现状保证：若备份、迁移或必要验证仍在窗口内且超时，应报告分段事实，不为了达标跳检查。生产全程不新建开发、验收、临时调试实例。

### 7.3 生产备份和迁移分别在哪里进行

| 动作 | Ubuntu 开发/验收 | Unraid 生产 |
| --- | --- | --- |
| 日常开发数据 | 每个 task 自己的 PG14 容器、数据库和 volume；使用 D0/D1/D2 | 不使用生产库 |
| 生产发布前备份 | 可把指定 dump 复制到 Ubuntu 做隔离恢复验证；不连接生产执行写入 | **在 Unraid 本机**由正式 backup 镜像从当前 PG14 生成；当前目标目录为 `/mnt/user/backup/market-watch`，配置归档也在此目录 |
| 迁移预演 | 对 F1/F2，在 Ubuntu 独立 PG14 恢复副本执行最终候选的 `alembic upgrade head`，核对表、指纹和旧版兼容性 | **最终迁移在 Unraid 生产 PG14 上执行**，由 release `migrate` 服务连接生产数据库；不是先在 Ubuntu 改好数据库再整库复制回生产 |
| 恢复演练 | 在独立 PG14 restore project 新建临时数据库实际 `pg_restore`，完成后删除/退役该 project | 不在生产库上创建 restore database，不给生产账号临时提权 |
| 应用切换 | 不启动生产 worker，不接真实通知 | 备份成功、迁移成功后，按顺序启动 API/worker，核对 health、SSE、队列和供源 |

当前生产数据库服务名为 `postgresql14`，数据目录绑定在 `/mnt/disk1/appdata/postgresql14`；生产 Compose project 为 `market-watch`。这些路径和名字只用于本次现场基线，实际发布仍以当次展开的 standalone Compose 和发布清单为准。不能启动停止的 `postgresql14-14.10-rollback-20261015` 去共享该数据目录，也不能把停止旧容器当作恢复演练。

具体顺序是：

1. Ubuntu 先用候选镜像在 R2/R3 完成功能、迁移或恢复预演，保存候选清单和兼容结论。
2. 获得生产发布授权后，在 Unraid 本机获取发布前全量逻辑备份和私密配置归档；备份使用现有锁，失败就停止发布。备份生成成功、SHA256 和 `pg_restore --list` 通过，不自动等同于实际恢复通过；记录真实 `snapshot_at` 和完成时间。
3. 如该风险类别要求最新恢复点实际验证，将 dump 只读传到 Ubuntu 独立 PG14 restore project，实际恢复并核对后再进入切换；Ubuntu 不把恢复库作为生产数据库使用。
4. 在 Unraid 停止会写生产库的必要 worker，运行最终候选的 `migrate` 服务对**当前生产 PG14**执行迁移；记录退出码、耗时、schema revision 和锁/错误情况。F0 无结构变化时仍可运行只读的版本/配置门禁，但不凭空执行迁移。
5. 迁移成功后启动 API 和 worker，逐项健康检查；失败则按 F1/F2 规则处理，不能直接假设 `alembic downgrade` 或恢复旧 dump 是安全回滚。

这样，生产数据只在 Unraid 的正式 PG 中迁移；Ubuntu 的数据库只承担隔离验收和恢复证据。日常三个并行任务不会复制 11.56 GiB 的生产库，也不会把开发数据回传 Unraid。

### 7.4 回滚边界

| 失败阶段 | 措施 | 数据处理 |
| --- | --- | --- |
| 构建、验收、传输、备份或预检失败 | 候选失败，保留证据；生产不切换 | 不触碰生产数据 |
| F0 切换后未 ready / 功能失败 | 用已记录的上一稳定镜像和配置恢复，单写入者启动，重验入口和心跳 | 不恢复旧 dump、不丢弃上线后用户操作 |
| F1 迁移失败 | 停止继续切换；按已演练结果决定保留旧版、修复前进或专项恢复 | 不假设事务外 DDL/回填已自动回滚；禁止无验证 `alembic downgrade` |
| 数据损坏或 F2 失败 | 保留当前现场与可取证备份，进入专项恢复 | 恢复到独立目标验证后再正式切换，明确备份后增量及不可重放通知的处理；不得直接覆盖原库 |
| 仅 Ubuntu 新入口失败 | 回到已保存的旧版工具/任务配置，暂停本任务的新启动 | 不重建/清空其他项目，不覆盖尚未合并的缓存优化 |

F0 应用回滚目标 RTO ≤5 分钟、回滚动作不损失当前数据库中的业务数据；历史队列与外部投递是否可重放需单独验证。灾难恢复 RTO 当前未知，先实测；已验证备份的时效目标 ≤24 小时，同机备份仍不提供异机容灾。F2 的数据 RPO 需专项确认，不能套用应用回滚的无数据恢复路径。

## 8. 生命周期、清理与保留边界

### 8.1 统一任务台账

以 `mw-docker` 为唯一事实入口，固定持久化状态根，记录 task/owner/branch/完整提交/project、所需 profile、端口、volume、镜像消费引用、数据基线、预算、最近活动、到期时间和保留原因。临时目录里的历史登记只盘点和导入核实结果，不盲目合并或覆盖；台账与实际 Docker 资源交叉核对。

建议状态：`active ⇄ parked → ready_for_retire → archive_verified → retired`。park 只是按用户安排停止已登记任务，保留库和镜像，不写完成标记；24 小时到期先提醒，不自动停机或删除。没有 owner、用途冲突、失联或验证失败的任务进入人工核实清单，不自动退休。

验收结束仍执行现有流程：精确预览 → 停本任务写入 → 私有归档 → **实际恢复与全 schema 行数/内容摘要核对** → 重查跨任务引用 → 删除精确资源 → 登记完成。小数据能让这条路径变快，第一阶段不削弱校验。

恢复任务应单独登记「源备份、实际恢复结果、是否启动过写入者、源备份保留引用」，与镜像构建 task 分开。未来可评估：对完全由不可变母备份生成、未产生独有写入的恢复副本，复用母备份和本轮恢复证据，避免为了删除恢复副本再重复 dump/restore。**必须先修订对应规则、实现检测与负面测试，现行工具不支持时保留资源，不绕过。**

### 8.2 清理对象与禁区

| 资源 | 将来可清理条件 | 保护边界 |
| --- | --- | --- |
| Ubuntu 项目容器/网络 | 精确 project + 已核实归属 + 已结束 + 归档/恢复通过 + 新鲜引用检查 | 当前六组未结束或归属待核实项目均不在删除范围 |
| Ubuntu PG volume | 本任务独占、内容已归档实际恢复、无其他容器/绑定依赖 | 共享卷、external/bind DB、未知卷、失败卷保留；不按 unused 或名字前缀删 |
| acceptance/development 镜像 | managed、匹配 task/project、完成、过期、无任何运行/停止容器和保护索引引用 | 借用镜像、基线输入、正式/回滚镜像、未知镜像保留；不强删 |
| BuildKit / OCI 缓存 | 专用 builder 的既有 GC、已核实工具私有缓存策略 | 不做全局 builder prune，不直接删 containerd/overlayfs 文件或 builder volume |
| 导入 tar/临时文件 | 目标身份与完整性验证通过、源产物仍可取回、清单记录精确路径 | 不清空 `/tmp`、仓库 artifacts 或用户目录；许可文件和私有配置另行保护 |
| 工作树/node_modules/构建目录 | 任务 owner 核实，无未提交/未推送/私有独有内容，列清单后另行处理 | 不从 branch 已合并推断工作树可删；不动并行开发目录 |
| Unraid 资源、旧发布/镜像/备份 | 另一次明确生产资源处置授权，列精确清单与恢复依赖 | 本轮全部不动；不得全局 prune 或批量删除旧 release |

尤其保护生产 PG bind 数据、PG14.10 回退容器、当前和回滚镜像、所有仍有引用的正式清单、私有配置及备份；不能启动旧 PG 共享当前数据目录来「验证回滚」。Docker named volume 清单也不包含生产 bind 数据的大小，不能据其几十 MB 判定数据库占用很小。

建议日常开发镜像继续用已有 7 天保留期；独立验收归档在成功退役后保留 14 天，软预算 5 GiB，失败和显式 hold 不按 TTL 删除。正式产物至少保留最近 3 个稳定版本、当前及全部在用回滚链；不再需要的历史 release 用单独、可审查的退役清单处理，不能修改现有自动清理去扫 release 标签。

生产备份拟采用「每日 7 份、每周 4 份、每月 3 份」分层保留，按集合去重；发布前/PG 升级备份、唯一验证恢复点、活动回滚引用及 hold 额外固定保留。**新备份未实际恢复、异机副本未核验、依赖未解除时，不轮换删除唯一可用旧点。** 配置归档与对应数据库和镜像清单配套保留。100 GiB 是预警预算；保护项超预算时报告，不打破保护。应另行建立加密异机副本及可恢复性证明，本轮未验证现有异机副本。

日志先在新 Ubuntu Compose 设置 `json-file max-size=10m, max-file=3`，必要时再按业务调整。不要直接改 daemon 全局配置重启 Docker；现有容器不会因为新增配置就自动获得轮转，后续由各任务正常重建生效。生产现有项目日志已是 50m ×1，本轮不改。

## 9. 分阶段实施与退出条件

工作量为单人实施粗估，不含等待验收、资源扩容或生产授权的时间；每阶段先在新的 Ubuntu 任务中实施，不覆盖其他工作树。

| 阶段 | 实施项 | 交付和退出条件 | 预计工作量 |
| --- | --- | --- | --- |
| S0 统一事实与工具 | 核实六组任务 owner/状态；对齐安装版与 main，保留 OCI 缓存优化并补 PG14.24；将现场路径/版本变成统一状态索引 | 工具版本可追溯；无孤立 project；只读 status 能列数据/镜像引用与预算；未知项仍受保护 | 0.5–1 天 |
| S1 个人轻量验收与 PG 复用 | 实现 D0/D1 生成和恢复清单；R1/R1W 文件、端口记录、通知/供源隔离、日志轮转、PG 首次初始化/后续复用/按需 reset；并发由用户手动控制 | 两个 R1 无数据串扰、无外发通知；普通重跑保留 PG volume 与数据；CPU/内存上限确实生效，备份恢复退役闭环通过 | 1–2 天 |
| S2 镜像消费与最终验收 | 先实现 release 产物引用保护及验收/恢复消费者退役；解决公开运行时图表来源配置；建立最终候选清单 | 同一产物从 R2 到目标导入验证；失败/并发引用时拒绝清理；全部跨来源/登录边界回归通过 | 1–2 天 |
| S3 发布分级与计时 | 整理当前发布工具与旧文档入口；实现 F0/F1/F2 门禁、提前传输/备份/演练、回滚清单和分段计时 | Ubuntu 演练完整流程及失败路径；仅用户授权该次发布后才运行 Unraid 切换 | 1–2 天 |
| S4 可选生命周期收口 | 手动 park、到期提醒、归档预算、历史资源分类、独立 restore-job 生命周期；不增加调度租约 | 新任务可完整退役；进行中、未知归属、恢复失败、共享引用均不被误删；老资源只产出处置建议 | 1–2 天，按需要 |
| S5 按测量追加能力 | 用户按实测决定第 3 个 R1 是否并行；评估私有 registry、任务域名、共享 PG | 有实测收益和新增运维预算；不因已有技术选择而强行引入 | 按结果另估 |

本分支已新增 `mw-docker preview prepare/up/status/stop/reset`，与现有 `build/compose-build/retire/cleanup` 共用任务登记；主机安装版尚未替换。`park/accept/promote/rollback` 仍不存在，按后续实测收益决定是否增加。如需 Makefile，只作现有命令的别名，不另建状态和清理系统。

共享 PG 试点只在 S5 资源数据显示值得时进行：新建 Ubuntu 专用服务，每任务独立 database 和最小权限角色，限制连接数/查询时间，禁止跨库连接；验证数据库创建/迁移/扩展/故障是否影响邻居，保留 R3 独占 PG。需先调整现行独立 volume 约束及退役实现；`CREATE DATABASE TEMPLATE` 仍是复制而不是零成本快照。试点失败回到任务独占 PG，小数据包和镜像流程继续复用。

## 10. 验收标准与观测方法

以下是各阶段的完整目标，不代表本次全部完成。已运行的 R1 隔离、复用、重置及小库恢复 smoke 单独见第 11 节；30 分钟并发稳定性、十次启动分位数、R2/R3、生产发布与删除闭环仍需后续实测。

| 范围 | 必须通过的标准 |
| --- | --- |
| 任务隔离 | 同时运行的 task/project/网络/volume/数据库/凭据/端口均不同；A 的迁移、重启和退役不能改变 B 的数据、连接或容器状态 |
| 数据基线 | SHA、schema、PG 实际版本、行数/内容摘要、场景时间和通知隔离均可验证；抽查无生产身份、session、真实投递目标；每个任务恢复到独占库 |
| PG/JIT | 实际 140024 和 provider 探测通过；连接策略 inherit/on/off 各自保留；性能测试明确是否加载 LLVM，不能用统一 jit=off 掩盖资源问题 |
| 并发资源 | 由用户安排两个 R1 持续至少 30 分钟无 OOM/重启；第三个 R1 仅在资源实测达标且用户安排后验证；R2/R3 不与重型任务并行；主机可用内存不低于 2 GiB、预计及实际可用磁盘不低于 20 GiB；逐容器核对 cgroup 限额和日志轮转 |
| 启动与正确性 | 预构建镜像和 D1 下，新 R1 从开始初始化到 ready 的 p95 目标 ≤180 秒；连续测 10 次，记录 restore/migrate/start 分段；活动任务功能测试全部通过，响应 p95 相对同 profile 串行基线目标 ≤1.5 倍 |
| 最终镜像 | R2 报告记录实际产物身份；生产导入不重构建，身份映射/层/有效配置可复核；主站/图表验收请求全部落在 Ubuntu，0 生产请求、0 凭据泄漏；版本元数据与真实组件来源一致 |
| 完整业务链 | 被测 profile 覆盖所需 worker；SSE/历史/聚合/指标/供源正常，真实新分钟推进；通知只用测试接收器，无生产投递；不能用 ready 代替功能结论 |
| 发布效率 | F0 试点停写较 934 秒减少 ≥50%；成熟目标 ≤120 秒；记录备份/传输/恢复/迁移/切换/观察各段实际耗时，门禁未通过不得算成功 |
| 恢复与回滚 | 对适用备份实际恢复，所有业务表和关键用户状态一致；F0 切回旧镜像 ≤5 分钟且保留新增业务数据；F1 在迁移后库验证旧版读写，F2 单独验证 RPO/RTO |
| 清理安全 | 在隔离任务验证：进行中、过期未完成、停止容器引用、未知归属、借用镜像、release/rollback、恢复失败、跨任务卷和竞态均拒删；成功退役后只有精确项目资源消失，母产物/其他任务保持原状 |
| 空间闭环 | 连续三个「创建→验收→退役」周期后，资源台账与实际一致；除明确保留的归档/热缓存外不单调增长；比较文件系统净占用，不把镜像虚拟大小当收益 |

性能实验需登记专属窗口及环境变化：禁止同时跑其他任务的重构建、全量恢复或清理；对照使用同镜像、同 D2/D3、相同 JIT/缓存状态与 SQL 参数，分别报告冷/热、p50/p95、峰值 RSS、CPU 和 I/O。R1 限额下的测量只用于验收资源评估，不外推生产性能。
