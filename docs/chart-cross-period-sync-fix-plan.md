# 跨周期历史定位与十字线同步：根因及修复方案

2026-10-04。分析基线：本地 `62488c6`；生产 v1.7.0 源码标签 `e40eaac`。原诊断状态：生产复现、跨周期对照及隔离修复原型已完成。产品实现与隔离验收现已完成适用检查，未部署生产；见[实现与验收记录](chart-cross-period-sync-acceptance.md)。

## 1. 结论与证据范围

两个问题是共用导航及同步流程的缺陷，M5 更容易暴露第一个问题，但两者都不局限于 M5 或四图。

1. **远距离定位被当作连续补齐历史**，原生请求包含目标到已载入边界的整段历史；超过请求容量后，错误又留在原生线程内，时间轴未退出加载状态。
2. **十字线先按旧视区定位，图表随后才移动**；移动和补数完成后没有按原始时间重新投影，下一次鼠标移动才补做同步。

生产验证使用真实 Playwright Chromium，访问 `https://trade.kookvv.com:8443/advanced-charts`，图表来源为 `https://charts.kookvv.com:8443`。临时浏览器会话拦截用户布局、设置等状态写入。隔离验证使用实际许可 v31.1 原生库和合成 24×7 datafeed，无生产 API 调用。

[精简、去除用户状态标识的测量记录](verification/chart-sync-diagnosis/evidence.json)保存了下面的生产对照、跨周期结果及原型结果。合成 datafeed 用于验证机制；不能据此声称所有行情商、交易日历和周期已完成生产验收。

## 2. 问题一：超限、商品代码错误及图表卡住

### 2.1 已复现的触发链

生产 EURUSD 的 H4/W1/D1/M5 四图中，只在 W1 拖动一屏、开启时间同步，M5 发出：

| 字段 | 实测值 |
| --- | ---: |
| `limit` / `countBack` | 60031 |
| M5 当前每屏估算 | 127 |
| 储备批次 | 2 屏 |
| 桥接 `from` | 1765607280000 |
| 桥接 `before` | 1790820300000 |
| 宿主回复 | 请求不在允许范围内 |
| 对应后端 HTTP | 未发出 |

关闭时间同步后做同样的 W1 拖动，M5 最大请求为 254，未出现拒绝。这说明 60031 主要来自跨周期定位需求，并非正常两屏储备。

### 2.2 根因定位

- 许可库模型的 `_gotoTimeImpl` 在目标早于现有历史时，调用 `estimateLeft(target)`，再加半屏宽度，向原生时间轴请求历史。它希望补齐一段连续历史，并非只读取目标附近一屏。
- [bridge.js](../advanced-host/bridge.js) 的 `getBars` 原样传递原生 `countBack`。这是当前数据合同的正确行为；任意截小它会让原生需求仍未得到满足。
- [AdvancedWorkspace.tsx](../web/src/advanced/AdvancedWorkspace.tsx) 的 data 消息校验拒绝 provider `limit > 20000`。此次请求在这里被拒绝，因此不足以证明 OANDA 不提供那段 M5 历史。
- 后端 [DataQuery](../backend/alerts/chart_api.py) 同样限制 `limit/countBack <= 20000`；[provider_cache.py](../backend/alerts/provider_cache.py) 还限制真实区间需求加计算前缀不超过 [CAPACITY](../backend/alerts/provider_history_policy.py)。只放宽前端上限仍会失败。
- `getBars` 错误传给原生 `err` 后，适配器线程保留 `_errorMessage`，后续 `_processPendingSubscribers` 会把同一个错误返回给新请求。
- 原生时间轴正常完成路径会清除 `_requestingMoreData`，此错误路径未完成同样的收尾。实测适配器 `_requesting=false`，但 M5 时间轴 `_requestingMoreData=true`；再次拖动后仍保持该组合。
- [native-reserve.js](../advanced-host/native-reserve.js) 在时间轴正在必需加载时退让，无法越过这个未释放状态。因此后端已有缓存、储备重试都不能自行恢复这次卡住。

“商品代码错误”属于历史错误进入原生序列错误流程后的表现，此次没有证明商品代码真的无效。`dataReady()` 也可能沿用旧数据而返回 true，不能单独用它证明失败后的恢复。

### 2.3 举一反三

| 周期 | 超限和卡住风险 | 本轮证据 |
| --- | --- | --- |
| M1、M5、M15、M30 | 高；跨越几个月或几年很容易累积巨大需求 | M5 生产复现；四周期隔离复现 |
| H1、H4 | 同一机制，目标更远时也会超限 | MN 远跳至约 2017 年时，隔离请求分别为 85073、20993 |
| D1、W1、MN | 机制相同；达到 20000 根需要更长历史，通常先遇到品种起点 | 容量问题未在这三周期逐一实测；不得写成已验收 |

容量取决于实际 bar 数、已载入边界、视区和指标前缀，不能用固定日历跨度作为所有品种的共同上限。24×7 和外汇周末停盘的结果会不同。

同一错误路径还可能受到合法请求的超时、503 或取消影响。宿主目前把 `inflight >= 8` 也归入“请求不在允许范围内”，必须区分繁忙与参数超限；本次 60031 的拒绝条件已确定，无需靠繁忙假设解释。

其他入口也要纳入：2/4/8 图、同周期但处于不同历史位置的图表、日期跳转、保存布局恢复、`setVisibleRange`、日期范围同步以及周期切换。Yahoo、Binance 复用桥接与原生适配器；行情商真实窗口限制应单独处理。

## 3. 问题二：时间已移动，十字线要再晃鼠标才对齐

### 3.1 排除取数失败的独立生产复现

H4/W1/D1/M5，开启时间及十字线同步、关闭日期范围同步。W1 点击 2026-09-21，点击后保持鼠标不动 3 秒；本次没有请求拒绝或 API 错误。

| 目标图 | 点击后视区已到目标 | 鼠标静止时十字线 | 再移动鼠标后 |
| --- | --- | --- | --- |
| D1 | 是 | 2026-09-28 | 2026-09-21 |
| H4 | 是 | 2026-09-27 21:00 | 2026-09-20 21:00 |
| M5 | 是 | 2026-09-15 05:30 | 2026-09-21 00:00 |

H4 最终标签与 W1 字面日期不同，是交易时段映射的结果，不能简单要求所有周期的时间戳逐字相等。

### 3.2 根因定位

1. 原生 `setExternalPosition` 将同步时间映射成目标图索引，并调用 `setCurrentPosition`。
2. 后者使用 `coordinateToVisibleIndex`，会把屏外坐标夹到**旧可见范围**的边缘。
3. 原生 `syncScroll` 随后以 `forEach` 启动各图 `syncTimeWithModel`，没有等待每图跳转完成，也没有重新应用十字线时间。
4. 视区变化不会自动把旧索引重新映射到原始同步时间；补入历史后，索引含义甚至会改变。
5. 新鼠标事件重新广播源时间，此时目标已在视区中，所以恢复正确。

所有周期共用这些方法。在隔离库中，H1/H4/D1/W1 均出现静止点击与移动鼠标后的位置差异；M5 也独立复现。已经缓存的历史只需要移动视区，同样可能出现，无需网络慢或超限。

现有 [advanced-viewport-sync.browser.cjs](../web/tests/advanced-viewport-sync.browser.cjs) 在跳转后又执行了 hover，混合周期重点为 M5/M15。重新 hover 恰好掩盖了“点击后静止”的缺陷。

## 4. 推荐方案：统一协调导航、历史窗口和语义光标

### 4.1 按实际需求区分连续拖动与远距离定位

保留 v1.7.0 正常拖动策略：普通储备阈值两屏、每批一屏；快速拖动或较慢读取时临时三屏、每批两屏。此轮不减少这些储备，也不把后端预热 1000/4000 根直接推到每个前端图表。

为每图建立 `navigateToTime` / `navigateToRange` 协调入口，由可靠原生目标事件进入，覆盖上述导航入口。不能在已经超限的 `getBars` 中猜测用户原本点击哪一天。

- 目标在已载入数据内：继续原生移动视区。
- 目标距已载入边界很近，连续补齐需求小：继续原生分页。
- 目标很远：建立以目标为锚的有限历史窗口。预算由视区、旧侧两至三屏储备、有限较新侧回拖范围、指标计算前缀和原生对齐余量组成；目标与现在之间的整段走廊不属于这个窗口。
- 窗口日期和实际数量由原生交易日历及后端覆盖判断，遵守 `[from,to)`、排序、唯一时间戳及真实历史边界。不得用“分钟数 × 周期”替代 D/W/M、周末和 DST 的实际 bar 映射。
- 有效窗口的必需需求加前缀不得超过 20000；先减少可选缓冲。用户确实要求显示超过容量的整段范围时，明确提示范围过大并允许缩小，不伪造满屏、不自动改变用户缩放来隐藏问题。

### 4.2 有限窗口必须改变原生适配器的锚点

只调用 `setVisibleRange`、公开 `timeframe`、`resetData` 或截小 `countBack` 不足以解决问题。[此前跳转研究](native-chart-additive-buffer-jump-study.md) 已记录公开历史范围仍请求到当前日期。本轮探针进一步确认，适配器 `_ensureRequestedTo` 在缓存为空时以 `_now()` 为右侧锚，还会把较旧 `range.to` 到该锚点的 bar 数加进需求。

推荐在现有 SHA 校验的许可库挂钩基础上扩展最小导航适配层：

1. 为历史窗口提供明确的初始右边界和数据源代次。
2. 在创建/重建对应数据源时给出目标窗口与实际初始根数。
3. 仅对这个历史窗口，以窗口右边界初始化适配器读取锚点；后续正常向左分页仍沿窗口最早 bar 推进。
4. 已确认新窗口有效后恢复柱间距、指标、画线和价格轴，定位目标并重放光标。失败时保留原有效视图。

**隔离原型已证明入口可行：**同一 M5 目标原请求 200081 根；仅重设原生时间范围并重建源仍请求 200833 根。补上历史窗口适配器右边界后，实际请求为 448 根，`from=1730563200`、`to=1730697600`，成功定位 `1730678400`。随后真实鼠标拖动约 0.9 屏、保持按下时视区已移动，无新增历史请求；返回最新使用独立 450 根请求，没有补齐几年走廊。

原型使用实际库的浏览器内临时探针，只证明一个 M5 窗口的可行性。正式代码不能把探针直接复制上线；指标重算、画线保持、实时流、窗口共享及取消仍需完成下述验收。

### 4.3 同商品、同周期多图必须隔离不相接的窗口

当前原生适配器及储备登记主要按商品和周期共享线程。对其中一图盲目清空线程，会影响另一图；把远历史窗口和最新窗口放进同一连续序列，也会再次引入走廊需求。

将原生数据源共享范围改为“真实序列身份 + 相接历史窗口”。不相接的历史窗口使用独立内部窗口标识及代次，保持外显商品代码、行情商身份和后端缓存键不变。相同窗口可共享；后端继续通过既有 PostgreSQL 覆盖和取数租约复用数据。储备登记、实时订阅 ID、历史更正状态及刷新入口都要识别窗口身份，不能仅修改线程工厂。

历史窗口不直接拼入跨越多年缺口的最新 tick。最新报价及最新窗口继续接收实时更新；历史窗口按自身覆盖接受更正。返回最新明确切换窗口。窗口必须有有限生命周期，回收不可见/过期源及请求，不能把一次窗口化变成每次点击永久新增前端缓存。

历史窗口内向更早方向继续使用原生分页；向较新方向接近右侧边界时，要预备相接的下一窗口并在有效数据到达后移动边界。原生默认只保证向更早取数，不能让用户向较新方向拖动时进入永久未来空白。相接窗口保留重叠数据与几何位置，较新边界达到实时尾部时再回到最新模式；该路径尚未由本轮单次向旧历史拖动原型覆盖。

### 4.4 所有失败必须完成原生生命周期

补充结构化错误，保留后端错误码经过 [api.ts](../web/src/api.ts)、postMessage、宿主及原生适配层。目前 API 包装只保留错误文案。

| 类型 | 应有行为 |
| --- | --- |
| 容量超限 | 优先转为有限定位窗口；真实过大视区明确提示 |
| 繁忙、503、超时 | 本次结束，保留有效 bar，允许有限重试或用户下次操作重试 |
| 取消/旧代次 | 结束所属旧请求，不改变新窗口或新光标 |
| 真实历史起点/供应商窗口 | 仅按后端已确认覆盖及边界结束分页；返回有效可用数据 |
| 商品确实不存在 | 才进入商品无效状态 |

原生请求开始时记录游标及缓存代次。失败后需同时收尾适配器请求/订阅、时间轴加载标记、导航 deferred 和宿主 token；恢复有效旧游标，避免 `_errorMessage` 永久污染该序列。可恢复历史错误不应覆盖现有图表为商品无效。

不能把错误改成 `noData:true`，不能只清 `_requestingMoreData` 后立即重新发出同一个巨大请求，也不能盲目调用会再触发分页的 `onTimeScaleCompleted(false)`。普通错误不得无限重试。需要从已卡住的 v1.7.0 状态恢复时，应按匹配窗口/缓存代次清除错误并重建有限源；`resetData` 或切周期本身没有被验证为可靠恢复。

### 4.5 保留时间语义，跳转完成后重放最新光标

为每图记录来自源图的最新光标时间、`syncSourceTarget`、商品/价格和源图身份，不把旧像素或旧索引作为最终状态。导航代次与光标版本分开：鼠标移动更新光标，不自动取消正在完成的有效导航。

在目标图导航完成、数据加载完成以及最终视区绘制之后，重新映射**最新仍有效**的光标。已缓存的纯视区移动也必须执行。使用原生会话转换，把 W1/D1/MN 与分钟图定位到相应实际 bar。

重放走外部定位路径，避免递归广播。鼠标离开、关闭十字线同步、源图变更或布局销毁时清除待重放状态；较旧完成回调不能把光标拉回此前位置。十字线同步关闭时不重放，也不改变仅开启十字线同步时原本的视区行为。

**隔离原型已通过：**包装 `setExternalPosition` 保存原始时间，在 `syncTimeWithModel` 完成及两次绘制调度后重放，H1/H4/D1/W1/M5 的目标光标在鼠标静止阶段与再次移动后的结果一致。它仍不能完成已被超限拒绝的导航，必须与窗口及错误收尾一起修复。

### 4.6 构建与缓存交付

继续使用 [patch-native-reserve.mjs](../advanced-host/patch-native-reserve.mjs) 的原始 SHA、唯一锚点、重复安装及关闭校验，Git 只保存自有挂钩代码，不保存许可 bundle。

[nginx.conf](../advanced-host/nginx.conf) 对带 hash 的 bundle 设置一年 `immutable`，目前补丁修改字节后仍沿用供应商原文件名。后续修改库时必须生成新的内容版本 URL/目录，并让入口引用它；单独更换 host hash 不会使旧库资源失效。验收同时覆盖新浏览器和已缓存旧版本的浏览器。

## 5. 实施拆分及验收门槛

建议按以下顺序交付，合并前验证完整链路：

1. 补入静止点击及超限后再操作的失败回归，结构化错误与原生失败收尾先保证不再卡死。
2. 加入语义光标保存/重放，覆盖仅视区移动和异步补数。
3. 实施有限历史窗口及共享隔离，让远日期定位真正可用。
4. 集成现有储备、历史更正、实时订阅和布局生命周期；更新库资源 URL 后再做发布验收。

| 验收维度 | 必须覆盖 |
| --- | --- |
| 周期/图数 | 支持的九周期，2/4/8 图；高周期到低周期、同周期不同位置、反向同步 |
| 静止鼠标 | 屏外点击后不再 hover；等待导航完成后检查实际光标时间标签及绘制位置 |
| 历史容量 | 已缓存/未缓存；连续需求小于及大于 20000；远跳请求只包含目标有限窗口 |
| 操作入口 | 点击、拖动释放、日期对话框、范围同步、历史布局恢复、切周期、回到最新 |
| 异步错误 | 超时、503、繁忙、取消、乱序；随后正常操作能恢复，无永久 loading、假商品错误或假历史终点 |
| 共享窗口 | 同商品同周期多图，一图在最新、另一图在远历史；一图重建不清空另一图 |
| 指标/交易日历 | 原生及 Python 指标的真实前缀；OANDA/Binance/Yahoo 适用周期，周末、节假日、DST、W1/MN 标签 |
| 现有体验 | 正常一屏拖动及按住时绘制保持顺畅；保留柱宽、画线、价格轴、用户开关及布局 |
| 内存/后端 | 连续远跳不会积累无限窗口，不返回整段多年历史；已有缓存命中复用 PG，有限预热不扩成全量取数 |
| 发布缓存 | 旧缓存浏览器确实加载新库 hash，关闭挂钩后可恢复已验证基线 |

本方案保留原诊断与验收门槛。后续产品实现、已完成检查及尚未覆盖范围见[实现与验收记录](chart-cross-period-sync-acceptance.md)，不把隔离验收等同于已修复生产。
