Project: `market-watch-v132-ui`.
Worktree: `/home/quant/repos/market-watch-deploy-v1.3.2`.
Branch: `deploy/v1.3.2`. API/web baseline: `v1.3.2` / `9596b25`.
Chart menu source: `7bf84bb` (theme-specific background and homepage branding).

LAN entry: **https://192.168.7.232:15653**.
Local-only entry: **https://v132.localhost:15653**.
Chart origin: **https://chart-v132.192.168.7.232.sslip.io:15654**.
The chart hostname resolves to the Ubuntu LAN address and keeps login cookies
off the chart origin. The web image embeds this origin at build time. Browser
clients need DNS resolution for the chart hostname, which was verified here.
Ports 15653/15654 bind only to loopback and the selected LAN interface.
The database has no host port.

The local TLS certificate includes the LAN IP and chart hostname. For a new
browser, trust the public certificate for both origins, or visit each origin
once and accept the local certificate exception. The private key stays on the
Ubuntu machine. No administrator or provider credentials belong in Git.

The PostgreSQL container, default network and `market-watch-v132-ui_pgdata`
volume belong solely to this project. Runtime images are fixed by local image
ID, so another branch retagging an image does not change this deployment.
Private env/TLS files and the source database snapshot live in the mode-0700
directory `/home/quant/.local/share/market-watch/v1.3.2-ui`, with files mode 0600.
This directory persists independently of temporary-directory cleanup.

A read-only consistent `pg_dump` of the shared `market_watch_dual` database
was restored to the new database `market_watch_v132_ui`. The source had already
reached `p17_volume`; only the dedicated copy was downgraded using that
migration's implementation to `o16_managed_revisions`, the v1.3.2 schema.
The removed volume fields/tables remain in the source and retained snapshot.
All key row counts and complete workspace/preference document digests were
checked before starting this instance and remained identical. The two
instances now evolve separately; later changes are not synchronized.

Start or update this project from the dedicated worktree:

```bash
sg docker -c 'deploy/releases/v1.3.2-ui.sh up -d --no-build --wait'
sg docker -c 'deploy/releases/v1.3.2-ui.sh ps'
sg docker -c 'deploy/releases/v1.3.2-ui.sh logs --tail 100 api'
```

The helper explicitly selects the project, compose file and non-secret env.
Do not use the old dual-acceptance command to deploy this branch.
Do not delete the persistent database volume when recreating services.

Rebuild the web image for this LAN chart origin:

```bash
sg docker -c 'docker compose -f deploy/releases/v1.3.2-ui-build.yaml build web'
```

Record the resulting image ID in `v1.3.2-ui.env` before starting containers.
If the host's DHCP address changes, update both port bindings, public URL,
embedded chart origin and TLS SANs, then rebuild web. Reserving 192.168.7.232
in the router keeps this entry stable.

Evidence is under `docs/verification/v1.3.2-isolated/`. Notification delivery
remains disabled, and the dedicated API/worker database pools each use one
connection with zero overflow. Existing branch projects are preserved.

Browser validation used the actual LAN URL: HTTPS login, chart rendering,
theme-specific computed colors, the corner menu position, keyboard controls,
800px layout and theme persistence. Six successive switches/reloads passed
after waiting for each theme-save response. The earlier GET-only wait allowed
an immediate reload before an asynchronous save completed; this is documented
in `lan-browser-save-race.json`, and the regression test now waits for the
matching successful POST acknowledgement. No product code was changed for
this test timing issue. Of 1,141 chart requests checked during that run, none
included login cookies or an Authorization header. Original theme content was
restored and test workspaces removed. All 34 previously running containers
retained their IDs; the shared database stayed on `p17_volume`.
